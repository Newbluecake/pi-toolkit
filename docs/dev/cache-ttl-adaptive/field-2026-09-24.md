## 3. 发现的问题

1. **「会话级永久」熔断实际只是 stack 级**（缺陷）：`CacheAdaptiveService` 构造时 `state = createInitialAdaptiveState()`
   （`src/service/cache-adaptive.ts`），`/reload` 触发的 session_start 重建会把 write/fee 预算与 breaker 全部清零。
   `adaptive.ts` 注释称 breaker 为 session-permanent（G-F §4.2），与实际不符。阶段 D 的约 $5 入场费即由此而来。
   修法方向：从本会话的 `subagent:cache-adaptive` 条目（decision 里带完整 `budget` 快照、reconcile 带 `breaker`）回灌状态，
   同 keepalive/quota 的读回模式。
2. **请求前缀分成两条交替的谱系**（未定位根因）：reload 后的请求按 `input` 分两类——`in=0` 的一条约 294K→327K，
   `in=2/4` 的一条约 364K→408K，差约 70–80K 且在增长；两条各自读自己的缓存，互不命中。
   阶段 D 的 1h 写在短谱系（04:52:19），下一个请求在长谱系（04:54:14）⇒ 入场费白付。
   差额随对话增长，怀疑与历史 thinking 块在不同请求中被保留/剥离有关；需要打开 pi-traffic-record 抓 wire 级载荷确认
   （`traffic.db` 最后写入 09-24 01:15，本段未开启）。
3. **大量整前缀重写与自适应无关**：阶段 C 有多次 1.8–5min 短空档就整前缀 miss（如 02:17、02:24、03:20），
   这些时刻 system prompt 发生了变化——写项目记忆（`## Memory` 注入块变化）、增删临时 agent 类型
   （`Available subagent types` 列表变化）、switch_context 压缩（01:58）。对本会话的实验流程来说难以避免，但说明
   「system prompt 中的动态段落」本身就是主要的缓存成本来源，值得单独评估（例如把 memory / 类型列表移到前缀之后）。
4. **1h 实际存活偏短**再次得到印证：13.2–13.5min 空档两次均 miss（17:05 的 1h 写、以及阶段 C 的 5m）；
   `ADAPTIVE_COVER_MS = 1h` 的乐观假设在该路由上不成立（记忆中已有此条，等遥测）。

## 4. 结论

自适应**在阶段 A 起了作用**（一次 7.8min 空档命中），但**整体净亏**：一次对死缓存的 1h 重写触发熔断，
reload 又把熔断清零、在前缀谱系分裂的情况下付了两次白费的入场费。优先修 §3.1（熔断/预算跨 reload 持久），
§3.2 需要抓包定位。

## 5. 追加排查：插件导致的整前缀失效（2026-09-24）

**机制**：`before_agent_start` 在**每一轮 agent 开始时**（用户消息、子 agent / 后台任务完成通知唤醒）重建 system prompt。
pi-toolkit 往 system prompt **末尾**追加三段动态内容：agent 类型列表（`src/index.ts`，每轮实时读 `types.list()`）、
可用模型列表（同处）、项目记忆块（`src/memory/inject.ts`，写入后下一轮重渲染；`memory.freezeInjectionAfterWrite` 默认 false）。
system prompt 之后紧跟整段对话，而之前唯一的缓存断点在工具定义末尾（本机 11,356 tok），
所以这三段**任何一个字节变化 = 整段对话按 5m 价全量重写**（本会话每次 14–42 万 token，$0.7–2.1）。

**本会话 21 次整前缀重写的归因**：

| 类别                                                | 次数     | 例子                                                                           |
| --------------------------------------------------- | -------- | ------------------------------------------------------------------------------ |
| 自然过期（空档 > 5min 且无保活命中）                | 4        | 01:35（8h）、04:41（24.8min）                                                  |
| 前一轮写了项目记忆 / 增删了 agent 类型 / 改了 skill | 约 6     | 02:24、03:20、04:14、05:07                                                     |
| reload（基础 system prompt 变化）                   | 1        | 04:51                                                                          |
| 1h 命名空间隔离（设计内的入场费）                   | 2        | 04:52:19、04:54:14                                                             |
| **无法用上述原因解释**                              | **约 8** | 01:44、01:45（R=0）、02:28、02:42、03:47、04:54:30（R=0）、05:09、05:10（R=0） |

**`R=0` 且发生在同一轮中途**（04:54:30、05:10:30）——system prompt 在轮中不会重建，只能是**工具定义或其 cache_control 变了**；
已排除 `ask_user` 的 `setActiveTools`（仅无界面时触发）与 cache-ttl（非升级请求原样放行）。
结合 §3.2 的 A/B 两条前缀谱系（`in=0` 与 `in>0` 交替、差 70–80K 且增长），怀疑存在「每次请求载荷形态不稳定」的插件或 pi 核心行为。
**需要线级载荷才能定位**：`/record on` 后抓一段连续请求，对比 A/B 两类请求的 tools / system / thinking 块 / cache_control。
