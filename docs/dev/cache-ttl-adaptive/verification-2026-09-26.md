# adaptive 多场景策略矩阵验证与修订（2026-09-26）

> 问题：当前默认（adaptive + keepalive）相比「始终 5m」「始终 1h」到底省多少？
> 方法：先在仿真里原型化修复、验证经济性，再改 `src/`（用户要求「先验证修复后策略再改代码」）。
> 仿真：`ADAPTIVE_ECON_REPORT=1 npx vitest run tests/cache-ttl/adaptive-economics.test.ts`
> （strategy matrix 段；驱动的是真实的纯函数 reducer，上游缓存按 §16.3/§17.2 的命名空间事实建模）。

## 1. 矩阵口径

- 5 种策略：`5m`（auto）、`5m+ka`、`1h`（mode=on，保活因 gate #7 不 ping）、`adaptive`、`adaptive+ka`（生产默认）。
- 12 种负载：密集无信号 / 密集+常驻 subagent / 人为思考空档 3–15m / 派单×4 等 8·20·40·58m /
  bash 构建×3 等 25m / compact 抖动+bash / mixed day / 午休 55m 后 bash×4 25m / 派单 58m 后 bash×4 25m。
  每个负载以一条无信号的开场请求起头（新会话第一个请求之前不可能有后台任务）。
- 1h 存活 60m（文档值）/ 25m（现场：23.2m 仍读中、≥27.5m 死）/ 10m；读价 0.1×（官方）/ 0.05×（路由实价，F7）。

## 2. 仿真器修正（先于任何结论）

- **keepalive gate #8**：窗口 capture 带的是**被捕获请求之前**那条账本，所以会话第一个请求之后的空档永远不 ping
  （`prefix-unproven`）。旧仿真在第一个请求后照样 ping，并在第一个请求上放了强信号，制造出一个不存在的
  「F-B：首请求冷升级绕过 keepalive-covers」。真实代码的 R1（首请求 horizon=undefined）是对的，**F-B 撤销**。
- 压缩后 `readLatestAssistantUsage` 仍读到压缩前的账本，horizon 不应因压缩变 undefined。

## 3. 发现与修复

| #       | 严重度 | 发现                                                                                                                                                                                                                                          | 修复（`src/cache-ttl/adaptive.ts`）                                                                                                                                                                                                                  |
| ------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **F-D** | Major  | F1 的 `keepalive-covers` 看的是**所有**空档。一次无后台任务的人为长空档（午休 55m，保活不 ping、adaptive 也不会为它付费）进入环后，F1 对整个会话永久失效：之后每次 25m 构建等待都「入场费 + 续期 + 照常 ping」双付。                          | 新环 `armedGaps`：只收保活**证明过读中**的空档（服务层以 `provenCacheReadAt() > lastRequestStartedAt` 判定，`decide` 在本请求重新 capture 之前运行，读到的正是刚结束的那段空档）                                                                     |
| **F-A** | Major  | 5m 请求读的是更长的 5m 链、不刷新 1h 条目；保活撑住空档时 1h 条目照样按其寿命死去。cover 固定按 1h 乐观计 ⇒ 下一次强信号的「已覆盖续期」实为整前缀 1h 重写，记入入场费、热探针豁免（F5）、`1h-ineffective` 被 F-C 掩盖 ⇒ 每轮重复直到费预算。 | 已覆盖续期结算时读崩塌（同谱系、前缀未缩短、路由已知）⇒ 学到上界 `learned1hLifeMs = 决策时刻 − 上一个 1h 写入点`（同路由取小）；此后 cover = `min(1h, 0.8 × 上界)`，并立即收紧本次续期刚武装的 cover；随审计条目跨 /reload 恢复（路由绑定，R9 语义） |
| **F-C** | Minor  | 1h 判决只看真实请求间隔；被 ping 撑住的空档里命中的是 5m 链，却记为 `indirect1hConfirms` / `max1hSurvivalMs`（伪证据；< 49m 所以不会误让位，但掩盖 1h 已死、污染遥测）。                                                                      | `lastGapPingBridged` = 空档被武装且距最近一次被证明的读取 ≤ 一个 5m TTL；此时不做 1h 判决、不记证据；这类空档后的读崩塌按漂移处理（清 cover）                                                                                                        |

原型阶段还验证过两个否决方案：

- C 的第一版（把整个间隔改成「距最近 ping」）会让空档环不再出现 >49m 的空档，把 adaptive 唯一赚钱的场景
  （等 58m、1h 活 60m）从 $5.92 抹回 $8.50 —— 所以 C 只作用于 1h 判决，空档环仍用真实请求间隔。
- 「覆盖期默认改 20m」与「读崩塌直接熔断」：与 A（学习封顶）在所有负载上数值相同，A 保留了 1h 真能活满时的收益，选 A。

## 4. 结果（12 负载等权合计；`src/` 实现后与原型 A+C+D 逐分一致）

| 1h 存活 / 读价 | 5m     | 5m+ka     | 1h        | adaptive+ka 修前 | **adaptive+ka 修后** |
| -------------- | ------ | --------- | --------- | ---------------- | -------------------- |
| 60m / 0.1×     | 101.43 | 97.85     | **82.71** | 100.04           | 98.28                |
| 25m / 0.1×     | 101.43 | **97.85** | 115.22    | 111.53           | 105.11               |
| 60m / 0.05×    | 84.78  | 71.99     | **64.49** | 75.27            | 73.47                |
| 25m / 0.05×    | 84.78  | **71.99** | 97.86     | 86.03            | 79.44                |

- 修后比修前省 1.8%–7.7%；「午休后构建」一行从 +$1.8～+$4.9 回到与保活持平，
  「派单 58m 后构建」的整前缀 1h 重写从 3 次降到 1 次。
- **仍未胜过 5m+ka**：剩余差距来自「看到一次 >49m 武装空档就押注入场费」——这一注只在 1h 真能活过那段空档、
  且之后还有 ≥2 次同样长的空档时回本（§3.2 回本点）。1h 短命路由上它是每会话一次的探索成本（押注 → 读崩塌/熔断）。
- 「始终 1h」只在 1h 真能活满 60m 时最优（人为思考空档也被覆盖）；在现场测得的 ~25m 寿命下反而最贵。
