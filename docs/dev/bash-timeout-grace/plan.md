## 1. 路线与推荐

| 路线                                    | 决策方                  | 结论                                                                   |
| --------------------------------------- | ----------------------- | ---------------------------------------------------------------------- |
| **A 子会话 bash 自动后台 + `bash_job`** | 子 agent                | **采用**（U1）                                                         |
| **A+ job 级截止：宽限 + 通知 + extend** | 调用 bash 的 agent      | **采用**，只作用于**已转后台且带 timeout** 的 job                      |
| **A++ 子会话收尾保持（U2）**            | 子 agent 被持续要求等待 | **采用**：job 未结束不让 run 正常结束，直到 job 结束或 run 被停止/到期 |
| B 看门狗 tool 相位宽限                  | 父会话                  | 延后（U5）                                                             |
| C 主会话参数                            | —                       | 不改（U5：无 timeout 后台 job 不设上限）                               |

```
job 截止（仅显式 timeout）        → 宽限 60s → 调用方：bash_job extend | kill | 不理（到点杀）
子会话收尾（仍有后台 job）        → 保持（等全部结束/封存/保持到期）→ 子 agent：wait | kill | extend
run 截止（Agent 总预算）          → 宽限 → 父会话：extend_subagent_timeout（已有）
run 即将终态                      → 封存 → 取退出事实写进终态 → 杀全部子 job → 父会话终态通知
```

**对状态机的承诺（v4 定稿）**：相位、状态、计时器、效果集合**语义不变**；新增一个元数据型 session_event `exit_facts`（与 `model_changed` 同类，E23，但位置在 generation 检查之后、`terminal()` 检查之前，§3.8）和 `finish()` payload 透传一字段。按 AGENTS.md 同步 core 测试：矩阵单元不变（session_event 列的代表事件仍是 `text_delta`），性质测试新增 P15（§3.8）。`src/core/deadline.ts`、`src/runtime/watchdog.ts` 不改。

**v4 的两条简化**：① `bash_job` 工具从不等待恢复流程（v3 §2.5 步骤 5 删除）——内存 entry 是唯一权威，孤儿在被收养前就是今天的 `not found`；② 收尾保持的计费不再靠「批次数」推导，改为**每 run 显式轮次预算**（§3.5，C3 待确认），上界可由 FakeClock 直接断言。

## 2. job 级截止（A+）

### 2.1 数据（JobRecord 可选字段，仍 `v:1`）

| 字段                                                | 含义                                                                                           |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `deadline.timeoutMs`                                | 模型传的 `timeout`（走现有 `resolveTimeoutMs`，> 0）。**没传 = 没有 `deadline` 字段**（U3/U5） |
| `deadline.policy`                                   | 创建时冻结的 `{graceMs, maxExtensions, maxTimeoutFactor}`；改配置只影响新 job                  |
| `deadline.dueAt` / `hardAt`                         | `spawnedAt + timeoutMs` / `spawnedAt + ceil(timeoutMs × maxTimeoutFactor)`                     |
| `deadline.graceUntil?` / `graces` / `graceNotified` | 宽限窗口与跨 reload 去重                                                                       |
| `deadline.extensions` / `grantedMs` / `lastReason?` | 续期计数与审计                                                                                 |
| `deadline.seq`                                      | 每次变更 +1                                                                                    |
| `owner?: "subagent"`                                | 子会话创建的 job                                                                               |

兼容：旧 record 无 `deadline` ⇒ 无 timeout；非法 `deadline`（非有限、`dueAt > hardAt`、policy 越界）⇒ 丢弃该字段 + warn 一次，按无 timeout 处理；旧版本代码读新 record ⇒ 未知字段丢弃；配置变更 ⇒ 沿用 policy 快照。

### 2.2 纯函数 `src/bash/deadline.ts`（与 `src/core/deadline.ts` 同构，含 D-6）

| 函数                                       | 规则                                                                                                                                                            |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jobExtendability(record, now)`            | 终态→`already_terminal`；无 deadline→`no_timeout`；未转后台→`foreground`；`maxExtensions=0` 或用满→`limit_reached`；`hardAt − max(now,dueAt) ≤ 0`→`no_headroom` |
| `jobGraceWindow(record, at)`               | `graceMs ≤ 0` 或不可续（D-6）→`undefined`；否则 `min(at + graceMs, hardAt)`                                                                                     |
| `applyJobExtension(record, extendMs, now)` | `base=max(now,dueAt)`；`next=min(base+extendMs, hardAt)`；零净增拒绝；清 `graceUntil`；`extensions+1`、`seq+1`                                                  |
| `resumeDeadline(record, now)`              | `graceUntil ≤ now`→`expire`；`dueAt ≤ now` 且无宽限→按 `jobGraceWindow(record, now)` 进宽限或 `expire`；否则 `arm(nextAt)`                                      |

### 2.3 manager 行为

| 时刻            | 仍在前台                                | 已转后台                                                                         |
| --------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `dueAt` 到      | pi 语义：立即杀，抛 `timeout:<s>`（U5） | 可宽限→进宽限、`onDeadline(grace)`、唤醒 `waitExit`；不可宽限→立即杀 `timed_out` |
| `graceUntil` 到 | —                                       | 杀，`timed_out`，完成通知注明「超时 + 宽限后无人续期」                           |
| `extend`        | 拒绝 `foreground`                       | `applyJobExtension` → 重排 timer → `onDeadline(extended)`                        |

### 2.4 竞态与 I/O 挂起（**内存为准、落盘后写**）

v2 把 deadline 裁决放进 store 的 `update` 里，store 一旦挂起，超时就永远不会执行（违背零 hang）。v3 改为：

| 规则 | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1   | 每个 job 的内存 entry 是 deadline 的唯一裁决点。JS 单线程 ⇒ 同步裁决天然串行；timer 回调、extend、kill、exit 处理都**同步**读改内存 entry                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| R2   | timer 回调捕获 `seq`：entry 已终态或 `seq` 已变 ⇒ no-op；时刻未到 ⇒ 重排                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| R3   | 终态转换同步清 timer、settle waiter；宽限到期的 kill 信号**立即发出**（不等落盘）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| R4   | 宽限到期 kill 前确认仍 running；exit 事件若 `exitCode !== null`（自然退出）以真实退出码为准，不贴 `timed_out`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| R5   | 持久化是后写：内存变更后把新 deadline 入队到 store 串行链；终态转换仍按现状由 `transitionJob` 拒绝倒退（E14）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| R6   | 通知去重：`graceNotified`/`notifiedAt` 在内存置位后发送，落盘后写；进程重启后以磁盘为准，最多重发一次（与现有完成通知同级）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| R7   | `extend` 工具：同步裁决后返回；只等落盘至多 2s，超时则在结果里注明 `persist pending`（不阻塞模型）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| R8   | 已 dispose 的 manager：timer、`onDeadline`、`notify` 全部 no-op；`extend()` 抛 `stale bash job manager`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| R9   | **读不倒退**（复审 v3-3）：`putRecord` 合并 `deadline` 时按 `seq` 取大——内存 `seq ≥` 磁盘 ⇒ 保留内存 `deadline`（其余字段照旧 E27 规则）。于是 `manager.load()`（`bash_job status/wait` 的磁盘优先读）与任何磁盘回读都不能把未落盘的 extend 抹掉                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| R10  | **写不倒退**：deadline 的每次后写都用 `store.upsert(jobId, mutate)`（新，§2.5）；`mutate` 内做 CAS——`current.deadline.seq ≥ next.deadline.seq ⇒ return undefined`（不写）。终态转换仍由 `transitionJob` 拒绝倒退（E14）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| R11  | **同目录单链**：同一目录的所有 `JobStore` 实例共用一条进程级串行链（§2.5「共享链」），`update/upsert` 的读-改-写对所有写入者原子；R10 的 CAS 因此不会被另一条链的交错写打穿                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| R12  | **staged 落盘有界 + spawn 窗口取消**（复审 v3-4、v4-4、v5-2）：内存 entry 在 `running` 之前有三个子态 `staged(persisting) → staged(spawning) → running`，外加一个独立标志 `cancelled`（由 `cancelReserve` 或封存置真，只增不减）。`started` 流程：`await race(store.save(staged), STAGE_PERSIST_TIMEOUT_MS = 30s)`（用户放宽）→ **检查 `cancelled`/`admit()`** → 置 `spawning`、发起 `spawnJob` → resolve 后**在同一同步段**：`entry.local = handle`、记 `pid/pgid`，再**检查 `cancelled`**：真 ⇒ `handle.termination = "killed"`、`killJobTree(pid, {graceMs: 0})`（不 await），exit 事件走现有 `finalizeLocal` 得到唯一终态 `killed`；假 ⇒ `running` 转换。失败分支：save 超时 ⇒ `failed`（`finalText: "bash job store did not persist the staged record within 30s; command not started"`）、不 spawn；save 后发现 `cancelled` ⇒ `killed`（无进程）、不 spawn；`spawnJob` reject ⇒ `failed`（无论是否 cancelled，进程从未存在）。**任何返回的 pid 都先纳入 entry 再裁决**，所以不存在「pid 返回但无人认领」的窗口；每个 entry 恰好一次终态（`transitionJob` 拒绝第二次）。`failed/killed` 后写经同一条链排在 save 之后，磁盘终态不会被迟到的 `staged` 覆盖。E14「先落盘再 spawn」不变。**30s 是 job 的落盘预算（后台 / fire-and-forget 全额适用）；等待 `started` 的工具调用另受 §3.6 约束** |

### 2.5 /reload 交接、共享写链与恢复取消（复审 v3-2、v3-3）

**目标**：① 交接 job 的 deadline timer 恢复不依赖任何 I/O；② 旧 manager 的迟到写入不能覆盖新 manager 的状态；③ 恢复流程超时后不再改动活跃栈。

#### 共享写链（`src/bash/job-store.ts`）

| 项        | 内容                                                                                                                                                                                                                                                                                                                                                                    |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 注册表    | `Symbol.for("pi-subagent:bash-job-store-chains")` → `Map<dir, Chain>`，`Chain = { queue: Promise<unknown>; pending: number; lastUsedAt }`（`pending` = 已排队 **+ 在途** 的操作数，入队 +1、settle −1）。无模块级可变状态，/reload 后同一 dir 拿到同一条链                                                                                                              |
| 取链      | **store 不缓存链对象**：每次 `enqueue` 都同步 `chainFor(dir)` → 确认未被淘汰 → `pending++` → 入队，四步在**同一同步段**完成（中间无 await）。`save/load/loadAll/update/upsert/remove/prune`、旧 manager dispose 后的迟到写全部经此路径，没有绕链的写                                                                                                                    |
| 淘汰      | 容量 64。`chainFor` 在 size > 64 时按 `lastUsedAt` LRU **只淘汰 `pending === 0` 的链**；全忙 ⇒ 不淘汰、Map 暂时超容、warn 一次 `bash job store chains over capacity (N busy)`。因取链与入队同步，忙链永不被淘汰 ⇒ 任意时刻同 dir 的所有写者拿到同一对象（R11 不变量）；被淘汰的链必然空闲，下一次取链新建的链是该 dir 唯一的链                                          |
| 闭包保留  | 一个永不 settle 的 fs 调用使其链 `pending ≥ 1` 永不淘汰，链上排队的闭包（record JSON、mutate 函数，KB 级）随之常驻——与今天单 store 的私有队列被挂起写卡住等价，上界 = 出现过挂起写的 dir 数；接受，不做额外回收                                                                                                                                                         |
| 遥测      | （复审 v5-5）`chainStats()`：`{ dirs, busy, maxPending, oldestPendingMs }`（每条链记 `oldestEnqueuedAt`）；`chainFor` 顺带检查：某链 `pending > 256` 或最老在途 > 60s ⇒ 该链 warn 一次 `bash job store chain <dir> backlog: 300 pending, oldest 75s`；`/agent status` 的 bash-jobs 行追加 `chains 3 (busy 1, oldest 12s)`。**永不为容量淘汰忙链**（上一行）；遥测只观测 |
| `enqueue` | `createJobStore` 不再持有私有 `queue`，改为 `chainFor(dir).enqueue(fn)`；`save/load/loadAll/update/remove/prune` 语义不变                                                                                                                                                                                                                                               |
| `upsert`  | 新方法 `upsert(jobId, mutate: (current: JobRecord \| undefined) => JobRecord \| undefined)`：链内读（可为 `undefined`）→ `mutate` → 非 `undefined` 则 `writeAtomic`。deadline 后写、交接 job 的重定位落盘（下文）、R12 的 `failed` 都走它                                                                                                                               |
| 边界      | 只解决**同进程**多 manager 写同一目录（/reload、`/new`、`/resume`）。跨进程同目录写入不在范围（目录按 sessionId 划分；`recover()` 的 hostPid `foreign` 判定照旧）                                                                                                                                                                                                       |

#### 交接步骤（`src/stack.ts` + `src/bash/session-dirs.ts`）

| 步骤 | 同步/异步 | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| 4    | 取消令牌  | `recovery = new AbortController()`；`signal` 传入 `migrateFlatRecords/handoffInProcess/adoptOrphans/recover/moveRecordFiles/reconcileRootDir/sweepJobFiles/gcSessionDir`。触发源：unref 的 `RECOVERY_DEADLINE_MS = 10s`（步骤 3 的恢复段）；`bashJobs.dispose()`（本 stack 被下一次 build 取代）。**线性化点**：`signal.aborted` 置真的那个同步时刻。**检查点**：每次 I/O（`readdir/readFile/stat/rename/unlink/writeAtomic`、链入队）**发起前**与每个 `await` **返回后**；检查点见 aborted ⇒ 不发起新 I/O、不 `putRecord`/`applyTransition`/重排 timer/通知、不把已返回的结果折叠进内存，函数直接返回。线性化点落在某个 fs 调用已发起之后时，**允许该单次调用完成**（一个 rename/writeFile 是原子的，不会留半写文件），其结果被丢弃。`recover()` 返回带 `partial: true` 的 summary；warn 一次 `bash job recovery cancelled (timeout\|superseded) after N/M records` |

| 6    | 异步      | **清理串行化**（复审 v4-2、v5-4）：今天 `reconcileRootDir()` 与恢复 IIFE 并行（`src/stack.ts:1823-1825`），会与 `adoptOrphans` 同时读写他会话目录。v6 改为恢复 IIFE 的最后一步，用**独立的** `cleanup = new AbortController()`（已 `abort()` 的 controller 不能复用）：恢复段结束且 `!recovery.signal.aborted` ⇒ 武装 unref 的 `RECONCILE_DEADLINE_MS = 30s` 定时器并以 `cleanup.signal` 调 `reconcileRootDir`；恢复段被取消 ⇒ `cleanup` 永不武装、跳过清理并 warn（下一次 build 会再做，清理本就是幂等的保留期扫描）。`bashJobs.dispose()` 同时 `abort()` 两个 controller（幂等）。三种顺序：恢复成功→清理 30s 段；恢复超时→无清理；dispose 在恢复中→两段皆停 / dispose 在清理中→清理停。恢复期间不存在任何并行的目录清理                                                                                                                                           |

**为什么旧 manager 的写不需要整体拒绝**：旧 manager 在 dispose 后仍可能落盘的只有 ① 未导出的前台 job 的终态（`finalizeLocal`，owner 仍是旧 token）、② 在途的 `notifiedAt`/`outputTruncated` patch、③ 已排队的 deadline 后写。①② 是**必须**落盘的正确信息；③ 与新 manager 的写经同一条链串行 + R10 CAS ⇒ 只可能被拒绝，不可能覆盖更新的状态。整体拒绝会丢 ①（前台 job 在盘上永远 `running`），故排除（§8）。

**跨目录窗口**：步骤 2 之后、步骤 3 rename 之前，新 manager 的 deadline 后写会在新目录 `upsert` 出 json，而 log 仍在旧目录——内存 `logPath` 指向旧路径，所以 status/wait 读日志正确；此窗口内崩溃 ⇒ 新目录 json 的 `logPath` 指向旧目录文件，`recover()` 的 `readOutput` 仍按 `logPath` 读到（旧目录文件由保留期清理）。可接受，T12 断言无半写 JSON。

结论：交接期间 deadline timer 的恢复**不依赖任何 I/O**（步骤 1→2 同步）；旧写入不能倒退新状态（R9–R11）；恢复流程无论挂起还是迟到都改不了活跃栈（步骤 4）。

### 3.5 收尾保持（U2；复审 v3-1 ⇒ 显式轮次预算，C3 待确认）

放行检查（任一不满足 ⇒ 返回 `undefined`）：

| 序  | 检查                                                                                     | 放行原因               |
| --- | ---------------------------------------------------------------------------------------- | ---------------------- |
| 1   | `childSettleHold !== false`                                                              | 开关关                 |
| 2   | `event.outcome === "completed"`                                                          | abort / error          |
| 3   | `event.context.canContinue`                                                              | pi 不允许续轮          |
| 4   | `!registry.isSealed(sessionId)`                                                          | run 在结束             |
| 5   | `hostView` 存在且 `!stopping()`                                                          | 无宿主或正在停止       |
| 6   | 有**非终态**后台 job（`staged` 含在内：R12 保证 ≤ 30s 内转 `running` 或 `failed`）       | 无需保持               |
| 7   | `rounds < cap`（下文）                                                                   | **轮次预算耗尽**（C3） |
| 8   | `hold = min(W_HOLD=120s, watchdogDueAt − now − MARGIN_HOLD=15s)` 且 `hold ≥ HOLD_MIN=5s` | 看门狗即将到期（C1）   |

**唤醒条件**（不变：不再「任一 job 结束就唤醒」）：`await race(allJobsEnded, graceImminent, whenSealed, sleep(hold))`

| 唤醒原因                                          | 返回                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 封存 / host stopping                              | 放行（不计轮）                                                                                                                                                                                                                                                                          |
| **全部**非终态 job 结束                           | `{entries:[...event.entries, 完成摘要], continue:true}`；这些 job 标 `seen`；`rounds+1`                                                                                                                                                                                                 |
| 一个或多个 job 进宽限且 `graceUntil` 早于保持结束 | `{entries:[...event.entries, 宽限提醒], continue:true}`；`rounds+1`。**同窗合并**：一次保持内 `graceImminent` 只结算一次——醒来时把此刻所有处于宽限的 job 列进同一条提醒；已经在提醒里列出的 job 在下一次保持不再单独唤醒（它的宽限窗口只剩 kill 或 extend 两种去向，extend 是主动行为） |
| 保持到期（仍有 job）                              | `{entries:[...event.entries, 保持提醒（附这段时间已结束的 job 摘要）], continue:true}`；`rounds+1`                                                                                                                                                                                      |

- 保持期间单个短 job 结束**不唤醒**，只累积进下一次摘要；`entries` 拼接 `event.entries`（E9）；不改任何 deadline。
- `rounds` 只数 hook 返回 `continue:true` 的次数（三类唤醒都算，放行不算）；`rounds`/`cap`/`holdMsTotal` 在 child.ts 闭包里，进退出事实 `hold` 与遥测。

**轮次预算 `cap`**（复审 v3-1）：

```
cap  = childSettleHoldMaxRounds > 0 ? childSettleHoldMaxRounds
                                    : 2 × R_wait                          // 默认「auto」
R_wait = ⌈H / W_HOLD⌉ + 2 + E + G₀                                        // 被动等待所需的轮数上界（可证，下），恒 ≥ 1
  H = hostView.hardDeadlineAt() − t₀     t₀ = 本 run 首次进入保持的时刻；hardDeadlineAt 冻结（E32）⇒ H 在 t₀ 后不变
  E = hostView.maxExtensions()           run 级：默认 3（与 G₀ 不重复：E 计 run 截止后移，G₀ 计 job 宽限唤醒）
  G₀ = Σ_j (maxExtensions_j − extensions_j)   对 t₀ 时刻所有非终态、带 deadline 的 job j 的**剩余**宽限次数求和，t₀ 冻结
```

默认 30m 预算、无 timeout job：`R_wait = 15 + 2 + 3 + 0 = 20`，`cap = 40`；同预算下 5 个未续期过的 timeout job：`G₀ = 15`，`R_wait = 35`，`cap = 70`；consult 150s 预算：`R_wait = 2 + 2 + 3 + G₀`。

**可证性质**（T21 用 FakeClock 直接断言，不依赖模型行为假设）：

| 性质 | 陈述                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q1   | 任何模型行为下，由 `agent_before_settle` 引发的续轮数 `≤ cap`；到 `cap` 后放行，run 以已有输出正常结束（然后封存、杀 job、退出事实注明 `hold budget exhausted (40/40)`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Q2   | 每次 `sleep(hold)` 醒来时 `now ≤ watchdogDueAt(t_hold) − MARGIN_HOLD`；`hold < HOLD_MIN` 必放行 ⇒ 保持从不越过看门狗（C1 保持）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Q3   | **被动模型**——定义：t₀ 之后不创建 job、不 `extend`、不 `kill`、不调 `bash_job wait`（任何长度）、不改变 job 集合，只回文字——的续轮数 `≤ R_wait < cap`。证明分两类：① 保持到期类 ≤ `⌈H/W_HOLD⌉ + 2 + E`：`hold = W_HOLD` 的至多 `⌈H/W_HOLD⌉` 次；`hold < W_HOLD` 只在 `D = effectiveDeadlineAt` 逼近时发生，醒来后的下一次 `hold = D − now − 15 ≤ 上次 − L < HOLD_MIN` 除非 `D` 后移，而 `D` 只经 run 宽限（1 次）与 `deadline_extended`（≤ E 次）后移 ⇒ 尾段 ≤ `1 + 1 + E`；② 宽限类 ≤ `G₀`：被动模型不 extend ⇒ 每个 job 至多进宽限 1 次（进宽限后只会被杀），且同窗合并（上表）⇒ 宽限唤醒次数 ≤ t₀ 时非终态 timeout job 数 ≤ `G₀`（每个这样的 job 剩余次数 ≥ 1，否则 D-6 不宽限）。**适用范围**：t₀ 之后新增的 job、新增的宽限、任何 `wait/extend` 都是主动行为，只由 Q1 的 `cap` 覆盖，不进 Q3 |
| Q4   | hook 只在一轮模型调用结束时触发 ⇒ 相邻两次续轮之间至少一轮模型调用；结合 Q1 的 `cap`，总费用 ≤ `cap` 轮 + 模型自身发起的轮次                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

Q3 说明默认 `cap` 只会被**模型主动行为**（每轮再起新 job、极短 wait 后结束轮次）触到；1 长 job 被动等待的 V4/V7 场景永远触不到——这就是 U2 的有界化：**`cap` 是反空转例外，不是「与 U2 等价」**（U2 字面「直到 job 结束或 run 总预算耗尽」；C1 是用户已接受过的同类例外）。触顶时放行 = job 仍在跑时让 run 结束，运行结果在退出事实与父通知里可见（§3.7）。**默认值需用户确认（C3）**。

最后一轮（`rounds === cap − 1` 返回的提醒）文案追加：`Final reminder (40/40): when this turn ends the run finishes and every running bash job is killed. Use bash_job(action:"wait") now if you still need the result.`

**零 hang**：保持 = pi 钩子里一次有界 await（≤ 看门狗截止 − 15s，Q2）+ 至多 `cap` 轮模型调用（Q1）。run 被停止时 runner guard 不等 prompt 即走收尾，`sealBeforeTerminal` 封存 → `whenSealed` 唤醒 → 放行。总时长上界与今天相同：`hardDeadlineAt + abortGraceMs + reapMs`。

保持提醒文案（英文 token）：

> ⏳ Background bash job j_… is still running (7m12s, `go test ./...`). You cannot finish while it runs (reminder 3/40). Call `bash_job(action:"wait", job_id:"j_…")` to keep waiting, `bash_job(action:"kill", …)` if you no longer need it, or `bash_job(action:"extend", …)` if its timeout is about to fire. Finished since last reminder: j_… exit 0, j_… exit 1.

### 3.6 子会话的「必须在截止前返回」（复审 v2-2、v3-4、v3-5）

**问题**：v2 以 `D − 15s` 触发后台，但触发后还有 spawn、`store.save`、`markBackgrounded` 等 await，任何一个卡住都会撞上 tool 看门狗。

**做法：spawn 之前建立同步控制面，触发后的返回路径全同步；`started` 永不 reject。**

| 组件                                        | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `manager.reserve(init)`（新，同步）         | 查 `admit()`（S1）→ 分配 jobId → 建内存 entry（`staged(persisting)`）→ 返回 `{ jobId, logPath, started }`。`started: Promise<{ ok: true; job: CreatedJob } \| { ok: false; error: Error }>`，**永不 reject**（复审 v3-4）：内部按 R12 走 save → spawn → `running`；任一步失败/取消 ⇒ 同步把内存 entry 转 `failed`/`killed`（R12 表）、settle waiters、后写经链、resolve `{ok:false}`。这样 wait/status/保持摘要/退出事实都读得到失败，且零 unhandled rejection。`manager.cancelReserve(jobId)`（新，同步）：置 `cancelled`；`staged(persisting)` ⇒ 立即内存 `killed`（save 迟到后不 spawn）；`staged(spawning)` ⇒ 只置标志，pid 返回时由 R12 的同步检查杀；`running` ⇒ 等价现有 `kill()`                                                                                                                                                                      |
| `manager.markBackgroundedSync(jobId)`（新） | 同步写内存 `backgroundedAt`，持久化后写（R5/R10）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| 返回时刻 `R`                                | 调用开始时 `D0 = hostView.watchdogDueAt()`，`R = min(now + autoBackgroundMs, D0 − MARGIN_RETURN)`，`MARGIN_RETURN = 3s`（≥ 2 个看门狗 tick + 1s 判定滞后，E30）；timer 触发时再读一次 `D`，更早则立即返回                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| 触发后                                      | `markBackgroundedSync` + 同步构造返回文本（jobId、logPath 在 `reserve` 时已知；pid 若未知写 `starting`）+ `hostView.noteToolReturn(toolCallId, now)` → return。**不 await** `started`/落盘/任何 I/O                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **两层 race**（复审 v4-4、v5-1）            | 与现有结构一致（E34），只是内层的 `create()` 换成 `reserve()`：**外层**（`createBashTool.execute`）`settled = 内层 exec 的整体 promise（含 await job.exit）`，与 `triggerAtR`（R 定时器；`run_in_background:true` 时改为「`reserve` 已返回」即立刻）及 abort 做 race——`settled` 只在命令结束时 resolve，所以 **R 贯穿整个调用**，无论内层正停在 `await started` 还是 `await job.exit`。**内层**（`execViaManager`）：`reserve()` 同步（E33 ⇒ 外层紧接着就能读到 `jobId/logPath`）→ `await race(started, abort)`（`started` 自身 ≤ 30s，R12）→ `{ok:false}` 抛 `error`（pi 语义：exec 抛错）→ `await race(job.exit, abort)`（原有；timeout 由 manager 掌管，§2.6）；abort ⇒ 同步 `cancelReserve(jobId)`（或已 spawn 时现有 `killTree`）并抛 `aborted`。**内层不认识 R**：外层返回后内层照常跑完，结果由 `adoptInnerPromise` 收进 `finalText`（现有 §2.3 机制） |
| **单次原子裁决**                            | 外层用一个同步 latch `decision: "foreground" \| "background" \| undefined`：`settled.then(sync cb)` 与 R 定时器回调、abort 回调三者都先 `if (decision) return;` 再赋值，然后各自完成自己的分支（foreground：清 R 定时器、透传 pi 结果 / 抛错；background：`markBackgroundedSync` + `stopForwarding` + `adoptInnerPromise` + 同步构造文本 + `noteToolReturn` + return）。三者都是同步回调，事件循环一次只跑一个 ⇒ 「R 与 `started`/`exit` 同时到」只有一个赢家，不可能既返回前台结果又标后台。`run_in_background:true`：`trigger` 立刻成立 ⇒ 同一 latch 走 background                                                                                                                                                                                                                                                                                          |
| 工具调用等待上界                            | ① 子会话（有 `D`）：外层 `R = min(now + autoBackgroundMs, D − MARGIN_RETURN)` ⇒ 调用 ≤ `R − now` 后必返回（`starting`（无 pid）或带 pid 的后台文本）；`started` 的 30s 预算与命令本身继续在后台。**`toolMs = 8s`**：`R = D − 3s = 5s` 处外层触发 ⇒ 5s 返回，不管内层停在哪个 await；**`toolMs ≤ 3s`** ⇒ 下一行的同步返回。② 主会话（无 `D`）：`R = now + autoBackgroundMs`（默认 290s，今天的语义）；内层 `await started` 由 R12 的 30s 兜底 ⇒ store 永挂时 30s 抛错、不启动进程；Esc ⇒ abort 分支立即返回并 `cancelReserve`。③ `run_in_background:true`：`reserve` 后 latch 立即取 background，`started` 全额 30s 在后台计                                                                                                                                                                                                                                   |
| `R ≤ now`（含 `toolMs ≤ MARGIN_RETURN`）    | 调用一开始就同步返回（等同 `run_in_background`，但不等 pid）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `bash_job wait/status`（子会话模式）        | 等待时长 `min(wait_ms ?? 30s, 120s, D − now − MARGIN_RETURN)`；到 `R` 时**所有磁盘读**（`loadRecord`、`readStatusTail`）与 R race，超时就用内存 entry，日志尾写 `log tail unavailable (time budget)`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| `D` 未定义                                  | 不截断                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 无 hostView                                 | 静态 `D = 调用开始 + toolMs`（单个工具成立，并行批次不保证，warn 一次）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| 后台槽满                                    | 子会话超额转后台（C2）；只有 `run_in_background:true` 的新 spawn 受上限拒绝                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

**上界与系统边界 B-LOOP**（复审 v3-5）：触发后的代码路径没有 await，工具 `execute` 在 `R` 之后的同一个宏任务里 resolve。但从 resolve 到 runner 收到 `tool_end` 之间，pi 会 `await` 第三方扩展的 `tool_execution_update` / `tool_result` / `tool_execution_end` 钩子（E26），所以返回路径**不是纯微任务链**。本特性的保证因此写成：

> **B-LOOP**：在 `[R, D]` 内，「事件循环滞后 + pi 后置钩子链（第三方 `tool_result`/`tool_execution_end` 钩子）」的总耗时 ≤ `MARGIN_RETURN − 1s`（1s 留给看门狗 tick 判定，E30），则 run 一定在 `D` 前离开 `tool_exec`。这是零 hang 的**系统边界**而非本特性的硬保证：事件循环卡死时 host 看门狗同样停摆，任何进程内机制都无法兜底。

验收与观测（不声称硬保证）：

| 手段         | 内容                                                                                                                                                                                                                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 滞后遥测     | 子会话 bash 工具在 `R` 上报 `noteToolReturn(toolCallId, at)`；host 在 `onStateChange` 看到该 `toolCallId` 的 `tool_end`（`diag.toolHistory[].endedAt`）时算 `lag = endedAt − at`；`lag > MARGIN_RETURN/2` ⇒ warn 一次 `bash auto-background return lag 1.9s (boundary 3s)`，进 `hold`/退出事实遥测 |
| T15 边界用例 | 真实 timer：`R` 前 100ms 起同步阻塞 1s + 注册一个 1s 的 `tool_result` 钩子 ⇒ `tool_end` 仍早于 `D`；阻塞 4s ⇒ 断言进入「边界告警」路径（warn 已发、run 被 tool 看门狗按今天语义杀掉、job 经封存被杀），而**不是**断言返回成功                                                                      |

代价：子会话里 job_id 可能指向尚未拿到 pid 的 job（与主会话「pid 确认后才给 job_id」不同，文案写明 `starting`）。

### 3.7 通知路由与退出事实（复审新 3、4）

**子会话里不使用 `triggerTurn:true`**（E11：空闲时会自起一轮）：

| 事件              | 子会话处理                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| job 完成          | **不发消息**。交付渠道：`bash_job wait/status` 返回值、保持摘要、退出事实                                                                                     |

**退出事实进入终态（不再走内存快照）**：

```
runner.sealBeforeTerminal
  └─ sealSession(runId, sessionId)            // host: registry.sealAndKill → facts（同步，读内存）
  └─ dispatch session_event{t:"exit_facts"}   // reducer：diag.exitFacts = facts（非终态才写，E23 同类）

```

| ----------------------- | --------------------------------------------------------------------------------------- |
| 父会话终态通知          | `payload.exitFacts`（`src/stack.ts` 终态格式化）                                        |

渲染：

```

```

`terminating` 表示封存时已发 SIGTERM（最终 kill 结果写入 job store，不回改通知）。`facts.hold.exhausted` 为真时追加一行 `Settle hold budget exhausted (40/40 reminders); the run was released with jobs still running.`
