## Decisions taken (the plan left these open; conservative choice, kept in `protocol/proxy.ts` unless noted)

1. **`portRange` grammar** is strict: `"<lo>-<hi>"`, decimal, no leading zero, no inner whitespace, outer whitespace trimmed, `lo ≤ hi`, ports 1024..65535 (`PROXY_PORT_RANGE_MIN_PORT`/`MAX_PORT`, so no privileged ports), span ≤ 256. A single port (`"7900"`) is rejected. Helpers `parseProxyPortRange`, `formatProxyPortRange`, `proxyRangeContainsPort` live there.
2. **`ports.json` size cap = the configured range size** (≤ 256), not the plan's "≤ 50", because §5 allows ranges up to 256 ports. The ports.json IO budgets (64 KiB / 1 s load, 2 s write) are NOT frozen, per the plan author. They stay internal to `ports-map.ts` for X1a.
3. **"128 global" (§3.2)** is applied to codes and sessions independently (`PROXY_CODES_GLOBAL`, `PROXY_SESSIONS_GLOBAL`).
4. **Reason → response pairing** (`PROXY_REASON_RESPONSE`, frozen): syntax/scheme/userinfo/port/dns-failed → 400 `E_PROXY_DENIED`; public/link-local/metadata/multicast/reserved/translation/unspecified/mixed-answer/self-port → 403 `E_PROXY_DENIED`; dns-timeout/port-busy/ports-store → 503 `E_PROXY_UNAVAILABLE`; ports-exhausted → 409 `E_LIMIT`; reverse-proxy → 409 `E_PROXY_UNAVAILABLE`. The plan lists the reasons and the status classes but not the per-reason pairing.
5. **Extra non-deny reasons**: 503 `E_PROXY_UNAVAILABLE{closing|revocation-gap|listen-timeout}` (`PROXY_UNAVAILABLE_EXTRA_REASONS`); 409 `E_LIMIT{proxies}`; 429 `E_RATE{codes|sessions}` for the §3.2 "Overflow ⇒ 429" caps (`PROXY_CAP_REASONS`).
6. **`POST /api/proxy/stop` 200 body** = `{ ok: true }`. Instance-id grammar `^[A-Za-z0-9_-]{8,64}$` (opaque; X1b picks the format inside it).
7. **Service surface** (from the plan author's answers): `open(identity, target, browserHost, seq0)` without `viaTrustedProxy` (routes refuse with 409 `reverse-proxy` first), `currentSeq()`, `revokedSince(seq0, identity): boolean | "gap"`, `list(identity)`, `stop → {ok}|{ok:false,code:"E_NOT_FOUND"}`, `revoke`, `activeConnections`, optional `status()`, `dispose`. `ProxyRoutes.handle(req,res,method,path,io): Promise<boolean>`; `ProxyRouteIo` carries `strictCsrfOk()`, `xPwhOk()`, `resolveIdentity`, `readJson`, `sendJson`, `sendError`, `listener`, `expectedOrigin`, `browserHost`, `viaTrustedProxy`. Mounted as `FrontendDeps.proxy?`. The `lanHostSnapshot` construction dependency and the `subscribeAuthRevoke` extra are duck-typed and are not declared in `ports.ts`.
8. **UI client deadline** `PROXY_CLIENT_TIMEOUT_MS = 15 000`, placed in `contract.js` (client-only, like `VERSION_INFO_CLIENT_TIMEOUT_MS`).
9. **`ProxyScope = { lan: boolean }`** and `ProxyListView` are the UI view models. `proxyScopeOf` itself belongs to X2.

## Things X0 could not do inside its domain (for the main session / later packages)

- **`WebHubSettings.proxy` type**: the interface lives in `src/web-hub/agent/index.ts` (X1c domain). `settings.ts` widens it locally (`AgentWebHubSettings & { proxy?: WebHubProxySettings }`). X1c should fold `proxy?` into the agent interface and drop the intersection.
- **`API_ERRORS` tail-append** of `E_PROXY_DENIED` and `E_PROXY_UNAVAILABLE` in `protocol/http-contract.ts` is outside the domain. `PROXY_ERROR_CODES` declares them, and X1c should append them (tail-only). Until then `statusFor` would map an unknown code to 500 if routed through `errorCode()`. Routes that answer via `io.sendError(status, code)` directly are unaffected.
- **`settings.ts` cannot value-import `protocol/proxy.ts`**: `tests/web-hub/boundary.test.ts` freezes its value-import closure and is outside the domain. `settings.ts` therefore carries a parity copy of the range parser and the defaults, pinned equal by `proxy.test.ts`. Adding `"../web-hub/protocol/proxy.js"` to `SYSLOAD_FILE_CLOSURE` would remove the duplication.
- **`portRange` editor validation**: the `/agent settings` editor only requires a non-empty string, like `webHub.nodeLoader`. A bad range is rejected at load time (default + `port-range-invalid` warning from `parseWebHubProxyBlock`). The warnings are returned, not logged, so repeated settings parses don't spam. `agent/proxy-status.ts` (X1c) can surface them.
- If the default range itself overlaps `webHub.port`, the parser can't help (same as `lan.port`'s default collision). The hub's second-line check (X1c) is the veto.
