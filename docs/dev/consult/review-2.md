## 评审结论：有条件通过

上一轮的两个核心阻塞在代码层面可行：#1 fork 准入绕过 canSpawn，#2 工具侧 `forkFrom` 加 `driver.resume`。B 形态的只读域思路也可行：adapter 能读到 `spec.request.forkSessionFrom`，注入点都在一个函数里。

还有 1 个阻塞项和 3 个严重项：

- **阻塞（#1）**：工具在 run 结束前拿不到 consultRunId。轮次/成本帽挂不上，fork 清理登记有竞态。
- **严重（#2）**：只读域漏了 `sessionSpec.tools` 覆盖。按方案写法，grep/find/ls 永远不会被激活，某些专家类型会变成零工具。
- **严重（#3）**：P0 没测一个 B 形态特有的致命点：fork 历史里有新工具表中不存在的 tool_use 块，provider 是否接受。
- **严重（#4）**：B 下缓存必然全量 miss，默认 `maxCostUsd=$0.5` 低于方案自估的首请求成本（约 $1.5），而且帽在 message_end 判定，会误杀已写完的答案。

这 4 项先在方案正文改好（#1 涉及包 A 冻结面，P0 要先补 #3），之后只需针对这几项复核。

**结论：有条件通过。** 核心的 fork 链路和 B 形态只读域都能实现，以下 4 项要先在方案正文改好：

- **阻塞（#1）**：consult 工具在 run 结束前拿不到 consultRunId，watcher 挂不上，fork 清理有竞态。改用 `spawn()` 加 `expectAck`，`onReaped` 改成带 `forkSessionFrom`，并且要在包 A 冻结前改。
- **严重（#2）**：只读域只改了 tool-scope，没覆盖 `sessionSpec.tools`。enforcer 只能删不能加，grep/find/ls 永远不会被激活，某些专家类型会变成零工具。
- **严重（#3）**：P0 没测 provider 是否接受「历史里有未声明工具的 tool_use 块」。这个形态从没跑过，要作为阻塞级必测项补上。
- **严重（#4）**：成本帽在 message_end 判定，会误杀已完成的答案；B 下缓存必然 miss，首请求约 $1.5，高于默认的 $0.5 帽。
