# consult 机制生产效果评估（2026-10）

> 独立评估：评估者没有参与 consult 的设计和实现。只读分析了 `~/.pi/agent/sessions/` 里的真实生产历史，
> 脚本与中间数据在 `/tmp/consult-eval/`（`scan.py`、`scan2.py`、`an1.py`–`an6.py`），没有写 `~/.pi`。
> 待回答的问题：consult 在质量、成本、时间三方面有没有带来**可观测的**正向效果？

## 0. 结论速览

| 维度                               | 判定                           | 置信度 | 一句话                                                                                                                         |
| ---------------------------------- | ------------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------ |
| 质量（首验通过率、返工、方案遵守） | **不确定**（机制层面弱正向）   | 低     | 包级指标看不出正向效果，挂专家的包反而更差，但这几乎肯定是选择偏差（难包才挂）；逐条看问答，请教确实改变了行动、也避免过返工   |
| 成本                               | **负向（局部）/ 中性（全局）** | 中     | 单次中位 $0.84，是实验估计的 7–80 倍；占提问 run 自身花费的 16%，占同期全部 subagent 花费的 2.5%；没有证据表明它换回了返工节省 |
| 时间                               | **中性略负**                   | 中     | 单次中位 38s、P90 92s，占提问 run 墙钟的 5%；没观察到轮数或时长下降                                                            |
| 可靠性（拿到可用答案的比例）       | **负向**                       | 高     | 非测试调用中 29% 没拿到完整答案（轮次帽 / 成本预检 / 超时 / 参数错误），完成的回答里 20% 被截断，由此又产生 12 次追问          |

总体：**consult 现在的生产用法没能证明它对性能有正向优化**。原因不在于证明了它无效，而在于两点：
① 数据是观察性的，选择偏差压倒一切；② 有相当一部分花费落在「不该用 consult 的场景」和「工具本身的摩擦」上。
受控实验（§10–19）验证过的那个用法——下游缺一个读不到的拍板决策，于是开口问——在生产里确实存在，逐条看也有效，
但只占调用的一半左右，还被成本和失败率稀释了。

## 1. 方法与数据覆盖

- **数据源**：扫描 `~/.pi/agent/sessions/**` 里 336 个含 `subagent:run` 条目或 `consult` 工具结果的会话文件。
  - run 表：`subagent:run` 每个 runId 取 `updatedAt` 最新的一条，读 `diag.{label,agentType,model,usage.costUsd,turns}`、`outcome.durationMs`，以及最终文本。
  - 是否挂了专家：主会话（以及嵌套）`Agent` toolCall 的 `arguments.experts`，经同一 toolCallId 的 toolResult `details.runId` 映射到 run。resume 派发按 `resume` 参数映射。
  - consult 调用：子会话里 `toolName:"consult"` 的 toolResult `details`（`costUsd/durationMs/turns/outcome/truncated/toolCounts/expertRunId`）。
    同一会话文件被多次 resume 时，按调用时间落在哪个 run 的 `[createdAt, settledAt]` 窗口归属，避免重复计数（未去重时虚高为 293 次）。
- **成本口径**：已核实提问方 `diag.usage.costUsd` ≈ 自身消息成本 + consult 成本（例如 `r_Y3BWGZ4S`：自身 0.975 + consult 1.655 = 2.630），也就是说 consult 已经折入提问 run 的花费。
- **覆盖**：2026-08-31 → 10-10 共 3,829 个普通 run；专家机制首次使用在 09-25。09-25 之后有 1,323 个 run，花费 $5,662。
- **包级配对**（质量对比用）：同一主会话内，开发 run（general/frontend-dev，排除 fix 类）配对它结束后第一个 label 词集 Jaccard ≥ 0.5 的 verifier；
  首验结论从 verifier 文本的 `验收结论：通过/有条件通过/打回` 抽取（人工抽查 25 条，规范格式占绝大多数），配上 254 个包。
  `nFix`（后续 fix run 数）是按 label 词重叠匹配的，会把同批包的修复算进来，**只能当方向参考**。
- **排除**：`/tmp/pi-accept` 验收会话和「consult提问方/asker」测试 run（7 次调用）不进效果分析；
  09-23 那批 label 叫 `consult-plan…` 的 run 是 consult 设计期的普通 run，不算 consult 调用。

## 3. 效果估计（观察性，混杂严重）

**解读**：54 个挂专家的包全部来自 5 个主会话，正是 bash-timeout-grace、web-hub LAN、#22 memory、#26 Vue、#32 control、
session-history、steer-recall 这些 L3 大特性；按 dev-flow，「L3 写包必挂」。开发成本（$8.8 vs $3.6）、轮数（129 vs 80）
本身就说明它们难得多。按任务长度、模型、是否引用方案和冻结面分层后，差距缩小但方向不变。
**结论：选择偏差远大于任何可能的 consult 效应，这些数字不能解读为「consult 有害」，也不能解读为「consult 有益」。**
「调用过」和「没调用」的对比同样内生：模型往往是遇到歧义才开口问。

## 4. 开销与故障

- **花费**：consult 合计 $143.80，占 125 个提问 run 总花费（$891，已含 consult）的 16%，占全部挂专家 run（$2,069）的 7%，
  占同期全部 subagent 花费的 2.5%。没拿到完整答案的调用花了 $24.35。
- **单价比设计预期高一个数量级**：实验 4 中短 prompt 专家约 $0.01，实验 5 中长上下文专家 $0.08–0.12；
  dev-flow skill 写的是「glm < $0.05、Claude 19k ≈ $0.07」。生产中只有 glm 专家符合（中位 $0.05）；
  opus 专家中位 $1.24，gpt-5.6 专家 $0.64–0.96。原因是生产专家的上下文中位有 120k–225k，而 fork 后的首请求几乎从不读缓存（cacheRead 中位 0）。
- **轮次帽（24 次，13%）**：集中在「复验问上一轮验收员」（9 次）和「承接前一个 dev」（8 次）。这两类问题需要专家去读**新**东西，3 轮不够。
  sonnet-5 专家有 5 次试图调用 fork 里并不存在的 `bash`（`r_SWCKP4D1`、`r_VP48ZC1P`、`r_B7WPQRXN`、`r_M3AAE5NB`），白白耗掉轮次。
  另外 gpt-*-sol 经 zhipu-pool 的撞帽调用 `costUsd=0`，真实花费可能没有计入。
- **成本预检拒绝（16 次）**：基本都是向 fable 写的长方案专家提问（如 `bash-timeout-grace-plan-v6`、`web-hub-LAN-plan-v8`，单次首请求估价 $2–3.6），
  也就是最需要请教的那些专家恰好最贵、最常被拦。
- **最差批次**：web-hub LAN W2（`r_VP48ZC1P`、`r_12JXPA1Z`、`r_SWCKP4D1`、`r_JAPK073J`、`r_B0GJV7J7` 等），
  13 次调用中有用答案为 **0**（6 次预检拒绝、5 次撞帽、2 次询价测试），花费 $3.99，5 个包首验全部打回。
- **工具摩擦**：
  - 白名单描述列出的是 `label (r_xxx)`，模型照抄这个字符串就报「不在白名单（allowed: 同一字符串）」，共 5 次
    （`r_Z4FJ9S62`、`r_CA50NE5P`、`r_X4MAJFN9` 等，`matchExpertRef` 不识别这种展示格式）。
  - 撞轮次帽时的提示文案写的是「did not answer within 150s」，实际耗时只有约 20s，会误导提问方。
  - 2,000 字上限截断导致 12 次追问。截断方式是首尾保留，丢的恰好是逐条清单的中段。

## 5. 与受控实验对照

| 实验结论（baseline-results §15–19、exp-trim）  | 生产中是否成立                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 轮内同步 + 信息读不到时，模型会自发请教（8/8） | 部分成立：挂专家后 40% 的 run 会问。生产 prompt 往往已推送了大部分信息，低于 100% 是合理的        |
| 请教大幅提升决策遵守（2.25 → 7.0）             | **无法验证**：包级结果被选择偏差淹没；逐条看，「问到的点」的验收多数 ✅，没问到的点照样被打回     |
| 专家凭上下文一次答完、0 工具调用               | 大体成立：完成的回答中 87% 是 1 轮、0 工具                                                        |
| 单次请教约 $0.1                                | **不成立**：中位 $0.84，opus 专家 $1.24                                                           |
| 生产上限内都能完成（exp-trim FULL 9/9）        | **不成立**：非测试调用 29% 没拿到完整答案                                                         |
| 推送最稳，拉只补残差                           | 生产里有约 20–28% 的调用（复述报告 6、复述上轮打回点 15–31、截断追问 12）其实是在拉本该推送的东西 |

实验证明的是**能力**：特定条件下有用。生产数据显示的是**用法**：设计用途约占一半，剩下的花在误用、摩擦和失败上。

## 6. 建议

### 6.1 什么时候挂专家，什么时候不挂（修订 dev-flow「挂专家」节）

1. **保留**：开发写包挂 Plan/architect（方案经修订、存在取舍点）；返工挂打回它的 verifier（问「判据的意图」和「我这个修法能不能过」）。
   这两类是样本里帮助最明显的。
2. **改成推送**：
   - 复验、复审要的「上一轮打回点和判据」：主会话手里就有报告原文，直接贴进 prompt，不再挂上一轮验收员。
     只有在需要「判据背后的意图」时才挂。
   - Plan 修订要的「评审意见全文」：同样直接推送，禁止 consult 复述报告。
3. **禁止**（skill 已有规则，但被违反了 6 次，需要写进 Agent/consult 工具描述，或在派发时拦截）：
   - verifier 挂它验收的开发 run；
   - reviewer/verifier 向作者问「对不对 / pass 还是 fail / 最可能有什么缺陷」。
4. **不要挂**：
   - 上下文 > 250k 的专家（fable 长方案）：几乎必然被预检拒绝；应把关键决策落盘后推送。
   - 「承接前一个 dev」：要的是新的代码事实，不是专家记忆里的东西，11 次里只有 3 次答出来。
5. **在 dev-flow 和 agent-handoff 里更新成本说明**：把「glm < $0.05、Claude 19k ≈ $0.07」改成实测值——
   glm 专家约 $0.05；Claude/GPT 长会话专家 $0.6–1.6 一次，首请求不读缓存。
   「不问不收费」仍然成立：挂了不问不花钱，但一旦问了就不便宜。

### 6.2 工具层修复（成本低，收益确定）

- `matchExpertRef` 接受白名单描述里的 `label (runId)` 展示格式，或改为只展示 label、把 id 单独一列（消除 5 次无谓错误）。
- 撞轮次帽 / 预检拒绝的文案写清真实原因和耗时，不要统一写「within 150s」。
- 截断改为保留开头 + 提示「请分段追问第 N–M 条」，或对清单类回答放宽到约 4k；同时在 consult prompt 里要求「清单每条 ≤2 行」。
- 专家 prompt 里明确「你只有 read/grep/find/ls，没有 bash」，减少 sonnet 的未声明工具尝试。
- 记录 zhipu-pool 等路由撞帽时的真实花费（现在是 `costUsd=0`）。

### 6.3 要做真正的 A/B，需要先补这些埋点

现在的数据无法回答「consult 有没有用」。原因有三：派发参数里的 `experts` 没进 `RunDiagnostics`；没有车道和包的 id；verifier 结论是自由文本。建议：

1. `diag.experts`（白名单 runId）、`diag.consults`（次数、成本、结局汇总），以及 `SpawnRequest` 里可选的 `lane` 和 `packageId`，
   都持久化进 `subagent:run`。
2. verifier/reviewer 用 StructuredOutput 输出 `{ verdict, blockers[], packageId }`，开发 → 验收直接按 packageId 关联，不再靠 label 猜。
3. 预注册的随机化实验：对 dev-flow 里标「可选」的 L2 写包（方案直白、一次通过），以及至少一批 L3 包，按包随机 50/50 决定是否挂 Plan 专家，
   其余推送内容保持一致。主指标是首验通过率和返工轮数，次要指标是总成本（含返工）和墙钟。
   按本次观测的首验通过率约 0.3–0.5 估算，要检测 15 个百分点的差异，大约需要每臂 150 个包，需要数周的生产流量；做不到这个量就不要声称有效。
4. 在此之前，把本报告当作「consult 的生产 ROI 没有被证明」的依据：维持「先推后拉」，削减 §6.1 中的误用场景。
   按 §2 的分类，这些场景合计 80 次调用、$54.8，即约 44% 的调用、38% 的 consult 花费。

## 7. 局限

- 完全是观察性数据，没有随机化。包配对依赖 label 词重叠，`nFix` 偏粗。首验结论靠正则抽取，只人工抽查了 25 条。
- 「是否有帮助」的 26 条样本由单人判断，没有盲评，也没有第二评审。
- 数据集中在 pi-toolkit 自身开发（51/54 个挂专家的包），时间只有约 2 周（09-25 → 10-09），不能外推到其它仓库或其它车道配比。
- 工具结果里的 `costUsd` 依赖路由是否回报价格。部分路由（zhipu-pool 撞帽）报 0，consult 花费可能被低估。
