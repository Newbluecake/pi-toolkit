# consult：轮内同步向「掌握知识的 agent」请教 —— 需求简报

> 状态：需求已定，待出方案。证据来源：`docs/dev/fabric-v2/baseline-results.md` §10–19（实验 1–5）。
> 本工具是 fabric v2（已搁置，`docs/dev/fabric-v2/plan.md`）中**唯一被实验证明有价值**的部分的最小落地。

## 1. 要解决的问题

多 agent 串行协作时，下游 agent 需要上游 agent 掌握、但**在环境里读不到**的知识（拍板过的决策、否决过的方案及理由、
用户偏好）。不给获取渠道时，下游会顺着现有代码的惯性做出错误设计；或在被暗示「有信息」时越权翻会话记录。

## 2. 证据（为什么是这个形态）

| 发现                                                                     | 数据                                                           | 出处          |
| ------------------------------------------------------------------------ | -------------------------------------------------------------- | ------------- |
| 阻塞式中继（结束本轮、等调度方转问）下，模型不请教                       | 0/2                                                            | §12           |
| **轮内同步**（一次工具调用当轮返回）+ 信息确实读不到时，模型**自发**请教 | 8/8（实验 3–5）                                                | §15、§17、§19 |
| 请教显著提升质量                                                         | 不给信息 2.25 → 可请教 7.0（满分 7，两评审一致率 97%）         | §19           |
| **长上下文的真实上游 agent** 被 resume 后同样答得准                      | 3/3 按最终修订作答，0 次把作废决策当现行                       | §19           |
| 单次请教成本                                                             | 长上下文专家约 $0.08–0.12；专家请教时 0 次工具调用             | §19           |
| 通用 `Agent({resume})` 下调用出错                                        | 1/4 漏写 `resume` ⇒ 问了一无所知的新 agent，后者越界搜索编答案 | §19           |
| 专家回答偏长                                                             | 约 12K 字/次                                                   | §19           |
| 推送（交接包）仍是最稳的主渠道                                           | 7.0；请教是补充                                                | §17、§19      |

## 3. 功能需求

- **F1 专用工具**：`consult({ expert, question })`，同一次工具调用内返回专家的回答文本。
  `expert` 只能指向一个**已结束、会话已持久化**的 run（run id / label）。**不存在「新起一个 agent」的退路**——
  目标无效就直接返回明确错误（e1-r2 教训：问一个无知的新 agent 比不问更糟）。
- **F2 不污染、可并发**：请教不改动专家的原始会话（不续写其 session 文件），同一专家可被多个 agent 同时请教
  （当前 `Agent({resume})` 续写原会话、且有 resume 锁，两者都不满足）。倾向「fork 专家会话再提问」，由方案论证。
- **F3 跨 `/reload` 可用**：已结束的专家在 `/reload` 之后仍可被请教（当前 run 记录是内存态的，reload 后无法 resume）。
- **F4 有界、零挂死**：短时限（默认值由方案定，参考量级 2–3 分钟）、回答长度上限、轮次/成本上限；
  超时或失败**快速返回**一个「专家未能回答」的结果（相当于 fabric v2 设计中的 `nack`），提问方转为自查。
  必须遵守本仓库的分层 deadline / watchdog / reaper 不变量；请教方被中止时请教随之中止。
- **F5 回答格式**：引导专家「先给结论、再展开」，并在长度上限内作答；专家默认不需要工具（实验中 0 次调用），
  是否允许只读工具由方案取舍。
- **F6 可观测**：请教在 fleet widget / agent 树中可见（作为提问方的子节点），成本计入；
  **不产生顶层完成通知**，不唤醒主会话。
- **F7 谁能被问、谁能问**：需要支持「调度方在派发下游时指定可请教的专家」这一主用法
  （与 agent-handoff skill 的交接包配合）。是否允许请教任意已结束 run、主会话能否使用、需不需要 frontmatter 开关，由方案取舍。

## 4. 非目标

- fabric v2 的其余部分：广播、看板、唤醒规则、异步消息、配额与降级、按接收方状态分级投递。
- 向**运行中**的 agent 请教（那是 `steer_subagent` / fabric 的范畴）。
- 自动选择专家（由调度方或提问方显式指定）。

## 5. 约束

- `AGENTS.md` 全部约定：零挂死不变量（分层 deadline + watchdog + reaper + 可确认的投递）、
  timer 一律 `unref()`、禁止模块级可变状态（`/reload` 同进程重激活）、HOST_KEY 守卫、子会话保持惰性。
- TypeScript strict 全套；工具参数用 typebox schema；pi peer 版本区间 `>=0.84.0 <0.86.0`。
- 与 cache-ttl 子系统的交互需说明（fork 后的请教共享专家的上下文前缀，缓存可能命中或错过）。
- 已有的「静默后台 run」设计（`docs/dev/fabric-v2/silent-run-a1.md` 等）可作参考，但 consult 是**前台、同步、随提问方级联中止**的，
  语义不同。

## 6. 留给方案回答的开放问题

1. fork 的机制：pi SDK 有无现成的会话 fork / branch 能力？没有时「复制 session 文件再 open」是否安全（会话 id、父子关系、
   持久化位置、清理策略）？fork 出的会话是否持久化？
2. 专家的指定方式：派发时的白名单（如 `Agent({ experts: [...] })`）vs. 同会话内任意已结束 run vs. 同一棵 agent 树内的 run；
   主会话是否也提供该工具。
3. 跨 `/reload` 的 run 记录重建：从 `subagent:run` 会话条目重建哪些字段即可满足请教（至少 runId、label、sessionFile、type、model）。
4. 请教 run 的类型、模型与 thinking：沿用专家原 run 的配置，还是允许覆盖？
5. 回答长度上限的实现方式（截断 vs. 让专家自行控制 + 截断兜底）与默认值。
6. 与现有嵌套 `Agent` 工具、`tool-scope`、CC2 通知抑制、fleet widget 的集成点。
7. 测试策略：状态机 / 不变量测试如何覆盖（超时、专家不存在、专家会话缺失、并发请教、reload 后请教、提问方中止）。
