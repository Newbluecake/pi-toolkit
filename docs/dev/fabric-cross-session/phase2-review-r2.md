## 问题清单

### 阻塞路径与上轮未闭合项

B1 是 **r2 修复中新增的阻塞路径，属于上轮 #2 的延续**，不是扩展评审范围。

| #   | 严重度          | 位置                                | 问题                                                                                                                                                                                                                                                                                                                                                                                    | 建议                                                                                                                                                                                                                                                            |
| --- | --------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | 阻塞（Blocker） | §6.2 deferred、§6.5 墓碑清理        | **墓碑寿命没有覆盖延迟动作的寿命。** 真实 pi 在 `_emitAgentSettled()` 中依次 await `_deferredSettledActions`。xs 动作前面可以排着另一个长 run，该 run 不受 xs 的 rootRunMaxS 约束。xs 截止后转墓碑，但墓碑在 `deadlineAt+3600s` 可清理，容量规则又允许淘汰墓碑。此前驱动作稍后结束，xs 才开始执行时，token 可能已无账本记录；方案没有规定这种 xs trigger 必须拒绝，仍会出现无监管启动。 | token 记录只能在证明对应动作不可能再执行后释放；容量不足应拒绝新增，不能遗忘仍可执行的请求。另一种闭合方式是明确“本扩展 xs trigger 无有效授权即在首个请求前中止”，同时闭合 handedOver 例外。补“前驱 run 超过墓碑保留期后才执行 xs”的测试，不能只测迟到几秒。    |
| M1  | 严重（Major）   | §7.2 关闭证据、§7.4 无 TOCTOU 声明  | **后续输入不是切换取消证据。** `session_before_switch` 的某个异步 handler 尚未返回时，旧会话仍可处理 input，甚至启动 run；现有 pi `prompt()` 没有“等待切换处理器结束”的互斥。此时按 r2 清掉 switch 栅栏，切换仍可能继续，重新放行写旧会话。另外，完成事件中的 `setTimeout(0)` 可早于后续异步事件 handler 返回，不能单独证明 controller 已清理。                                         | 删除“出现 input/BAS 就证明取消”的推断。无终止证据时保持拒收，使用已定义的本地 reset，或增加能证明操作结束的接缝。补“慢 before_switch 期间插入人类输入”和“完成事件后续 handler 长时间 await”的用例。同步 dispatch 块只能解决块内竞态，不能证明栅栏外部状态正确。 |
| M2  | 严重（Major）   | §8.1 发送端守卫、§8.2–§8.3 异常结果 | **send 后不能把 origin_changed 映射为 none。** 例如旧会话已发 send、接收端已经追加消息，发送方随后切换会话；结果返回前守卫失败，按现文会返回 `none{origin_changed}`。这与实际副作用及 NQ2 相反。接收管道的兜底异常若发生在 dispatch 之后，也不能无条件回 `none{receiver_error}`。                                                                                                       | 按发送阶段区分：send 前守卫失败可返回 none；send 发出后，保留已知远端结果，或在失去确认时返回 unknown，不能凭本地会话变化推导未投递。异常处理同样要区分副作用之前/之后。补“接收成功后、响应返回前切换”的测试。                                                  |
