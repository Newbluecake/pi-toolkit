## 4. 顺带修复的 N1 潜在缺陷（helper.mjs 内，N2 接线后才会触发）

1. **setup 模式成功被判成失败**：`decidePrivateOutcome` 在没有 `piExit` 且 P1 返回 0 时给 1（run 模式的「P1 没跑 pi 却返回 0」防御）。setup 模式从不跑 pi，成功路径因此会让 `init --private` 退出 1。改为：`mode:"setup"` ∧ `inNsDone:true` ∧ 无 `failCode` ⇒ 0；run 模式规则不变（单测钉住两边）。
2. **`lock --lazy` 可能杀死监督进程**：P1 原先在进入 session 阶段**之后**才注册 SIGUSR2；记录写成 `session` 与 P1 `await` 返回之间有窗口，`lock --lazy` 此时发出的 SIGUSR2 会按默认动作终止 P1。改为在「信号优先」块里一开始就注册（`S.onUsr2` 延迟绑定；launching 阶段收到的记为 pending，进入 session 时执行一次；其他阶段忽略）。`lazyDetach` 本身仍只在 session 阶段动作。

## 6. 残留与后续（N4 接手）

- `--kill` 在 launching 阶段、`finalizing` 等待、以及由 `lock` 发起的 orphan/orphan-ns 外部收尾只有纯函数与假实例覆盖：真实环境中这些窗口太短或需要刻意制造崩溃，留给 N4 e2e（§6.2）用注入点覆盖。outerPrivateCleanup 本身已由 N1 真机用例（P1 被 SIGKILL）覆盖。
- `--lazy` 的固有残留照旧（R2x）：既有 cwd、已打开文件、运行中的作业仍可访问明文，直到会话结束；文案已如实说明。
- 旧布局库不计算私有视图（它们没有租约文件，也不可能有私有实例；Q-L0 只读兼容）。
- 调用者在**另一个**库的私有 ns 内对本库操作：按普通规则判定（本库记录的 ns 与调用者不同）；ns 内扫描不完整时结果偏 fail closed（拒绝），不会误放行。
