## 3. 给下游包的接口说明

### A0（agent 骨架）

- 构建 stack 时：
  1. `root = ensureStoreRoot(dir, { inVault })`。`inVault` 用 secure 域的 `vaultRoots` + `inVaultDir` 拼成谓词；`resolveStoreRoot` 已经对字面路径和 realpath 各查一次。
  2. `self = readSelfIdentity()`。返回 `undefined` 说明没有 /proc，此时禁止执行。
  3. `epoch` 取随机值。
  4. `store = openSessionStore({ root, sessionId, self, epoch, inVault })`。锁是内核 flock，不再需要 `judge`；`epochDisposed` 只在 `recoverRuns(store, self, judge)` 判 run 持有者时使用。运行环境必须有 util-linux 的 `flock`（缺失 ⇒ 所有事务 E_BUSY）。
- `session_start` 时依次调用：
  1. `sweep(store, { armedSince })`。返回的 `plan.supplementalAt` 用 unref 定时器补一次 sweep；`plan.tasks[].more` 为真就立即再 sweep。
  2. `recoverRuns(store, self, judge)`。
- 定时器到期：调用 `autoClaim(store, { taskId, t, armedSince, holder, gate })`，其中 `gate` 就是锁内执行的 `assertExecutable`（模式矩阵、归属 sid、secure 域、epoch 是否已 dispose）。只有返回 `fired` 时才在锁外 spawn 或入队。返回 `ineligible(early)` 表示墙钟落后于 T（回拨），按当前时钟重新 arm。返回 `error` 且带 `uncertain:true` 表示账本已 rename 但目录 fsync 失败：**不得 dispatch，也不得盲目重试**，稍后重读账本决定（见 §6）。
- 关闭时最先执行：`closeEpoch(openSessionStore({ …, lockTimeoutMs: SCHED_LOCK_SHUTDOWN_TIMEOUT_MS }), holder)`。
- 收到 `sched_receipts`：`store.transact(d => ({ value: removePendingReports(d, ids), write: true }))`。
- `sched_run`：先自己校验 sessionId 和 expiresAt，再调用 `manualClaim(store, { taskId, reqId, defHash, holder, gate })`。结果映射为 `started` 或 `refused(code)`。24h 内未过期的 reqId 已有 32 个时，新 reqId 得到 `refused(E_LIMIT)`（不记录，重试可在最早一个过期后成功），已记录的 reqId 照常重放。
- GC：`gcSessionReports(store, now)` 和 `recycleSessionDir(store, now)` 可以惰性调用，例如 stack 构建时或每小时一次；全局报告上限用 `gcGlobalReports(storeOpts, now)`。

### A1（background / note）

- 进入终态：
  1. 报告文件（`reports/<reportIdOf>.md`，0600，`reports/` 0700 由 `writeReportLocked` 创建）与账本更新在同一次 `writeReportLocked` 里完成。
  2. 在它的 `commit` 回调里依次调用 `finishRun(d, runKey, {state, reason, reportFile, note:"pending", noteId}, now)` 和（需要推送时）`addPendingReport(d, pendingReportFor(sid, run, status), now)`。
  3. `finishRun` 返回 `"late"` 表示终态已被别人写过，这时不发报告。
- 写报告**只能**用 `writeReportLocked(store, { reportFile, data, now, commit })`：容量准入、GC、写文件和账本提交都在同一把 writer 锁内完成（第 2 轮 m2）。`commit(draft, ctx, written)` 里写 `finishRun` 和（`written` 为真时）`addPendingReport`；`written=false`（`overCap`）时 run 标 `report-skipped(cap)`。不要「先 `gcSessionReports` 再写」。
- note 核验：发送前用 `sessionFileAnchor(file)` 取锚点；发送后调用 `findSessionEntry({ file, anchor, key:"noteId", id })`。S0 的 `noteFileOffset` 只能存数字：跨进程补投时只有 offset 没有锚点，应传 `offset: 0`（≤16 MiB 全量扫描，fail-closed）；传裸 offset>0 时找不到只会得到 `inconclusive(unanchored)`。
  - `absent` 只表示「扫到文件末尾都没找到」。要算作「确认缺失」，还必须 `judgeHolder(noteHolder, self).liveness === "dead"`。
  - `too-large` ⇒ 记 `unverified`。
  - `inconclusive`（deadline / short-read / changed / unsettled / unanchored）⇒ 稍后重试，绝不当作缺失、绝不补投。
- 跨进程补投时的领取（更新 noteHolder、noteFileOffset）由 A1 自己用 `store.transact` 写。

### A3（工具 / 命令）

- 创建任务时，同一个 transact 里 push 任务定义并写 `occ[id] = initOcc(task, now)`。
- 任何修改都走 `changeTask(store, id, mutate)`：它先按旧定义 sweep（积压超过一次 sweep 的块预算时分批写入进度，最多 `CHANGE_BACKLOG_ROUNDS=4` 轮，仍未结清 ⇒ E_BUSY），全部结清后 hash 变化或任务刚变为可执行时才 voidUntil。
- 批准用 `approveTask(store, id, reviewedHash, via)`，内部做 CAS，不一致返回 E_REV。
- 删除用 `removeTask(d, id)`；它保留 runs 和 pendingReports。
- repair 用 `store.repair()`：走普通锁，持有者存活 ⇒ E_BUSY 并提示「进程退出后自动释放」。没有强拆入口。
- `update` 禁写字段的 schema 校验由 A3 负责（`SCHED_UPDATE_FORBIDDEN_FIELDS`）。

### H1（hub）

- 启动时调用 `resolveStoreRoot(HubConfig.schedule.dir, { inVault })`。抛出的 `SchedFsError.reason` 为 vault / moved / … 时，整体判 degraded。
- 扫描：`listSessionDirs(root)`，再对每个会话 `readSessionState(root, dir)`。这两个都是同步、有上限的调用；H1 需要在外面套 single-flight、2s deadline 和 IO 台账，并用代次屏蔽迟到结果。
- 报告：`readReportFile(root, dir, entry.reportFile)`。
- next / 观察时钟用 `compileWhen` + `nextOccurrence`；对账用 entry 自带的 `count`。需要重算时用**同一个** `countOccurrences`。观察判定用 `withinTolerance` / `sweepCut`。
- 结果未知：`unknownRunKeys(state, hubSelf)`。

## 6. 遗留问题与提示

- Linux-only（偏差 #9）。如果以后要支持 macOS，需要另做一套 openat 风格的方案。
- reader 和 writer 的 IO 都是同步、有大小上限的，但无法被 deadline 中断（对本地普通文件来说，这是可以接受的有界操作）。hub 的 2s deadline、IO 台账和代次屏蔽由 H1 在外层实现。
- `gcGlobalReports` 会逐个会话取锁，会话目录最多 64 个；它跳过 degraded 或缺失的会话。
- 旧引擎的测试 `tests/schedule/{cron,scheduler,store}.test.ts` 仍然通过，等 A0 退役旧引擎时一并处理。
- **依赖 util-linux `flock`**（安全评审 B1）：锁通过 `flock(1)` 作用在我方 fd 上实现（Node 没有 flock 绑定，同 `src/secure/settings-lock.ts`）。没有该二进制时所有事务 E_BUSY（fail closed）；A0 应在启动时探测并给出明确提示。每次加锁有一次 `spawnSync`（毫秒级），事务频率很低，可以接受。
- **建议 S0 增加锚点字段**（安全评审 M4）：例如可选的 `noteAnchor` / `digest.inflight.anchor`（字符串，存 `encodeAnchor` 的结果，≤128 字符）。在此之前跨进程补投只能用 offset 0 全量扫描（≤16 MiB，超出记 unverified）。
- **uncertain 提交的后续处理**（安全评审 M5）：`autoClaim` 返回 `uncertain:true` 时，账本里可能已有一条本进程持有、状态 dispatching 的 run，而调用方没有 dispatch。`recoverRuns` 会把活着的持有者判为存活，这条 run 不会被自动转换。建议 A0 在拿到 uncertain 后稍后重读：如果该 runKey 存在且持有者是自己，就用 `finishRun` 写成终态（例如 unknown）。这属于 A0 的调用约定，S1 只负责如实报告。
- 会话目录创建的多进程竞争测试是概率性的（撤销修复后不一定每次都能复现竞态）；确定性证据是「外部持有 `.store.lock` ⇒ 创建 E_BUSY」那条。
- **全局报告上限是软上限**（第 2 轮 m2）：`writeReportLocked` 只对本会话上限做硬准入；跨会话的 2000 份 / 128 MiB 由 `gcGlobalReports` 事后收敛，期间可能短暂超出。要做硬准入，需在 store 级锁内同时盘点 64 个会话，代价与锁顺序（store → session）都要另行评估。
- **session-proof 的 settle 窗口**（第 2 轮 M4）：刚改动不足 50 ms 的会话文件证明不了缺失，pi 正在写入的文件会返回 `unsettled` 或 `changed`，A1 稍后重试即可（at-most-once 语义下只会漏、不会重）。有了 settle 窗口，起始快照距上次修改至少 50 ms，之后的任何写入都落在更晚的 tick，ctime 必变。剩下的理论残余只有一种：墙钟在扫描前大幅向前跳变，让刚改过的文件被误判为已稳定。
