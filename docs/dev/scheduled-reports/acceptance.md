# 定时任务（会话可感知）— 真机验收清单（I1）

规格：`plan.md` §14「真机验收清单」+ I1 新增项。本清单只验证自动化测试无法覆盖的真实环境行为（真实 TUI、真实飞书客户端、真实 hub 与真实模型提供方、traffic.db 字节比对）。自动化覆盖映射见 `I1-report.md` §3。

## 前置

1. `schedule.enabled=true`、`webHub.enabled=true`（control 开）、`feishuBot.enabled=true`（已绑定一个飞书私聊到被测会话，`/cur` 确认）。`/reload` 后 `/webhub restart`（hub 由谁拉起谁决定，R11 同类残留）。
2. 在 tmux 里开独立的 pi 会话（TUI），工作目录用一个临时仓库，**不要**用日常会话。需要时另开第二个终端的 pi 打开同一会话文件（用例 2、3）。
3. 基线：`/schedule` 应列出空表；`/agent status`、`/webhub status` 记下基线；`ls ~/.pi/agent/schedules/` 看会话目录；`~/.pi/agent/pi-subagent-schedules.json`（旧文件）**不得**出现。
4. 开 `traffic.enabled`（用例 8 用），`/record on`。

## 用例（plan §14 八条）

| #   | 操作                                                                                                   | 期望                                                                                                                                                                                                     |
| --- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `/schedule add` 建一个两分钟后触发的 background 任务（once 或 `*/2 * * * *`），批准；等待              | 状态栏出现下次触发倒计时 → 到点 fleet 中出现 `sched:` 行 → 会话里出现 quiet 结果消息，**不新开一轮**（无模型回合）→ 飞书收到报告卡片；报告很长时卡片附 md 文件；`/schedule log <id>` 显示 completed      |
| 2   | 关闭 TUI，等它跨过触发点                                                                               | 飞书收到「已错过」；同一小时内再次错过**不再**收到消息，下一个整点收到一条汇总；重新打开会话，digest 只出现一次，AI 能引用其中内容；对账不重复推送                                                       |
| 3   | 让 AI 用 `schedule` 工具 create 一个任务                                                               | 状态栏出现 `pending 1`；任务不会执行；网页审阅对话框看到完整内容并批准后才生效。审阅期间在另一个终端改了 prompt ⇒ 批准被拒（`E_REV`），要求重新审阅；AI `resume`/`run_now` 一个未批准任务被拒            |
| 4   | 建一个 message 形式的任务；在对话进行中让它到点                                                        | 不打断当前这一轮；本轮 settled 并过静默期后才执行；执行中途插话 ⇒ 结果标 continued（人接手，无上限）；全程无人插话时 60 分钟上限到点自动中止（可把时间推进用于演示：只确认到点行为与终态原因，不必真等） |
| 5   | 后台任务（background）运行中执行 `/quit`                                                               | 飞书推送「结果未知」；重开会话后 digest 中有该记录；`/schedule log` 显示 `unknown(owner-closed)`                                                                                                         |
| 6   | 飞书里 `/schedule`：列出任务；对离线会话执行 `run`；在终端修改任务后再 `run`；在非 cron 时刻执行 `run` | 列表正确；离线 ⇒ 回复不在线；已修改 ⇒ 回复「已修改」（要重新确认定义）；非 cron 时刻 `run` 正常运行，且**不**改变下次触发水位                                                                            |
| 7   | 关闭 web-hub（`/webhub stop`，本地模式）；让任务到点；再启动 hub（24h 内）                             | 停机期间执行、去重、digest 都正常；hub 恢复后刚才的报告被补推一次（不重复）；超过 24h 的不补推                                                                                                           |
| 8   | 用 traffic.db 对比：开 schedule 前后同一会话的 system prompt；再 fork 出子会话                         | system prompt 字节不变（任务摘要只在上下文尾部 `pi_schedules` 段）；fork 出的子会话没有父会话的任务段，`/schedule` 在子会话里报 E_CHILD                                                                  |

## SC1（plan §14 集成场景，无自动化双进程集成，真机补）

| #   | 操作                                                                                                                                                  | 期望                                                                                                                                                                                                   |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 0   | 把同一个会话文件 `--session` 同时在两个终端的 pi 里打开（两个进程、同一 sessionId），建一个 `* * * * *` 的 background 任务并批准，等待跨过 3 个整分钟 | 每个整分钟的触发**只执行一次**（`/schedule log <id>` 里每个 occurrence 恰一条 run，runKey 不重复；spawn 只发生在持有者进程）；另一进程不会重复执行；关掉持有者后，另一进程在下一个触发点接管而不是双跑 |

## I1 新增项

| #   | 操作                                                                                                                                                                                                                                                                                                                          | 期望                                                                                                                                                                                                                                                                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9   | 让会话上下文逼近压缩阈值（例如把 `compact.*` 阈值调低或灌入大量文本），再让一个 message 形式任务到点                                                                                                                                                                                                                          | pi 先做 pre-start compaction，随后定时消息**恰执行一次**（C-S5 修复）；compaction 期间任务不被判 unknown、不重复发送；`/schedule log` completed。compaction 异常久（>10 分钟）时任务被切断并标 unknown(start-timeout)，无模型请求                                                                                                               |
| 10  | 构造阻塞（**不要用 `/reload`**——它重建 stack、内存阻塞计数清零，演示不了）：让会话里弹出一个 ask_user 对话，在 web 端回答/取消的同时在 TUI 里关闭同一对话制造竞态，使其 `ui_prompt_end` 丢失；或在 TUI 里对一个 `/tree` 导航/`/fork` 选择器按 Esc 取消（取消的窗口没有完成证据，fence 保持打开）；之后让 message 形式任务到点 | 消息一直排队等待（`/agent status` / `diagnostics` 能看到 fence 窗口或 `uiPrompts`）；执行 `/schedule repair`（本地）后调度器的栅栏窗口与对话计数被重置，排队消息继续派发；`/fabric fence reset` 同样触发该重置（该命令受 `webCommandPolicy.fabric` 管，默认 web 可执行；`/schedule repair` 则 web 一律拒绝）；从 web 发 `/schedule repair` 被拒 |
| 11  | message 形式任务排队中（会话忙），执行 `/schedule pause <id>`（以及 `rm <id>` 各一次）                                                                                                                                                                                                                                        | 排队的运行立刻变 dropped（原因 task-changed，面板显示对应文案），之后不会发出该条消息；handoff 形式则立即收到 `handoff-recap` quiet 说明；另一终端的 `pause <id> --all` 只撤销 ledger 半边（他进程内存队列仍靠发送前 CAS 兜底，见残差）                                                                                                         |
| 12  | 关闭 schedule（`schedule.enabled=false` + `/reload`）                                                                                                                                                                                                                                                                         | 无 `schedule` 工具、无 `/schedule` 命令、无状态栏项、无 `pi_schedules` 段、hub 无 `sched.v1` cap；不创建 schedules 目录；已有 trigger 到达时只被孤儿 guard 拦截（不触发模型）                                                                                                                                                                   |
| 13  | 飞书侧：定时消息运行（message 形式）期间观察飞书                                                                                                                                                                                                                                                                              | 该运行的 done 通知被精确抑制（`sched_bound`），人工接手（merged/continued）后恢复通知；这条自动化只在 H1/F1 单元层覆盖，**必须真机确认**                                                                                                                                                                                                        |
| 14  | 飞书 `/schedule run <id>`（在线会话，立即运行）                                                                                                                                                                                                                                                                               | 会话内执行并推送报告；没有子进程 e2e 自动化，**必须真机确认**                                                                                                                                                                                                                                                                                   |
| 15  | 在用例 9 的 compaction 进行期间（压缩请求还没返回时），在 TUI 里执行 `/new`（或 `/fork`、`/tree`）并把它的确认对话挂着不动，再等压缩结束                                                                                                                                                                                      | 定时触发被拒（`unknown(owner-closed)`），**没有**主请求发往模型（看 traffic.db 或提供方日志）；取消该 `/new` 后会话正常；之后下一次触发点恢复正常                                                                                                                                                                                               |
| 16  | 用例 9 的环境里同时启用 `fabric.crossSession`（xs）——生产里 xs 的 `session_before_compact` handler 排在调度器前面                                                                                                                                                                                                             | 与用例 9 同样的暂停语义：压缩期间超过 60 秒不会被判 start-timeout，压缩结束后恰执行一次                                                                                                                                                                                                                                                         |
