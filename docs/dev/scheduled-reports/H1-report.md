## 2. 关键决策与依据

1. **ports.ts 零改动**（本包文件域不含它）：协调者由 hub.ts 构建，经两处 duck-typed 附加流转——`frontendDeps.schedules`（http.ts 侧 `FrontendDepsSchedulesExt` 同款拓宽，`HttpFrontendExt` 先例）与 agent-server 的可选 `schedule` dep。`HubEvent` 不加 `schedules` 变体：SSE 直发走 `RouteSet.onSchedules`（与 load 同构，不经 bus、不进 replay ring）。
2. **帧不进 registry**：三帧在 agent-server 截走（`fsb_req`/`xs_req` 先例），registry/ports/边界零改动。
3. **观察时钟**：单定时器臂向最近观察点（nextAt+90s），触发时**重读该会话**判 `decidedThrough < T` 且无在线视图才记观察并立即经合并槽通知一次；启动只补看最近 10 分钟内到期的观察点（每任务每轮 ≤16 个，更密的交给对账）。在线判定用 registry 的 `session.sessionId` + `isConnected`。
4. **at-most-once 通知序**：合并 flush 先 `store.flush()`（hub 状态落盘）再 `bot.sendNotice`（§7.2「先写 hub 状态再入队」）。全局 ≤30 条/小时，超出不丢——留在结转下小时再试（`noticesDeferred` 计数）。
5. **droppedIndexCap（会话级）挂在排序第一个任务的合并槽**；会话无任务时进该会话独立 `""` 槽。这是「并入该会话下一条通知」的具体落法（已披露偏差）。
6. **回执视图在 hub 内存**（`receipts()` 由 F1 喂、F1 绑定时应重放全量持久快照）；hub 不持久化回执——F1 的 `scheduleReceipts` 台账才是事实源（§7.1）。`sched_receipts` 在回执状态变化与会话 attach（bus `session`/`agent_up`）时推给在线视图。
7. **报告发现四条件**（§7.1）：未过期、无回执、`endedAt ≥ installedAt`（installedAt 未知视为 0）、bot 已配置且 open；发现后把带惰性 `readReport()` 的视图交给 F1（正文不进协调者内存）。未绑 F1 ⇒ 不投递（索引等满 24h 窗口，N1 语义不变）。
8. **零面**：`config.schedule` 键不存在 ⇒ 协调者不构建、cap 不加、路由 404/401 原矩阵、SSE 无帧、`sched_*` 帧落入 registry 被忽略、零磁盘访问（含 hub 状态文件）。三份 fabric off golden、`legacy-xs-v071` fixture 零改动（实测通过）。
9. **坏 root 降级**：`resolveStoreRoot` 失败 ⇒ 空投影 + WARN + `status().degraded`，hub 照常运行；cap 仍声明（spawn.v1 先例：UI 需要解释）。恢复需 `/webhub restart`（已披露）。
10. **hub.log 只记元数据**：所有日志行不带路径/正文（S1 的错误 detail 本就不含路径）。
