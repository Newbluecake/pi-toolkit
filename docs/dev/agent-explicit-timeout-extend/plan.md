## 0. 一页结论

1. **宽限/延长机制本身不动**：判定全部收敛在 `src/core/deadline.ts` 的 `extendability()` / `graceWindow()` / `hardDeadlineAtFor()`；显式预算不可延长的**唯一原因**是 `applyBudgetPolicy({ explicitTotal: true })` 把 `maxTotalFactor` 钳成 1（⇒ `H === D0` ⇒ `no_headroom`）；workflow 侧唯一原因是 `src/tools/workflow-tool.ts` `mergeBudget()` 写死 `maxTotalFactor: 1`。
2. **区分模型面显式与程序派生显式**（采纳主会话倾向）：新增 `SpawnRequest.timeoutPolicy?: "fixed" | "extendable"`，**缺省 = fixed**（兼容 + fail-safe）；只有 `Agent` 工具（顶层 + 嵌套，共用 `baseRequest`）在传 `timeout_s` 时写 `"extendable"`；workflow 子 run / consult / goal / tidy / RPC 零代码改动保持硬顶；workflow 子 run 仍钉 `W.hardAt`。
3. **策略是 run 的持久事实**（v2）：spawn-service 把请求解析成确定值写进 `diag.timeoutPolicy`，随所有持久化面走；resume 按 R-inherit 继承；所有「是否 fixed」的文案判断读真字段。
4. **延长规则复用默认预算旋钮**（`budget.totalGraceMs` 90s / `maxExtensions` 3 / `maxTotalFactor` 2）——**默认 2×，不是 3×**（3× 是 bash job 的 `bashJobs.maxTimeoutFactor`）；不改默认值。
5. **不保留模型面「真·硬顶」开关**：不延长时只比旧语义多 ≤ `min(G, (f−1)·T)`；严格截断 = 收到宽限通知即 `abort_subagent`；全局退路 `extend.enabled=false`。
6. **零挂起加固为强制项**（v2）：计时器分段（消除 >24.8 天延迟的 1ms 忙等）+ 跨度钳位 + 非有限 `extendMs` 防御 + schema 7 天上限。
7. **状态机迁移语义零改动**：不新增 input kind / phase / effect，168 格 MATRIX 与 P1–P15 oracle 不变；reducer 只有三处「数据面」改动——`enqueued` 镜像 `timeoutPolicy`、跨度改走 `clampSpanMs`、`deadline_extended` 非有限防御（新增 P16 属性 + 定向用例）。

## 2. 新语义定义（决策）

### 2.1 E1 · 模型面显式 `timeout_s` 与默认预算同权

`Agent({ timeout_s: T })`（顶层与嵌套）与 `SubagentWorkflow({ timeout_s: T })`：

- 软截止 `D0 = enqueuedAt + T`；硬天花板 `H = min(enqueuedAt + ceil(f·T), capAt)`（今天 `H = D0`），`f` = 合并后的 `budget.maxTotalFactor`（默认 2），`capAt` = `SpawnRequest.deadlineAt`（Agent 工具今天不设）。
- 到 `D0` 时若处于 OVERTIME 相位且 `extendability` ok ⇒ 宽限 `graceUntil = min(D0 + G, H)`，按 `extend.notify` 通知；宽限内 `extend_subagent_timeout` 可救回。
- 延长 ≤ `N` 次，`deadlineAt' = min(max(now, deadlineAt) + extendMs, H)`；次数用完或顶到 `H` 后的截止**不再宽限**。
- 启动相位到点：`not_started` ⇒ 不宽限（同默认预算，D-14）。
- 两个上界：无人延长 `≤ T + min(G, (f−1)·T)`；最坏 `≤ f·T`（均再加 `abortGraceMs + reapMs + tick` 收尸）。

### 2.2 E2 · 程序派生显式预算保持硬顶（`timeoutPolicy` 缺省 = `"fixed"`）

| 调用方                             | 为什么必须硬顶                                                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| workflow 子 run（`host.ts`）       | 「子 run 不晚于 workflow」由 `deadlineAt=W.hardAt` + `stopOwned` 结构性保证；子 run 自行宽限会出现 RK-12(a)「编排器已放弃、子 run 仍在宽限」 |
| consult fork（`consult/tool.ts`）  | fork 文件回收、`watcher.ts` 上限、`waitOutcome` 无 `waitMs` 都以「150s 必死」为前提                                                          |
| `/goal` 验证 run（`goal/hook.ts`） | 外层 `evalTimeoutMs` / eval watchdog，内层放宽会竞态                                                                                         |
| memory tidy 提案 run（`index.ts`） | 命令自持结果、`suppressDelivery`，无人接宽限通知                                                                                             |
| RPC 远端 spawn（`rpc/server.ts`）  | 跨进程稳定协议，无 extend 通道；白名单发不进新字段                                                                                           |

```
  req.timeoutPolicy                                   // ① 新请求显式（Agent 工具 timeout_s ⇒ "extendable"）
  ?? (resume ? resumeTarget.timeoutPolicy : undefined) // ② R-inherit（§2.7），旧条目缺字段 ⇒ undefined
  ?? (req.budgetOverride?.totalMs !== undefined ? "fixed" : "extendable") // ③ 形状推导（仅作用于「请求」，不是从 run 快照推断）
fixedDeadline = resolvedPolicy === "fixed"
```

`"fixed"` 也可不带 `totalMs`（默认预算也硬顶），今天只会由 R-inherit 产生。`AgentTypeConfig.budgetOverride` 仍不算显式。

**命名**：字段叫 `timeoutPolicy` 而非 `deadlinePolicy`——后者已被 bash 子系统 `JobDeadlinePolicy`（`bash/manager.ts`、`stack.ts` `buildBashJobManager`）和 workflow-agent-queue 评审**否决删除**的 `deadlinePolicy: "hard" | "owner_extendable"` 占用；取值用 `"fixed"` 而非 `"hard"`——extendable run 也有 `hardDeadlineAt`，「hard 策略」与「hard ceiling」易混读。

### 2.3 E3 · 不保留模型面「真·硬顶」开关

| 方案                              | 评估                                                                                                                                 |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **A. 统一可延长，无开关（采纳）** | 不延长时只差 `≤ min(G,(f−1)T)`；严格截断有现成动作（宽限通知即 `abort_subagent`）；全局退路 `extend.enabled=false`；模型面零新增参数 |
| B. `timeout_hard: true`           | 双参数是 D-5/D-12 记录在案的混淆源；只省 ≤90s + 一次唤醒                                                                             |
| C. 新增 `soft_timeout_s`          | 违背拍板，两个时间参数并存最易混淆                                                                                                   |

反方：① 长尾截断要可预测——不理会时死线 `T+≤G` 且 `T` 时刻必通知（顶层恒后台）；dev-flow 改为「宽限通知：值得等就延长，否则 abort 拆小重派」。② 多一次唤醒——与默认预算同价，`extend.notify=off` 可静音。③ 花费——每次延长都是显式工具调用，次数/总寿命双上限。④ 自动化依赖硬顶——仓内程序生产者全部 E2；仓外仅 RPC（恒 fixed）。底层 `timeoutPolicy` 已就位，将来要逐调用硬顶只需把 `"fixed"` 映射到 Agent 参数面。

### 2.4 E4 · 复用默认预算旋钮

复用 `budget.totalGraceMs / maxExtensions / maxTotalFactor`（含 agent-type 层、`extend.enabled` 钳位）：一份 `extendability`/`graceWindow` 逻辑；factor 是相对 `T` 的倍数天然缩放；`/agent settings` 不变。绝对量上限不是 factor 的职责——由 §3.3 的 schema 7 天上限与 core 跨度钳位承担。默认 2×（Q1：如要 3× 改 `budget.maxTotalFactor: 3`，对默认预算与显式 `timeout_s` 同时生效）。

### 2.5 E5 · 嵌套 `Agent` 的 `timeout_s` 同样 extendable（用户拍板，已知取舍）

两个参数面共用 `baseRequest`，统一写 `"extendable"`。**已知接受的取舍（写入 AGENTS.md）**：嵌套显式 run 到点进入的宽限**不通知任何人**（CC2：`notificationSuppressedRunIds` 丢弃子 run 的 `notify_deadline`），**子会话内也没有延长入口**（`extend_subagent_timeout` 只在主会话 post-guard 注册、`RESERVED_TOOL_NAMES` 拒绝注入）；因此实际效果是「静默多活 ≤ `min(G,(f−1)T)` 后 `timed_out`，期间父 run 的阻塞 turn 继续等待；主会话可凭孙 run id 显式延长」——与嵌套**默认预算** run 今天的行为一致。闭环由 §7 N1–N3 锁定。

### 2.6 E6 · `SubagentWorkflow` 显式 `timeout_s`

`mergeBudget` 只覆盖 `workflowTotalMs`，不再写 `maxTotalFactor: 1` ⇒ `hardAt = start + ceil(f·T)`，宽限/延长/通知走既有 workflow 路径，零逻辑改动。子 run 钉死关系不变（子 run 仍 `deadlineAt = W.hardAt` + 程序 fixed 预算 + `wf_` 父拦截）；workflow 无 fixed 生产者，**不引入** workflow 级策略字段。启动文案自动带 `(extendable up to …)`。

### 2.7 E7 · resume 语义（R-inherit）与持久化协议（v2 新增）

**规则**：resume 起的新 run **继承原 run 已持久化的 `diag.timeoutPolicy`**，除非新请求显式给出策略（Agent 工具 `resume` + `timeout_s` ⇒ 新请求的 `"extendable"` 赢）。**只继承策略，不继承原 `totalMs`**——新 run 的预算仍完全由新请求合并（维持 C19 现状：`resume` 是新 dispatch，「再给它 2h」应写在新调用里）。旧版条目缺字段 ⇒ 不继承 ⇒ 落 §2.2 第 ③ 项。

### 3.3 跨度与有限值守卫（P1，强制）

**决策**：core 层一律**安全降级（钳位）**，模型面 schema 一律**拒绝**。

- 理由：core 的输入来自 settings / agent-type / RPC / 程序派生，拒绝会表现为远离成因的 spawn 失败，且「拒绝」在 reducer 里只能是 `illegal`（静默忽略）；钳位保持 run 有界、行为可预测（只会更紧）。模型面拒绝则是自纠错的 schema error。
- `MAX_DEADLINE_SPAN_MS = 365 天`：远大于任何合法预算，`enqueuedAt + 365d` 仍是安全整数；`clampSpanMs(ms)` = `Number.isNaN(ms) || ms <= 0 ? undefined : Math.min(ms, MAX_DEADLINE_SPAN_MS)`（`+Infinity` ⇒ 上限）。

| #   | 位置                                                                                                  | 守卫                                                                                                                                                                                                                                                               |

| G1  | `core/deadline.ts` `hardDeadlineAtFor`                                                                | `t = clampSpanMs(totalMs)`，`undefined` ⇒ 返回 `undefined`（既有防御语义）；`f = Number.isFinite(factor) ? max(1, factor) : 1`（非有限 factor 降级为 1 = 更紧）；`span = max(t, clampSpanMs(Math.ceil(t·f)) ?? t)`；`raw = enqueuedAt + span`；再与 `capAt` 取 min |
