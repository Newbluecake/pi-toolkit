# 任务：fabric v2 消息投递层实施方案

你在 `/home/bluecake/ai/pi-toolkit` 仓库工作。这是 pi 编码 agent 的扩展 `pi-toolkit`，其中 `src/fabric/` 是现有的 v1 inter-agent 消息织网（`message_agent` 工具、按 agent 类型 frontmatter 的 `can_message` 路由、mailbox、per-link throttle 等）。

现在要做 **fabric v2**。请产出它的**消息投递层实施方案**。

## 需求概要（来自前序阶段的交接）

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播；
- **R2**：发送永不阻塞——发送方绝不等待对方回复。

前序阶段已与用户讨论并拍板了以下关键设计决策，**必须遵守**：

1. **彻底删除 `can_message`**：不设任何「谁能给谁发」的权限白名单（需求 R3：不限制发送能力）。`authorize()` 只保留方向性的协议规则（例如 result 必须上行），那是协议自洽，不是权限。
2. **广播恒不唤醒任何 agent**（不变量 I-W）：只有点对点（direct）消息可以唤醒接收方（包括唤醒正在运行的 agent 起一轮、或复活已结束的 agent）。理由：广播命中 N 个 agent 就唤醒 N 个，会把成本炸成 O(N)；唤醒必须是具名、担责、计入接收方预算的定向动作。
3. **广播 = 一条看板记录**（`to:"board"`），恒 O(1)，绝不向 N 个接收者逐个 push。接收方自己拉取看板。
4. **投递纪律按接收方状态分级，不设 `urgent` / 优先级标记**：接收方是运行中的子 agent → push；接收方是主 agent（root）→ push，但受 wakeRoot 开关与配额约束；接收方已结束（终态）→ 进看板，或（仅点对点 query）复活它。评审中曾有「发送方可置 urgent:true 请求 push」的提案，已被否决并删除。
5. **看板只在当前主 session 内有效**（用 `appendEntry` 写入、读回），不跨会话持久化。跨会话知识复利留给 memory 子系统。
6. **超限降级，永不拒收**：配额/收件箱满时按 push → notify → pull 逐级降级，任何一次发送都不会返回失败（R3 的字面要求）。
7. **`nack`（"我不知道"）是一等公民的消息 kind**：R2 的直接后果——让发送方尽早转为自查，比等超时快一个数量级。

## 方案必须覆盖

1. 消息模型：字段与 kind 列表；
2. 发送权限与路由规则；
3. 点对点与广播各自的投递方式（push / notify / pull 由什么决定）；
4. 接收方的唤醒规则（什么消息能让一个 agent 起一轮模型调用、能否复活已结束的 agent）；
5. 看板（共享公告）的存储方式与有效范围；
6. 配额 / 收件箱满时的处理；
7. 要改哪些文件与函数（基于现有 `src/fabric/` 代码）；
8. 测试要点。
