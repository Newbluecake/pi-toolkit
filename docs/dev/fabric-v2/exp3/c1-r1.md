## 0. 已拍板决策（约束基线，不可协商）

| #   | 决策                                                             | 理由                                                                                                                                                   |
| --- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **彻底删除 `can_message`**：不设任何发送权限白名单               | R3。`authorize()` 只保留方向性协议规则（如 result 必须上行）——那是协议自洽，不是权限                                                                   |
| 2   | **广播恒不唤醒任何 agent**（不变量 I-W）                         | 广播命中 N 个 agent 就唤醒 N 个，成本炸成 O(N)；唤醒必须是具名、担责、计入接收方预算的定向动作                                                         |
| 3   | **广播 = 一条看板记录**（`to:"board"`），恒 O(1)，绝不 N 路 push | 唯一能让 R1 的广播不炸成本的结构；接收方自己拉取看板                                                                                                   |
| 4   | **投递纪律按接收方状态分级，不设 `urgent` / 优先级标记**         | 运行中子 agent → push；root → push 但受 `wakeRoot` 与配额约束；终态 → 看板，或（仅点对点 query）复活。评审中「发送方可置 `urgent:true`」提案已否决删除 |
| 5   | **看板只在当前主 session 内有效**（`appendEntry` 写入、读回）    | 无陈旧治理成本；跨会话知识复利留给 memory 子系统                                                                                                       |
| 6   | **超限降级，永不拒收**：push → notify → pull 逐级降级            | 任何一次发送都不会返回失败（R3 的字面要求）                                                                                                            |
| 7   | **`nack`（"我不知道"）是一等公民的消息 kind**                    | R2 的直接后果——让发送方尽早转自查，比等超时快一个数量级                                                                                                |

由评审吸收的两条关键事实更正（影响下文所有设计）：

- **F1（§15.1）**：pi 的 steer 语义是「当前 assistant turn 的工具调用执行完之后、下一次 LLM 调用
  之前」注入，**并入同一外层 turn**——push 给运行中的子 agent 只花 context token，**不产生额外轮次**
  （「打断一轮」只对空闲 root 与终态 revive 成立）。因此原「回答 push / 其他 notify」的按 kind 分级
  **作废**，改为按接收方状态分级（决策 4），`urgent` 字段取消。
- **F2（§15.5 裁剪）**：`roster` selector、`urgent`、`hop/maxHops`（无转发路径，死代码）、隐式兴趣域、
  `mutation` 破格（与 I-W 矛盾）、`scope.symbols`、`boardSenderSharePct`、`answered` supersede 均砍掉。
  剩余最小集：新 kind query/answer/nack/announce + `to:"board"` + `replyTo`/`topic`/`evidence` 字段
  - 两级投递路径 + 看板 + `read_board`。

## 1. 消息模型（字段与 kind 列表）

### 1.1 kind 列表

| kind          | 方向   | 用途                                          | 可经 `message_agent` 发送 |
| ------------- | ------ | --------------------------------------------- | ------------------------- |
| `progress`    | 任意   | 运行通报（v1 保留；有 supersede 语义）        | ✅                        |
| `finding`     | 任意   | 结论性发现（v1 保留）                         | ✅                        |
| `directive`   | 下行   | 指令（v1 保留；仅 parent→child，协议规则）    | ✅                        |
| `result`      | 上行   | 子 run 结果回传（v1 保留；仅 child→parent）   | ❌（协议内部使用）        |
| `dead_letter` | 系统   | 投递失败回执（v1 保留；仅 from==="system"）   | ❌                        |
| `query`       | 任意   | **提问：无义务、无阻塞、可被忽略**（新）      | ✅                        |
| `answer`      | 任意   | **回答**：`replyTo` 指回 query（新）          | ✅                        |
| `nack`        | 任意   | **「我不知道 / 不在我的范围」**（新，决策 7） | ✅                        |
| `announce`    | →board | **广播公告**：恒落看板（新，决策 3）          | ✅（仅 `to:"board"`）     |

### 1.2 信封增量（`src/core/message.ts` 的 `MessageEnvelope`）

```ts
export type NodeRef = RunId | "root" | "system" | "board"; // 新增 "board"

export interface MessageEnvelope {
  // v1 字段不变：key / from / to / kind / seq / generation / payload / ref / via / ttlMs / createdAt
  replyTo?: MessageKey; // 问答关联；复用 v1 的 from:to:generation:seq correlation id
  topic?: string; // 看板归档键；announce 与一切落看板的消息必填
  evidence?: Array<{ file: string; lines?: string; quote?: string }>; // answer 必填（D-12）
  digest?: string; // 系统计算 sha256(kind+topic+normalizedText)，去重用，发送方不可指定
  discipline?: "push" | "notify" | "pull"; // 系统在 admit() 裁定并写死，非发送方请求
}
```

- `makeMessageKey`/`validNode` 增加 `"board"`；root 作为发送方时 generation 恒取 1（v1 规则仅约束
  system=0、其余 ≥1，root 无 generation 概念，由主会话注册的工具闭包固定传 1）。
- `formatMessage()` 的 `不可信输入: from -> to` 头覆盖全部新 kind（不可信输入边界不变）。
- **验证规则**（admit 入口强校验）：`announce` 必须带 `topic`；`answer` 必须带 `evidence`（D-12——
  答案是「另一个 LLM 的记忆」，强制证据让接收方 O(1) 抽查而非 O(n) 重查）；`answer`/`nack` 应带
  `replyTo`（缺失则降级为普通 finding 语义处理，不报错）。

## 2. 发送权限与路由规则

### 2.1 `authorize()` 重写（删 `can_message`）

```ts
export function authorize({ kind, relation, from }: AuthorizationInput): boolean {
  if (!MESSAGE_KINDS.includes(kind)) return false;
  // 方向性协议规则（协议自洽，不是权限）：
  if (kind === "dead_letter") return from === "system";
  if (kind === "result") return relation === "child"; // 结果只能上行
  if (kind === "directive") return relation === "parent"; // 指令只能下行
  // progress / finding / query / answer / nack / announce：任意关系全开（R3）
  return true;
}
```

- `relation === "unrelated" | "self"` 不再被拒：跨树、任意深度、同级全通。
- `CanMessage`、`effectiveCanMessage()`、`MentionRoute` 与 `authorize` 的 `canMessage`/`mention`
  分支全部删除；`@label` 退化为**寻址语法糖**（label → runId 的解析），不再是一种授权模式
  （`via.mode:"mention"` 保留，仅作溯源展示）。
- `FabricTree` 保留但**降级为溯源标注**：`relation()` 仅供 `formatMessage` 展示（接收方信任先验）、
  `via.lca/hops` 审计；`isRootChild` 不再 gating 任何投递。

### 2.2 寻址

| 地址形式   | 含义                                                            |
| ---------- | --------------------------------------------------------------- |
| `<runId>`  | 点对点（direct）                                                |
| `"root"`   | 主会话（direct）                                                |
| `"board"`  | 广播：一条记录落看板（决策 3）                                  |
| `"@label"` | 注册过的顶层 agent 的语法糖，解析为 runId；终态则走 revive 判定 |

`FabricTree.targetState` 增加：`targetState("board") === "running"`（看板不是可 gone 的目标——
否则滞留 board 记录会触发向广播者发死信，构成 I-W 漏洞）。

## 3. 点对点与广播的投递方式（push / notify / pull 由什么决定）

### 3.1 `resolveDiscipline()` —— 替代 `effectiveChannel()`

纯函数，在 `admit()` 内调用一次，结果写入记录后**永不变更**（不新增 FabricRecord 状态）：

```ts
resolveDiscipline(input: {
  kind: MessageKind; to: NodeRef;
  targetState: "pending_start" | "running" | "gone";
  wakeRoot: boolean; inboxUsed: number; inboxCap: number; canRenderEntries: boolean;
  isAnswerToOpenQueryOf: (to: NodeRef, replyTo?: MessageKey) => boolean;
}): "push" | "notify" | "pull"
```

裁定顺序（决策 4 + F1）：

1. **广播**（`to === "board"`）恒 `"pull"`（落看板）——封死 W1；
2. **终态目标**（`targetState === "gone"`）：恒 `"pull"`（落看板）；若 `kind === "query"` 且
   `autoRevive` 开启，额外触发一次后台 revive（W2，见 §4）；
3. **pending_start 目标**：恒 `"pull"`（run 尚未起，消息等它 running 后由 pump 交付…… 若到达时已
   终态则按 2 处理；board 兜底不丢）；
4. **运行中子 agent**：`"push"`（F1：只花 token 不花轮次）；若接收方摄取预算满
   （`inboxUsed >= inboxCap`）→ `"notify"`；若发送方存储上限也耗尽 → `"pull"`；
5. **root**：`wakeRoot && inboxUsed < rootInboxCap` → `"push"`（`sendRootContext`，触发一轮）；
   预算满或 `wakeRoot:false` → `"notify"`（`sendRootDisplay` 一行提示 + 落看板）；
   `canRenderEntries === false`（print mode / 渲染降级）→ `"pull"`；
6. **保留配额**（评审 M6 修复）：`answer`/`nack` 命中 `isAnswerToOpenQueryOf`（接收方确实问过）
   以及协议类 `result`/`directive`/`dead_letter` **不计入 `inboxUsed`、不受第 4/5 步降级**——
   否则协议消息会把接收方自己问来的回答挤出 push，形成优先级反转。代价如实声明：接收方得到的
   是**速率上界**（per-receiver 间隔）而非总量硬界。

> 评审 M-3 修复：规则 1 必须是「`to === "board"`」而非「audience 非 direct」——`audience` 字段已随
> 裁剪删除，且不带区分信息的存量消息（系统死信、/reload 后的 v1 残留 pending）必须默认按
> direct/push 处理，否则死信永不泵送。持久化记录缺 `discipline` 字段时（v1 旧档），hydrate 一律
> 补 `"push"`；`from === "system"` 的死信显式盖 `"push"`。

### 3.2 三种纪律的真实投递动作

| discipline | root 接收方                                                               | 运行中子 agent                                                                                            | 终态 agent                                 |
| ---------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| `push`     | `sendRootContext`（`deliverAs:"steer"` + `triggerTurn:true`）             | `ports.inject` = `runner.steer`（并入下一次 LLM 调用，不产生额外轮次，F1）                                | （仅 query → revive，见 §4；其余不进此列） |
| `notify`   | `sendRootDisplay`（`appendEntry`，display-only 不进模型 context）+ 落看板 | **落看板**（pi 无「不触发 turn 就注入运行中会话」的原语——诚实边界：可能永不被看到，这正是 R2 承认的前提） | 落看板                                     |
| `pull`     | 落看板，等主动 `read_board`                                               | 同左                                                                                                      | 同左                                       |

关键实现简化（评审 M3 采纳）：`notify`/`pull` 记录在 `admit()` 内**同步落看板，成功后直接
`engine.put({ ...record, state: "delivered", terminalReason: "board" })`**——`put` 不查转移表
（`src/delivery/engine.ts` 的 `put()` 只写 store，不校验 `allowed`），因此：
`src/stack.ts` 里 `buildFabric` 的 `allowed` 转移表**零改动**，7 处逐字复制该表的测试 fixture 也
零改动；且这些记录不进 mailbox，不可能变成 pump 候选，杜绝「pending 僵尸」。看板写失败
（`appendEntry` 抛错）时以 `{ state:"dropped", terminalReason:"board_write_failed" }` 审计终结并
`console.warn`——「至少一次投递，或以带审计的方式终结」保持成立。**`FabricMailbox.pump()` 的候选
筛选增加一条 `r.discipline === "push"`。**

### 3.3 点对点（direct）的完整路径

```
message_agent({to, kind, text, ...})
  → admit()：authorize → resolveDiscipline → engine.put
     ├─ push   → mailbox.pump() → claim → boundedSend（与 steerMs 赛跑）→ verdict
     │            ├─ ok → delivered（throttle.noteDelivered）
     │            ├─ retryable → backoff 重试（attempts < deliveryAttempts）
     │            └─ 终败 → answer/nack：board_fallback（D-8）；finding/directive：死信（见 §6.3）
     ├─ notify → 同步落看板 + （仅 root）sendRootDisplay 一行 → put delivered
     └─ pull   → 同步落看板 → put delivered
  → 工具立即返回（R2）：{ status, discipline, key, seq, hint: "已投递，不阻塞——继续当前工作" }
```

### 3.4 广播的完整路径

`message_agent({to:"board", kind:"announce", topic, text})` → `admit()` → **恒一条记录**、
恒 `pull`、落看板即 `delivered`。**零 push、零 revive、零死信**（看板不会 gone）。
若发送方确实需要某人注意这条公告，唯一合规途径是**另发一条点对点消息**（升级通道，见 §4）。

## 4. 接收方的唤醒规则

「唤醒」显式拆为两种形态，统一受**不变量 I-W**约束（决策 2）：

> **I-W：只有 `direct` 消息可以产生唤醒。任何广播（`to:"board"`）恒不唤醒任何 agent。**

| 形态             | 含义                            | 触发条件                                                                      | 机制                                                                                                                   |
| ---------------- | ------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **W1** turn 唤醒 | 让**运行中**的 agent 处理消息   | direct + discipline==="push"                                                  | 子 agent：`runner.steer`（并入下一次 LLM 调用）；root：`sendRootContext`（`triggerTurn:true`），受 `wakeRoot` 开关约束 |
| **W2** 复活唤醒  | 让**终态** agent 重新起一个 run | **direct 且 `kind==="query"`** 且 `autoRevive` 开启且会话级 revive 预算未耗尽 | 后台非阻塞 auto-revive（见下）                                                                                         |

硬规则（三个 choke point，属性测试断言处）：

1. `resolveDiscipline()` 对 `to === "board"` 恒 `"pull"`（封 W1）；
2. W2 的触发面**显式要求** `direct && kind === "query"`——`progress`/`finding`/`announce` 发给终态
   目标一律落看板，绝不 revive（把已结束的 agent 拉起来只为听一条通报是纯烧钱）；
3. **所有** `sendRootContext` / `runner.steer` / `spawn({resumeFrom})` 调用点统一断言来源记录满足
   direct + kind 合规——不在三个落点各自为政地拦，而是在唯一出口断言（评审对 v1.3 的攻击证明
   分散拦截必有漏）。

### 4.1 auto-revive（W2）的机制与约束

- **fire-and-forget**（R2）：`message_agent` 立即返回 `{ status:"reviving", target }`，不等待复活结果。
- 复活走 `spawn({ type: 目标原类型, resumeFrom: 目标 runId, slotless: true, deadlineAt: 夹紧 })`，
  prompt 携带问题正文 + 「请用 message_agent 以 answer（带 evidence）回复提问者」指引。
- **评审 B2 修复（本方案将 revive 列为独立里程碑的前置设计）**：
  - 带 `parentRunId` 的普通 spawn 会触发 `canSpawn` 嵌套校验，config error 会被 fire-and-forget
    静默吞掉；**不带**则复活 run 不进 CC2 过滤集（`runtime-adapter.ts` 的 `childRunIds`），其结束
    通知以 `triggerTurn:true` 唤醒 root——**一条绕过 I-W 的唤醒路径，`wakeRoot:false` 也管不住**。
    ⇒ revive 需要专属 spawn 通道：**显式跳过 canSpawn 嵌套校验 + 注册进通知抑制集（结束不通知、
    答案只经 fabric answer 消息回流提问者）**；
  - **评审 M8 修复**：`resumeLocks` 的真实行为是**拒绝**（"already has a resume in progress"）而非
    合并，fire-and-forget 会吞掉它、第二个提问者的 query 静默消失 ⇒ router 维护
    `reviving: Map<target, newRunId>`；revive 期间到达的同目标 query **不再二次 spawn**，待新 run
    `running` 后作为普通 push steer 进去；
  - **label 不 repoint**（评审 §8 约束）：`spawn-service.ts` 的 `labelAction` 增加第三态 `"keep"`，
    复活 run 不得抢占 `@expert` 原 label（否则问答 run 会把标签偷走）；
  - 成本闸：`autoReviveMaxPerSession`（默认 10）兜底；`deadlineAt` 由发起方剩余 deadline 夹紧
    （CC4 只收紧不放松）。
- **诚实边界**：revive 是一次带完整历史 context 的 run，冷缓存下实测一次定位问答 ≈ 1 轮 / $0.19 /
  16s（前序阶段探测数据点）；缓存过期后可能贵于提问方自己调研。因此 revive 排在最后里程碑，
  且工具描述必须写明成本。

### 4.2 root 的唤醒

- direct → root 的 push 会在用户空闲时启动主会话一轮，这是「向主 agent 请教」的必要代价，由
  `rootInboxCap`（12）约束；`fabric.wakeRoot:false` 时 root 一切入站降级为 `sendRootDisplay` +
  看板（T17）。
- **诚实边界（评审 M2）**：root 前台阻塞在一个 `Agent` 工具调用里时（最长 `foregroundAutoBackgroundMs`
  = 600s），steer 语义决定提问要等该轮结束才进 context——「向主 agent 请教」在纯前台串行调度下
  延迟无上界。缓解：调度方用 `run_in_background` 派发（本仓库工具已默认推荐）；本方案不改 pi 内核。

### 4.3 升级通道

广播需要引起某人注意时，发送方必须**显式对该接收方再发一条点对点消息**。唤醒因此永远是具名、
可审计、计入接收方预算的动作。

## 5. 看板（共享公告板）

### 5.1 职责与存储（决策 3 / 5）

`src/fabric/board.ts`（新组件）：广播的落地载体 + 迟到答案的归宿 + 新 agent 的启动知识来源。

- **存储**：`appendEntry(customType: "subagent:board", entry)` + 写后读回校验，完全复用
  `src/adapters/pi-outbox-store.ts` 的 append-only 模式；内存索引（topic → keys、全局 FIFO）随写随更。
- **重建**：`session_start` 时从 prefetched `subagent:board` 条目重建（与 `buildFabric` 现在从
  `subagent:run` 条目重建 tree 同源写法）；`/reload` 经读回路径恢复（run 记录会丢，看板不会）。
- **有效范围**：仅当前主 session，**不跨会话**。新主会话看板归零；跨会话沉淀用现有 memory 子系统。
- **容量**：全局 FIFO `boardCap`（500）、每 topic `boardTopicCap`（50）；截断时优先保留最新与被
  `replyTo`/`ref` 引用过的条目（淘汰从未被读的 delivered 条目时只淘汰内容、保留 headline 目录行）。

### 5.2 读取面

- 新工具 `read_board({ topic?, since?, limit?, all? })`：默认返回调用方 cursor 之后的条目
  （按时间倒序、headline 一行 + 近 N 条全文），推进 per-reader cursor；`all:true` 逃生阀。
- headline 自描述格式（L4 纪律，防误判）：`[topic] 一句结论 (@from, 年龄)`；answer 条目附
  `evidence` 供 O(1) 抽查。

### 5.3 启动注入（评审 B1 修复——不能走 `before_agent_start`）

`before_agent_start` 在子会话里根本不触发（`src/index.ts` 的 HOST_KEY 守卫先 return，注释写明
"Child sessions never see this hook"；memory 能生效是因为它 pre-guard 注册且自带闭包状态，而
看板状态在宿主 stack 里）。⇒ 注入改为**宿主侧 spawn 时拼进 prompt**：`runtime-adapter.ts` 的
`buildPrompt()` 路径上，fabric 启用时为每个新 run 前置一段预算化的 `## 看板` 块：

- 内容 = topic 目录 + 近期条目的一行 headline（预算 `boardInjectBudgetChars`，默认 2000 字符，
  指纹缓存避免重复渲染，仿 memory 的预算化渲染）；附「用 read_board 取全文」指引。
- resume 复活的 run 同样注入（在 revive prompt 前置）。

### 5.4 主会话也注册 `message_agent`（评审 §6.3）

`message_agent` 目前只注入子会话（`runtime-adapter.ts` 的 customTools 段）。「新 agent 向主 agent
请教」要求 root 能回答 ⇒ **主会话也注册 `message_agent` + `read_board`**（`src/index.ts` 组装区、
post-guard、`fabric.enabled` 门控、`from:"root"` + 固定 generation 1）。root 收到 direct query：
预算内 push 进 root context（主 agent 当轮即可回答）；预算外 / `wakeRoot:false` → display 行 +
看板，主 agent 可主动 `read_board`。

## 6. 配额与收件箱满时的处理

**总原则（决策 6）：超限降级，永不拒收。全链路不存在「发送失败」。**

### 6.1 四道幅度闸（裁剪后）

| 闸             | 机制                                                                                                                                                                                 | 默认                          |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------- |
| 接收侧摄取预算 | `inboxOf(node)` 统计该接收方 `pending\|claimed` 且 `discipline==="push"` 的**非协议**条数；满 ⇒ 降级 notify                                                                          | `inboxCap: 8`（root 沿用 12） |
| 发送侧存储上限 | v1 的 `maxPerRun`/`findingQuota`/`directiveQuota` **降级为存储上限**：超出 ⇒ 该消息直接落看板（pull），返回 `{status:"boarded"}` 而非失败                                            | 沿用 20/10/5                  |
| 内容去重       | `digest = sha256(kind+topic+normalizedText)`；同 `(digest, to)` 在 `dedupeTtlMs` 窗口内已存在 ⇒ 幂等返回 `{status:"duplicate"}`（dropped + `rejected.reason:"duplicate"`，不是错误） | `dedupeTtlMs: 600_000`        |
| 速率平滑       | `FabricThrottle` per-link `minIntervalMs` 保留；`rootMinIntervalMs` 泛化为 `receiverMinIntervalMs`（root 保留更严值）；**超时只推迟不拒收**（v1 已如此）                             | 30s / 10s                     |

裁剪说明：`hop/maxHops`（无转发路径）、`boardSenderSharePct`（会淘汰尚未回答的 query）按 F2 砍掉；
「接收方 context 总量硬上界」如实降级为**速率上界 + 广播恒 O(1)**（保留配额的存在使总量上界不可兼得）。

### 6.2 收件箱满时的发送方反馈

`message_agent` 恒返回成功，`status ∈ {accepted(pushed), accepted(notify), boarded, reviving,
duplicate}`，附一句「不阻塞，别等」。接收方视角：push 挤不进 ⇒ notify/pull；对 root 的 notify 是
可见的一行提示，对运行中子 agent 的 notify 就是看板（诚实边界，§3.2）。

### 6.3 死信与 board_fallback（D-8 + 评审 M4/M-6 修复）

- **push 终败**（target_gone / attempts_exhausted / ttl_expired）时：
  - `answer`/`nack` → **转存看板**（`board_fallback`，state=delivered）——迟到回答从失败变成知识
    沉淀，下一个碰到同问题的 agent 直接读到；
  - `finding`/`directive` → 仍签**死信**（发送方需要失败信号，不能看到 delivered 就以为送达），
    死信正文附看板引用（若带 topic 也同步落板）；
- `board_fallback` 的判定必须在 `issueDeadLetters()` **按 sender 分批之前逐条**完成——保住
  「一条原始消息至多一条死信」不变量（`dlRefs`/`dlPlaceholders` 原子序不变）；
- `mailbox.pump()` 的 **ttl 与 pre-claim target_gone 两个分支**同样硬编码了
  `kind === "finding" || "directive"`——新 kind 会被静默丢弃。三处（pump 两分支 + `verdict()` 失败
  分支）统一改走同一个 `boardFallbackFor(record)` 判定（评审 M-6）。

## 8. 非阻塞问答的完整生命周期（R2 的验收样例）

```
A: message_agent({ to:"@expert", kind:"query", topic:"arch-decisions", text:"你当时为什么否决了方案 X?" })
   → 工具立即返回：「已投递，不阻塞。收到回答会作为消息进入你的上下文。不要为此等待——继续当前工作。」
   → A 继续干活（没有停下）
```

| 结局                | 处理                                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 对方在跑且知道    | 回 `answer`（`replyTo` + `evidence`）⇒ 命中 A 的 openQuery ⇒ **push**（保留配额，不挤占）进 A 的 context（并入 A 的下一次 LLM 调用，F1）          |
| ② 对方在跑但不知道  | 回 `nack` ⇒ 同样 push ⇒ A 立刻转自查，不等超时（决策 7）                                                                                          |
| ③ 对方已终态        | direct + query ⇒ 后台 auto-revive（slotless / deadlineAt 夹紧 / 通知抑制 / label keep / reviving 合并）；专家复活后以 answer 回流；A 早已在做别的 |
| ④ 没人回 / A 已结束 | 不发死信：answer 迟到 ⇒ 按 topic **转存看板**（D-8）；query 本身 TTL 到期即安静终结（提问无义务）                                                 |

**prompt 纪律（与机制同等重要，随 M4 落进工具 description 与注入文案）**：
① 问完继续——提问不等待，立刻继续当前工作或先做粗筛；② 答案到了就转向——push 进来的 answer
若覆盖正在做的事，立刻停止并采用（附 evidence 抽查指引）；③ 开工先 `read_board`——迟到的答案
救不了已经干完的活。缺 ② 是同类机制最常见的失效模式（模型无视注入的答案继续傻干）。

## 11. 风险与诚实边界

| 风险                                                                                            | 处置                                                                                                                                      |
| ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| notify 对运行中子 agent 近乎无效（pi 无静默注入原语）                                           | 如实记录（§3.2）。这是 pi 能力边界不是方案缺陷；pi 将来提供静默注入时 notify 可无损升级                                                   |
| root 前台阻塞于 Agent 调用时，向 root 请教的 push 延迟无上界                                    | 鼓励 `run_in_background` 派发（工具描述已推荐）；不改 pi 内核                                                                             |
| revive 是带完整 context 的 run，缓存过期后可能贵于自查                                          | 排最后里程碑；`autoReviveMaxPerSession` 兜底；工具描述写明成本                                                                            |
| 删 `can_message` 后暴露面扩大（任意 agent 可唤醒 root；看板经启动注入构成持久化 prompt 注入面） | `不可信输入` 头覆盖全部 kind；answer 强制 evidence + 抽查指引；`wakeRoot` 可一键关；注入块带来源围栏。残余风险如实接受（需求方已确认 R3） |
| 看板内容质量依赖 prompt 纪律（前序实验：无纪律 ⇒ 最便宜也最不核验）                             | §8 三条纪律随 M4 落 description；工具描述写明成本                                                                                         |
| topic 命名漂移                                                                                  | topic 只是归档键不是检索承诺；headline 自描述 + `all:true` 逃生阀                                                                         |

**前置说明（诚实）**：前序阶段的量化实验（baseline-results §10–13）表明：结构化交接（fileIndex +
核验纪律，已固化为 skill）已拿到成本 −34~~53%、游荡 −91~~100% 的收益，且**不需要 fabric v2 任何
代码**；而 v2 独有的「请教」通路（H2）在阻塞中继形态下两轮均未被使用、尚未检验成立。本方案
是按需求完成的投递层设计；工程投入前建议先以「轮内同步请教工具」形态验证 H2（下游确实会用），
再按 §10 顺序落地 P1–P3（性价比主体），P5 视数据决定。
