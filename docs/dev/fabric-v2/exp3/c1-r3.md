## 1. 消息模型

### 1.1 节点与链路（不变）

- `NodeRef = RunId | "root" | "system"`（`src/core/message.ts`，不变）。
- 链路 = `(from, to, generation)`，`MessageKey = from:to:generation:seq`，逐链路单调 seq，admitted 与
  rejected 都消耗 seq（v1 语义，不变）。广播扇出的每条接收方记录都有独立 key（链路 = from→该接收方）。

### 1.2 kind 列表（v2 决策）

| kind          | 归属     | v2 变化 | 语义                                                       |
| ------------- | -------- | ------- | ---------------------------------------------------------- |
| `progress`    | 用户可见 | 不变    | 易失状态汇报；同链路新消息 supersede 旧消息（v1 语义保留） |
| `finding`     | 用户可见 | 不变    | 有价值结论，值得注入接收方上下文；投递失败有死信义务       |
| `directive`   | 用户可见 | 不变    | 要求接收方行动；点对点专用（不进广播，见 §3.2）            |
| `result`      | 系统内部 | 不变    | run 结果回投（delivery 子系统语义，工具面不开放）          |
| `dead_letter` | 系统内部 | 不变    | system→发送者的投递失败回执（I-F11 义务审计，不变）        |

**不新增 kind**：广播不是 kind（是路由形态，见 §1.3）；看板帖子不是消息（是独立存储记录，见 §5）。
理由：v1 的六态投递状态机、per-kind 配额、死信义务全是 `(state, kind)` 的函数（I-F11），新增 kind 会
牵动状态机矩阵、配额表、死信义务三处语义；而 R1 的两个新能力（广播、看板）都可以在不扩 kind 的前提下
表达——广播 = 既有 kind 的扇出投递，看板 = 根本不经过投递状态机（写入是同步的，没有投递生命周期）。
`⚠️`（前序讨论的"消息类型"若拍板了新增 kind，以那份纪要为准）。

### 1.3 envelope 扩展（`src/core/message.ts`）

```ts
export type MessageKind = "progress" | "finding" | "directive" | "result" | "dead_letter"; // 不变

export interface MessageEnvelope {
  // …v1 全部字段不变（key/from/to/kind/seq/generation/payload/ttlMs/createdAt/ref）…
  via?: {
    mode: "tree" | "mention" | "broadcast"; // v2 新增 "broadcast"；磁盘旧记录无 mode ⇒ 视为 "tree"（v6 兼容规则沿用）
    lca: NodeRef; // broadcast 记 "root"（审计占位，扇出不走树路径）
    hops: NodeRef[]; // broadcast 恒 []
  };
  broadcastId?: string; // v2 新增：同一次广播扇出的所有记录共享；仅 via.mode==="broadcast" 时存在
  delivery?: "push" | "notify"; // v2 新增：admission 时钉死的投递模式（§3）；旧记录缺失 ⇒ 按 §3.1 表回推
}
```

- `delivery` 在 admission 时一次判定并持久化，投递期不重推导（与 v6 的 `via.mode` 钉死原则一致：
  显示/投递一律读持久化字段）。
- `broadcastId = newRunId()`（复用 `src/core/ids.ts`），用于：扇出分组渲染、接收方去重（同一
  broadcastId 只投一次——防发送方重试造成重复扇出）、回执聚合。

### 1.4 看板记录（新类型，不属于 MessageEnvelope）

```ts
// src/fabric/board.ts（新文件，pi-free）
export interface BoardEntry {
  id: string; // newRunId()
  from: NodeRef; // 发帖者（root 或 run）
  text: string; // ≤ fabric.maxChars（admission 截断，同 v1 truncate 策略）
  tag?: string; // 可选频道过滤（如 "plan"、"block"）
  createdAt: Millis;
  ttlMs: number; // 0 = 整会话存活（默认）
  pinned?: boolean; // FIFO 淘汰时跳过
}
```

## 2. 发送权限与路由规则

### 2.1 发送权限（v2 核心变化）`⚠️`

v1：`authorize()` 按**树关系**放行——`result` 仅 child、`directive` 仅 parent、progress/finding 按
`can_message`（默认 `["parent"]`）——兄弟/旁支一律拒绝，这是 R1 的直接障碍。v2 改为：

1. **发送方**：必须是 fabric 已知且 running 的节点（root/system/run；v1 的 `sender is not running` 检查保留）。
2. **接收方**：必须是 fabric **已知节点**——`root`，或树内 run（状态 running / pending_start / 已 settle
   但仍在 `reconcileTtlMs` 墓碑窗口内）。未知 runId ⇒ 同步回执 `unknown_target`（不产生 pending 记录）。
3. **关系限制取消**：`progress`/`finding`/`directive` 的点对点发送不再检查 parent/child/sibling 关系；
   `result` 仍限 child→parent（协议方向语义，不属用户面），`dead_letter` 仍限 system。
4. **`can_message` 语义翻转**：v1 默认 `["parent"]`；v2 默认**不限制**，仅当 agent 类型 frontmatter
   **显式声明** `can_message` 时，作为该类型**外发** allowlist（关系词 + `mention`）生效——显式声明者
   保持其收紧意图（向后兼容、保守迁移）。root/system 不受限。
   新增设置键 `fabric.defaultCanMessage: "any" | "parent"`（默认 `"any"`，可一键回退 v1 行为做灰度）。
5. **`mention`（@label）门槛取消**：v1 要求 `can_message: mention` 才能用 @label；v2 对所有 agent 开放
   （label 注册表仍只有 root 子节点，见 §4.4）。自指禁止保留。

理由：R1 的字面要求就是任意↔任意；保留 `can_message` 声明式收紧满足最小权限的 agent 类型；
"已知节点"边界把消息面限定在本会话的 agent 树内（跨会话不是 fabric 的职责，是 memory 插件的职责）。
**备选**（被否决）：完全无限制含未知 runId——会鼓励对不存在目标的探测式发送，且无审计价值。

### 2.2 路由规则

- 投递路径**物理上都是直达**（v1 已如此：`ports.inject` 直接 steer 目标自己的 session；root 走
  `pi.sendMessage`），`via.lca/hops` 仅是审计元数据。v2 不引入逐跳转发——树只是权限/审计/选择器的
  数据源，不是投递通道。广播同理（每接收方一条直达记录）。
- `@label` 路由：mention 注册表解析（`src/mention/registry.ts`），目标 = 该 label 当前绑定的 runId；
  运行中 ⇒ 走 admit（`via.mode:"mention"`）；已 settle ⇒ 走 resume 复活（§4.4）。

## 3. 点对点与广播的投递方式

### 3.1 决定函数：push / notify / pull 由什么决定

**由 kind（紧急度类）× 目标状态 × 通道水位决定，v2 MVP 不给接收方逐条订阅开关**（`⚠️` 接收方侧
`steerable`/过滤配置列为后续扩展）。判定在 admission 时一次完成并钉进 `delivery` 字段：

| kind（路由形态）              | 目标 running                                    | 目标 pending_start          | 目标 gone（墓碑窗口内/外）              | 目标 = root                                                         |
| ----------------------------- | ----------------------------------------------- | --------------------------- | --------------------------------------- | ------------------------------------------------------------------- |
| `directive` p2p               | **push**（steer，触发一轮模型）                 | 排队（P3 等运行，TTL 兜底） | 死信回发送者（v1）                      | push（context 通道，triggerTurn）                                   |
| `finding` p2p                 | **push**（steer）                               | 排队                        | 死信回发送者（v1）                      | push（context 通道，v1）                                            |
| `progress` p2p                | **notify**（收件箱登记，不 steer）              | 排队（notify）              | drop（v1，无死信义务）                  | display 通道（v1 不变，不唤醒）                                     |
| 广播（progress/finding 扇出） | **notify**（每接收方一条记录，digest 批量唤醒） | 排队（notify）              | 跳过该接收方（进回执 undelivered 名单） | —（广播不含 root：root 有会话可见的完整日志，扇出给它只是噪音）`⚠️` |
| 看板帖子                      | 无投递（同步写入看板存储）                      | 同左                        | 同左（目标无关）                        | 同左                                                                |

- **push**：mailbox claim → `ports.inject`（run）/ `sendRootContext`（root）→ 目标起一轮模型调用。
  v1 P/V 状态机、per-target 单在飞（I-F10）、steer 超时（I-F14）、throttle/backoff 全部沿用。
- **notify**：记录进入目标收件箱（engine `pending`），**不发起 send**。出口有两个（先到先得）：
  1. **pull**：接收方调用 `message_agent` 的 `check` action 主动拉取（§3.3），拉到的记录转
     `consumed(terminalReason:"pulled")`；
  2. **digest push（安全网）**：收件箱由空转非空时起一个去抖定时器（`fabric.digestDebounceMs`，
     默认 3s；`systemClock.setTimer` 已 unref，满足 `pi -p` 纪律），到点把该目标所有 notify 记录
     **合并成一条 steer**（同一同步段逐条 claim、一次 `boundedSend`、verdict 批量应用到整批——
     I-F10 仍成立：每目标同时至多一个在飞 send）。digest 文本 = 每条一行（kind/from/seq/截断文本），
     上限 `digestMaxBatch`（默认 10）条，超出部分汇总计数。pull 先发生 ⇒ 取消定时器。
- **pull**：见 §3.3 工具面。digest 保证"从不主动 check 的 agent"也能在一个去抖窗口内感知 notify 消息
  （finding 广播不丢），pull 保证"想控制自己上下文的 agent"可以免打扰地取信。

### 3.2 广播（一对多）`⚠️`

- **工具面**：`message_agent` 增加 `action: "broadcast"`，参数 `selector` + `kind ∈ {progress, finding}` + `text`
  （`directive` 不允许广播：指令天然有唯一责任主体，扇出指令会产生多 agent 同时行动的语义混乱与成本风暴）。
- **目标集合（selector）**，在发送时刻对树求值一次（快照语义，之后新起跑的 agent 不补投）：
  - `"all"`：树内全部 running/pending_start 的 run（不含发送者自身、不含 root，见 §3.1 表）；
  - `"siblings"`：与发送者同父的 run；
  - `"children"`：发送者的直接子 run；
  - `"subtree"`：发送者的整棵子树（不含自身）。
- **形态**：**一条逻辑广播 = admission 时扇出的 N 条 per-接收方 FabricRecord**（各自独立 key/seq，
  共享 `broadcastId`，`via.mode:"broadcast"`，`delivery:"notify"`）。不采用"单条记录 + 接收方各自拉取"的
  虚拟组播：只有扇出成记录才能复用 v1 的配额、throttle、TTL、死信、ack 语义，且每接收方的投递结局
  （delivered/consumed/dropped）可独立审计。
- **扇出上限**：`fabric.maxFanout`（默认 24）。选择器命中数超限时**截断**（树序/label 字典序取前 N），
  回执注明 `truncated: true` 与实际命中数；不静默截断。
- **扇出原子性**：整批记录在 router.admitBroadcast 的一个同步段内 put（任一 put 抛错 ⇒ 全批不入，
  回执 `internal_error`）；配额/水位检查在扇出前完成（见 §6）。

### 3.3 点对点发送与工具面（R2 的落实点）

`message_agent` 工具（`src/tools/message-agent-tool.ts`）参数扩展，保持向后兼容：

```ts
{
  action?: "send" | "broadcast" | "check" | "post",  // 缺省 "send"（旧参数形态 to+kind+text 原样可用）
  to?: string,          // send：runId | "root" | "@label"
  kind?: "progress" | "finding" | "directive",
  text?: string,
  selector?: "all" | "siblings" | "children" | "subtree",   // broadcast 用
  tag?: string,         // post（看板）用
}
```

- `send`：admission（同步、纯内存 + 一次 appendEntry）→ 立即返回**回执**：`{status:"accepted", key, seq}`
  或 `{status:"quota_exhausted"|"target_backpressure"|"unknown_target"|"not_authorized", …}`。
  **execute() 绝不 await 任何投递 port、verdict、对方读取或 ack**（R2）。v1 已满足（admit 是同步的），
  v2 把它写成被测试钉死的不变量（§8）。
- `check`：拉取自己的收件箱（全部 notify-pending 记录转 `consumed("pulled")` 并返回正文）+ 看板未读摘要
  （§5）。同样同步快速返回。
- `post`：看板发帖（§5），同步写入返回 `{entryId}`。
- 提示面：agent 类型的 prompt 模板与 `/agent` 帮助文案补一句"可随时 `check` 收件箱与看板"——不注入
  系统提示（避免每 child 固定开销），靠 digest 安全网兜底从不 check 的 agent。

## 4. 接收方的唤醒规则

### 4.1 什么消息能让 agent 起一轮模型调用

| 唤醒途径                         | 触发条件                                                            | 机制                                                                                          |
| -------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **steer 注入**（真正唤醒）       | p2p `finding`/`directive` 到 running 目标；root 的 context 通道消息 | v1：`ports.inject` = `runner.steer` / `pi.sendMessage({deliverAs:"steer", triggerTurn:true})` |
| **digest steer**（批量温和唤醒） | 任一目标 notify 收件箱空→非空后 `digestDebounceMs` 到点且未被 pull  | §3.1：一条合并 steer                                                                          |
| 不唤醒                           | `progress`（p2p/广播）、全部广播、看板帖子、root display 通道       | —                                                                                             |

- `directive` 永远 push（这是它区别于 finding 的语义：要求行动）。`finding` 也 push（v1 行为，信息
  有价但不要求行动——若上游拍板为"finding 降级 notify"，改 §3.1 表一格即可，机制已就绪）`⚠️`。
- **节流防风暴**：per-target 单在飞（I-F10）+ per-link `minIntervalMs` + root `rootMinIntervalMs` +
  root ingress cap 全部沿用；新增 digest 去抖把 notify 洪峰压成单条 steer。同一目标在一轮模型调用
  期间积压的多条 push 消息：v1 语义是逐条 steer（pi 侧排队到下一轮），v2 不改（`⚠️` 若要 push 也
  合并，复用 digest 编译器即可，属实现细节）。

### 4.2 pending_start（排队中目标）

v1 P3：不动，等 `onSnapshot` → `markRunning` → `pump(target)` 唤醒投递；TTL 兜底。v2 完全沿用
（push 记录在目标起跑后 steer；notify 记录在目标起跑后进其第一个 digest 窗口）。

### 4.3 已结束的 agent：能否复活

- **按 runId 寻址**：**不复活**。墓碑窗口内 finding/directive ⇒ 死信回发送者（v1）；progress ⇒ drop。
  理由：runId 是一次性执行的句柄，复活它意味着发起一次新的模型调用——这是**派单决策**，不应由
  一条消息隐式触发。
- **按 @label 寻址（复活通道）**：沿用并放宽 v1 mention 的 resume 语义——目标已 settle 且仍在
  墓碑窗口内 ⇒ `spawn({resumeFrom: runId, prompt: "[fabric mention resume …] 不可信输入: …\n\n"+text})`，
  产生**新 run、新 generation**，消息作为其 resume prompt 前缀（v1 机制原样）。v2 变化：
  1. 取消 `can_message: mention` 门槛（§2.1）；`⚠️`
  2. kind 放开到 progress/finding（v1 即如此）；`directive` 经复活**默认仍禁止**（复活 = 新 run 新预算，
     "指令一个已结束的 agent"的授权主体不清，成本不可控）`⚠️` 默认 off，设置键
     `fabric.reviveDirective: false` 可开；
  3. 新增**复活配额** `fabric.reviveQuota`（per 发送者 run，默认 2，计数维度与 deadLetterQuota 相同），
     超限回执 `quota_exhausted(kind:"revive")`，防标签骚扰式无限复活；
  4. `mention.send` 的 `await spawn(...)` 只等 run **创建**（spawn 服务在启动即返回，不等 settle），
     不违反 R2（R2 禁的是等"对方回复"，不是等系统受理）；若实测 spawn 受理路径可能慢（排队），把
     resume 改为提交后即回执 `{status:"reviving"}`、失败走死信——列为实现期选项。

### 4.4 root 的唤醒

v1 语义不变：context 通道（finding/directive/dead_letter）`triggerTurn:true` 唤醒主会话；display 通道
（progress）只渲染不唤醒；`rootInboxCap` 在 admission 拒绝过载（§6）。root 永不"被复活"（它常驻）。

## 5. 看板（共享公告）

### 5.1 定位

一个**本会话 agent 树共享的、追加为主的公告存储**：发帖者写一次，所有 agent（root + 全部 run）可读。
它是 notify/pull 语义的极致形态——**发帖永不唤醒任何人**，消费全靠 pull（`check`）与 digest 摘要行。
典型用途：广播任务上下文、发布共享事实、留言给还没起跑的 agent。

### 5.2 存储方式与有效范围 `⚠️`

- **存储**：主会话的 session 条目（`pi.appendEntry`，customType `subagent:fabric-board`，事件溯源式：
  每次发帖一条 entry，重建时重放并施加 caps），运行时持有内存镜像。完全复用 v1 fabric outbox 的
  `createPiOutboxStore` 模式（`src/adapters/pi-outbox-store.ts`）与 `buildSessionStack` 的 prefetched
  读回——**天然跨 `/reload`**（内存态在 stack 重建时从条目重放，避开"reload 清空内存态"这个已知坑）。
- **有效范围**：**单个主会话的 agent 树**（root + 本会话全部 run）。**不跨会话**——跨会话/跨天的
  共享记忆是 memory 插件（cwd-keyed）的职责，两者刻意不重叠。
- **子会话访问**：子 run 不自行读条目（其扩展被 HOST_KEY 守卫置惰性）；一律通过注入的 `message_agent`
  工具（`action:"post"/"check"`，execute 在宿主进程内闭包持有 board 句柄）——与 v1 注入
  message_agent 同一通道（`src/service/runtime-adapter.ts` customTools）。

### 5.3 容量与生命周期

- `fabric.boardMaxEntries`（默认 200）：FIFO 淘汰最旧非 pinned 条目（重建重放时同样施加，淘汰确定性）。
- `fabric.boardPostQuota`（per 发送者，默认 20/会话）：防刷屏，超限同步回执 `quota_exhausted`。
- TTL：条目可带 `ttlMs`（发帖时可选，0 = 整会话存活）；懒过期——`check` 读与 stack 重建时过滤
  `createdAt + ttlMs < now`，不另起清扫定时器（无定时器纪律负担）。
- 每读者游标（内存 Map<NodeRef, boardId>）记录"已读到哪条"，`check` 的未读摘要据此生成；
  `/reload` 后游标清零 ⇒ 各 agent 会重看一遍近期未读——可接受的幂等噪音（条目带 id，agent 可自行去重）。

## 6. 配额 / 收件箱满时的处理

总原则（R2 的推论）：**一切超限都是 admission 时刻的同步回执**——发送方立刻知道结局，不存在等待、
排队重试或"等对方腾地方"。发送方想重发是它自己的决策（新消息、新配额计数之外按 v1 规则：rejected
记录不计 kind 配额、不进 pump 候选）。

| 维度                         | 键（默认）                                                             | 触发时行为                                                                                                                                                                               |
| ---------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| per 发送者 progress 配额     | `fabric.maxPerRun`（v1）                                               | 回执 `quota_exhausted`；rejected 记录落盘审计（v1）                                                                                                                                      |
| per 发送者 finding/directive | `fabric.findingQuota`/`directiveQuota`（v1）                           | 同上                                                                                                                                                                                     |
| per 发送者广播配额           | `fabric.broadcastQuota`（默认 4）                                      | 回执 `quota_exhausted`。**广播一次计 1**（不按扇出数烧 finding 配额——否则广播毫无意义）；代价是广播绕开 finding 配额，可接受：广播是弱投递（notify-only），且有自己的配额与扇出上限 `⚠️` |
| per 发送者死信               | `fabric.deadLetterQuota`（v1）                                         | 死信抑制（v1：`suppressed_quota` 落原记录审计）                                                                                                                                          |
| per 发送者复活               | `fabric.reviveQuota`（默认 2）                                         | 回执 `quota_exhausted(kind:"revive")`（§4.3）                                                                                                                                            |
| 目标 push 收件箱（含 root）  | `fabric.inboxCap`（默认 8；root 沿用现 `rootInboxCap` 语义并改名统一） | admission 回执 `target_backpressure`（v1 root 语义推广到所有目标：只数 push 通道的 pending+claimed，与发送者数量无关的数学上界，I-F12 推广）                                             |
| 目标 notify 收件箱           | `fabric.notifyInboxCap`（默认 16）                                     | 同上回执 `target_backpressure`（notify 记录数 push 池之外单独计数；digest/pull 消化后腾位）                                                                                              |
| 广播扇出                     | `fabric.maxFanout`（默认 24）                                          | 截断 + 回执 `truncated:true`（§3.2）；接收方个体满仓 ⇒ 跳过该接收方，回执附 undelivered 名单（≤5 个名字 + 计数，形状仿死信 ref）                                                         |
| 看板容量 / 发帖配额          | `fabric.boardMaxEntries` / `boardPostQuota`                            | FIFO 淘汰（对发送方透明，回执仍 ok）；发帖配额超限回执 `quota_exhausted`（§5.3）                                                                                                         |
| 正文长度                     | `fabric.maxChars`（v1）                                                | admission 截断（v1 策略，首 75% + 尾 25%）                                                                                                                                               |

死信义务不变（I-F11）：finding/directive 的 ttl/gone/attempts 失败仍走 dead_letter；progress 与广播
中的 progress 无义务；**广播 finding 的死信义务保留**（每条扇出记录独立判定——这是扇出成记录的又一收益）。
