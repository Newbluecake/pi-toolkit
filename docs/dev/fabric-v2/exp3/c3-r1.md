# fabric v2 消息投递层实施方案

> 仓库：`/home/bluecake/ai/pi-toolkit`（运行时标识仍为 `pi-subagent`，见 AGENTS.md——不要在 `src/` 里"完成改名"）。
> 前置阅读：`docs/dev/subagent-push/subagent-push-plan.md`（v1 织网的六态状态机、root ingress gate、死信义务 I-F11 等，v2 全部继承）、`docs/dev/fabric-mention/fabric-mention-plan.md`（@label 直达路由）。
> 本方案只做**消息投递层**：消息模型、路由、投递分级、唤醒、看板、配额降级、文件级改动与测试要点。不含：fabric v2 的多轮协商协议语义（query/result 内容规范）、UI 美化、跨会话知识复利（归 memory 子系统）。

## 0. 需求、拍板决策与不变量

### 0.1 需求

- **R1** 任意两个 agent 点对点通信 + 一对多广播；
- **R2** 发送永不阻塞——发送方绝不等待对方回复；
- **R3** 不限制发送能力；任何一次（协议合法的）发送都不会返回失败。

### 0.2 已拍板决策（本方案的硬约束，逐条映射为实现不变量）

| #   | 决策                                                                    | 实现不变量                                                                                                                                     |
| --- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 彻底删除 `can_message`，无白名单；`authorize()` 只留方向性协议规则      | **I-A**：`src/` 中 `CanMessage` / `effectiveCanMessage` / `can_message` frontmatter 全部删除；授权检查只剩 §1.3 的协议规则（协议自洽，非权限） |
| 2   | 广播恒不唤醒任何 agent                                                  | **I-W**：`to:"board"` 的消息在代码路径上**结构性地**接触不到 steer / sendMessage(triggerTurn) / spawn——board 模块没有这些端口（§4.4）          |
| 3   | 广播 = 一条看板记录，恒 O(1)                                            | **I-B**：broadcast 在 `admit()` 同步段落内落一条 board entry 并直接转 `delivered`，不进 pump、不遍历接收者（§3.2）                             |
| 4   | 投递纪律按接收方状态分级，无 `urgent`/优先级标记；发送方无法请求 push   | **I-T**：tier（push/notify/pull/revive）是 `(接收方状态, 网关)` 的纯函数，消息上没有任何发送方可写的投递控制字段（§3.1）                       |
| 5   | 看板只在当前主 session 内有效（`appendEntry` 写入读回），不跨会话持久化 | **I-S**：board 存储是 `subagent:fabric-board` custom entries + 会话内内存索引；无文件落盘、无跨会话读取（§5）                                  |
| 6   | 超限降级，永不拒收                                                      | **I-N**：quota/收件箱满 → push → notify → pull 逐级降级；`admit()` 对协议合法输入恒返回 `ok:true`（§6）                                        |
| 7   | `nack`（"我不知道"）是一等 kind                                         | **I-K**：`MessageKind` 含 `nack`；与 `result` 同为 query 的应答 kind，受同一 correlation 规则约束（§1.2）                                      |

补充边界（写明以免歧义）：**协议违规不是"拒收"**。`result/nack` 没有合法 `in_reply_to`、`dead_letter` 伪造发送者、给自己发消息这类属于调用方 bug，`admit()` 返回 `ok:false, status:"protocol"` 并附修复提示——这是 I-N（容量永不拒收）之外的独立维度，快速失败对模型是教学信号。

### 0.3 继承自 v1 且不动的纪律

- 六态状态机 `pending/claimed/delivered/consumed/dropped/abandoned`、`claimed` 仅内存（D17）、`claimToken` 实例隔离（I-F15）、`boundedSend` 超时竞速（I-F14）、死信义务纯函数可审计（I-F11）、root ingress gate 的瞬时 cap 语义（I-F12）——全部保留，v2 不新增 delivery state（见 §6.3 的例外说明）。
- fire-and-forget：`admit()` 全同步、不 await 任何投递动作（v1 已如此，v2 把 @label 终态目标的 resume 也移出工具调用路径，§4.3）。
- `unref()` 定时器纪律、ESM `.js` 后缀、typebox schema、严格 TS。

## 1. 消息模型

### 1.1 envelope 与 record（`src/core/message.ts`）

```ts
export type NodeRef = RunId | "root" | "system"; // 不变：发送者恒为 NodeRef
export type AddressableRef = NodeRef | "board"; // 新增：只有 to 可以是 board

export type MessageKind =
  | "progress" // 进展通报（廉价、可被新进度取代）
  | "finding" // 结论性发现
  | "directive" // 指令
  | "query" // 新增：提问——唯一可以"复活"终态接收者的 kind
  | "result" // 对 query 的有效回答（必须带 in_reply_to）
  | "nack" // 新增：对 query 的"我不知道/无法回答"（必须带 in_reply_to）
  | "dead_letter"; // 仅 system → 发送者

export interface MessageEnvelope {
  key: MessageKey; // `${from}:${to}:${generation}:${seq}`，to 允许 "board"
  from: NodeRef; // host 钉死，调用方不可伪造
  to: AddressableRef;
  kind: MessageKind;
  seq: number; // 逐链路单调，含降级记录（v1 语义不变）
  generation: Generation;
  payload: { text: string }; // 仍受 fabric.maxChars 截断
  inReplyTo?: MessageKey; // 新增：result/nack 必填，指向被应答的 query 的 key
  topic?: string; // 新增：board 过滤用短标签（≤32 字符，仅 progress/finding/query 可带）
  via?: { mode: "tree" | "mention"; lca: NodeRef; hops: NodeRef[] }; // 审计用，语义同 v1
  ttlMs: Millis;
  createdAt: Millis;
}
```

`FabricRecord = MessageEnvelope & 投递壳`，壳新增三个**可选**字段（旧记录无这些字段照常 hydrate，零迁移）：

```ts
export type DeliveryTier = "push" | "notify" | "pull" | "revive";
export interface FabricRecord extends MessageEnvelope {
  state: FabricDeliveryState;      // 六态不变
  attempts: number;
  claimToken?: string;             // 仅内存（D22 不变）
  updatedAt: Millis;
  deliveredAt?: Millis;
  tier?: DeliveryTier;             // admit/pump 时钉死的投递层级决策（审计 + pump 分派依据）
  deliveredVia?:                   // delivered 时的通道审计
    | "push_steer"                 //   运行中子 agent：session steer
    | "push_root"                  //   root：sendMessage triggerTurn:true
    | "notify_root"                //   root：sendMessage triggerTurn:false（nextTurn）
    | "revive"                     //   终态目标：resume 复活（deliveredVia 附 reviveRunId，见 §4.3）
    | "board";                     //   看板（broadcast 直达，或降级的终点）
  reviveRunId?: RunId;             // deliveredVia==="revive" 时指向复活出的新 run
  degraded?: { reason: DegradationReason; fromTier: DeliveryTier }; // 降级审计（§6）
  rejected?: …                     // v1 字段：v2 起仅剩 "protocol" 一种来源（见 §6.1）
  deadLetter?: …;                  // v1 字段，语义收缩（§6.3）
  terminalReason?: string;
  storageKey?: string;
}
```

`makeMessageKey` / `parseMessageKey` / `validNode`：`to === "board"` 放行（`from` 永不放行 board）；board 链路的 seq 仍按 `(from,"board")` 递增。`formatMessage` 头部追加 `in_reply_to`/`topic`，其余不变（"不可信输入"前缀保留——删除 can_message 之后，来源不可信的假设反而更重要，接收方 prompt 仍须自证）。

### 1.2 kind 语义与合法目标矩阵

| kind        | 用途              | 可 to board                    | 可 to 终态 run       | 应答义务                        |
| ----------- | ----------------- | ------------------------------ | -------------------- | ------------------------------- |
| progress    | 进展通报          | ✔                              | （进看板，无人唤醒） | 无                              |
| finding     | 结论发现          | ✔                              | 同上                 | 无                              |
| directive   | 指令              | ✘（指令必须具名担责，见 §4.1） | 同上                 | 无（协议上鼓励 ack，v2 不强制） |
| query       | 提问              | ✔（开放问题，谁读到谁可答）    | ✔ 唯一可触发复活     | 接收方应回 `result` 或 `nack`   |
| result      | query 的有效回答  | ✘（必须点对点回到提问者）      | ✘                    | —                               |
| nack        | "我不知道/答不了" | ✘                              | ✘                    | —                               |
| dead_letter | 投递失败通知      | ✘                              | ✘（发给发送者）      | —                               |

`nack` 的价值（决策 7）：R2 下发送方不等回复，但一个**廉价的负应答**让发送方立刻停止等待假设、转为自查——比 TTL 超时（`reconcileTtlMs` 量级）快一个数量级。协议上 `nack` 与 `result` 平权：都要求 `in_reply_to`，都走点对点直达，都被 I-T 分级投递。

### 1.3 协议规则（`authorize()` 的全部残留，替代白名单）

`src/core/message.ts` 中 `authorize()` 重写为 `authorizeProtocol()`，纯函数、无权限输入：

1. kind ∈ 七种；`from !== to`（自环无意义，协议拒绝）；
2. `dead_letter` ⇒ `from === "system"`（不可伪造）；
3. `result` / `nack` ⇒ 必须携带 `inReplyTo`，且该 key 经解析指向一条**本会话内已知**的 query，其 `to === 发送者` 或 `to === "board"`（board 上任何人可答）。"已知"由 router 以事实传入（`hasQuery: boolean`，engine + board 联查，§2.2），保持函数纯净可测；
4. `to === "board"` ⇒ kind ∈ {progress, finding, query}，且不得携带 result/nack；
5. 其余任意方向放行：sibling、unrelated、child→parent、跨子树、@label 直达——**没有关系检查**。`relation()` 仅保留用于 `formatMessage` 显示与 `via` 审计。

### 2.2 寻址与路由

- **地址解析**（发送工具内完成，全部同步）：`"root"` → root；`"board"` → board；`@label` → MentionRegistry.resolve（先 query.get(runId) 判状态再交给 admit，同 v1 mention 路径，但删除授权与无条件 resume）；裸 runId → 直达（targetState 交给 mailbox 分级）。
- **逻辑路由**：`via.lca/hops` 照 v1 由 FabricTree 计算，纯审计（v1 的物理投递本就是按 runId 直投 steer，不经中继——v2 不引入多跳中继，树只回答"这条消息在树上走了什么关系"）。
- **correlation 联查**（`FabricRouter.knownQuery(inReplyTo, sender)`）：engine 里 `kind==="query" && (to===sender || to==="board")` 的记录 + board store 里 `kind==="query"` 的 entry，二者并集即已知 query 集。query 记录被清理（TTL/收缩）后，迟到的 result/nack 会得到 `ok:false, status:"protocol", reason:"unknown in_reply_to"`——发送方可改发 `finding`。

## 3. 点对点与广播的投递方式

### 3.1 tier 决策矩阵（I-T：接收方状态的纯函数，与发送方、kind 的"重要性"无关）

tier 在**两个时点**计算：`admit()` 时给初值（写进 `record.tier`，工具结果即时反馈），`pump()` 分派时按最新 targetState 复核修正（admit 与投递之间接收方可能已经终态化）。决策输入只有：接收方 tree/query 状态、wakeRoot 开关、root ingress 计数、revive 网关、（发送方）quota。

| 接收方状态                                                | 决策                                                  | tier     | 物理动作                                                                                                                                                               |
| --------------------------------------------------------- | ----------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 运行中子 agent                                            | push                                                  | `push`   | claim → `ports.inject` → `handle.steer`（v1 不变，含 per-link throttle / backoff / boundedSend）                                                                       |
| root（context 通道）                                      | wakeRoot ✔ 且 rootInbox < cap 且 rootMinInterval 放行 | `push`   | claim → `ports.sendRootContext`：`pi.sendMessage({…display:false}, {deliverAs:"steer", triggerTurn:true})`（v1 不变）                                                  |
| root（context 通道）                                      | wakeRoot ✘ 或 cap 满或 interval 未到                  | `notify` | claim → `ports.sendRootNotify`：同消息 `{deliverAs:"nextTurn", triggerTurn:false}`——落进 session 日志，**下次自然回合**进入上下文，不强制起轮（§6.2 的 notify 计数闸） |
| root（display 通道，即 progress+progressChannel=display） | 恒不唤醒                                              | `notify` | `ports.sendRootDisplay`（v1 的 appendEntry 显示行，不变）                                                                                                              |
| root notify 队列也满                                      | 降级到底                                              | `pull`   | 转 board（§3.3 第 3 类）                                                                                                                                               |
| 终态 run + kind=query + revive 网关 ✔                     | 复活                                                  | `revive` | claim → `ports.revive`（§4.3；异步、fire-and-forget）                                                                                                                  |
| 终态 run + 其他 kind（或 revive 网关 ✘ / 失败）           | 降级                                                  | `pull`   | 转 board，`delivered` + `deliveredVia:"board"`                                                                                                                         |
| pending_start                                             | 等待                                                  | —        | pump 跳过（v1 不变）；TTL 到期按 §6.3 处理                                                                                                                             |

要点：

- **发送方无法影响 tier**。参数里没有 `urgent`、没有优先级；quota 超限影响的也只是"降到底层"，不是"能否发出"（I-N）。
- `notify` 的成本语义：不消耗一轮模型调用，内容挂在下一个自然回合上。它是 push 与 pull 之间真实存在的中档，不是显示美化。
- `pull` 对 direct 消息的语义 = "接收方（或 root、或人）稍后用 `read_board` 看到"；对已终态且无人复活的接收者，board 同时是**审计落点**——消息没有丢，只是没人拉。

### 3.2 广播（`to:"board"`）：恒 O(1)（I-B）

`admit()` 内同步完成，**不产生 pending 记录、不进 pump**：

1. `authorizeProtocol` 过 board kind 约束（§1.3-4）；
2. 计 seq/key（链路 `(from,"board")`），quota 计数照常（§6.1）；
3. `board.post(entry)`：appendEntry 一条 `subagent:fabric-board`（载荷见 §5.1）+ 内存索引；appendEntry 抛错则仅内存降级（I-S 不变）；
4. engine.put 一条 `state:"delivered", deliveredVia:"board"` 的 record（审计与 seq 连续性；delivered 是终态，pump 的 `pending` 过滤天然跳过）；
5. 返回 `{ok:true, status:"posted", key, seq}`。

对任意数量 N 的潜在接收者：appendEntry 恰 1 次、steer/spawn 0 次、循环 0 个——O(1) 是结构保证，不是统计性质。接收方拉取见 §5.3。

### 3.3 board 上的三类 entry（同一种存储，三种来源）

1. **broadcast**：`origin:"broadcast"`，to 恒 `"board"`；
2. **degraded direct**（终态接收者 / notify 满降级）：`origin:"degraded"`，`to` 保留**原意图接收者** runId——board 读工具据此向 root 呈现"这条是发给死掉的 X 的"；engine 中对应 record 已转 `delivered`（deliveredVia:"board"）；
3. （仅内存视图，不新增 entry）**board query**：broadcast 的 query 就是普通 entry，`result`/`nack` 通过 `in_reply_to` 关联它即可。

## 4. 接收方唤醒规则

### 4.1 总纲：唤醒是具名、担责、计入预算的定向动作

能引起一次模型调用（起一轮或复活）的**只有**：

1. direct push 到运行中的子 agent（steer）；
2. direct push 到 root（triggerTurn，受 wakeRoot + §6.2 网关）;
3. direct **query** 复活终态 agent（§4.3，受 revive 网关）。

广播不唤醒（I-W）；notify 不唤醒；board 不唤醒。`directive` 不允许上 board 的理由也在这里：指令意味着"要求某个确定的对象消耗一轮预算"，广播指令恰好是"匿名地花 N 个人的钱"，与决策 2 的成本论证同构。

### 4.2 唤醒运行中的 agent（v1 机制不变）

`ports.inject` → `runnerRef.current.steer(runId, formatted)` → `handle.steer`。steering 消息注入当前 turn 或触发下一轮，即"唤醒正在运行的 agent 起一轮"。`boundedSend` 以 `settings.budget.steerMs` 竞速（I-F14），失败按 v1 的 attempts/backoff 重试。新增一条复分级：**push 途中目标转终态**（verdict `not_running`/`target_gone`）时，query 先尝试 revive、其余转 board——一次性 re-tier，不回到重试循环。

### 4.3 复活已结束的 agent（仅 p2p query）

- **入口**：pump 发现 `targetState === "gone"` 且 `record.kind === "query"`。
- **网关**（`src/fabric/revive.ts`，全部内存计数，session 生命周期）：
  - `fabric.revive.enabled`（默认 true）；
  - per-target：同一**原始 runId** 复活次数 < `revive.maxPerTarget`（默认 1——防止反复戳同一具尸体）；
  - per-session：总复活数 < `revive.sessionCap`（默认 8）；
  - 深度：复活产生的 run 再去复活别人时，revive 链深 < `revive.maxDepth`（默认 2）——防"复活链"震荡；
  - 类型可解：`query.get(runId).diag.agentType ?? "general-purpose"`。
- **动作**：`ports.revive(record)` → `spawn.spawn({ type, resumeFrom: 原runId, label: 沿用原 label（repoint）, prompt: 头部标注来源/不可信 + query 正文 + "回答后用 message_agent 向 <from> 发 result（in_reply_to=<key>）；无法回答则发 nack，然后结束" })`。复活 run 是普通 root-child run：自己的 watchdog/预算、计入全局并发与费用统计——这就是"计入接收方预算"的落点；"具名担责"= record key + `reviveRunId` 审计 + 发送方 queryQuota 计数。
- **verdict**：spawn 返回 `{runId}` ⇒ `delivered`，`deliveredVia:"revive"`，`reviveRunId` 记录之，并在 FabricTree append 新边（新 run 挂 root）；spawn 失败 ⇒ 降级 board（不重试 spawn——复活不是投递义务，是尽力而为的定向唤醒）。
- **工具调用不阻塞**（R2）：复活在 mailbox pump 内异步进行。v1 `mention.ts` 在工具 execute 里 `await spawn` 的路径同步删除——@label 终态目标也走本节分级（这是行为变化：subagent 的 @ 消息不再无条件 resume；**用户**级 `src/mention/mention.ts` 不动，用户戳人是人类预算，天然具名担责）。
- 树边注记：复活的 run parent 记 root（mention 先例），发送方与它的关系通过 `in_reply_to` 表达，不再依赖树。

### 4.4 I-W 的结构性保证

`src/fabric/board.ts` 的依赖面只有 `appendEntry`/`getEntries` 端口与纯内存结构——它**拿不到** `runnerRef`（steer）、`pi.sendMessage`、`spawn`。broadcast 路径在 `router.admit()` 内终结（delivered），不产生 pump 候选。因此"广播唤醒了谁"不是靠测试约定的约定俗成，而是模块间不存在该调用边（在 §8 用依赖面单测 + 性质测试双重锁定）。

## 5. 看板（共享公告）

### 5.1 存储（I-S：当前主 session 内有效）

- **落点**：主 session 的 custom entries，`customType = "subagent:fabric-board"`，经 `pi.appendEntry` 写、`ctx.sessionManager.getEntries()` 读（与 `subagent:fabric` 记录日志同模式）。不写文件系统、不写跨会话存储；`/reload` 后由 prefetched entries 重建（同 session 文件 ⇒ 看板存活；新 session ⇒ 空看板）。
- **载荷**（快照式，读工具不需要回查 engine）：

```ts
interface BoardEntry {
  key: MessageKey;
  from: NodeRef;
  to: "board" | NodeRef; // degraded 项保留原意图接收者
  kind: "progress" | "finding" | "query" | MessageKind; // degraded 直达消息可带原 kind
  origin: "broadcast" | "degraded";
  text: string;
  topic?: string;
  inReplyTo?: MessageKey;
  postedAt: Millis;
  ttlMs: Millis;
}
```

- **内存索引**（stack 闭包内）：数组 + FIFO cap（`fabric.boardCap`，默认 200，超限逐出最旧——**逐出不是拒收**，I-N 的最后一层）+ 每调用方读游标 `Map<NodeRef|“root”, MessageKey>`（最后一次 list 的最新 key）。
- **模块纯度**：`board.ts` 不 import pi（端口注入，同 `PiOutboxHost` 模式），可单测。

### 5.2 有效范围与边界

- 生命周期 = 主 session（与 fabric engine 的会话内持久化对齐）。
- TTL（`fabric.boardTtlS`，默认 1800s）只约束**读取窗口**（默认只列 TTL 内的 entry），不删除 session 日志里的历史 entry。
- 跨会话复利明确**不在本层**：交给 memory 子系统（AGENTS.md 已划定 `src/memory/` 职责）。看板不落 `~/.pi/agent/memory/`。

### 5.3 读取（拉取是接收方的动作，永不被动）

- **子 agent**：新工具 `read_board`（`src/tools/read-board-tool.ts`），随 message_agent 一起注入（runtime-adapter customTools + grantedReserved）。参数 `{ topic?, kind?, limit?, markRead? }`；返回 TTL 窗口内、自己游标之后的 entry 列表（默认上限 50 条，文本截断 `fabric.maxChars`）。子 agent 的 system prompt/派单 prompt 层面引导"空闲时查板"（prompt 文案不在本层强制）。
- **root**：`src/index.ts` 在 HOST_KEY 守卫之后注册 host 侧 `read_board`（fabric.enabled 门控、仅主会话）——root 被 notify 降级或想看板时自取。
- **人**：TUI renderer（§7-16）把 board entry 渲染成 `[board <kind> from @label]` 行。

## 6. 配额 / 收件箱满：降级而非拒收

### 6.1 发送方配额（per-sender，per-kind，跨 tier 计数）

| 配额键                                                                             | 默认 | 超限行为（对比 v1：v1 是 admission 拒绝 + dropped 记录）                                                         |
| ---------------------------------------------------------------------------------- | ---- | ---------------------------------------------------------------------------------------------------------------- |
| `fabric.maxPerRun`（progress）                                                     | 20   | **降级 board**（`degraded:{reason:"sender_quota", fromTier}`），record 照常 accepted；TTL 压到 60s（防刷板自愈） |
| `fabric.findingQuota`                                                              | 10   | 同上                                                                                                             |
| `fabric.directiveQuota`                                                            | 5    | 同上（board 上虽不允许 directive 广播，但**降级产物**允许落板——它是审计不是广播）                                |
| `fabric.queryQuota`（新增）                                                        | 10   | 同上                                                                                                             |
| `fabric.boardQuota`（新增，per-sender 的 board 发帖总数，broadcast+degraded 合计） | 20   | 仍发（board 是地板，无处再降），但 entry TTL 压 60s 且工具结果带 `degraded:"board_quota"`                        |
| `fabric.deadLetterQuota`                                                           | 5    | 不变（死信是通知不是投递，§6.3）                                                                                 |

配额计数维度、`hydrate` 的恢复规则、`seq` 连续性语义全部继承 v1（`used` map、rejected 不计 kind 配额但耗 seq——v2 里 `rejected` 只剩 protocol 一种，几乎不再出现）。

### 6.2 root 收件箱（ingress）网关

- `rootInboxCap`（默认 12）：计数 pending+claimed 的 context-tier 记录（v1 口径不变）。**cap 满不再拒绝**（v1 `target_backpressure` 删除）：新消息 tier 初值降为 `notify`。
- notify 也有闸：`notifyOutstanding = deliveredVia==="notify_root" 且 deliveredAt > lastRootTurnAt` 的计数（`lastRootTurnAt` 由既有 root `turn_end` 订阅刷新，compact-hint 同款挂点）。`notifyOutstanding ≥ rootInboxCap` ⇒ 降级 board。理由：notify 挂在下一次自然回合的上下文上，无闸则刷屏只是换了时点。
- `rootMinIntervalMs`（默认 10s，0=只宣称瞬时 cap 的 v1 语义不变）：只作用于 push tier 的节奏；间隔未到时消息**停留 pending**（throttle 排程），不降级——它本来就是延迟不是满。
- `fabric.wakeRoot`（新增，默认 **true**，与 v1 `sendRootContext` 的 triggerTurn:true 行为连续）：false 时 root 恒不强制起轮，context tier 直接从 notify 起步。progress→root 走 display 通道（`progressChannel:"display"` 默认），本来就从不唤醒——不变。

### 6.3 死信的语义收缩

v1 中 `target_gone` 触发死信（finding/directive）。v2 里终态目标是**一级降级目标（board）**而非投递失败，死信只保留两类触发：

- `ttl_expired`（pending 期间没人可投：pending_start 挂到超时等）；
- `attempts_exhausted`（push 反复 steer_timeout）。

死信本身仍从 system 发给原发送者（kind=dead_letter，`from:"system"` 协议钉死），`from` 为 run 的死信投递按 §3.1 正常分级（发送者已终态 ⇒ 落板，`deadLetter.status` 语义不变）。I-F11 的"义务纯函数"不变：`state∈{dropped,abandoned} ∧ kind∈{finding,directive} ∧ deadLetter===undefined ⇔ 义务未履行`。

### 6.4 AdmissionResult v2

```ts
export type AdmissionResult =
  | { ok: true; status: "accepted"; key; seq; tier: DeliveryTier; degraded?: Degradation } // direct
  | { ok: true; status: "posted"; key; seq; degraded?: Degradation } // broadcast
  | { ok: false; status: "protocol"; reason: string }; // 调用方 bug，非投递失败
```

`quota_exhausted` / `target_backpressure` 两个 ok:false 分支删除（I-N 的直接体现）。工具返回文本附一行降级说明（英文 token：`degraded→board`），模型能感知并自我节制。

## 10. 实施顺序与风险

**P1**（纯内核，无 pi 依赖）：`core/message.ts` + `fabric/board.ts` + router broadcast/降级 + 对应单测/性质测试。
**P2**（投递分级）：mailbox tier 复核、`sendRootNotify`、wakeRoot/notifyOutstanding、settings——v1 行为回归锚点全部跑绿。
**P3**（唤醒与拉取）：`revive.ts`、mention 收敛、`read_board`（注入 + host 侧）、renderer、index/stack 接线。
**P4**：集成测试、CHANGELOG、`docs/dev/fabric-v2/` 落档（本方案 + 评审记录）。

**风险与对策**：

1. _notify 刷屏下个自然回合_——§6.2 notifyOutstanding 闸 + 每 sender quota 双重上界；
2. _复活链震荡_——maxDepth 2 + perTarget 1 + sessionCap 8；
3. _board 变垃圾场_——boardCap FIFO + TTL + boardQuota（60s 短 TTL 自愈）；
4. _删除 can_message 后的骚扰面扩大_——保留 per-link throttle（30s）与 per-kind quota，且接收方 prompt 的"不可信输入"纪律不变（`formatMessage` 前缀保留）；
5. _root turn_end 钩子不可用_（旧 pi 版本）——`lastRootTurnAt` 缺省 0 时 notifyOutstanding 退化为"只数本 stack 生命周期"，保守方向偏差，不阻塞。
