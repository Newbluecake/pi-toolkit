## 0. 定位与继承的决策

### 0.1 需求（需求方原话约束）

| #   | 需求           | 含义                                              |
| --- | -------------- | ------------------------------------------------- |
| R1  | 点对点 + 广播  | 任意两个 agent 之间可通信；也可一对多广播         |
| R2  | 发送永不阻塞   | 不能保证对方知道或有能力回复 ⇒ 发送方绝不等待对方 |
| R3  | 不限制发送能力 | 不设"谁能给谁发"的权限白名单                      |

原始痛点：主 agent 手动转接前一个 agent 的结果，下一个 agent 仍重复调研——目标是让知识可寻址、
可沉淀、可请教（含复活已结束的 agent）。

### 0.2 核心语义转换 [D-1′, E-3]

R1 + R3 的组合后果是"无限制广播 + 推送式投递 = context 投毒 + turn 放大"。因此：

> **约束不放在"谁能给谁发"（发送权限），放在"什么进得了我的 context"（接收侧摄取预算）。
> 超限不拒收，只降响度。**

前稿的三级投递纪律（push/notify/pull）**塌缩为两级：`push` / `board`**。依据是评审推翻性更正
[B-M1]：pi 的 steer 语义是把内容并入接收方**同一外层 turn 的下一次 LLM 调用**
（`agent-loop` 的 `while (hasMoreToolCalls || pendingMessages.length > 0)`），对运行中的子 agent
**不产生额外轮次**，真实成本只有 context token ⇒ notify/pull 对运行中接收方没有区别，统一为
board。`urgent` 参数与 G1 闸门随之取消 [B-M1]。

| ID   | 决策                                                                                 | 来源/状态                                                                      |
| ---- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |

`scope.symbols`、`boardSenderSharePct`（会淘汰未回答的 query）、`answered` supersede。

## 1. 消息模型（任务点 1）

### 1.1 NodeRef 与 kind

```ts
// src/core/message.ts
export type NodeRef = RunId | "root" | "system" | "board"; // +"board"

export type MessageKind =
  | "progress"
  | "finding"
  | "directive"
  | "result"
  | "dead_letter" // v1 原样保留
  | "query" // 提问：无义务、无阻塞、可被忽略；direct 且目标终态时可触发 W2 复活
  | "answer" // 回答：replyTo 指回 query；强制 evidence
  | "nack" // 「我不知道 / 不在我的范围」——一等公民，极便宜 [D-7]
  | "announce"; // 公告：恒 to:"board"，落看板，永不 push、永不唤醒 [D-5/D-14]
```

kind 语义与地址**正交**（协议 kind 除外）：`query`/`finding` 等也允许 `to:"board"`（例如
ask-early 的「我要查 X，谁知道」广播）；`announce` 恒指看板。方向性协议规则见 §2.1。

### 1.2 信封增量

```ts
export interface MessageEnvelope {
  // v1 字段不变：key/from/to/kind/seq/generation/payload/ref/via/ttlMs/createdAt
  replyTo?: MessageKey;              // 问答关联；v1 的 from:to:generation:seq 天然是 correlation id
  topic?: string;                    // 看板归档键；to==="board" 时必填 [D-12]
  discipline?: "push" | "board";     // admit() 内一次定死、永不变更 [D-4]
  evidence?: Array<{ file: string; lines?: string; quote?: string }>;  // answer 必填 [D-12]
  freshness?: { gitHead?: string; at: Millis };   // 读者据此判断过期（L5 防误信）
  digest?: string;                   // sha256(kind + to + normalizedText)，去重窗口用
}

// payload 扩展（向后兼容，均可选）：
payload: {
  text: string;                      // headline / 正文
  files?: Array<{ path: string; role: "read" | "edited"; hits?: number }>;  // fileIndex [E-1]
};
```

说明：

- **`payload.files` 是本设计相对前稿最重要的增量 [E-1]**：实验证明真正的收益载荷是
  「坐标地图」（fileIndex），且它**机械可生成**——直接从该 run 自己的
  `diag.toolHistory[].argsPreview` 导出（`previewToolArgs` 的 preferred key 已含
  `path`/`file_path`，零新增埋点），不依赖 agent"主动想起来写"，因此不受 result 的压缩瓶颈
  约束。run 结算时自动落一条 `announce` 到看板（§5.4），非 agent 自觉。
- 不引入独立的 `audience` 联合类型（前稿 bug [B-M3] 的根源——`audience` 可选导致存量消息
  全被判成广播）：**地址拓扑由 `to` 单独表达**，`to === "board"` 即广播，其余即点对点。
  判据必真、无缺省歧义。
- `via.mode` 保留 `"mention"` 仅作溯源展示（mention 退化为 `@label` 寻址语法糖）。

### 1.3 去重与拒绝原因

`rejected.reason` 增加 `"duplicate"`。`digest = sha256(kind + to + normalizedText)`，同
`(digest, to)` 在 `dedupeTtlMs`（默认 10min）窗口内重复 ⇒ `dropped(duplicate)`。非阻塞下环
不死锁只放大，去重负责掐死字面重复 [D-10]。

## 2. 发送权限与路由规则（任务点 2）

### 2.1 `authorize()` 重写 [D-2]

```ts
export function authorize({ kind, relation, from, to }: AuthorizationInput): boolean {
  if (!MESSAGE_KINDS.includes(kind)) return false;
  if (kind === "dead_letter") return from === "system";
  if (to === "board")
    return kind === "announce" || kind === "query" || kind === "finding" || kind === "progress" || kind === "answer"; // 公告类可广播；协议 kind 不可
  if (kind === "result") return relation === "child"; // 结果只能上行（协议自洽，非权限）
  if (kind === "directive") return relation === "parent"; // 指令只能下行
  // progress / finding / query / answer / nack / announce：任意关系全开（R3）
  // —— unrelated / self / 跨树 / 任意深度 / 同级，全部放行
  return true;
}
```

- **方向性规则不是权限，是协议自洽**（result 必须上行、directive 必须下行、dead_letter 只能
  system 发）——保留；其余关系（含 `unrelated`/`self`）全开。
- `can_message`/`CanMessage`/`effectiveCanMessage()`/`MentionRoute` 及 `authorize` 的
  `mention` 分支**整体删除**；`relation === "unrelated" | "self"` 不再被拒。
- 旧 frontmatter 里的 `can_message:` 只 WARN 不报错（"v2 已移除，发送不再受限，该声明被忽略"）。
- **暴露面如实承认**（评审攻击点）：删除后，任意深度、正在处理不可信 web 内容的 agent 都能
  push 拥有全部工具的 root。防线不是恢复权限闸，而是：①root 的入站受 `rootInboxCap` +
  `wakeRoot` 开关约束；②`formatMessage()` 的 `不可信输入: from -> to` 头覆盖全部 kind；
  ③root 被 push 内容进入 context 时保留该头与 relation 标注（信任先验）。

### 2.2 寻址与解析（router 侧）

| 地址形式                | 解析                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| `to: <RunId>`           | 点对点，任意关系                                                                                      |
| `to: "@label"`          | 点对点，经 `MentionRegistry.resolve()` → runId；**不再要求 root 直属、不再要求 can_message: mention** |
| `to: "root"`            | 发给主调度器（受 `wakeRoot`，见 §3.2）                                                                |
| `to: "board"` + `topic` | 广播：恒 1 条看板记录 [D-5]，扇出 O(1)，永不 push、永不 revive [D-14]                                 |
| `to: "system"`          | 仅 dead_letter 协议路径                                                                               |

路由仍沿 agent 树逐跳穿线（`via.lca/hops` 记录溯源 [D-11]），但 `relation` **不再参与放行**，
仅写入 `formatMessage()` 头供接收方判断可信度。

## 3. 投递纪律：push / board 由什么决定（任务点 3）

### 3.1 `resolveDiscipline()` —— 替代 `effectiveChannel()`

纯函数，在 `FabricRouter.admit()` 内调用一次，结果写入 `record.discipline` 后**永不变更** [D-4]。

```ts
function resolveDiscipline(input: {
  kind: MessageKind;
  to: NodeRef;
  isReplyToOpenQueryOf: (receiver: NodeRef, replyTo?: MessageKey) => boolean;
  receiverState: "pending_start" | "running" | "gone" | "root";
  inboxUsed: number;
  inboxCap: number;
}): "push" | "board" {
  // ① 广播恒 board（封 W1/W2 的第一道闸，D-5/D-14）。判据是 to 而非可选的 audience——
  //    存量消息（系统死信、/reload 后 v1 残留 pending）天然不满足 to==="board"，不会误判 [B-M3]
  if (input.to === "board") return "board";
  // ② 协议消息保持 v1 语义：result/directive/dead_letter 恒 push（不占接收方预算，见 §6）
  if (input.kind === "result" || input.kind === "directive" || input.kind === "dead_letter") return "push";
  // ③ 终态目标：一律 board（是否额外 revive 由 §4.3 的 W2 闸独立裁定，不是投递纪律）
  if (input.receiverState === "gone") return "board";
  // ④ 对「我发出的 query」的回答/婉拒 → push（保留配额内，§6）
  if ((input.kind === "answer" || input.kind === "nack") && input.isReplyToOpenQueryOf(input.to, input.replyTo))
    return "push";
  // ⑤ 其余直达（query/progress/finding/nack 未命中 open query）按接收方状态：
  //    运行中子 agent：push 成本只有 token（steer 并入下一次 LLM 调用）[B-M1]
  //    root：push 真起一轮（受 wakeRoot；root 正忙于前台 Agent 调用时降提示行，§3.3）
  // ⑥ 接收侧摄取预算耗尽 ⇒ 降级 board，绝不拒收 [D-6]
  if (input.inboxUsed >= input.inboxCap) return "board";
  return "push";
}
```

### 3.2 两类接收方的真实投递通道（如实记录能力边界）

| 接收方          | `push` 的实现                                                                                 | `board` 的实现                                                              |
| --------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 运行中子 agent  | `runner.steer`（port `inject`）——并入其**同一外层 turn 的下一次 LLM 调用**，无额外轮次 [B-M1] | 看板记录 + 机会式提示（§5.5）                                               |
| root            | `sendRootContext`（`deliverAs:"steer", triggerTurn:true`）——真起一轮                          | `sendRootDisplay`（`appendEntry`，**display-only 不进模型 context**）+ 看板 |
| 终态 agent      | （仅 direct + query 触发 W2 复活，§4.3；复活后的新 run 收到 query）                           | 看板记录，等未来读者                                                        |
| `pending_start` | 等待 running 快照 hint（v1 mailbox 语义不变）                                                 | 同 board                                                                    |

`progressChannel` 设置项保留解析但标记 legacy：`"display"` ⇒ root 的 progress 走 board+display
行；`"context"` ⇒ root 的 progress 走 push（等价旧行为）。

### 3.3 root 的两个已知限制（评审 [B-M2]，如实写入实现与工具描述）

1. **root 前台 `Agent` 调用期间收不到 push**：`sendRootContext` 走 steer，而 root 正阻塞在
   Agent 工具调用里（`foregroundAutoBackgroundMs: 600_000`）。处置：投递层把这类 query 降为
   `sendRootDisplay` 提示行 + 看板；工具描述明确「向 root 提问在后台调度
   （`run_in_background`）下才即时有效」。
2. **`wakeRoot: false`**（默认 true 可配）：root 的一切入站 push 降为 display 行 + 看板，零
   turn 触发——防用户空闲时被 subagent 烧 token；此时主 agent 只能主动 `read_board`。

### 3.4 点对点与广播的成本结构（一句话版）

- **点对点**：至多 1 次 push（受接收方预算），token 有界、轮次只在 root/复活两种接收方上发生。
- **广播**：恒 1 条看板记录，0 次 push、0 次复活——"想引起某人注意，唯一途径是点对点"（唤醒
  因此永远是具名、可审计、计入接收方预算的动作；广播真重要时，发送方须显式补发一条 direct）。

## 4. 接收方唤醒规则（任务点 4）

### 4.1 唤醒的两种形态

| 形态   | 含义                                      | 机制                                                           |
| ------ | ----------------------------------------- | -------------------------------------------------------------- |
| **W1** | turn 唤醒：让**运行中/root** 接收方起一轮 | `push`（`runner.steer` / `sendRootContext(triggerTurn:true)`） |
| **W2** | 复活唤醒：让**终态** agent 重新起一个 run | auto-revive（`spawn({resumeFrom, ...})`，D-9）                 |

### 4.2 不变量 I-W [D-14]

> **只有 `to !== "board"` 的点对点消息可以产生 W1 或 W2。任何广播恒不唤醒任何 agent。**

出口断言（评审攻击后的修正：不能只靠 `resolveDiscipline` 的三个落点，**必须在唯一出口处断言**）：
所有 `sendRootContext` / `runner.steer` / `spawn({resumeFrom})` 的调用点（port 层）统一检查
`record.to !== "board"`，violation 直接抛错——封住 B2 类绕过路径（复活 run 的完成通知不得带
`triggerTurn:true` 去敲第三方）。

W1 的实际成本（决定策略合理性的事实 [B-M1]）：

- 运行中子 agent：steer **不产生额外轮次**（并入下一次 LLM 调用），成本只有 token；
- 空闲 root：真起一轮（该轮可直接调写工具）——最贵，受 `wakeRoot` + `rootInboxCap` 双闸；
- W2 复活：一次带完整 context 的新 run——最贵，见 §4.3。

### 4.3 W2 复活的触发面与实现约束

**触发条件（全部同时满足）**：`to !== "board"` **且** `kind === "query"` **且** 目标
`targetState === "gone"`（终态）**且** `reviveOnDirectQuery` 开启。
`progress`/`finding`/`nack`/`answer` 发给终态目标一律只落看板——把已结束的 agent 拉起来听一条
通报是纯烧钱。`query` 之外的 kind 不复活；mention 通道的既有 resume 分支在 M1 阶段**不动**
（否则中间态违反 I-W [B3]，见 §9 里程碑）。

实现约束（[B2]/[M8] 处置，缺一即坏）：

1. **不带 `parentRunId`**：带了会触发 `canSpawn` 嵌套校验 → config error 被 fire-and-forget
   静默吞掉；代价是复活 run 不再挂在提问者名下（这正是需要的——它不是委派）。
2. `slotless: true`（不进 `concurrencyLimit` 槽池，防与提问者互等死锁）+ `deadlineAt` 由发起方
   剩余 deadline 夹紧（CC4 只收紧不放松）。
3. **抑制完成通知入队**（notifier 以 `triggerTurn:true` 唤醒 root 的路径必须关闭）——答案**只经
   fabric 回流**（复活后的专家 `message_agent(kind:"answer", replyTo)`），这正是 I-W 出口断言的
   覆盖对象。
4. **`resumeLocks` 拒绝不是合并**（返回 "already has a resume in progress"）：router 维护
   `reviving: Map<target, newRunId>`，revive 期间到达的同目标 query 不再发起新 spawn，待新 run
   running 后 steer 进它 [M8]；同时走**不 repoint label** 的路径（`@expert` 不能被问答 run 抢走）。
5. `autoReviveMaxPerSession`（默认 10）兜成本。

**前提假设的诚实标注 [E-4]**：三轮实验中，阻塞式中继形态下**两个 agent 均 0 次主动请教**
（提问摩擦高于自己 grep）——「下游会主动请教」目前**未被证实**。重启 fabric v2 的前提是先用
「轮内同步 `ask_expert` 工具」形态检验 H2（摩擦与一次 grep 相当）。**投递层按本方案先行；
W2（M6）的实施投入等 H2 验证结论**。

## 5. 看板：存储方式与有效范围（任务点 5）

### 5.1 职责

广播的落地载体 + 迟到答案的归宿 + 新 agent 的启动知识来源（取代"主 agent 手动转接文件"）。

### 5.2 存储 [D-3, D-4]

- **仅当前主 session，不跨会话**：`appendEntry(customType: "subagent:board", entry)` append-only
  写入 + 读回校验，完全复用 `src/adapters/pi-outbox-store.ts` 的模式；`session_start` 从
  prefetched 条目重建（与 `buildFabric()` 里重建 tree 的写法同源）。新主会话看板归零；跨会话
  知识沉淀走现有 `memory` 子系统（已存在，不重复建设）。
- **不进 mailbox、不进状态机**：board 路径在 `admit()` 内同步写看板成功后直接
  `engine.put({ ...record, state: "delivered", terminalReason: "board" })`——`put` 不查转移表
  ⇒ `src/stack.ts` 的 `allowed` 表与 7 处逐字复制它的测试 fixture **全部无需改动** [B-M3]。
- 容量：全局 FIFO `boardCap`（默认 500）+ 每 topic `boardTopicCap`（默认 50）；截断优先保留
  ①最新、②被 `replyTo`/`ref` 引用过的条目。

### 5.3 读取：`read_board({ topic?, files?, since?, limit?, all? })`

- 默认视图按 `topic` 与 `files` glob 交集过滤（`payload.files` 是主检索键，topic 是自然语言
  会漂移、只作辅键）；`{ all: true }` 逃生阀。
- 调用即推进该 reader 的 cursor；headline 形式
  `[topic] path1,path2 — 结论一句 (@from, 12m, abc1234)`——读者只花 headline token 决定是否
  取全文，模型是最终裁判。
- 每条带 `freshness.gitHead`（对不上标 ⚠️ 可能过期）+ `不可信输入` 围栏——看板是持久化
  prompt 注入面（类存储型 XSS），围栏降险不消除，`evidence` 强制支持 O(1) 抽查 [D-12]。

### 5.4 写入者与载荷 [E-1]

| 写入者                                                                                | 条目                                                                          |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| agent `announce`                                                                      | 主动公告（强制 `topic` [D-12]）                                               |
| **run 结算钩子**                                                                      | 每个 run `onRunSettled` 时**机械导出**一条 fileIndex 条目（`payload.files` 从 |
| `diag.toolHistory[].argsPreview` 提取 read/edit 路径，去重计数）——不依赖 agent 自觉， |
| 突破 result 的压缩瓶颈；topic 取 run 的 type/label                                    |
| board_fallback                                                                        | 迟到/无法投递的 `answer`/`nack` 按 `topic` 转存 [D-8]                         |
| query 广播                                                                            | ask-early 的「我要查 X，谁知道」；任何读到且知道的 agent 可回 direct `answer` |

### 5.5 启动注入与提示行（B1 处置后的落点）

- **启动注入不走 `before_agent_start`**——该 hook 注册在 `HOST_KEY` 守卫之后，**子会话根本
  看不到** [B1]。改为**宿主侧 spawn 时拼进 prompt**：`src/service/runtime-adapter.ts` 组装
  `SessionSpec`/prompt 时追加 `## 看板` 块——topic 目录 + 命中该 run 文件域条目的 headline
  （预算 `boardInjectBudgetChars`，默认 2000 字符），复用 memory 的预算化渲染手法（围栏/tail
  sentinel）。resume 的 run 同理。
- **注入文案必须附带核验型指令** [E-2]：实验 A1nd 臂证明只给坐标不给纪律 ⇒ 最便宜也最不核验
  （盲信上游错误）。三条纪律写死：开工先看板、坐标按需抽查（抽 1–2 处 `evidence`/`file:line`
  验真）、答案覆盖当前工作即转向。
- **turn 边界提示行**：不是消息、不占预算——挂在三个零成本位置：①`message_agent` /
  `read_board` 工具回包尾部（「看板未读 N 条，topic: ...」）；②主会话 TUI（fleet widget /
  status 行，display-only）；③push 消息投递时给 root 的 display 行捎带。**不给子会话注册任何
  依赖 session hook 的机制**（B1 教训）。

## 10. 风险与开放问题（如实）

   截断 + run 结算钩子只写结构化坐标（机械、无空话）。不是配额。
3. **看板是持久化 prompt 注入面**：围栏 + evidence 抽查 + freshness 标注降险不消除；核验纪律
   文案是行为层补偿（E-2）。
4. **root 前台期间提问不可达**（§3.3）：已如实写入工具描述；彻底解法（Agent 等待循环内暴露
   query 为 tool update）留待 pi 宿主能力。
5. **迟到答案可能白费一次 revive**：`autoReviveMaxPerSession` + prompt 纪律「开工先问」缓解。
6. **删除 `can_message` 不可逆**：需求方已确认；未来若需沙盒化不可信 agent type 的发言限制，
   须另行设计（建议届时做成接收侧 deny-list，与 R3 兼容）。
