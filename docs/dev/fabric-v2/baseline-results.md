## 3. 本轮最重要的发现：预注册的 M1 指标定义错了

按 `baseline-experiment.md` §4 的预注册判据，"M1 下降 > 40%" 才算 H1 成立；**实测 M1 不降反升 29%**，字面判据 ⇒ H1 不成立。

但把 M1 拆开看，真实情况相反：

- A1 **重读 A 读过的文件更多**（18 vs 15）；
- A1 **游荡到 A 没碰过的文件更少**（8 vs 13，−38%）；
- A1 的 **grep 次数暴跌 72%**（29 → 8）。

⇒ **结构化交接省下的是「找」，不是「读」。**

M1 = 重叠/B总数 之所以误导，是因为分母（B 碰的文件总数）本身就是被干预变量。B1 精准地只碰相关文件，重叠**占比**自然更高——它衡量的是"聚焦度"而非"浪费"。

**修正后的主指标**：

- **M1′ = 非重叠文件数**（B 碰了而 A 没碰的）——游荡的直接度量；
- **M1″ = 搜索类工具调用次数**（grep/find）——定位成本的直接度量。

> ⚠️ 这是**事后修正**，有过拟合本轮数据的风险。M1′/M1″ 必须在后续重复轮中作为**新的预注册指标**独立验证，不能拿本轮数据既定义指标又验证指标。

## 4. 效力警告（必须先说）

- **n=1/臂**。LLM 轮次与成本的天然方差很可能就在 ±20% 量级，本轮所有 Δ 都落在这个量级内，**单独看不足以断言因果**。唯一超出噪声量级的是 grep −72%。
- A1 是**捆绑处理**（更丰富的包 + "别重读/别重走"的纪律），无法区分两者各自的贡献。要拆需第四臂（给完整包、不给纪律）。
- 偏差记录：`Agent({schema})` 崩溃（见项目记忆 `agent-tool-schema-bug.md`），A 的结构化输出改用 prompt 内 JSON 代码块，校验由"双重"降级为调用方自行 parse；thinking 用 medium 而非 architect 常规 high（两臂一致）。

## 5. 取数管线的两个 bug（已修，记录备查）

1. **只取 `args.path` 会低估 ~80%**：探索型 agent 的文件接触绝大多数发生在 `bash grep/sed/find` 里。必须解析 `command`。
2. **绝对路径静默漏匹配**：子 agent 惯用 `/abs/repo/src/x.ts`，而路径正则要求 `src` 前是空白/引号类边界字符，`/` 不在其中 ⇒ **整段漏匹配、不报错、只返回 0**。首次运行时 A 的 33 个文件被提取成 0。修法是先剥仓库根前缀再匹配。
   这个 bug 若未被发现，会让整个实验得出"两臂都没碰任何文件"的荒谬结论而不自知。

## 6. 对 fabric v2 的直接启示（暂定，待重复轮确认）

评审（`plan.md` §15.6）判定"看板和 result 撞同一个压缩瓶颈"。本轮数据提示这个判断**对结论叙述成立，对文件索引不成立**：

- 真正产生收益的载荷是 **`fileIndex`（坐标地图）**，而非 `conclusion`（结论叙述）；
- `fileIndex` 与 `conclusion` 有一个关键差别：**它是机械可生成的**（可直接从 agent 自己的工具调用历史导出），不依赖 agent"主动想起来要写"，因此**不受压缩瓶颈约束**；
- 若后续轮次证实这一点，fabric v2 的看板应当以**结构化坐标**为主载荷，而不是自然语言公告——这会显著改变 §6 的设计。

### 10.2 在不越权的前提下，数据实际说明了什么

1. **最稳健的效应是 M1′（游荡）而不是 M1″（搜索）**：两个干净轮里 A1 几乎不再碰 A 没碰过的文件（0、1 vs 5、11），三轮（含受污染的第 1 轮 13→8）方向全部一致。
   ⚠️ M1′ 是由第 1 轮数据事后定义的指标，它在第 2/3 轮通过属于**独立验证**（数据产生前已写入 §9），但它**不是**主判据——结论应表述为"辅助指标稳健成立"，而非"H1 成立"。
2. **成本降幅稳定在 34–53%**，两轮 A1 均显著便宜且无交叉。
3. **A0 臂组内方差极大**（引用数 17 vs 1、工具调用 37 vs 50），印证了 n=1 结论不可信的判断；单轮数据会被噪声任意翻转。

### 10.3 A1nd（完整包、无纪律）——一个反直觉的发现

预期：去掉"别重读"纪律 ⇒ agent 会**多读**。**实测相反**：A1nd 只读了 2 次文件（A1 两轮为 16–18 次），工具调用、成本、引用数**全场最低**（19 / $0.30 / 3）。

解读（**n=1，仅作假设**）：纪律那句话的实际作用不是"授权跳过"，而是**把注意力引向 `fileIndex`/`ruledOut`，促使 agent 按图有选择地核验**。去掉它，agent 直接吸收 `conclusion` 就写方案——**最便宜，也最不核验**。

这对设计有直接影响：**只给结构化包、不给核验指令，可能诱发盲信**，把上游 agent 的错误原样传下去。便宜不等于好。

### 10.4 结论与建议

- **H1（结构化交接能削减重复调研）**：预注册主判据未通过；但辅助指标（游荡 −91~~100%、成本 −34~~53%）在干净重复轮中一致成立。**判定：部分支持，效应真实存在但落在"少游荡"而非"少搜索"。**
- **零工程量的干预已拿到可观收益**：仅用现有 `schema`（绕过 bug 后改为 prompt 内 JSON）+ `fileIndex`/`ruledOut` + 核验型纪律，下游成本降三到五成。**这一步不需要 fabric v2 的任何代码。**
- **H2（向终态专家请教）尚未检验**（A2 臂未跑）。在它被检验之前，**不能**据此断言 fabric v2 不必做——只能断言"结构化交接这一步已足够值得先做"。
- **对 fabric v2 设计的修正**（若日后复活）：看板的主载荷应是**机械生成的结构化坐标**（`fileIndex`，可从 agent 自身工具调用历史导出，不受压缩瓶颈约束），并**必须附带核验型指令**以防盲信（§10.3）。

### 10.5 本轮修掉的取数 bug（第 3、4 个）

3. **把调度方主会话误认作每一臂**：按"工具调用参数里包含输出路径"匹配时，主会话派单 prompt 里也写着每臂的路径 ⇒ 五臂全部映射到同一 session，产出**看似合理的垃圾表**。修为：必须有 write/edit/bash 真正写入该路径，且排除调用过 `Agent` 的会话。
4. **引用计数漏计为 0**：B 的写法是 `` `src/stack.ts` 1434 ``（反引号 + 空格），只认 `path:line` 的正则全部漏掉。

## 11. A2 臂预注册（检验 H2：向已结束的专家请教，写于数据产生之前，2026-09-24）

**实现方式（零改动）**：原计划让 B 自己 `Agent({resume})` 请教 A，但做不到——嵌套派生需要带 `can_spawn` 的新类型，
新类型只在 `session_start` 加载，而 `/reload` 会清空内存态的 run 记录（`spawn-service` 的 `records` 不从会话条目重建），
A 从此无法 resume。因此改为**调度方中继**：B 用原版 architect、只拿 `conclusion`（与 A0 同基线），
被告知可在最终回复只输出 `ASK_EXPERT: <问题>` 后结束；调度方 resume A 取答，再 resume B 并转交答案。
这正是用户原始诉求的形态（经主 agent 向已结束的 agent 请教），但它是**阻塞式**的，不是 fabric v2 设想的非阻塞在途请教。

**探测数据点**（预注册前已发生，如实记录）：冷缓存下 resume A 问一个定位问题 = 1 轮、0 工具、$0.19、16s，答案准确。

**冻结基线**：resume 会续写 A 的会话文件，A 回答时若调用工具会回溯改变各臂 M1′ 基线。
取数一律使用冻结副本 `/tmp/exp_hold/A-frozen.jsonl`（冻结于 A2 派发前）。

**指标与预测**（对照 A0 两个干净轮均值：成本 $0.74、M1′ 8、M1″ 23）：

| 指标     | 定义                                     | 预测                                             |
| -------- | ---------------------------------------- | ------------------------------------------------ |
| 总成本   | B 各段 + 所有请教（A 的 resume）成本之和 | < A0 均值 × 0.7                                  |
| M1′ 游荡 | B 碰过而 A 没碰的文件数                  | < A0 均值                                        |
| M1″ 搜索 | B 的 grep/find 次数                      | < A0 均值                                        |
| 请教次数 | B 发出 `ASK_EXPERT` 的次数               | ≥ 1（若为 0 ⇒ 该轮 H2 **未被触发**，不计入判定） |

**判据**：两轮中触发了请教的轮次，总成本均 < $0.52（A0 均值 × 0.7）且 M1′ < 8 ⇒ H2 在「中继」形态下得到支持。
另记录与 A1（结构化交接，均值 $0.42）的对比，回答「请教」能否替代或补充「交接包」。

**隔离复核（补记）**：第 2/3 轮各臂的工具调用只引用了**自身**的输出路径，未窥探 `/tmp/exp_hold/` 中的其它文件 ⇒ 第 2/3 轮确认干净。
A2 前进一步收紧：交接输入单独放 `/tmp/exp_a2_in/`，设计文档移到隐藏目录，旧产出清空，A2 产出写 `/tmp/exp_out_a2/`。

| （对照）A1 均值 | —        | 32.5     | 0.5      | 14.5     | 0.42 | 20.5 | —             |

**按预注册判定**：两轮请教次数均为 0 ⇒ H2 **未被触发**，不计入判定。**H2 仍未检验。**

尽管 prompt 明确写了「当你需要它掌握的具体知识时，**优先请教它，而不是自己重新调研**」，两个 agent 都选择了自己查——
A2-r1 甚至 grep 了 27 次（全场第二多），并在最终回复里自述「所有关键论断均已根据源码进行了验证」。

**这本身是一个重要发现（n=2，但两轮一致）**：

- 在「必须结束本轮才能提问」的**阻塞式中继**形态下，模型几乎不会主动请教——提问的摩擦（中断自己的工作流、等待）高于自己 grep 的成本；
- 模型的倾向是「自己核实优先」，这与 A1 臂中「即使被告知可以跳过，仍会重读关键文件」的行为一致；
- **对 fabric v2 的含义**：revive/请教路径的前提假设是「下游会主动请教」。至少在阻塞形态下这个前提**不成立**。
  若日后要再检验，唯一值得测的形态是**轮内同步工具调用**（`ask_expert(question)` 直接返回答案、不中断当前轮）——
  它的摩擦与一次 grep 相当。这需要给 B 的类型开 `can_spawn` 并在 `/reload` 之后、于同一会话内重新跑一个探索者 A（因为 run 记录不跨 reload）。

A2 的游荡数（3、3）低于 A0 均值（8），但请教从未发生，二者 prompt 的唯一差别是那段「可以请教」的说明——
这个差异在 n=2 下不足以区分于噪声，**不做解读**。

## 14. 实验 3 预注册：决定性实验——在对请教最有利的条件下，下游会不会主动请教？（写于数据产生之前，2026-09-24）

**动机**：A2 中请教次数为 0，但混有三个非模型因素：①阻塞式中继摩擦大；②所需信息都能从代码读到（自己查是理性的）；③样本窄。

### 15.1 Q1：**C1 3/3 主动请教** ⇒ 按预注册判据，**不支持「模型层面不主动请教」**

三轮 C1 都在**任何泄漏发生之前**就发起了请教（首次请教位于第 4/15/15 次工具调用，泄漏均在其后），
所以 Q1 的判定不受后述专家失灵与泄漏的污染。

结合 A2（阻塞中继、信息可从代码读到 ⇒ 0/2 请教）：
**决定模型会不会请教的，主要是接口摩擦与「信息能否自己获得」，而不是模型能力。**
在轮内同步、且信息确实读不到时，模型会主动、而且相当早地开口（c1-r2 第 4 次工具调用就问了）。

### 15.2 Q2：作废

**专家失灵**：专家回答「我没有与你讨论过的记录」。根因是 pi-toolkit 的一个核心缺陷——
**`prompt_mode: replace` 的 agent 类型，其 system prompt 从未被应用**（`runtime-adapter.ts#buildPrompt` 在 replace
模式下只返回任务 prompt，`SessionSpec` 没有 system prompt 字段，全仓库也没有其它注入点）。专家实际上是一个
不带任何角色设定的通用 agent。**这同时意味着此前所有实验中的 architect/Explore 也都没有拿到角色设定**
（各臂一致，组间比较不受影响，但它们都不是"真正的" architect/Explore）。

**泄漏**：专家失灵后，下游普遍转为**全盘搜索**——翻 `~/.pi/agent/sessions` 旧会话记录、找到 `/tmp/.fv2_private`
读 `plan.md` 与决策文件、读 `~/.pi/agent/agents/domain-expert.md`。无专家的 c0-r1 同样自发翻了 32 次旧会话。
⇒ **同用户权限、带 bash 的 agent，在"被告知存在但拿不到"的信息面前会主动搜索整个文件系统**；
藏文件做不到真正隔离，只能靠 prompt 禁令 + 事后检测。

### 15.3 附带发现

- **信息饥渴会驱动越权搜索**：告知「有决策但未展开」而又不给获取渠道（C0）或渠道失灵（C1/C2）时，
  agent 会去翻会话记录等不该碰的地方。对产品的含义：**要么给出可用的获取渠道，要么别暗示存在它拿不到的信息。**
- 首批只启动了 2 个进程：`pi -p` 在 `while read` 循环里吞掉了 stdin（已用 `</dev/null` 修正）。

| 判据                          | 结果                   | 判定                               |
| ----------------------------- | ---------------------- | ---------------------------------- |
| Q2：C2 − C0 ≥ 2               | 6.5 − 2.0 = **4.5**    | ✅ **请教有实际价值**              |

### 17.2 解读

1. **不给信息时，下游被现有代码带偏**：C0 两轮都保留了 `can_message` 权限校验（D1 违反）、都用发送方指定的优先级决定投递（D4 违反）、
   都在超限时拒收（D6 违反）；c0-r2 还让广播逐个 push 并可唤醒接收方（D2/D3 违反）。这正是"读得到的旧代码 vs 读不到的新决策"
   的典型后果——**下游不会凭空猜对拍板决策，它会顺着现有代码的惯性走**。
2. **请教几乎把差距补平**：C1/C2 均分 6.5，比 C0 高 4.5 分，离推送上限（7.0）只差 0.5；而每轮请教成本仅约 $0.01，
   B 总成本并未上升（C1 反而最便宜）。
3. **自发请教与强制请教效果相同**（C1 = C2 = 6.5）：在信息确实读不到时，不需要强制，模型自己会问。
   强制的「开工前先问」反而没被遵守时序（C2 都先读代码、第 22/27 次调用才问），但不影响结果。
4. **剩余的 0.5 分差距**集中在 D1（c1 两轮 sonnet 判违反、kimi 判遵守——评审分歧点）与 D6（c2-r1 两位都判违反）。
   推送能把「全部决策」一次性交给下游；请教则依赖下游**问到了点子上**——没问到的点仍可能被旧代码带偏。

### 17.3 总结：回答「多智能体对话能力是否在模型层存在不足」

| 问题                 | 结论                                               | 证据                                                 |
| -------------------- | -------------------------------------------------- | ---------------------------------------------------- |
| 模型会主动请教吗？   | **会**——在请教摩擦低（轮内同步）且信息确实读不到时 | 实验 3/4 自发请教 5/5；A2（阻塞中继、信息可自取）0/2 |
| 请教有用吗？         | **有用**，质量 2.0 → 6.5                           | 实验 4，两评审一致率 93%                             |
| 请教能替代交接包吗？ | **接近**（6.5 vs 7.0），成本更低                   | 实验 4                                               |
| 之前「不问」的原因   | 接口摩擦 + 信息可从代码读到（自己查是理性的）      | A2 vs 实验 3/4 对照                                  |

**⇒ 瓶颈主要在接口设计，而非模型能力。** 模型会在合适的时机开口、问到点子上、并把答案用对。

**对 fabric v2 的含义（重新评估）**：「向掌握知识的 agent 同步请教」这一能力**被证明有价值**，且模型会自发使用。
但本实验的专家是「知识写在 system prompt 里的新 agent」，不是「被 revive 的已结束 agent」——
真实的 revive 路径还要面对：终态 run 记录不跨 `/reload`、resume 锁（同一专家同时只能答一个）、专家上下文里的知识是否仍然可取。
**建议的最小落地形态**：一个轮内同步的 `ask_expert`/`consult` 工具（本质就是 `Agent({resume})` 的受控封装），而非完整的 fabric v2。

### 17.4 局限

- 每臂 n=2，单一任务（fabric v2 投递层）、单一被试模型（glm-5.3）；
- 专家知识是精确写好的 7 条决策——真实场景中上游 agent 的知识是散落在长上下文里的，可取性会更差；
- 评分只覆盖 7 条决策的遵守度，不衡量方案的其它质量维度。

## 18. 实验 5 预注册：长上下文的真实专家还能答准吗？（写于数据产生之前，2026-09-24）

### 19.4 解读与告诫

1. **知识在长上下文里仍然可取**：专家读过 84KB 的方案（正文与修订互相矛盾）后，不调任何工具、仅凭上下文就给出了与最终修订一致的完整转述（约 12K 字）。
   这是实验 4 留下的最大不确定性，现在得到了正面回答。
2. **天花板效应**：C1/C3/E1 全部 7.0 满分——7 条决策的细则已无法区分「有信息」的各臂之间的差异。
   结论只能表述为「长上下文专家**不劣于**理想专家与推送」，不能说它们完全等价。
3. **调用出错是真实风险（1/4）**：通用的 `Agent({resume})` 让下游有可能漏掉 `resume`，从而问了一个一无所知的新 agent；
   而那个新 agent 会**去别处搜索来编答案**。⇒ `consult` 必须是**专用工具**：参数只接受专家的 run，**不存在「新起一个」的退路**。
4. **成本结构**：一次请教约 $0.1，下游总成本（$0.64）与推送（$0.67）、不给信息（$0.60）相当，但质量从 2.25 提升到 7.0。
   专家的任务成本（约 $0.19）是上游本来就要做的工作，不算请教的额外开销。
5. **回答偏长**（约 12K 字）：`consult` 应当考虑回答长度上限或「先给结论再展开」的回答格式，避免挤占下游上下文。

### 19.5 总结论（实验 1–5）
