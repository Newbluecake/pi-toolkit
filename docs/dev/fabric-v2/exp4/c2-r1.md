# fabric v2 消息投递层 · 架构设计方案

> 版本 v1 · 2026-09-25 · 架构设计（本文档不含实现代码）
> 前序拍板决策经 domain-expert 确认（发送权限全通、广播=看板单记录恒 O(1) 且不唤醒、
> 投递分级按接收方状态、复活仅限点对点 query、看板 appendEntry/会话内有效、超限降级永不拒收、nack 一等 kind）。
> 未拍板项由本设计补齐并标注【设计补齐】。

## 1. 背景与目标

### 1.1 要解决的问题

v1 fabric（`src/fabric/`，设计文档 `docs/dev/subagent-push/subagent-push-plan.md` v5.1 + `docs/dev/fabric-mention/`）已提供
agent 间消息：`message_agent` 工具（kind: progress/finding/directive）、按 agent 树 relation + `can_message` frontmatter
授权、per-sender per-kind 配额、root 收件箱 cap + 背压拒绝、六态投递状态机（DeliveryEngine）、per-link throttle、
死信回投、@label mention 通道（仅 root 直属子代、终态目标 resume）。

v2 的两个硬需求：

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播；
- **R2**：发送永不阻塞——发送方绝不等待对方回复（既不等待投递，也不等待应答）。

### 1.2 已拍板决策（本设计的输入，不可推翻）

| #   | 决策                                                                                                                                                                          | 来源 |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| P1  | **彻底删除 `can_message` 授权**：任何 run 可向任何 run / root / @label 点对点发送（含嵌套、跨树 unrelated）；`authorize()` 只保留协议自洽规则（如 result 只能上行），不做权限 | 拍板 |
| P2  | **广播恒不唤醒任何 agent**（不变量 I-W）：唤醒必须是具名、担责、计入接收方预算的定向动作；不设 urgent/优先级标记（提案已被否决）                                              | 拍板 |
| P3  | **广播 = 一条看板记录（`to:"board"`），恒 O(1)**：绝不向 N 个接收者逐个 push；接收方自己拉取看板                                                                              | 拍板 |
| P4  | **投递纪律按接收方状态分级**（不是按消息标记）：运行中子 agent → push；root → push（受 wakeRoot 开关与配额约束）；已终态 → 看板 pull，仅点对点 query 可复活                   | 拍板 |
| P5  | **复活仅限点对点 query kind**，是看板之外唯一的定向复活路径                                                                                                                   | 拍板 |
| P6  | **看板**：广播载体；`appendEntry` 写入、读回；只在当前主 session 内有效，不跨会话（跨会话归 memory 子系统）；看板不触发唤醒                                                   | 拍板 |
| P7  | **超限降级、永不拒收**：配额/收件箱满时按 push → notify → pull 逐级降级，任何一次发送都不返回失败                                                                             | 拍板 |
| P8  | **`nack`（"我不知道/答不了"）为一等 kind**：R2 的直接后果，让发送方尽早转自查                                                                                                 | 拍板 |

### 1.3 约束条件

- 不破坏 v1 的既有不变量：at-least-once 投递、死信恰一、引擎 claim/claimToken/freeze 语义（I-F10/13/14/15）全部保留；
- `pi -p` 纪律（定时器经 Clock unref）、`/reload` 重建栈、子会话 host-guard 惰性等仓库级约定不变；
- pi 原语（已核实 `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.d.ts`）：
  `steer(text)` = 排队到当前 assistant turn 的工具调用之后、下一次 LLM 调用之前（运行中即"本轮可见"）；
  `sendCustomMessage(msg, {triggerTurn:false})` = 追加到 state/session、**不**触发新 turn（"被动可见"）；
  `sendCustomMessage(..., {triggerTurn:true, deliverAs:"steer"})` = 进 context 且触发 turn。

## 3. 总体设计

### 3.1 核心概念：三级投递阶梯（level ladder）

每条**点对点**消息在 admission 时被赋予一个初始 level，此后**只降不升**（不变量 I-L）：

```
push ──► notify ──► pull
（强制可见）  （被动可见）   （自行拉取）
     ▲ revive（query→终态目标的特殊 push 变体，单发）
```

| level    | root 接收方                                                                     | run 接收方                                                                                                | 语义                                                                 |
| -------- | ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| `push`   | `pi.sendMessage({deliverAs:"steer", triggerTurn:true})`（= v1 sendRootContext） | `session.steer(text)`（= v1 inject）                                                                      | 进 context 并**保证**接收方在本轮/下一轮 LLM 调用中看到（唤醒）      |
| `notify` | `pi.sendMessage({triggerTurn:false})`（被动 context）                           | `session.sendCustomMessage({triggerTurn:false, deliverAs:"nextTurn"})`（追加到子会话 state/session 文件） | 写入接收方 session，**不**强制任何 turn；接收方若自然再起一轮才看到  |
| `pull`   | 看板记录 + display 行                                                           | 看板记录（audience 指向该 run）                                                                           | 只落看板；接收方用 `board` 工具拉取；复活时随 resume prompt 注入摘要 |
| `revive` | —（root 恒 running）                                                            | 异步 `spawn({resumeFrom})` 携 query 重启                                                                  | 仅 kind=query、终态目标、复活预算内；spawn 失败降级 pull             |

**kind 固定路由**（不经阶梯，admission 直接定级）：`progress → root` 恒为 notify 的 display 变体（v1 display 通道行为保留：appendEntry 渲染一行，永不进 context、永不唤醒）；`broadcast`（`to:"board"`）恒 pull、单记录、O(1)。

### 3.3 一条点对点消息的生命周期（v2）

```
发送方调用 message_agent(to=runId|root|@label, kind, text)
  └─ tool 层：@label → registry 解析（失败=唯一地址类错误，结构化返回）
      └─ router.admit()（同步，O(1)）：
           ① sender running（root 恒 running）② 协议规则（self 拒、broadcast⟺board、
           ③ flood guard（唯一允许的失败）④ decideInitialLevel（接收方状态 × 预算 × 配额）
           ⑤ 超额 → 直接降级定级（配额满→pull；node cap 满→pull；wakeRoot off→notify）
           ⑥ seq（含 (from,"board") 链路）⑦ supersede（progress）⑧ engine.put(state=pending, level=L)
      └─ 立即返回 {ok:true, status:"accepted", key, seq, level}   ← R2：永不等待投递
mailbox.pump()（异步）：
  按 level 选 port：push→pushRun/pushRoot；notify→notifyRun/passiveRoot；pull→boardWrite；revive→revive
  失败链：push 重试耗尽 → 降 notify（attempts 重置）→ 耗尽 → 降 pull → boardWrite 失败重试耗尽 → dead_letter
  TTL 到期（任意 level）→ 降 pull（内容保住）；仅 pull 级写板失败才进死信/abandoned
```

## 4. 接口契约

### 4.1 消息模型（`src/core/message.ts`）

```ts
export type NodeRef = RunId | "root" | "system" | "board"; // +"board"
export type MessageKind =
  | "progress"
  | "finding"
  | "directive" // 保留
  | "query"
  | "nack" // 新增（P5/P8）
  | "broadcast" // 新增：看板广播（P3）
  | "result" // 协议保留，v2 工具面不暴露（未拍板）
  | "dead_letter";

/** 投递阶梯（P4/P7 的载体）。revive 是 query 专属的 push 变体。 */
export type DeliveryLevel = "push" | "notify" | "pull" | "revive";
/** 阶梯代价序，用于单调性校验（I-L）：只能向右移动。 */
export const LEVEL_ORDER: readonly DeliveryLevel[] = ["push", "notify", "pull"];

/** 看板受众：广播 = all；降级直发 = 指向原目标（保留原 kind 供拉取方过滤）。 */
export type BoardAudience =
  | { kind: "all" }
  | {
      kind: "direct";
      target: Exclude<NodeRef, "board" | "system">;
      origKind: Exclude<MessageKind, "broadcast" | "dead_letter">;
    };

export interface MessageEnvelope {
  key: MessageKey; // 四段 key 不变；to 允许 "board"（validNode 扩展）
  from: NodeRef; // run | "root"（v2 起 root 也可发送）| "system"（仅 dead_letter）
  to: NodeRef; // run | "root" | "board" | 发送者（仅 dead_letter）
  kind: MessageKind;
  seq: number; // 逐链路单调；board 链路 = (from, "board")
  generation: Generation; // 发送者 generation；root 恒 1；system 恒 0
  payload: { text: string }; // maxChars 截断规则不变（code-point 保头 75%/尾 25%）
  /** v2 新增：仅 to==="board" 或降级为 pull 的记录携带；直发记录为 undefined。 */
  audience?: BoardAudience;
  ref?: { keys: MessageKey[]; omittedCount: number }; // 仅 dead_letter，不变
  via?: { mode: "tree" | "mention" | "board"; lca?: NodeRef; hops?: NodeRef[] }; // +"board"（to=board 时 mode=board、hops=[]）
  ttlMs: number; // progress = progressTtlMs；其余 = reconcileTtlMs（不变）
  createdAt: Millis;
}

export interface FabricRecord extends MessageEnvelope {
  state: FabricDeliveryState; // 六态不变（pending/claimed/delivered/consumed/dropped/abandoned）
  level: DeliveryLevel; // v2 新增：当前阶梯位置；fold 旧记录缺省推导（见 4.6）
  attempts: number; // 当前 level 的尝试计数（降级时重置）
  claimToken?: string; // 不变（D22）
  updatedAt: Millis;
  deliveredAt?: Millis;
  rejected?: { reason: "flood_guard" }; // v2：唯一 admission 拒绝原因（见 4.4）
  deadLetter?: {
    reason: "ttl_expired" | "target_gone" | "attempts_exhausted" | "board_failed";
    status: "issued" | "suppressed_quota" | "suppressed_sender_gone";
    key?: MessageKey;
  };
  terminalReason?: string;
  storageKey?: string;
}
```

**kind 列表与通道/义务速查**（任务要求 1）：

| kind        | 用途                                                | 到运行中目标 | 到 root                                  | 到终态目标                            | 死信义务                               |
| ----------- | --------------------------------------------------- | ------------ | ---------------------------------------- | ------------------------------------- | -------------------------------------- |
| progress    | 状态通报（易失，supersede）                         | push         | **display**（appendEntry，不进 context） | dropped（target_gone，无义务，同 v1） | 无                                     |
| finding     | 事实/结论移交                                       | push         | push（受 wakeRoot/cap）                  | pull（board, audience direct）        | 有                                     |
| directive   | 指令（不可信输入标头不变）                          | push         | push                                     | pull                                  | 有                                     |
| query       | 求答（期望对方回 finding 或 nack）                  | push         | push                                     | **revive**（预算内）→ 失败/超额 pull  | 有                                     |
| nack        | "我不知道/答不了"（廉价回执，P8）                   | push         | push                                     | pull                                  | 无（信息性，丢了不追）                 |
| broadcast   | 看板公告（P3）                                      | —            | —                                        | —                                     | 无（写板失败重试后 abandoned，不回投） |
| result      | 协议保留（child→parent 方向规则保留），工具面不暴露 | —            | —                                        | —                                     | —                                      |
| dead_letter | system→发送者的投递失败审计                         | —            | —                                        | —                                     | 自身不再死信（v1 规则）                |

### 4.2 发送权限与路由规则（任务要求 2）

`authorize()` v2 —— **只保留协议自洽规则，删除全部 relation/canMessage 门控**（P1）：

```ts
export function authorize(input: { kind: MessageKind; from: NodeRef; to: NodeRef; mention?: MentionRoute }): boolean {
  // 1. kind 合法；dead_letter 仅 from==="system"（不变）
  // 2. from === to → false（"两个 agent"：不得自发）
  // 3. broadcast ⟺ to==="board"（双向绑定）；board 的 from ∈ runs ∪ {"root"}，排除 system
  // 4. 直发 kind（progress/finding/directive/query/nack）：from ∈ runs ∪ {"root"}，
  //    to ∈ runs ∪ {"root"}（不得发往 board/system）
  // 5. result：relation === "child"（树方向规则保留，协议保留 kind）
  // 6. mention 路由仅要求 mention.target === to（target 真实性，由 tool 层解析保证）
}
```

删除面：`CanMessage`/`effectiveCanMessage` 类型、`AuthorizationInput.canMessage`、relation 白名单分支、
`AdmissionInput.canMessage`、tool deps 的 `canMessage`、`agent-types.ts` 的 `can_message` 解析（L103-110）与
`AgentTypeConfig.canMessage`。已存在的 agent 类型 markdown 里的 `can_message:` frontmatter 成为被忽略的未知键，无需迁移。

**寻址**：`to` = runId（任意，含嵌套/跨树）｜`"root"`｜`"@label"`（registry 解析，first-wins 不变）｜`"board"`。
v1 mention 的 **root 直属子代限制取消**（`not_root_child` 分支删除）——R1 要求任意 agent 可达；用户侧 @ 自动补全
（`src/mention/autocomplete.ts`，仅列 root children）是独立 UX 面，本方案不动。
runId 从未在树/查询服务出现过（typo 防护）→ admit 抛 `"unknown target"`（地址错误，同 unknown_label 类别，不算拒收）。

**广播不做 tos[]/scope 选择器**【设计补齐】：多目标定向推送 = 发送方自己循环点对点（每次计入自己的 kind 配额，担责）；
匿名扇出（scope/topic）被 P2/P3 的拍板语义（广播恒 O(1) 恒不唤醒）排除，记为非目标/扩展点。

### 4.3 初始定级与降级规则（任务要求 3：push/notify/pull 由什么决定）

`decideInitialLevel`（纯函数，放 `core/message.ts`，输入由 router 组装）：

```
to === "board"                          → pull（恒；kind 必须 broadcast）
progress && to === "root"               → notify-display（kind 固定路由，附 display 语义标记）
targetState(to) === "pending_start"     → push（入队等待 onSnapshot 唤醒，同 v1 P3；TTL 兜底）
targetState(to) === "gone"（终态）:
    kind === "query" && 复活预算 > 0     → revive
    否则                                  → pull（audience = {direct, to, origKind}）
targetState(to) === "running":
    发送方该 kind 配额已满               → pull（发送方原因 → 降到最便宜级，P7）
    nodeInbox(to)（pending+claimed push 数）≥ nodeInboxCap → pull（保护接收方 context，P7）
    to === "root" && !wakeRoot           → notify（被动 context：用户偏好"别打断"）
    否则                                  → push
```

**投递期降级**（mailbox，只降不升，I-L）：

| 触发                                                           | 动作                                                                                                                                                                    |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| push 的 retryable 重试耗尽（steer_timeout/失败 × maxAttempts） | level → notify，attempts 重置为 0，回 pending                                                                                                                           |
| notify 的重试耗尽                                              | level → pull，attempts 重置                                                                                                                                             |
| 任意 level TTL 到期（P1）                                      | level → pull（**不再直接 abandoned**——内容进看板保住）；progress 例外：仍 consumed/dropped（易失语义不变）                                                              |
| revive 的 spawn 失败（admission 拒/超时）                      | level → pull（attempts=1 计入）                                                                                                                                         |
| pull 的 boardWrite 重试耗尽 / appendEntry 持续抛错             | 终态：finding/directive/query → dead_letter（reason `board_failed`）；nack/broadcast → abandoned                                                                        |
| target 变 gone（P2，push/notify 级）                           | level → pull（query 若复活预算尚有余量且此刻才首次判定 revive，可升为 revive——唯一例外：`pull→revive` 仅在"降级时尚未尝试过 revive 且 kind=query"时允许，其余严格单调） |

**配额与预算（v2 语义 = push/notify 预算，而非总量上限）**：

- per-sender per-kind（计数维度不变：per 发送者 run、跨 generation）：`maxPerRun`(progress,20) / `findingQuota`(10) /
  `directiveQuota`(5) / `queryQuota`(5)【新】 / `nackQuota`(10)【新】。只统计定级为 push/notify 的 admission；
  降级为 pull 的不占配额（同 v1 rejected 不占的口径）。
- **broadcast 不设配额**【设计补齐】：pull 无接收方成本，由 boardCap 环界存储。
- per-node 接收预算（P2"唤醒计入接收方预算"的落地）：`nodeMinIntervalS`（per 目标 push 最小间隔，泛化 v1 rootMinIntervalS，
  默认 10）与 `nodeInboxCap`（per 目标 pending+claimed push 上限，泛化 v1 rootInboxCap，默认 12）。root 与 run 一视同仁。
- `reviveQuota`（per 目标 run 复活次数上限，默认 3，栈生命周期内纯内存；防复活风暴——P5 未拍板项的补齐）。
- `senderTotalCap`（per 发送者全 kind 累计 admission 上限，默认 100）——**flood guard，全方案唯一允许抛错的 admission 失败**
  （`{ok:false,status:"flood_guard"}`；理由见 §5-D6：pull 级不受 kind 配额约束，无此闸则 appendEntry 可被单发送者无限灌）。

### 4.4 唤醒规则（任务要求 4）

1. **谁会被唤醒**：只有定级为 push/revive 的**点对点**消息（I-W 的正面表述）。
   - 运行中 run：`steer` 保证在下一次 LLM 调用前送达（本轮循环内可见 = 唤醒）；
   - root：`sendMessage(triggerTurn:true)` 触发新 turn；`wakeRoot=false`（设置键，默认 true）时 root 的 push 降为 notify，
     root 永不被 fabric 强制唤醒；
   - `pending_start` 目标：消息等待（engine pending），onSnapshot(running) 后 pump 投递——启动即唤醒。
2. **什么不唤醒**：notify（被动追加）、pull/看板、broadcast、progress→root 的 display 行。用户在 root 聊天里看到 display 行
   不构成唤醒（无人消耗模型预算）。
3. **复活**（P4/P5）：仅 kind=query、点对点、目标终态且 `reviveQuota` 未耗尽。机制 = 异步
   `spawn({ type: diag.agentType, resumeFrom: 目标 runId, parentRunId: 原父（树边保留，不升为 root 子代）, prompt: query 文本 + 看板待办摘要 })`
   （type/parent 取自 `QueryService.get(runId).diag.agentType` 与 `tree.edges`；resumeFrom 语义沿用 v1 mention 的
   `spawn({resumeFrom})` 路径）。**spawn 不 await 于工具调用**（fire in mailbox dispatch，boundedSend 超时兜底）——修复 v1 mention
   resume 的 await 阻塞点。复活产物是新 runId（续写原 session 文件，沿用既有 resume 语义）；@label 若存在由 onLabel(reassign) 跟随。
   复活的 resume prompt 附带 `board.pendingFor(runId)` 摘要（≤3 条 × 500 chars，最新优先）——看板对已死/复活 agent 的投递闭环。
4. **接收方回应契约**：收到 query 的 agent 用 `finding`（答）或 `nack`（答不了）点对点回复发送方（写进两个工具的 description）。

### 4.5 看板（任务要求 5）

- **存储**：看板不是独立存储——**看板记录就是 DeliveryEngine 里的 FabricRecord**（outbox customType `"subagent:fabric"`，
  appendEntry 写、prefetch 读回，P6 的字面落地）。`FabricBoard`（新，`src/fabric/board.ts`）是 engine 之上的**查询视图**：
  维护一个容量环索引（`boardCap`，默认 200，FIFO 淘汰最旧**索引项**——session 条目本身保留为审计，只是不再被视图列出），
  hydrate 自 prefetched 记录（to==="board" 或带 audience 的 pull 记录，按 createdAt 取环内最新 N 条）。
- **有效范围**：当前主 session（条目随主会话文件存在；新栈从同一文件重建）。跨会话/跨 /resume 明确不做（P6）。
- **写入面**：`message_agent(to:"board", kind:"broadcast", text)`（任何 run、root 皆可写——P6 未拍板项按 R3 倾向定为全可写）；
  降级直发自动写入（audience direct）。写板成功 = 该记录 delivered（level=pull）。
- **读取面**：新工具 `board`（见 4.7），注入所有子 run + 注册给 root。
- **可见性**：broadcast 与 audience=direct-root 的记录投递时附 display 行（root 聊天可见一行）；run→run 的降级直发
  不出 display 行（避免噪音）。
- **不设 TTL**【设计补齐】：session 生命周期有限、环已界内存；TTL 记为扩展点。

## 5. 关键决策（含取舍与理由）

- **D1 权限全通（P1 拍板）**：代价是失去拓扑级滥用约束；缓解 = per-sender 配额（push/notify 预算）+ per-node
  interval/cap（接收方预算）+ flood guard + 既有的"不可信输入"标头（`formatMessage` 保留）。拒绝的备选：默认全通+deny 列表
  ——拍板明确不要折中，deny 列表是 can_message 的复活。
- **D2 广播 = 看板单记录（P2/P3 拍板）**：显式多目标（tos[]）不做——扇出唤醒必须逐条担责（sender 循环点对点），
  匿名扇出的成本与责任都无法归属。对比"每接收者一条 record"：会产生 N 份状态机记录/N 次 throttle 判定，违反 O(1)。
- **D3 分级按接收方状态（P4 拍板），level 是记录字段而非发送方标记**：发送方在工具结果里**看到** level（信息），
  但**不能请求** level（urgent 提案已否决）。降级只由接收方侧预算触发（发送方配额触发的是 pull——发送方预算也是
  "对系统的责任"，落到最便宜级合理）。
- **D4 notify 的双实现**（root=被动 context，run=sendCustomMessage no-trigger）：pi 无子会话 display 面（print 模式无人观看），
  被动 context 是子 run 唯一的"不强制但可及"档。代价：notify 仍会进 context（若接收方再起一轮）——所以收件箱满的降级
  直接去 pull（不进 context），notify 只用于 wakeRoot-off 偏好与 push 重试耗尽（此时内容已等了 maxAttempts×backoff，
  被动可见优于完全不可见）。
- **D5 看板 = engine 记录之上的视图，非第二存储**：避免同一条消息双写（engine outbox + board 条目）；
  读回复用既有 prefetch（`buildFabric` 已扫全量 fabric 条目，零新增扫描）。代价：看板容量受 engine 内存影响
  （engine 本就全量驻留，v1 现状如此）；环只界"可见窗口"。
- **D6 flood guard 是唯一拒绝（对 P7 的诚实例外）**：pull 级不受 kind 配额约束（否则广播无法豁免），若无总量闸，
  单个失控发送者可无限 appendEntry 灌会话文件——"永不拒收"保护的是合法发送者不被静默丢消息，不保护失控进程。
  返回结构化 flood_guard 让模型可自察。若评审不接受，备选是 pull 也计 per-sender boardQuota 并降级为"计入 seq 但不落看板"
  ——更复杂且语义更差，不推荐。
- **D7 复活的预算与血统**：reviveQuota 防复活风暴（P5 未拍板项）；parentRunId 取原树边（对比 v1 mention resume 挂 root——
  那是用户语义，agent 间复活应保血统，否则嵌套 agent 被复活后失去上下文位置）。
- **D8 死信收缩为"看板写失败"的审计**：降级链保证内容最终要么送达某级、要么在看板——dead_letter 从"投递失败的通用义务"
  收缩为 board_failed 终因（target_gone/ttl_expired/attempts_exhausted 保留为 deadLetter.reason 枚举值是为了
  旧记录兼容与审计连续性）。I-F11 义务函数改为：`kind ∈ {finding, directive, query} ∧ state ∈ {dropped, abandoned}
∧ deadLetter === undefined` ⇔ 义务未履行（枚举里 query 加入）。
- **D9 TTL 到期降级 pull 而非 abandon**：v1 的 P1→abandoned+死信在"永不丢内容"目标下过激——写板几乎不会失败
  （appendEntry 内存+顺序写），把 TTL 到期当作"过时但仍有价值"落板更符合看板语义。progress 例外（易失）。
- **D10 root 也获得 message_agent/board**：R1 的"任意两个 agent"包含 root 会话（成本：post-guard 注册 + from="root"
  的 generation 恒 1）。收益：root 可广播（预算告警类公告）与 query 复活子 agent——对称且补齐 v1 缺口。

### 6.3 风险与提示

1. **pi sendCustomMessage(triggerTurn:false) 在 print 模式子会话的行为**需实现时实测确认（d.ts 声明 not-streaming+no-trigger
   只追加 state/session；若子会话有边界行为，notifyRun 降级为直接写 session 文件条目）。
2. **steer 落在目标 loop 尾部**（run 刚好 settle 的竞态）：steer_timeout→重试→耗尽→notify（被动追加，随 session 文件
   留给未来 resume）→TTL→pull——链条闭合，无内容丢失。
3. **passive(notify) 的 context 增长**：仅 wakeRoot-off 与重试耗尽路径使用，量被发送方配额约束；文档在 settings 描述中写明。
4. **flood guard 是全方案唯一"发送失败"**：评审重点确认（§5-D6）；数值 100 可调。
5. **复活预算跨 /reload 重置**（纯内存）：tombstone 在 reconcileTtlMs 后过期，天然有界；文档明示"栈内预算"语义。
6. **性能**：admit 恒 O(1)（decideInitialLevel 只查预算表与 nodeInbox 计数）；boardWrite O(1)；无任何 per-receiver 扇出。
7. 与 `docs/dev/subagent-push/subagent-push-plan.md` 的关系：v2 文档落地后应在该目录补 v6 变更说明（本方案的 §4.3/§4.4
   替代其 §8.2 admission 序的③④步语义；I-F12 泛化为 per-node）。
