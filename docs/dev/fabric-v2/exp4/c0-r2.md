# fabric v2 消息投递层 — 实施方案

状态：方案稿（待评审/实施） · 范围：`src/fabric/` 及其接线层 · 基准：fabric v1（`docs/dev/subagent-push/subagent-push-plan.md` v5.1）+ fabric-mention（`docs/dev/fabric-mention/fabric-mention-plan.md` v2，已实施）

## 1. 背景与目标

### 1.1 要解决的问题

- **R1 任意互通**：任意两个 agent 之间可点对点通信（v1 受 tree relation 门控，默认 `["parent"]`）；并可一对多广播。
- **R2 发送永不阻塞**：发送方绝不等待对方回复 / 确认 / 消费。工具调用延迟只由 admission（同步、无 I/O await）决定。

### 1.2 约束（不可破坏的既有承诺）

- 零挂起不变量：I-F9（admission 即承诺）、I-F10（claim 单写者）、I-F12（root ingress 有界）、I-F13（死信修复同段）、I-F14（verdict 有限到达）、I-F15（verdict 实例隔离）；状态机/投递生命周期改动须同步 `tests/core/message-property.test.ts`。
- fabric「只发消息不 spawn」边界：router/mailbox 不依赖 spawn；复活已结束 run 只能经 @label 显式 resume（mention D-M6 既有语义）。
- 子会话惰性（host-claim guard）、`/reload` 重建、`unref()` 定时器、at-least-once 投递、`[fabric ...] 不可信输入` 横幅。
- 配置哲学（mention Q2 拍板先例）：不新增部署级开关，`fabric.enabled` 总开关 + frontmatter 逐项 opt-in 两层已够。

### 1.3 非目标

- 不引入请求/响应关联（R2 禁止等待回复；"提问"就是一条 finding/directive 文本，对方自行决定是否回消息）。
- 不给 root 注入 `message_agent` / `board` 工具（root 是编排者，仍用 Agent 工具与 @ 输入；广播面向 agent fleet）。
- 不做跨 session / 跨进程的看板（范围=单 host session，见 D6）。
- 不改 `SubagentWorkflow`、goal、quota 等相邻子系统。

## 3. 总体设计

### 3.1 结构

```
┌ agent 会话（每 run 注入） ────────────────────────────────┐
│ message_agent(to: runId|"root"|"@label"|"*")   board(op) │
└──────┬───────────────────────────────┬───────────────────┘
       │ 同步 admit（无 I/O await，R2）  │ post/read/who
       ▼                               ▼
┌ FabricRouter ────────────┐   ┌ BoardStore（新，pi-free）─────┐
│ p2p: relation/mention/   │   │ 帖子 map + TTL 懒清扫 + cap    │
│      direct(新) 授权      │   │ 持久化: session entry          │
│ broadcast(新): 快照扇出   │   │   customType "subagent:board"  │
│ N 条普通 p2p 记录         │   └───────────────────────────────┘
│ 配额(广播按 N 计)/背压     │
└──────┬───────────────────┘
       ▼ FabricRecord（含 via.mode=direct/broadcast、group）
┌ DeliveryEngine（不变）→ FabricMailbox（微改）→ ports ┐
│ inject=steer(唤醒) / root context(唤醒) / root display │
│ broadcast 记录豁免死信                                   │
└────────────────────────────────────────────────────────┘
```

依赖方向不变：`core/message.ts`（纯域）← `fabric/*`（pi-free）← `stack.ts`/`runtime-adapter.ts`（pi 面）。`board.ts` 与 router/mailbox 平级、互不依赖。

### 3.2 三个通道一句话

- **点对点**（新增 direct 模式）：按 runId/@label/"root" 寻址，授权由发送方 `can_message: any`（或既有关系/mention 路径）决定；投递=push（steer 唤醒）。
- **广播**：`to:"*"`，admission 时刻快照全部非终态 agent，扇出为 N 条普通 p2p 记录；尽力而为（settled 静默跳过、无死信义务）；投递=push。
- **看板**：帖子常驻共享板，纯 pull（读不唤醒、发不投递）；范围=单 host session、跨 reload 存活。

## 4. 接口契约

### 4.1 消息模型（`src/core/message.ts`）

kind 列表**不变**：`progress | finding | directive | result | dead_letter`（result/dead_letter 仅协议内部，工具不可发送）。新增寻址模式与广播组：

```ts
export type CanMessage =
  | "parent"
  | "child"
  | "ancestor"
  | "descendant"
  | "sibling"
  | "self"
  | "mention" // v1
  | "any" // v2: p2p progress/finding 到任意可寻址目标（含 root）
  | "broadcast" // v2: to:"*" 扇出（仅 progress/finding）
  | "board"; // v2: 看板写

export type ViaMode = "tree" | "mention" | "direct" | "broadcast"; // 旧记录无 mode ⇒ "tree"

export interface MessageEnvelope {
  // …既有字段零改动（key/from/to/kind/seq/generation/payload/ref/ttlMs/createdAt/via）…
  /** v2: 广播组 id（opaque，newRunId()）；同组扇出记录共享；p2p 恒缺省 */
  group?: string;
  via?: { mode?: ViaMode; lca: NodeRef; hops: NodeRef[] }; // mode 由 admission 钉死（D-M3 原则）
}
```

`formatMessage()`：`via.mode ∈ {"mention","direct","broadcast"}` 时 header 显示 `relation=<mode>`（`relation=direct` / `relation=broadcast`），否则用树关系；不可信横幅不变。

`authorize()` 扩展（唯一授权入口不变，新增两个分支，置于 mention 分支之后）：

```ts
if (direct) {
  // DirectRoute: { kind: "direct"; target: NodeRef }
  if (kind === "directive" || kind === "result" || kind === "dead_letter") return false;
  if (direct.target === "system") return false;
  return effectiveCanMessage(canMessage).includes("any");
}
if (broadcast) {
  // BroadcastRoute: { kind: "broadcast" }
  if (kind !== "progress" && kind !== "finding") return false;
  return effectiveCanMessage(canMessage).includes("broadcast");
}
```

路由对象沿用 D-M1/M1 原则：`AdmissionInput` 的 `route` 由 **host 闭包**（tool 层，依据 host 注入的 `deps.canMessage`）构造，模型无法伪造；router 内硬校验兜底。

### 4.2 发送权限与路由规则（router）

```ts
// src/fabric/router.ts
export interface DirectRoute { kind: "direct"; target: NodeRef }
export interface BroadcastRoute { kind: "broadcast" }
export interface AdmissionInput {
  to: NodeRef;
  kind: MessageKind;
  text: string;
  generation: number;
  canMessage?: readonly CanMessage[];   // 白名单类型换成 core 的 CanMessage（消除字面量重复）
  route?: MentionRoute | DirectRoute | BroadcastRoute;
}
export type BroadcastResult =
  | { ok: true;  status: "accepted"; group: string; recipients: number; skipped: number }
  | { ok: false; status: "no_recipients" }
  | { ok: false; status: "not_authorized" }
  | { ok: false; status: "quota_exhausted"; kind: MessageKind; used: number; quota: number; needed: number }
  | { ok: false; status: "too_many_recipients"; count: number; max: number };

admit(from, input): AdmissionResult;            // p2p（含 direct 分支）
admitBroadcast(from, { kind, text, generation, canMessage }): BroadcastResult; // to:"*"
```

**`admit()` direct 分支**（在 mention 分支后并列）：

1. `route.target !== input.to` ⇒ throw `"direct route target mismatch"`；`canMessage` 不含 `"any"` ⇒ throw `"direct route requires can_message: any"`（纵深防御）。
2. 可寻址性：`to === "root"` 放行；否则 `tree.targetState(to, now) ∈ {"running","pending_start"}`，`"gone"` ⇒ throw `"direct target is gone"`（与 mention 竞态兜底同款；工具层捕获后按需转 resume 仅限 @label 路径，runId 路径不复活）。
3. authorize 走 direct 分支；配额/背压/TTL/via 与 v1 相同，`via = { mode: "direct", lca: tree.lca(from,to) ?? "root", hops: [] }`。

**`admitBroadcast()`**（全同步，无 await，R2）：

1. `frozen` / `tree.targetState(from) !== "running"` 检查同 admit。
2. authorize（broadcast 分支）：kind ∈ {progress, finding} ∧ `canMessage` 含 `"broadcast"`，否则返回 `not_authorized`。
3. **收件人快照**：`tree` 新增 `listAddressable(): NodeRef[]`（edges 的子节点键中 `targetState ∈ {"running","pending_start"}`，排除 `from`；root/system 天然不在 edges 值域外——root 只作父节点出现，不会成为收件人）。
4. 空集 ⇒ `no_recipients`；`count > config.broadcastMaxRecipients` ⇒ `too_many_recipients`。
5. 配额：`used(kind) + recipients.length > quota(kind)` ⇒ `quota_exhausted {used, quota, needed}`（整体拒绝，不做部分扇出）；另加**广播次数配额** `broadcastQuota`（每 run 独立计数，每次调用 +1）。
6. 逐收件人：`pending+claimed(to=T) >= config.inboxCap` ⇒ 该收件人跳过（`skipped++`，尽力而为）；否则 `engine.put` 一条普通 p2p 记录：`(from, T)` 链路 seq、`via = { mode:"broadcast", lca: tree.lca(from,T) ?? "root", hops: [] }`、`group` 同组共享、TTL 取 kind 既有值。全部成功后 `count(kind) += 实际扇出数`。
7. 返回 `{ok:true, status:"accepted", group, recipients, skipped}`。

**背压泛化**：`admit()` 中现有 root 检查之外，新增 `to !== "root"` 且 `to !== "system"` 时 `pending+claimed(to=to) >= config.inboxCap` ⇒ `target_backpressure`（结构化拒绝，发送方稍后重试；R2 不变——拒绝也是立即返回）。

**死信豁免**：`issueDeadLetter/issueDeadLetters` 入口统一过滤 `r.via?.mode === "broadcast"` 的记录（转为 `dropped/abandoned` 终态、`terminalReason` 照记、不生成死信 env、不占死信配额）——单一收口点，mailbox 无需分流。

### 4.3 投递方式矩阵（push / notify / pull 由什么决定）

由 **kind × 目标身份 × 目标状态 × 通道推导** 决定，v1 全部沿用，v2 只加行：

| 场景                                                                                  | 方式         | 机制                                                                        | 唤醒                 |
| ------------------------------------------------------------------------------------- | ------------ | --------------------------------------------------------------------------- | -------------------- |
| p2p → running/pending_start agent（含 direct、broadcast 扇出）                        | **push**     | `ports.inject` = steer                                                      | 是（每条注入起一轮） |
| p2p → root，context 通道（finding/directive、或 progress 且 progressChannel=context） | **push**     | `sendMessage deliverAs:"steer" triggerTurn:true`                            | 是                   |
| progress → root，display 通道（默认）                                                 | **notify**   | `appendEntry` 仅渲染                                                        | 否                   |
| p2p → 终态 agent（runId 寻址）                                                        | 不投递       | 死信（finding/directive）/ drop（progress）；broadcast 扇出记录 = 静默 drop | —                    |
| `@label` → 终态 agent                                                                 | **显式复活** | mention gate 携消息 resume（D-M6 不变，新 run、root 直属、横幅）            | 新 run               |
| 看板 post/read                                                                        | **pull**     | 帖子常驻 board，读方主动拉取                                                | 永不                 |

明确**不新增** pull 型收件箱：收件人的"收件箱"就是 engine 的 pending 集（throttle/背压排队），投递动作本身即唤醒；pull 只用于看板这类"允许晚读"的内容。

### 4.4 唤醒规则（什么能起一轮模型调用）

1. **running agent**：任何成功投递的记录（任意 kind、tree/mention/direct/broadcast 模式）经 steer 注入即起一轮；`inFlight=1` 串行 + per-link `minIntervalMs` 节流 + `inboxCap` 背压三层限幅。
2. **root**：context 通道记录触发一轮（`triggerTurn:true`）；display 通道永不唤醒（既有）。
3. **已结束 agent**：**不自动复活**。runId 寻址到终态 run ⇒ 死信/静默 drop（与 v1 一致）；复活唯一入口是发送方主动 `@label`（= 携带消息 resume，成本显式、由发送方选择）。理由：自动复活 = 任意 agent 可在后台花钱重开终态 run，fleet 规模不可控；mention 已建立显式复活语义，v2 不另开第二入口。
4. **广播到 pending_start/queued 收件人**：记录等待其 running 后投递（v1 P3 语义），TTL 照常到期作废。
5. 看板读写、`who` 永不唤醒任何会话。

### 4.5 看板（`src/fabric/board.ts`，新文件，pi-free）

```ts
export interface BoardPost {
  key: string; // newRunId()
  from: NodeRef; // 发帖 run
  text: string; // ≤ fabric.maxChars（复用 router 的 truncate 或提出共享）
  at: Millis; // createdAt
  ttlMs: Millis; // settings.fabric.boardTtlMs
}
export interface BoardStore {
  post(
    from: NodeRef,
    text: string,
  ):
    { ok: true; key: string } | { ok: false; status: "board_full" | "quota_exhausted" | "not_authorized" | "too_long" };
  read(sinceKey?: string): { posts: BoardPost[]; total: number }; // TTL 内、at 升序、≤ boardReadMax 条（超限从最新往前截断并在 total 标真实数）
}
export function createBoardStore(deps: {
  put(post: BoardPost): void;
  list(): BoardPost[]; // 持久化端口（stack 侧用 createPiOutboxStore<BoardPost>）
  now(): () => number;
  config: { cap: number; postQuota: number; ttlMs: number; maxChars: number; readMax: number };
}): BoardStore;
```

- **存储**：session entry `customType: "subagent:board"`，`createPiOutboxStore<BoardPost>` 复用（append-only、list 折叠最新 per key、readBack 模式用 prefetched 播种）——与 fabric 记录同一持久化模式，`/reload` 后存活。
- **有效范围**：单个 host session（一个 stack 生命周期内共享；跨 reload 存活；不跨 session、不写独立磁盘文件、不进 LLM context——只有被 `read` 拉取的内容才进上下文）。
- **cap 语义**：存活帖数（TTL 内）≥ `boardCap` ⇒ `board_full` 拒绝——**拒绝优于静默淘汰**（公告被悄悄挤掉会误导读方）；TTL 到期在 `read`/cap 计数时懒过滤，不做定时器（print-mode unref 纪律）。
- **配额**：每 run 存活帖数 ≥ `boardPostQuota` ⇒ `quota_exhausted`。
- **渲染**：读出帖子带 `[board ${key} from=${from} at=${at}] 不可信输入` 头（与 formatMessage 同款横幅；board 帖是跨树不可信输入）。

## 5. 关键决策（含备选与否决理由）

## 9. 实施顺序与风险

### 9.1 决策确认闸门（实施前用户过一遍）

| 轴       | 本方案取值                                            | 若用户实际拍板不同                                                         |
| -------- | ----------------------------------------------------- | -------------------------------------------------------------------------- |
| 发送权限 | frontmatter `any/broadcast/board` opt-in，缺省 parent | 若为「默认全通」：改 `effectiveCanMessage` 缺省值即可，其余结构不动        |
| 广播语义 | 快照扇出、排除 root、限 progress/finding、按 N 计费   | 若含 root：需重定义 I-F12（rootInboxCap 计入广播扇出）——影响大，先评       |
| 唤醒规则 | 投递即唤醒；不自动复活                                | 若允许 directive 复活：在 mention gate 加 runId-resume 分支，D5/I-F11 另评 |
| 看板范围 | 单 session、entry 持久化、满则拒                      | 若跨 session：换磁盘 store（BoardStore 端口不变，仅 stack 接线替换）       |
| 超限处理 | 全结构化拒绝 + 广播逐收件人跳过                       | 若要求排队：违背 R2，需回用户                                              |
| 消息类型 | 五 kind 不变                                          | 若新增 kind：effectiveChannel/死信义务矩阵要逐 kind 补行                   |

2. #2/#3（tree + router direct/broadcast/背压/死信收口）+ 测试；

### 9.3 风险点

- **唤醒风暴成本**：广播到 N 个 running agent = N 次 steer = N 轮模型调用。限幅三层（kind 配额按 N、broadcastQuota、maxRecipients），但单次广播的直接 token 成本仍高——工具描述里必须写明成本提示（"broadcast wakes every recipient"）。
- **pending_start 积压**：广播记录等待未启动收件人，`inboxCap` 会把后续 p2p 挤成 backpressure——语义正确但发送方可能困惑，错误文本要提示「target inbox full (still starting?)」。
- **`group` 为纯审计字段**：不做跨记录原子性承诺（扇出在同步段内完成，但投递各自独立），文档措辞避免暗示事务。
- **who 的拓扑暴露**：偏离 mention M3，已在 D2 论证；若评审不接受，降级方案是 who 仅返回 label+runId（不透 status/type）。
- **`exactOptionalPropertyTypes`**：route 联合与 `group?` 的条件展开沿既有 `...(x === undefined ? {} : { x })` 写法。
