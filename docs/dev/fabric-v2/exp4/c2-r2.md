## 1. 背景与目标

### 1.1 要解决的问题

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播。
- **R2**：发送永不阻塞——发送方绝不等待对方回复（不能保证对方知道答案、也不能保证对方有能力回复）。

v1 fabric（`src/fabric/`，设计文档 `docs/dev/subagent-push/subagent-push-plan.md` v5.1）是树形路由 + 白名单授权 + 死信系统的 MVP：默认 `can_message: ["parent"]`，按 kind 分级授权，配额用尽即拒绝（`quota_exhausted` / `target_backpressure`），只能给 running 目标 push、给 root 有限推送。

### 1.2 约束条件

- 必须复用现有四层骨架：`DeliveryEngine`（`src/delivery/engine.ts`）六态状态机、`FabricTree` 目标状态、`FabricThrottle` 节流、`FabricMailbox` 异步泵——v2 改造它们的分支语义，不推翻分层。
- 持久化沿用会话条目（`pi.appendEntry` + readBack 重建）模式；**跨会话/跨进程明确不做**【拍板】，持久知识归 memory 子系统。
- 发送方工具面 `message_agent` 已注入所有子 agent（`src/service/runtime-adapter.ts:388`），v2 保持单一发送工具，新增一个拉取工具。
- pi 加载扩展为运行时 TypeScript（jiti），`/reload` 不清模块缓存：所有可变态仍必须活在 stack 构建的实例里，禁止模块级可变状态。
- `unref()` 定时器、`pi -p` 兼容等既有纪律不变。

### 1.3 已拍板的核心原则（不可违背）

| #   | 原则                                                                                                        |
| --- | ----------------------------------------------------------------------------------------------------------- |
| P1  | **删除 `can_message` 白名单**，不限制"谁能给谁发"；`authorize()` 只保留方向性协议规则（如 result 必须上行） |
| P2  | **`nack`（"我不知道/答不了"）为一等 kind**——R2 的直接后果：不能等回复，nack 让发送方尽早转为自查            |
| P3  | **广播 = 一条看板记录**（`to:"board"`），恒 O(1)，绝不向 N 个接收者逐个 push                                |
| P4  | **投递级别由接收方状态决定**，不按 kind、不设 `urgent`/优先级标记（发送方可置 urgent 的提案已被否决）       |
| P5  | **不变量 I-W：广播恒不唤醒任何 agent**；唤醒必须是具名、定向、计入接收方预算的动作                          |
| P6  | 终态 agent **仅点对点 `query` 类消息可复活**（resume 续会话）                                               |
| P7  | 看板**只在当前主 session 内有效**，`appendEntry` 写入读回                                                   |
| P8  | **超限降级、永不拒收**：push → notify → pull 逐级降级，任何发送不因容量/配额返回失败                        |

### 3.2 一条消息的生命周期（统一降级律）

```
message_agent(to, kind, text)
   │  同步：admit()——协议检查 + 配额判定（超限→degraded 注记，不拒绝）+ 入 engine（state=pending）
   │  返回 { ok:true, delivery:<计划级>, degraded? }        ← R2：零 await，工具立即返回
   ▼
mailbox.pump()（既有异步泵，onChanged/onSnapshot/定时器驱动）
   │ 按 to 分派，deliveryPlan(record, targetState) 决定实际动作：
   │
   ├─ to:"board"                    → ports.toBoard()            → state=boarded（广播，恒 pull【拍板】）
   ├─ target running（非 root）      → ports.inject()（steer 唤醒） → state=delivered
   ├─ target root                   → push：sendMessage{triggerTurn:true}（须 wakeRoot && inbox<cap）
   │                                  否则 notify：sendMessage{triggerTurn:false} / display appendEntry
   ├─ target pending_start          → 等待（不动作，running 事件再泵）
   ├─ target gone && kind=query     → ports.revive()（spawn resume，复活）→ delivered/degraded
   └─ target gone && 其他 kind       → ports.toBoard()（dead-drop）      → state=boarded
   │
   ├─ push/notify 失败且可重试        → pending（退避重试，v1 语义）
   └─ TTL 到期 / 重试耗尽 / 配额超限  → ports.toBoard()（pull 兜底）     → state=boarded   ← 永不拒收
```

接收侧：

- running/root agent：push/notify 直达（steer 文本 / 上下文条目 / display 条目）。
- 任意 agent：随时调 `fabric_inbox` 拉取未读广播 + 自己的 dead-drop（pull）。
- 终态 agent 被 query 复活时，复活包装 prompt 提示其先调 `fabric_inbox`。

## 4. 接口契约

### 4.1 消息模型（`src/core/message.ts`）

**NodeRef** 扩展：

```ts
export type NodeRef = RunId | "root" | "system" | "board"; // "board" = 广播伪节点
```

**MessageKind** v2：

```ts
export type MessageKind =
  | "progress" // 状态汇报，不期待动作
  | "finding" // 信息性结论
  | "directive" // 给具名接收方的指令（不能复活终态方）
  | "query" // 点对点提问：唯一可复活终态 agent 的 kind【拍板 P6】
  | "nack" // "我不知道/答不了"：一等 kind，由接收方 agent 语义性发送【拍板 P2】
  | "result" // 协议 kind：仅 child→parent，不可经 message_agent 发送（v1 不变）
  | "dead_letter"; // @deprecated 遗留：v2 停止签发，仅为旧会话条目 hydrate/渲染保留
```

**MessageEnvelope / FabricRecord** 增量（其余字段不变）：

```ts
export interface MessageEnvelope {
```

### 4.2 发送权限与路由规则

**`authorize()` v2**（`src/core/message.ts`，重写）——只保留协议方向规则【拍板 P1】：

```ts
export function authorize({
  kind,
  relation,
  from,
  to,
}: {
  kind: MessageKind;
  relation: MessageRelation;
  from: NodeRef;
  to: NodeRef;
}): boolean {
  if (kind === "dead_letter") return false; // v2 不再签发（system 内部路径一并移除）
  if (from === to) return false; // 自环无意义
  if (kind === "result") return relation === "child"; // 协议：结果只能上行
  if (to === "board") return kind === "progress" || kind === "finding";
  // query/directive/nack 是具名定向动作；广播只允许无指向的 progress/finding【本方案】
  return true; // 其余任意 from→to 放行（R1）
}
```

删除项：`CanMessage`、`effectiveCanMessage()`、`AuthorizationInput.canMessage`、`MentionRoute` 作为授权依据（`MentionRoute` 类型保留，仅供 `via.mode="mention"` 渲染与 label 寻址）。

**路由规则**（`FabricRouter.admit()`）：

1. 发送者检查（协议完整性，保留 v1）：`from` 必须是运行中的 run（`tree.targetState(from) === "running"`）或 root/system；`generation` 必须可解析。违规仍抛错（这是调用方 bug，不是容量问题）。
2. `to` 解析：runId 直用；`"root"`/`"board"` 伪节点；`@label` 由 `MentionRegistry.resolve()` 换成 runId（label 不存在 → `{ok:false, status:"unknown_label"}`——这是寻址错误，不属于"拒收"）。v1 的 `not_root_child` 限制取消：任意已注册 label 可寻址【本方案】。
3. `authorize()` 协议检查。
4. 配额判定（见 §4.6）：超限**不拒绝**，置 `degraded.reason="quota_exhausted"`，计划级直接降为 pull。
5. 入队 `engine.put(state=pending)`，同步返回。

**AdmissionResult v2**：

```ts
export type AdmissionResult =
  | {
      ok: true;
      status: "accepted";
      key: MessageKey;
      seq: number;
      delivery: "push" | "notify" | "pull" | "revive"; // 计划级：按 admit 时刻的 target 状态推导
      degraded?: FabricRecord["degraded"];
    }
  | { ok: false; status: "unknown_label"; label: string }
  | { ok: false; status: "invalid_address" | "protocol_violation"; message: string };
// 永不出现容量类 ok:false —— v1 的 quota_exhausted/target_backpressure 拒绝形态废除【拍板 P8】
```

### 4.3 投递方式：push / notify / pull / revive 由什么决定

**决策规则 = 接收方地址 × 接收方状态（× root 专属开关），与 kind 无关、无发送方优先级标记【拍板 P4】**。纯函数 `deliveryPlan` 放 `src/core/message.ts`（可单测）：

```ts
export type DeliveryMode = "push" | "notify" | "pull" | "revive";
export function deliveryPlan(to: NodeRef, targetState: TreeTargetState): DeliveryMode {
  if (to === "board") return "pull"; // 广播恒 pull，O(1)【拍板 P3】
  if (to === "root") return "push"; // 实际 push/notify 在投递瞬间由 §4.3.1 决定
  if (targetState === "running" || targetState === "pending_start") return "push";
  return to !== undefined && /* targetState==="gone" */ true ? "pull" : "pull"; // 见下——query 的 revive 判定在 pump 层
}
// query×gone → revive 的完整判定放 mailbox.pump（需要 kind+targetState 联合）：
// planDispatch(record, targetState): to==="board"→pull; running→push; root→push|notify(§4.3.1);
//                                   gone&&kind==="query"→revive; gone→pull(dead-drop); pending_start→wait
```

**4.3.1 root 的 push/notify 瞬时判定**（投递时刻，非 admit 时刻）：

| 条件                                                                                       | 级别       | 载体                                                                                                    |
| ------------------------------------------------------------------------------------------ | ---------- | ------------------------------------------------------------------------------------------------------- |
| `channel==="context"` && `fabric.wakeRoot` && `rootInbox() < rootInboxCap` && 节流窗口已过 | **push**   | `pi.sendMessage({deliverAs:"steer", triggerTurn:true})`（v1 `sendRootContext` 不变）                    |
| context 消息但 `wakeRoot=false` 或 `rootInbox≥cap`                                         | **notify** | `pi.sendMessage({deliverAs:"steer", triggerTurn:false})`——进上下文、不主动起轮；root 下轮自然交互时可见 |
| `channel==="display"`（progress 且 `progressChannel="display"` 且可渲染）                  | **notify** | `appendEntry` display（v1 `sendRootDisplay` 不变，本就不触发轮）                                        |

- `rootInboxCap` 语义从 v1 的"准入拒绝阈值"改为**唤醒通道容量**：cap 内的消息才有资格 triggerTurn；超出者降级 notify。反压保留（唤醒频率有界），拒收消失【本方案，落实 P8】。
- `rootMinIntervalMs`/`minIntervalMs` 节流照旧只延迟、不降级（窗口过后重新按上表判定级别）。

**4.3.2 终态目标**：`kind==="query"` → **revive**（唯一复活路径【拍板 P6】）；其余 kind → **pull**（dead-drop 入板）。`pending_start` 沿用 v1：不动作，等 `running` 事件再泵。

**4.3.3 广播**：恒 pull、永不 fan-out、永不唤醒【拍板 P3/P5】。接收方经 `fabric_inbox` 主动拉取。

### 4.4 接收方唤醒规则

| 接收方状态       | 消息形态                        | 唤醒？              | 机制                                                                                                                                                                         |
| ---------------- | ------------------------------- | ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| running 子 agent | 点对点任意 kind                 | **是**              | `ports.inject` → `runner.steer`（steer 天然并入下一轮模型调用；若目标正处 turn 中则并入当前轮后的下一次调用——与 v1 相同）                                                    |
| root             | 点对点任意 kind（context 通道） | **条件**            | push：`triggerTurn:true`（须 `wakeRoot` && cap 内 && 窗口过）；否则 notify 不唤醒                                                                                            |
| 终态 agent       | 点对点 `query`                  | **是（复活）**      | `ports.revive` → `spawn({type, resumeFrom: runId, prompt: revivePrompt(record)})`，复用 v1 mention 的 resume 机制；复活 run 重挂为 root 子节点（v1 mention resume 既有行为） |
| 终态 agent       | 点对点非 query                  | **否**              | dead-drop 入板；若之后被任何路径复活，复活 prompt 提示其调 `fabric_inbox`                                                                                                    |
| 任意             | 广播（to:"board"）              | **永不**【拍板 P5】 | 仅看板                                                                                                                                                                       |
| pending_start    | 任意                            | 延迟                | 等 running 后按上表                                                                                                                                                          |

**revive 失败处理**：spawn 返回 config 错误（如 `already has a resume in progress` 的 resume 锁、会话文件损坏）→ 永不拒收：降级 dead-drop 入板 + `degraded.reason="revive_failed"`，**不自动重试复活**（复活是昂贵定向动作，失败即降级；查询方可从工具返回/`fabric_inbox` 观察到并自行决策）。

**nack 的流向**：nack 是接收方 agent 主动调用 `message_agent(kind:"nack", ref:<query key>)` 发回查询方的普通消息，按上表通用规则投递（查询方 running→push 唤醒、终态→dead-drop）。**系统不代发 nack**——投递失败兜底由降级链承担，两者不混淆【确认自 domain-expert 推断倾向】。

### 4.5 看板（共享公告）的存储与有效范围

- **存储**【拍板 P7】：`BoardStore`（`src/fabric/board.ts`，新建）双写——内存索引（真源视图）+ `pi.appendEntry("subagent:fabric-board", entry)`（持久审计 + `/reload` 重建源，readBack 模式下从 prefetched 条目 hydrate，与 `createPiOutboxStore` 同模式）。
- **有效范围**：仅当前主 session。跨会话/跨进程不做；会话结束后条目随会话文件存档但不再进入任何活跃视图。
- **容量与淘汰**【本方案】：活跃视图上限 `fabric.boardCap`（默认 100 条）FIFO 淘汰最旧 + `fabric.boardTtlMs`（默认 30min）过期剔除；会话条目本身 append-only 不删（审计留痕，膨胀由 TTL+条数+maxChars 三重上限约束——见 §6 风险 R3）。
- **读取**：`fabric_inbox` 工具（见 §4.7）。逐读者游标 `Map<reader, lastReadKey>` 存内存（不持久化；`/reload` 后重读一遍，TTL 兜底噪音上限）。
- **dead-drop 寻址**：优先按 label 匹配（`MentionRegistry.reassign` 使 label 跨 resume 存活——复活后的新 run 仍能读到旧 run 的信）；无 label 的 runId 直投，resume 换新 runId 后不可见，靠 TTL 自然淘汰（已知限制，见 §6 R5）。
- **谁能写/谁能读**：写 = 任意 running agent/root 经 `message_agent`（P1 无权限限制）；读 = 任意 agent/root 经 `fabric_inbox`。

### 4.6 配额 / 收件箱满的处理（永不拒收的具体化）

**发送侧配额**（per-sender-run per-kind 计数，维度沿用 v1【本方案保留】）：

| kind                                                                      | 设置键                    | 默认 | 超限动作                                                                     |
| ------------------------------------------------------------------------- | ------------------------- | ---- | ---------------------------------------------------------------------------- |
| progress                                                                  | `fabric.maxPerRun`        | 20   | 降级 pull（广播→注记后入板；点对点→dead-drop）+ `degraded:"quota_exhausted"` |
| finding                                                                   | `fabric.findingQuota`     | 10   | 同上                                                                         |
| directive                                                                 | `fabric.directiveQuota`   | 5    | 同上                                                                         |
| query                                                                     | `fabric.queryQuota`（新） | 10   | 降级 dead-drop（**不再复活**——超限的 query 按普通终态信处理）+ 注记          |
| nack                                                                      | `fabric.nackQuota`（新）  | 10   | 降级 dead-drop + 注记                                                        |
| （广播计数并入同 kind 配额，不分 to——计数维度是发送行为量，与目的地无关） |                           |      |                                                                              |

**接收侧/系统侧超限**：

| 情形                                        | 处理                                                                                            |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| root 唤醒通道满（`rootInbox≥rootInboxCap`） | 降级 notify（`triggerTurn:false` 送达，内容不丢、不唤醒）                                       |
| root 节流窗口未到                           | pending 等待（v1 语义），窗口过后重判级别                                                       |
| push/notify 重试退避                        | v1 `boundedSend`+throttle 退避重试照旧                                                          |
| TTL 到期 / attempts 耗尽                    | **降级 boarded（pull 兜底）**，不再 abandoned/dropped【本方案：把"永不拒收"贯彻到生命周期终点】 |
| 目标 gone（非 query）                       | 直接 dead-drop 入板（v1 死信路径废除）                                                          |
| revive 失败                                 | dead-drop 入板 + 注记                                                                           |
| 看板自身满                                  | FIFO 淘汰最旧（**仍不拒收**）；被淘汰者随会话条目留审计                                         |
| maxChars 超长                               | 截断（v1 首尾保留式 `truncate`），非拒绝                                                        |

**`dropped`/`abandoned` 残余语义**：仅剩存储/持久化失败（engine `onDegraded` 路径）与 v1 遗留记录，v2 正常流量不再产生。

### 6.5 风险与已知取舍

| #   | 风险/取舍                                                        | 缓解                                                                                                                                  |
| --- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | 删除 can_message 后，恶意/失控 agent 可骚扰任意 agent（含 root） | 配额降级制（超限→pull）+ per-link throttle + root 唤醒容量 + board FIFO；唤醒侧预算仍受控（I-W 只允许定向唤醒）                       |
