## 1. 背景与目标

### 1.1 要解决的问题

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播。
- **R2**：发送永不阻塞——发送方绝不等待对方回复（`message_agent` 调用即返回，投递、唤醒、复活全部异步发生在投递层）。
- **R3**（决策 1 的依据）：不限制发送能力——没有"谁能给谁发"的白名单。

### 1.2 硬约束（已拍板，不再论证）

1. **彻底删除 `can_message`**。`authorize()` 只保留方向性协议规则（result 上行、directive 下行），那是协议自洽，不是权限。
2. **不变量 I-W：广播恒不唤醒任何 agent**。只有 direct 消息可唤醒（唤醒运行中的 agent 起一轮、或复活已结束的 agent）。唤醒必须是具名、担责、计入接收方预算的定向动作。
3. **广播 = 一条看板记录（`to:"board"`），恒 O(1)**，绝不向 N 个接收者逐个 push；接收方自己拉取看板。
4. **投递纪律按接收方状态分级，不设 `urgent`/优先级标记**：运行中子 agent → push；root → push（受 wakeRoot 开关与配额约束）；终态 → 进看板，或（仅点对点 query）复活。
5. **看板只在当前主 session 内有效**（`appendEntry` 写入、读回），不跨会话持久化；跨会话知识复利归 memory 子系统。
6. **超限降级，永不拒收**：push → notify → pull 逐级降级，任何一次发送都不返回失败。
7. **`nack`（"我不知道"）是一等消息 kind**：让发送方尽早转自查，比等超时快一个数量级。

### 1.3 范围与非目标

- 范围：消息模型、授权/路由、投递分级、唤醒/复活、看板、配额降级，及对应文件级改动与测试。
- 非目标：`urgent`/优先级（已否决）；跨会话看板持久化；digest；result 上 fabric 工具面；用户侧 `@` 路由（`src/mention/mention.ts`）的行为变更；fabric v2 实验结论中的 ask_expert/中继问题（H2，属消息内容层，不属投递层）。

## 3. 总体设计

### 3.1 分层与依赖方向

```
            ┌────────────────────────────────────────────────────────┐
 tool 面     │ message_agent(发送, 永不阻塞)   fabric_inbox(拉取, 新) │
            └───────────────┬───────────────────────────┬────────────┘
                            │ 同步 admit / 同步 pull      │ 同步读
            ┌───────────────▼───────────────────────────▼────────────┐
 投递层     │ FabricRouter（准入: 协议规则+降级定级, 无拒绝配额）        │
            │ FabricBoard（看板视图+游标, 新, 只读 engine）             │
            │ FabricMailbox（pump: 分级投递 push/notify/pull/revive）   │
            │ FabricThrottle（push 限速, 不变）  FabricTree（状态oracle）│
            └───────────────┬─────────────────────────────────────────┘
                            │ DeliveryEngine（六态, 不变） → OutboxStore
            ┌───────────────▼─────────────────────────────────────────┐
 持久化     │ pi.appendEntry("subagent:fabric") + getEntries 读回       │
            │ （单一存储: 投递记录与看板记录同库, 看板=视图, session 级）│
            └──────────────────────────────────────────────────────────┘
```

依赖方向与 v1 完全一致：tool → router/mailbox → engine → store；tree/throttle 为纯内存 bookkeeping；pi 只在 stack.ts 的 ports 出现。新增 `FabricBoard` 只读 engine，不新增持久化介质。

### 3.2 一条消息的生命周期

1. **发送**（同步，微秒级）：`message_agent` 解析 `to`（runId / `"root"` / `"board"` / `@label`→registry）→ `router.admit()`：协议校验（authorize v2）→ 截断 → 定级预览（tier preview）→ seq/key → `engine.put(pending)` → 返回 `{ok:true, tier, ...}`。**无任何 await、无 spawn、无拒绝配额**（R2/R3/决策 6）。
2. **投递**（异步，pump 驱动）：mailbox 按接收方状态分级执行 §4.5 阶梯；board 记录永不 dispatch（决策 2/3）。
3. **拉取**（接收方主动）：`fabric_inbox` 返回收件箱未读 + 看板增量；direct 记录转 `delivered`（by pull），board 记录只推进游标。
4. **终结**：delivered（push/notify 后的 push 送达、pull 读取）/ consumed（supersede、sender_settled 的 progress）/ abandoned+死信（TTL，义务 kind）/ dropped（policy、attempts 耗尽）。

### 3.3 三条新不变量（叠加在 v1 I-F9/10/11/12/13/14/15 之上）

- **I-W（决策 2）**：`to==="board"` 或 `boardVisible===true`（停靠看板）或 `tier==="pull"` 的记录，mailbox **永不**对其调用 steer / `sendMessage({triggerTurn:true})` / spawn。唯一例外不存在——board 任何路径都不唤醒。
- **I-NR（决策 6）**：`admit()` 对一切**格式合法且地址存在**的输入返回 `ok:true` 且磁盘存在 pending 记录；配额/收件箱满只改变 `tier`，不改变 ok。
- **I-NB（决策 R2）**：`message_agent.execute()` 的调用路径上没有 await 任何投递/复活动作（admit 与 appendEntry 均同步）；复活由 pump 异步发起。

## 4. 接口契约

### 4.1 消息模型：kind 与 envelope

```ts
// src/core/message.ts
export type NodeRef = RunId | "root" | "system" | "board"; // board 仅可作 to
export type MessageKind =
  | "progress" // 状态汇报；可被同链路新 progress supersede；TTL = progressTtlMs
  | "finding" // 知识/结论；TTL = reconcileTtlMs；死信义务
  | "directive" // 指令；协议限定 parent→child；死信义务
  | "query" // 提问（v2 新）；唯一可复活终态接收方的 kind；死信义务
  | "nack" // "我不知道/无法回答"（v2 新）；对 query 的廉价否定应答；死信义务
  | "result" // 内部协议（child→parent），不在工具面
  | "dead_letter"; // 内部协议（system→sender）
```

envelope 增量（其余字段含 `via`/`ttlMs`/`createdAt` 不变）：

```ts
export interface MessageEnvelope {
  // ...v1 字段不变...
  /** v2 新：应答关联。nack 必填（指向被应答的 query key）；query/其它 kind 可选。 */
  inReplyTo?: MessageKey;
}
export type DeliveryTier = "push" | "notify" | "pull"; // v2 新，落 record 不落 envelope
```

`FabricRecord` 增量字段（`src/core/message.ts`；state 六态、attempts、claimToken、rejected、deadLetter 等壳字段不变）：

```ts
export interface FabricRecord extends MessageEnvelope {
  // ...v1 字段不变...
  tier?: DeliveryTier; // 投递分级；admission 定初值（board 恒 "pull"），pump 可降级改写（pending→pending annotate）
  boardVisible?: boolean; // 看板可见：to==="board" 隐含；direct 消息因终态停靠时显式置 true
  revivedAs?: RunId; // 仅 query 复活成功后 annotate（审计 + revive 配额重建依据）
  deadLetter?: {
    reason: "ttl_expired" | "attempts_exhausted" | "revive_failed" | "target_gone"; // target_gone 仅旧记录兼容，v2 不再产生
    status: "issued" | "suppressed_quota" | "suppressed_sender_gone";
    key?: MessageKey;
  };
}
```

`makeMessageKey`/`parseMessageKey`：`validNode` 加入 `"board"`；新增规则 `from !== "board"`（看板不发消息）。board 链路 seq = 既有 `(from, "board")` per-link 递增。

**TTL**：progress 用 `progressTtlMs`；finding/directive/query/nack 用 `reconcileTtlMs`（含看板停靠记录——看板同样按 kind TTL 清扫，session 结束即整库失效，决策 5）。

**死信义务（I-F11 的 v2 扩展）**：`state ∈ {dropped, abandoned} ∧ kind ∈ {finding, directive, query, nack} ∧ deadLetter === undefined` ⇔ 义务未履行。query/nack 入义务的理由：query 是发送方期待应答的交互原语、nack 本身就是"别等了"的信号，静默丢失二者都会让发送方退回超时等待——正是 nack 要消灭的成本。

### 4.3 发送权限与路由（决策 1）

`authorize()` 重写——**删除 `CanMessage` 类型、`effectiveCanMessage`、一切白名单**；输入只剩 `{kind, from, to, relation?}`：

| kind                         | 规则（全部是方向性协议，不是权限）                                                                                                  |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `dead_letter`                | 仅 `from === "system"`（内部）                                                                                                      |
| `result`                     | `relation(from,to) === "child"`（上行，内部）                                                                                       |
| `directive`                  | `relation(from,to) === "parent"` 且 `to ≠ "board"`（指令必须定向下行；广播指令无从判定方向 → 拒绝）                                 |
| `nack`                       | 仅 direct（`to ≠ "board"`）；`from ≠ to`                                                                                            |
| `progress`/`finding`/`query` | direct：任意关系（含 unrelated/sibling/ancestor——**这正是 R1**）；`to === "board"`：允许（广播）；`from === to`：拒绝（自环无意义） |
| 任意 kind                    | `from === "board"`：拒绝（board 不是发送方）；`from === "system"`（非 dead_letter）：拒绝                                           |

`relation` 退化为审计信息（`via.lca/hops`），**不再参与投递决策**——v1 投递本来就按 runId 直投，树只是拓扑 oracle（targetState）。

`can_message` 的删除面：

- `src/config/agent-types.ts`：停止解析 frontmatter `can_message`（存在时 WARN 一次："can_message is obsolete in fabric v2; ignored"），删除 `AgentTypeConfig.canMessage`（`src/core/types.ts`）。
- `src/service/runtime-adapter.ts` / `src/tools/message-agent-tool.ts` / `src/fabric/mention.ts`：canMessage 依赖全部摘除。

### 4.4 `@label` 寻址（简化）

`src/fabric/mention.ts` **删除**。理由：其两大职责在 v2 均消失——(a) `can_message: mention` 授权（决策 1）；(b) 终态 resume（v2 由投递层对 query 统一处理，且 v1 的 await-spawn 违反 R2）。剩余职责（label→runId 解析）下沉到 `message-agent-tool`：`to` 以 `@` 开头时经 `MentionRegistry.resolve` 解析（任意注册 label，不再限 root 直属——注册表本就含全部带 label 的 run）。`MentionSendResult` 类型随之删除；用户侧 `src/mention/mention.ts` 不动。

### 4.5 投递分级：push / notify / pull 的判据（决策 2/4/6）

**分级在 pump 时按接收方当时的状态求值**（admission 的 `tier` 只是预览，pump 是真相——接收方状态随时会变）。判据表：

| 接收方状态              | T0 push                                                                                                                | T1 notify                                                                                                                    | T2 pull                                                                                |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 运行中子 run            | steer 注入全文（v1 inject 路径不变，含 steerMs 超时/重试/at-least-once）                                               | 同一接收方**至多一条**未清偿的合并提示 steer：`[fabric] N message(s) waiting (from X, Y); call fabric_inbox`                 | 记录保持 pending（收件箱），`fabric_inbox` 拉取                                        |
| root（主会话）          | `sendMessage({deliverAs:"steer", triggerTurn:true})` 注入 context（受 wakeRoot、rootInboxCap、rootMinIntervalMs 三闸） | `appendEntry` + entry renderer 的 display 行（进用户视野、**不进 LLM context、不触发 turn**）；无 renderer 能力时直接落 pull | 停靠看板（boardVisible），`/agent` 与 renderer 可见                                    |
| 终态 run                | —（不存在 push）                                                                                                       | —                                                                                                                            | 停靠看板（boardVisible=true）；**仅 kind===query 且 revive 配额未耗尽** → 复活（§4.6） |
| `to:"board"`（广播）    | —                                                                                                                      | —                                                                                                                            | 恒 pull（admission 即定级，永不 dispatch）——**I-W**                                    |
| pending_start（排队中） | 等待 onSnapshot(running) hint（v1 P3 不变；TTL 兜底）                                                                  | 同左                                                                                                                         | 同左                                                                                   |

**降级触发（先 T0 后 T1 再 T2，逐闸下落）**：

- T0 的闸（任一失败即下落）：① 接收方 running（root 恒 running）② per-sender kind 配额未超（`used[from][kind] < quota`）③ 接收方收件箱未满（run：pending 数 < `runInboxCap`；root：context 类 pending+claimed < `rootInboxCap`）④ per-link throttle 与 root 速率闸（rootMinIntervalMs）——**注意 ④ 是时序闸不是降级闸**：未到时刻的消息保持 pending 等待（既有 wake 定时器），不下落 tier ⑤ root 专属：`wakeRoot === true`。
- T1 的闸：接收方为运行中 run——无未清偿提示（notify-outstanding）且该接收方 notify 配额（`notifyQuota`）未超；接收方为 root——有 `canRenderEntries`（display 通道可用）。**归因区分**：因**发送方**配额（闸②）降级的一律落 T2（发送方超产，不该再打扰接收方）；因**接收方**闸（③⑤）降级的走 T1（接收方无辜，给一条自取提示）。
- T2：停靠/等待。direct 到终态的落看板（boardVisible）；其余保持收件箱 pending。

**notify 的实现细节**：

- notify 是 mailbox 的旁路动作，**不 claim 记录、不改变记录状态**——底层消息仍 pending，等待 pull 或 TTL。
- 每接收方一个 `{ outstandingSince, notifiedCount }`（mailbox 内存态，session 栈生命周期）；清偿条件：接收方 pull（`fabric_inbox` 读取该接收方记录）或 outstanding 超过 `progressTtlMs`；`notifiedCount` 超 `notifyQuota` 后永落 T2。/reload 丢失内存态 ⇒ 最多重复一条提示（有界，可接受）。
- root 的 T1 = 逐条 display append（display 不唤醒、成本仅为渲染，无需合并；沿用 v1 `sendRootDisplay` 端口与"degraded 模式补 delivered 戳"的既有处理）。

**pull 的实现细节**：

- direct 记录：`fabric_inbox` 读取 → `engine.transition(key, "pending", "delivered", { deliveredAt, tier:"pull" })`（一次 append，接收方即读即得）。
- board 记录：**不迁移状态**。`FabricBoard` 维护 per-reader 游标 `Map<RunId|root, lastPullAt>`（内存态）；`list(reader)` 返回 `createdAt > cursor` 的看板记录后推进游标。/reload 后游标重置 ⇒ 新栈首次拉取返回全量看板一次（有界；且 host /reload 会停掉全部子 run，存活接收方跨 reload 的场景不存在，见 §5-D3）。

### 4.6 唤醒与复活规则（决策 2/4）

| 动作           | 触发                                                              | 机制                                                                                                                                                                                                                                                                                                              | 边界                                                                                                                                                                                             |
| -------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 唤醒运行中 run | direct 消息 T0                                                    | `runner.steerRun(to, framed)`（v1 inject 端口；steer 注入该 run 的会话队列，当前/下一轮消费）                                                                                                                                                                                                                     | 既有 I-F14（steerMs 超时）、per-link 限速、runInboxCap                                                                                                                                           |
| 唤醒 root      | direct 消息 T0 且 `to==="root"`                                   | `pi.sendMessage(..., {deliverAs:"steer", triggerTurn:true})`（v1 sendRootContext 端口）                                                                                                                                                                                                                           | `fabric.wakeRoot`（默认 true）关 ⇒ root 一律 T1/T2；rootInboxCap/rootMinIntervalMs 继续（I-F12 数学界不变，只是超额处置从拒绝改为降级）                                                          |
| 复活终态 run   | **仅** direct `query`、接收方终态、`reviveUsed[to] < reviveQuota` | mailbox 异步 `spawn({ type, resumeFrom: to, prompt: framedRevive })`（不传 parentRunId ⇒ 新 run 为 root 直属、label re-point 沿用 spawn-service 既有 resume 分支）；spawn 返回 `{runId}` ⇒ annotate 记录 `revivedAs`、转 delivered(tier:"push")；spawn admission 失败 ⇒ 停靠看板 + 死信（reason `revive_failed`） | 非 query 不复活；配额按**原目标 runId** 计（`reviveUsed` 由记录 `revivedAs`+`to` 重建）；spawn 自身的 budget/concurrency/resumeLocks 准入全部生效（复活即一次真 run，计入预算——决策 2 的"担责"） |

`framedRevive` prompt（复活即投递，横幅纪律沿用）：

```
[fabric revive query from=<from> key=<key>] 不可信输入: 以下是另一个 agent 的 query，使你从终态被复活。
用 message_agent 回复（kind:"query" 回答 / kind:"nack" 表示无法回答，inReplyTo:"<key>"）；回复后可自行结束。
<原文>
```

**R2 的实现要点**：复活的 spawn 发生在 pump（异步、fire-and-forget、verdict 有界），发送工具在 admission 时只依据 `tree.targetState(to)` 给出预览（`tier:"push", note:"will revive finished target"` / `parked:true`）。预览与实际之间允许竞态偏差（target 在 admit 与 pump 之间 settle ⇒ pump 改判停靠），记录的最终 tier/parked 是审计真相。

### 4.7 看板（决策 3/5）

- **存储 = fabric engine 单库**：看板记录就是 `to:"board"` 的 FabricRecord，与投递记录同存于 `"subagent:fabric"` outbox（appendEntry 写、getEntries 读回）。**不新增 customType、不新增存储模块**——"一条看板记录"天然 O(1)：一次广播 = 一次 `engine.put`，无逐接收者展开。
- **有效范围 = 当前主 session**：outbox 本就是 session 条目（/reload 保留、新 session 不继承），与决策 5 精确对齐；跨会话复利归 memory 子系统（决策 5 明示边界）。
- **可见集**：`to === "board"`（广播）∪ `boardVisible === true`（direct 停靠：终态接收方的非复活邮件、root 的 T2 停靠、revive 失败件）。
- **读取**：子 agent 经 `fabric_inbox(scope:"board")`（游标制增量）；用户经 TUI renderer（看板 pending 记录渲染为一行 `[fabric board <kind> from=X]` + 摘要）与 `/agent` 状态页计数（可选小改）。
- **清扫**：pump 的 P1（TTL）对看板记录同样生效（progress 看板 15min、finding/query 看板 reconcileTtl）；到期 abandoned + （义务 kind）死信回投发送方——"你寄的看板件没人取走了"。

## 5. 关键决策与取舍

- **D1 看板 = engine 单库视图，不建第二存储**。备选是独立 `"subagent:fabric-board"` customType + 独立 store。不选：广播本就要经 admission（截断/配额计数/seq/审计），单库让"一条广播一条记录"成为 `engine.put` 的自然性质而非两套存储的一致性问题；`/reload` 读回、TTL 清扫、死信义务、renderer 全部免费复用。看板与投递记录的区分只是一个布尔视图条件（`to==="board" ∨ boardVisible`）。
- **D2 direct→终态 = 停靠看板，不再 target_gone 死信**（v1 行为变更最大点）。v1 把 gone 目标的 finding/directive 丢弃并死信回发送方；v2 决策 4 明确终态接收方"进看板"。于是 `deadLetter.reason` 只剩 `ttl_expired / attempts_exhausted / revive_failed`（`target_gone` 留作旧记录兼容枚举，不再产生）。好处：邮件永不因接收方死亡而灭失，且后续任意一次 query 复活都能让接收方自查看板；死信配额只花在"真的没人要"的件上（TTL 到期）。
- **D3 board 游标制（内存），不做 per-reader 已读标记**。备选是记录上挂 `readBy: RunId[]`（append-only amend）。不选：一条广播的 `readBy` 随接收方数线性增长，且每次拉取都要 amend 一条 entry（append-only outbox 会为每次读放大一次磁盘写）。游标一条 Map 项搞定增量；代价是 /reload 后首拉全量一次——而 host /reload 会停掉全部子 run（`session_shutdown` 的 stop 循环），跨栈存活的接收方不存在，重置无实际伤害。
- **D4 notify 合并 + 归因区分**。不加 `urgent`（决策 4 已否决发送方标记），但接收方闸触发的降级若完全静默，无辜接收方永远不知道有邮件。解法是**每接收方至多一条未清偿提示**（清偿=拉取或 TTL），并且发送方配额超限的一律跳过 notify——降级的"打扰预算"只花在接收方需要知道的场合，不会成为发送方的放大器。
- **D5 revive 只放行 query + 配额按原目标计**。复活 = 一次真 run（token/费用全额），必须是"具名、担责、计入预算"的定向动作（决策 2 的理由直接套用）。`reviveQuota` 默认 1：同一终态 run 被 N 个 agent 各自 query 时，第一个复活它，其余停靠看板（复活后的 run 自己会拉看板看到其余 query——闭环成立）。备选"任意 kind 皆可复活"被否：progress/finding 复活一个死 agent 是纯浪费，directive 复活更是权限意义上的"遥控复活"，均不可接受。
- **D6 rootInboxCap 从"admission 拒绝"改为"降级闸"**（决策 6 的直接落地）。I-F12 的瞬时界证明依赖"admission 是唯一增点且被 ④ 守卫"——v2 中超 cap 的 admission 仍发生但 tier≠push，**不进入 push 计数集**，故 push 集的 `≤ C` 界保持成立（且不会再有 rejected 记录反噬 seq 审计）。速率界（⌈W/R⌉+1+f）完全不动。
- **D7 删除 `fabric/mention.ts`、@label 下沉到 tool**。v1 mention.ts 的三块逻辑（授权/root 直属校验/终态 resume）在 v2 分别被决策 1、R1（任意 p2p）、投递层复活取代；剩余 20 行解析逻辑不值得一个模块 + 一条 `MentionSendResult` 联合类型。用户侧 `src/mention/mention.ts`（用户 @ 消息）是独立入口，其 running→steer / 终态→resume 行为保留不动（用户是可信输入、且不经过 fabric admission）。
- **D8 `inReplyTo` 只做关联，不做会话**。不引入 reply-chain/session 状态机：nack 只需指回 query key，发送方自查转自查的逻辑靠模型读 key 即可。任何更重的关联（应答超时追踪等）属消息内容层，v2 投递层不背。

### 6.3 风险点

- **行为变更面大**：root 默认可被 push（progressChannel 删除）、终态邮件不再死信而是停靠、admission 不再拒绝——三项都要进 CHANGELOG 与 `/agent settings` 描述；灰度靠 `fabric.enabled` 默认 false 兜底。
- **revive 的成本外泄**：复活计入 spawn 预算但不是发送方预算（发送方只花了配额 1 个 query）。`reviveQuota` 默认 1 + queryQuota 默认 5 把上界压到每 run 最多复活 5 个目标、每目标 1 次；如现场证明过松，调 `reviveQuota: 0` 即全局禁复活（全部 query 停靠）。
- **steer 注入即上下文**：push 阶梯的 T0 对运行中 run 的每条消息仍是全文注入（v1 语义）。I-F12 只保 root 的界；run 侧的界由 runInboxCap+minInterval+per-sender 配额三闸合成，若现场出现"多发送方合谋灌一个 run"，下一步迭代候选是 run 侧速率闸（本方案不预实现，记为扩展点）。
- **旧记录兼容**：v1 存量记录（含 rejected、target_gone 死信）hydrate 时字段缺省——`tier` 缺省视为 push 语义（pending 的旧 finding 会按 v2 阶梯重判：运行中目标 push、终态目标停靠——行为漂移可接受且更优）；`via.mode` 缺省 "tree" 既有规则不变。
- **测试基线**：v1 的 property 测试（`tests/core/message-property.test.ts`）断言 `quota_exhausted`/`target_backpressure` 拒绝路径，需随 never-reject 重写为 tier 断言；mailbox 的 P/V 表测试大半保留（claim/verdict/backoff 骨架未动）。

## 8. 交付边界

本方案覆盖投递层全部契约（模型/授权/分级/唤醒/看板/配额/文件/测试）。下游实施时如需更高层编排（如 query 的应答超时提示、多轮协作协议），应在消息内容层（prompt/工具描述）解决，不得回加投递层的阻塞等待或权限白名单——那是 R2 与决策 1 的红线。
