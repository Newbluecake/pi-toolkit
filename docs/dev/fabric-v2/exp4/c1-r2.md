# fabric v2 消息投递层实施方案

状态：架构设计稿，供方案制定/开发使用 · 前序拍板决策已逐条溯源（✅=前序与用户已拍板；🟡=前序未拍板的空白，本方案给出的设计提议，实施闸门处可调整）

## 1. 背景与目标

### 1.1 要解决的问题

现有 `src/fabric/` 是 v1 inter-agent 消息织网：`message_agent` 工具按 agent 类型 frontmatter 的
`can_message` 白名单做关系门控（缺省仅 `["parent"]`），投递沿 per-link throttle + mailbox 泵 +
死信机制运行。v2 的两个硬需求：

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播；
- **R2**：发送永不阻塞——发送方绝不等待对方回复。

### 1.2 已拍板决策（✅，来自前序阶段，共 7 条）

| #   | 决策                                                                                                                                                                                                                                 | 对本设计的约束                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| D1  | **彻底删除 `can_message`**：不设任何「谁能给谁发」的权限白名单，任意两 agent 点对点通信；`authorize()` 只保留方向性协议规则（如 result 必须上行）                                                                                    | 权限层整体拆除，不是放宽默认值                                                                       |
| D2  | **广播恒不唤醒任何 agent**（不变量 I-W）：只有点对点消息可以唤醒接收方（含唤醒运行中 agent 起一轮、复活已结束 agent）；广播一律不唤醒                                                                                                | 唤醒必须是「具名、担责、计入接收方预算」的定向动作；广播命中 N 个接收者唤醒 N 个的成本 O(N) 不可接受 |
| D3  | **广播 = 一条看板记录**：`to:"board"`，恒 O(1)，只写一条看板记录，绝不逐个 push；接收方自己拉取看板                                                                                                                                  | 看板是广播的唯一载体                                                                                 |
| D4  | **投递纪律按接收方状态分级，不设 urgent/优先级**：运行中子 agent → push；主 agent（root）→ push 但受 wakeRoot 开关与配额约束；已结束（终态）→ 进看板，或（仅点对点 query）复活它。「发送方可置 `urgent:true`」的提案被明确否决并删除 | 投递级别由系统状态决定，发送方无权干预                                                               |
| D5  | **看板只在当前主 session 内有效**：`appendEntry` 写入读回，不跨会话持久化；跨会话知识复利留给 memory 子系统，fabric 不做                                                                                                             | 存储形态钉死为 session entry                                                                         |
| D6  | **超限降级，永不拒收**：配额/收件箱满时按 push → notify → pull 逐级降级；任何一次发送都不会返回失败                                                                                                                                  | 工具返回契约中不再有领域性 `ok:false`                                                                |
| D7  | **`nack`（"我不知道"）是一等公民的消息 kind**：不能保证对方有能力回复（R2 的直接后果），让对方尽早回 nack 使发送方转为自查，比等超时快一个数量级                                                                                     | kind 列表在 progress/finding/directive 之外至少新增 nack                                             |

### 1.3 前序未拍板的空白（🟡，本方案必须给出可编码提议）

消息字段完整清单、nack 外的 kind 列表（如 query）、广播范围的寻址表达、notify/pull 的具体语义、
看板容量与拉取方式、wakeRoot 的配置粒度、message_agent 工具参数变化、发送返回体形态、复活的具体
形态与预算。以上均无前序结论，本方案第 5 节逐条给出提议及理由，**不冒充拍板**。

### 1.4 约束条件

- 不改 fabric 总开关语义（`fabric.enabled`，默认 false 灰度）；非目标：部署级 mention 开关、
  跨会话看板持久化、发送优先级。
- pi 扩展在 `/reload` 时同进程重建，fabric 全部状态必须留在 session stack 闭包内（现状已如此）。
- 子 agent 会话 re-import 本扩展须保持 inert（HOST_KEY guard），fabric 组件只存在于主 session stack。

### 2.2 v1 中可直用的机制（v2 不重造）

- **向运行中子 agent 注入**：`ports.inject` → `runnerRef.current.steer(runId, formatted)`（有
  `budget.steerMs` 竞速保护）——这就是 push 到子 agent 的实现。
- **向 root 注入并触发一轮**：`pi.sendMessage({..., deliverAs:"steer", triggerTurn:true})`——push 到 root 的实现。
- **root 的非模型可见通道**：`sendRootDisplay` → `appendEntry`（progress 默认走此通道，progressChannel
  设置）——notify 到 root 的实现。
- **终态 run 的 resume 续跑**：`mention.ts` 的 `spawn({type, label, prompt, resumeFrom: runId})` +
  `registry.reassign`（stack.ts L1156 `onLabel`）——复活（revive）的实现母型。
- **持久化与重建**：outbox store（`subagent:fabric` session entry）+ `prefetched` 读回 + `hydrate()`。

## 3. 总体设计

### 3.1 模块划分与依赖方向

```
                    ┌────────────────────────── 主 session stack（src/stack.ts#buildFabric）──────────────────────────┐
                    │                                                                                          │
 message_agent 工具 │   board 工具(read_board)      FabricRouter ──配额/降级──▶ FabricBoard (新增)                    │
 (src/tools/) ──────┼──▶ src/fabric/router.ts ──┐        ▲                     · board 记录 O(1) append + FIFO cap  │
                    │                           │        │ board/revive 回调                                        │
                    │                           ▼        │                                                          │
                    │                      FabricMailbox ──pump/verdict──▶ FabricPorts                                       │
                    │                           │                             · inject → runner.steer (push/子)          │
                    │                           ▼                             · sendRootContext → steer+triggerTurn (push/root)
                    │                      FabricThrottle                   · sendRootDisplay → appendEntry (notify/root)  │
                    │                           │                                                          │
                    │                      FabricTree (targetState/边/tombstone; isRootChild 供 @label 限定)             │
                    │                           ▲                                                          │
                    │                      FabricRevive (新增) ← query→终态复活: spawn(resumeFrom)+label reassign        │
                    │                      mention.ts (@label 寻址; resume 复用 FabricRevive)                          │
                    └──────────────────────────────────────────────────────────────────────────────────────────────────┘
 纯域模型（无 pi import）: src/core/message.ts — envelope/kind/NodeRef("board")/authorize(纯协议规则)/formatMessage
```

依赖方向不变：`core` 纯域 ← `fabric/*` ← `stack` 装配 ← `tools`/`runtime-adapter` 注入。新增两个
fabric 子模块（board、revive），均为纯逻辑 + 显式端口注入，pi 依赖只出现在 `stack.ts`。

### 3.2 消息流（点对点）

```
发送方模型调用 message_agent(to, kind, text)
  └─ tool.execute（同步、不等待任何回复）
      ├─ to = "@label" → mention 寻址（label→runId，root 直属限定保留）→ 走 to=runId 分支
      ├─ to = "board"  → 广播：FabricBoard.append（一条 O(1) 记录，FIFO cap）→ 返回 {status:"boarded"}   [I-W: 全程不碰 steer]
      └─ to = runId/"root" → router.admit
          ├─ 校验：sender running、非 self、协议方向（result/dead_letter 规则）
          ├─ targetState(tree) 分级：
          │    running      → 记录 pending，mailbox.pump → push（inject/steer）或 root 通道
          │    pending_start → 记录 pending（pull 级排队，markRunning 后补投）
          │    终态,kind=query → FabricRevive.tryRevive（spawn resumeFrom，fire-and-forget）→ {status:"reviving"}
          │    终态,其他 kind  → FabricBoard.deflect（私信降级进看板）→ {status:"boarded"}
          ├─ 背压/配额检查 → 确定投递级别（push/notify/pull，见 3.3），永不 ok:false
          └─ 返回 {ok:true, status, key, seq}
接收方
  ├─ push 命中：steer/triggerTurn → 下一轮模型调用看到消息（formatMessage 标「不可信输入」）
  ├─ notify：display entry / fleet widget 徽标（模型本轮不可见）
  └─ pull：收件箱 pending，下次活跃由 pump 补投；TTL 过期 → dead letter
```

### 3.3 投递级别决策表（任务点 3：push/notify/pull 由什么决定）

投递级别 = f(接收方状态, kind, 背压/配额/wakeRoot/throttle)。发送方无任何干预手段（D4，无 urgent）。

| 接收方状态       | kind                         | 默认级别                                                                | 降级触发                                               | 降到                        |
| ---------------- | ---------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------ | --------------------------- |
| running 子 agent | 任意                         | **push**（`inject`→`runner.steer`）                                     | sender 该 kind 的 push 配额耗尽                        | notify → pull               |
|                  |                              |                                                                         | 该 link 在 throttle 冷却（`minIntervalMs`）            | pull（排队，pump 定时补投） |
| root             | progress                     | **notify**（display entry，v1 现状即如此，`progressChannel:"display"`） | —                                                      | —                           |
| root             | finding/directive/query/nack | **push**（`sendRootContext`，steer+triggerTurn）                        | `wakeRoot` 关                                          | notify                      |
|                  |                              |                                                                         | `rootInboxCap` 满（context 通道 pending+claimed 数）   | notify                      |
|                  |                              |                                                                         | push 配额耗尽 / root throttle 冷却                     | pull                        |
| pending_start    | 任意                         | **pull**（收件箱排队，target `markRunning` 后 pump 补投）               | —                                                      | —                           |
| 终态             | query                        | **revive**（resume spawn，一次全新模型轮；计入被复活方 spawn 预算）     | revive 开关关 / revive 配额耗尽 / spawn admission 拒绝 | board                       |
| 终态             | 非 query                     | **board**（转写一条看板记录）                                           | —                                                      | —                           |
| `to:"board"`     | 任意                         | **board**（一条 O(1) 记录；无投递状态机，写入即生效）                   | `boardCap` 满                                          | FIFO 淘汰最旧（仍 ok）      |

三级语义定义（🟡前序只钉了链名，语义为本方案提议）：

- **push**：消息注入接收方会话上下文并促成一轮模型调用。子 agent 经 `runner.steer`（受
  `budget.steerMs` 竞速）；root 经 `pi.sendMessage({deliverAs:"steer", triggerTurn:true})`。
- **notify**：消息进收件箱并落在**非模型通道**——root 为 display entry（`appendEntry`，用户可见、
  模型本轮不可见）；子 agent 为 fleet widget 消息徽标（UI 增强，可选）。不触发任何模型调用。
- **pull**：消息持久化为收件箱 pending（session entry），静默等待。接收方因**其他原因**下一次活跃
  （被 push、turn 边界、markRunning）时由 `mailbox.pump` 按 createdAt/seq 序补投；或经 `read_board`/
  收件箱读取面主动看到。TTL（`progressTtlMs`/`reconcileTtlMs`）过期走 dead letter。

级别只在 admit/pump 时由系统判定并随记录落档（复用 `effectiveChannel` 思路扩展为三级），投递路径上
不再二次推断；发送方工具返回里如实报告最终级别。

## 4. 接口契约

### 4.1 消息模型（`src/core/message.ts`）

```ts
export type NodeRef = RunId | "root" | "system" | "board"; // 新增 "board"
export type MessageKind =
  | "progress"
  | "finding"
  | "directive" // 社交三件套（v1 保留）
  | "query" // 🟡新增：提问，期待回复；唯一可复活终态接收方的 kind
  | "nack" // ✅D7：「我不知道/无法回答」
  | "result" // 内部协议：运行结果上行，不暴露给 message_agent
  | "dead_letter"; // 内部协议：system→sender 投递失败通知

export interface FabricRecord extends MessageEnvelope {
  state: FabricDeliveryState; // 状态机不变：pending/claimed/delivered/consumed/dropped/abandoned
  attempts: number;
  // ...v1 字段全部保留（claimToken/rejected/deadLetter/terminalReason/storageKey）
  board?: {
    // 🟡新增：看板记录溯源
    origin:
      | "broadcast" // 主动广播（to:"board" 直发）
      | "settled_deflection"; // 点对点消息因接收方终态而降级进看板
    intendedTo?: NodeRef; // settled_deflection 时的原目标
  };
}
// MessageEnvelope.payload/ref/via/ttlMs/createdAt 不变；
// nack 与 query 复用既有 ref?: { keys: MessageKey[]; omittedCount: number } 引用被回复消息（🟡）。
```

kind 语义与配额归置（配额键沿 v1 命名习惯）：

| kind                 | 用途                                               | 计数配额键（per sender）         |
| -------------------- | -------------------------------------------------- | -------------------------------- |
| progress             | 进展通报；对 root 默认 display                     | `maxPerRun`（沿用，默认 20）     |
| finding              | 有价值发现                                         | `findingQuota`（沿用，默认 10）  |
| directive            | 指令/要求                                          | `directiveQuota`（沿用，默认 5） |
| query                | 向具名 agent 提问，期待 finding/progress/nack 回复 | `queryQuota`（🟡新增，默认 10）  |
| nack                 | 回复「我不知道」，建议带 `ref` 引用原 query key    | `nackQuota`（🟡新增，默认 10）   |
| result / dead_letter | 内部协议，不走 message_agent                       | 不计入社交配额                   |

**配额语义变化（D6 落地）**：配额不再拒收，而是 **push 级配额**——耗尽后消息照常入收件箱但降级为
notify/pull，返回仍 `ok:true`（附 `degraded` 标注）。风暴防护因此从「拒收」转为「不再为超额消息花
模型调用预算」，消息本体永不丢（直至 TTL）。

### 4.2 授权（`src/core/message.ts#authorize`）

```ts
export function authorize({ kind, relation, from, mention }: AuthorizationInput): boolean {
  if (!MESSAGE_KINDS.includes(kind)) return false;
  if (kind === "dead_letter") return from === "system"; // 内部协议
  if (kind === "result") return relation === "child"; // 方向性协议规则（D1 保留项）
  if (relation === "self") return false; // 自发自收无意义，拒绝（🟡协议规则）
  return true; // 任意 from→to，含 to:"board"（D1）
}
```

- `CanMessage`/`effectiveCanMessage` 类型与 `canMessage` 字段从 `AuthorizationInput`/`AdmissionInput`
  删除；mention 分支的授权检查删除（`@label` 退化为纯寻址，root 直属与 gone 校验保留在 router）。
- `MentionRoute` 保留（寻址审计用，`via.mode:"mention"` 继续落档）。

### 4.3 路由与准入（`src/fabric/router.ts#admit`）

```ts
export interface AdmissionInput {
  to: NodeRef;                 // runId | "root" | "board"
  kind: MessageKind;           // 工具面限 progress|finding|directive|query|nack
  text: string;
  generation: number;
  route?: MentionRoute;        // 仅 @label 寻址；不再携带 canMessage
  ref?: { key: MessageKey };   // 🟡nack/query 引用原消息
}

export type AdmissionResult =
  | { ok: true; status: "sent" | "queued" | "degraded" | "boarded" | "reviving";
      key: MessageKey; seq: number;
      level?: "push" | "notify" | "pull";         // 直发路径的最终级别
      note?: string }                              // 降级/看板/复活原因（给发送方的可读说明）
  | { ok: true; status: "boarded"; key: MessageKey; seq: number; evicted?: number };  // 广播（boardCap 淘汰数）
  | { ok: true; status: "reviving"; label?: string; };                               // 复活已受理（fire-and-forget）
// 领域性 ok:false 全部取消（D6）。throw 仅保留 host/编程错误：
// "shutting down"、"sender is not running"、generation 缺失、mention route target mismatch。
```

`admit()` 内部分级（伪码序）：

1. `frozen`/sender running/self/协议方向校验（throw 契约不变）。
2. `to === "board"`：构造 `{to:"board", state:"delivered", board:{origin:"broadcast"}}` 记录，
   `FabricBoard.append`（O(1)，FIFO 淘汰），**不触碰任何 steer/triggerTurn 端口**（I-W），返回
   `{status:"boarded", evicted?}`。
3. mention 寻址校验（`route.target === to`、`isRootChild(to)`、非 gone）保留。
4. `tree.targetState(to)`：
   - `"gone"` 且 `kind === "query"` 且 revive 允许（开关+配额）→ 委托 `FabricRevive.tryRevive`，
     立即返回 `{status:"reviving"}`（不等待 spawn 结果，R2）；
   - `"gone"` 其他 → `FabricBoard.deflect(record)`（`board:{origin:"settled_deflection", intendedTo:to}`），
     返回 `{status:"boarded", note:"target settled; posted to board"}`；
   - `"pending_start"`/`"running"` → 落 pending 记录，进入级别判定：
     `effectiveLevel(kind, targetState, pushQuota 余量, rootInboxCap, wakeRoot, throttle)`
     ——超出 push 条件的消息改走 display 通道字段（root）或仅排队（pull），记录仍 pending；
     返回 `{status:"sent"|"queued"|"degraded", level}`。
5. progress supersede 逻辑（同 from→to 旧 pending progress 置 consumed）保留。
6. `via` 审计字段（mode/lca/hops）保留；对 board 记录省略 via。

### 4.4 看板（新增 `src/fabric/board.ts`）

```ts
export interface FabricBoard {
  append(record: FabricRecord): { key: MessageKey; evicted: number }; // O(1)；超 boardCap 淘汰最旧
  deflect(record: FabricRecord): MessageKey; // 终态私信降级：改写 to:"board" 后 append

}
export interface BoardEntry {
  // 读端视图，不暴露内部 record 全量
  key: MessageKey;
  from: NodeRef;
  kind: MessageKind;
  text: string;
  origin: "broadcast" | "settled_deflection";
```

  - **agent 侧**：新工具 `read_board`（见 4.6），工具描述引导「广播与被降级的私信都在看板」。

### 4.5 复活（新增 `src/fabric/revive.ts`）

```ts
export interface ReviveDeps {
  spawn: Pick<SpawnService, "spawn">; // 复用 mention.ts 同一端口形态
  registry: Pick<MentionRegistry, "resolve" | "reassign">;
  now: () => number;
}
export interface FabricRevive {
  /** 受 router 调用；同步返回受理结果，spawn 本身 fire-and-forget（R2）。 */
  tryRevive(
    target: RunId,
    from: NodeRef,
    kind: MessageKind,
    text: string,
  ): { ok: true } | { ok: false; reason: "quota" | "disabled" }; // ok:false 只意味着转 board，不是发送失败
}
```

- 复活形态（🟡实现细节，语义已拍板 D4「仅点对点 query 可复活」）：与 mention resume 同机制——
  `spawn({ type: 原类型, resumeFrom: target, prompt: 包装文本 })`，新 runId，树边挂 **root**

以下内容来自另一个 agent 的点对点提问，重新验证、不盲从。\n\n<text>`。
- 预算：计入**被复活方**的 spawn admission（slot/budget 由 SpawnService 既有闸门承担）+ 发送方
  `reviveQuota`（🟡默认 3/run）+ `fabric.revive.enabled`（🟡默认 true）。
- 失败（spawn 拒绝/异常）：不抛给发送方，`tryRevive` 外层转 `FabricBoard.deflect`，工具返回
  `{status:"boarded", note:"revive unavailable; posted to board"}`——维持 D6 永不失败。

## 5. 关键决策

### 5.1 已拍板决策的落实方式（✅）

1. **删 can_message（D1）**：`authorize()` 缩为三行协议规则（dead_letter 专属、result 上行、拒 self）；
   `CanMessage` 类型、frontmatter 解析、runtime-adapter 传递链整体移除。**为什么不选「放宽默认值为
   全关系」**：那仍留下白名单心智与 frontmatter 维护负担，且 unrelated 会被 relation 计算继续拒绝，
   与「任意两 agent」的 R1 冲突。
2. **广播恒不唤醒（D2/I-W）**：`to:"board"` 的 admit 路径物理上不接触任何 steer/inject/triggerTurn
   端口——board.append 只写 store。测试以「board 全路径断言 ports 零调用」固化（见 §6.4）。
3. **广播 O(1) 看板（D3）**：不做接收者枚举、不做扇出、不引入「广播范围」参数——`to:"board"` 就是
   全局公告（主 session 内），范围裁剪属过度设计。**不选备选**（按树/兄弟/自定义组扇出）的原因：任何
   扇出都重新引入 O(N) 与唤醒边界问题，且与 D2/D3 的 O(1) 表述直接冲突。
4. **按接收方状态分级（D4）**：§3.3 决策表；`urgent`/优先级字段确认不引入（已否决项不复活）。
5. **看板 session 内有效（D5）**：appendEntry 读写 + hydrate 重建；不做磁盘缓存、不跨 `/resume`
   续期（跨会话留给 memory 子系统）。
6. **超限降级永不拒收（D6）**：配额从拒收闸变为 push 级闸；`AdmissionResult` 领域面全 `ok:true`。
   **不选「拒收+返回失败」**：与 R2/D6 字面冲突；**不选「无限收」**：无配额则单 agent 风暴可以烧光
   root 的模型预算（rootInboxCap 的既有动机）。
7. **nack 一等 kind（D7）**：进入 kind 联合类型、配额表、工具 schema；与 query 构成最小问答闭环。

### 5.3 明确不做（本期非目标）

- root 发送侧新工具：用户对子 agent 的既有通道是 `@label`（running→steer / 终态→resume），维持。

### 6.2 迁移与兼容

- **breaking**：`AdmissionResult` 契约、`can_message` frontmatter 失效、`CanMessage` 类型删除。上游
  消费方仅限本包（tool/mention/tests），grep 确认无其他导出依赖；agent 类型文档需同步声明弃用。
- 存量 session entry（v1 记录）hydrate 兼容：`to:"board"` 不存在于旧数据，无冲突；旧 `rejected`

- `fabric.enabled` 默认 false 不变，v2 随灰度逐步放开；`wakeRoot:true`/`revive.enabled:true` 使默认
  行为与 v1 观感一致（root 照常被 triggerTurn，mention resume 照常）。

### 6.3 风险点

1. **prompt injection 面扩大**：任意 agent 可向任意 agent push 文本。缓解：`formatMessage` 的
   「不可信输入」标头保留并用于 revive 包装 prompt；read_board 输出同样带 from 标注。
2. **复活风暴**：三重闸（query kind 限定 + reviveQuota + SpawnService admission/slot）+ I-W 将
   广播排除在复活外；复活的新 run 挂 root，不再继承嵌套 spawn 权（canSpawn 仍按类型生效——需在
   下游方案中确认被复活类型的 canSpawn 是否要收紧，本方案建议维持现状并在观察后调整）。
3. **「永不失败」掩盖故障**：降级信息只在 `note` 里给发送方模型，用户侧重放路径弱。缓解：dead letter
   仍可见、`/agent` board 摘要、fleet widget 徽标（notify 级）。
4. **rootInboxCap 降级后模型不可见**：降为 display 的 root 消息只有用户看得到——这是 v1
   `progressChannel:"display"` 的既有行为，非新风险，但 finding/directive 降级是新路径，观察期建议
   `/agent` 里列出「最近降级消息」计数。
5. **reload 语义**：board 内存窗口与 revive 配额计数随 stack 重建（session entry 重建 board，
   配额计数器回零）——与 v1 配额的 reload 行为一致，不单独持久化。
