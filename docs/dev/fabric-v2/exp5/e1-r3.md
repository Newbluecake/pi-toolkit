# fabric v2 消息投递层实施方案

> 定位：本方案是 fabric v2（任意 agent 点对点 + 一对多广播、发送永不阻塞）的**消息投递层实施口径**。

## 1. 背景与目标

### 1.1 需求

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播。
- **R2**：发送永不阻塞——发送方绝不等待对方回复。

### 1.2 已拍板的总体方向（前序阶段，本方案必须遵守）

1. **发送权限彻底放开**：`can_message` 白名单整体删除；授权只剩三条方向性协议自洽规则（§4.2）。
2. **广播 = 一条 `to:"board"` 记录**：发送时不确定目标集合，恒 O(1)，绝不 fan-out、绝不 N 路 push；相关性在读取侧判定（topic / replyTo）。
3. **唤醒硬约束 I-W**：只有 direct 点对点消息可产生唤醒；广播恒不唤醒任何人。要唤醒必须显式再发一条点对点消息。
4. **投递三级塌缩为两级**（push / board）：按**接收方状态**裁定（D-1′），不按消息内容/发送方意愿。
5. **超限不拒收，只降级**：全链路不存在"配额拒绝/未授权"；超限一律 push→board（answer/nack）或 display（root 的 progress）降级。
6. **看板仅当前主 session 有效**：不跨会话，跨会话沉淀归 memory 子系统。
7. **死信保留但收窄**：v1 死信机制（原子序、`dlRefs`/`dlPlaceholders`、一条原消息至多一条死信）不变；`board_fallback` 仅用于 answer/nack。
8. **v1 五个 kind 全保留**，新增 query/answer/nack 三个 kind（最小集）；`urgent`、`hop/maxHops`、roster、公平份额闸、L2/L3 兴趣域全部砍掉。

### 1.3 约束与前提

- **实施前提**：需求方已拍板"先跑 baseline-experiment 量化收益，再决定工程投入"。本方案按最小集（§1.2 第 8 条）编写；实验不通过则归档不实施。
- **并行改动警告**（§15.7）：仓库存在 quota 并行改动（22 文件 +620 行），与 fabric 改动面高度重叠，§1 的行号锚点已漂移。**本方案一律用符号锚点（文件 + 函数/字段名）**；落地前须 rebase 到 quota 改动之后重新核对。
- 不破坏既有零挂起不变量（I-F10–I-F15 全部保留）；`npm run typecheck` / `npm test`（1800+）/ format:check 全绿。
- TypeScript strict（`exactOptionalPropertyTypes` 等）+ ESM `.js` 后缀导入 + typebox 参数 schema 约定照旧。

## 3. 总体设计

### 3.1 结构

```
                    message_agent(to: runId|root|@label|board, kind, text, topic?, replyTo?, evidence?)
                                        │
                              FabricRouter.admit()          ── 同步、零 await（R2）
                              ├─ authorize()（方向性协议自洽，§4.2）
                              ├─ replyTo/evidence 校验（answer/nack）
                              ├─ dedupe（digest+to 窗口，§4.6）
                              ├─ resolveDiscipline()（D-1′，§4.3，写死进记录）
                              ├─ inboxOf(target) 满则降级（§4.6）
                              └─ engine.put(record) ＋（board：同步落板→直 put delivered）
                                        │
              ┌─────────────────────────┼──────────────────────────┐
        discipline="push"          discipline="board"          gone+direct+query
              │                         │                        │
      FabricMailbox.pump()        BoardStore.append()        ports.revive()（M6）
      （只泵 push 记录）           （写板即 delivered，           spawn(origin:"fabric-revive")
      ├─ TTL/退避/throttle          无 pending 僵尸）           slotless/label keep/
      ├─ claim → boundedSend                                    跳 canSpawn/抑 notifier
      │    ├─ 运行中 run → ports.inject（steer）                 └─ 答案经 fabric answer 回流
      │    ├─ root context → ports.sendRootContext（triggerTurn）
      │    ├─ root display  → ports.sendRootDisplay（不进 context）
      │    └─ gone+query    → ports.revive
      └─ verdict → delivered / 重试 / 死信 / board_fallback
                                        │
        read_board(topic?,since?,limit?,from?) ◄── 接收方主动拉取（pull）
        spawn 时注入预算化 board 摘要块（B1：宿主侧拼 prompt）
```

### 3.2 保留的不变量（v1 全数继承）

I-F9（admission 即承诺）、I-F10（claim 单写者）、I-F11（死信义务纯函数）、I-F12（root ingress 有界）、I-F13（ref 查重与终态同段）、I-F14（verdict 有限到达）、I-F15（verdict 实例隔离）——语义不动，`docs/dev/subagent-push/subagent-push-plan.md` 仍是权威。

### 3.3 新增不变量

- **I-W（board 永不唤醒）**：`to:"board"` 或 `discipline:"board"` 的记录不得引发任何 `runner.steer` / `pi.sendMessage({triggerTurn:true})` / `spawn({resumeFrom})` 调用。在**唯一出口处断言**（§4.4 的 `assertWakeAllowed`，落点在 `stack.ts` 的 ports 实现内，不在各调用点分散判断）。
- **I-B（board 无僵尸）**：`discipline:"board"` 的记录只以 `delivered`（terminalReason:"board"/"board_fallback"）或 `dropped`（terminalReason:"board_write_failed"，answer/nack 附死信）落 engine，**永不 pending**。板写在 admit/pump 的同步段内完成，失败即终态——这是 M3 处置（"先写板成功后直 `engine.put`（put 不查转移表）"），**不改 `stack.ts` 的 `allowed` 转移表**（7 处测试 fixture 零同步）。
- **I-D（去重窗口）**：同 `(digest, to)` 在 `dedupeTtlMs` 窗口内的重复消息恰一次进入投递，重复者 `dropped` + `rejected.reason:"duplicate"`。
- **I-R（复活单例）**：任一时刻一个终态目标至多一个在途 revive（`router.reviving` 映射）；revive 期间到达的同目标 query 挂起，待新 run running 后 steer 注入（M8 处置），不重复 spawn。
- **R2（发送零阻塞）**：`message_agent.execute()` 全程无 await 业务结果——admit 同步返回；revive 是 fire-and-forget（spawn 结果经 verdict 异步回流，reject 必须被捕获处理而非吞掉，B2/M8）；`boundedSend` 与 `fabricSteerTimeoutMs` 赛跑。阻塞式 consult 的 slot 死锁 / resumeLocks 互等 / A↔B 环等待在 v2 结构上不可能；回复**延迟**无上界（前台 root 最长约 `foregroundAutoBackgroundMs` 600s，§5.2 G-B）。

## 4. 接口契约

### 4.1 消息模型（`src/core/message.ts`）

```ts
export type NodeRef = RunId | "root" | "system" | "board"; // "board" 仅可作 to，不可作 from
export type MessageKind =
  | "progress"
  | "finding"
  | "directive"
  | "result"
  | "dead_letter" // v1 保留
  | "query"
  | "answer"
  | "nack"; // v2 新增（最小集）
export type Discipline = "push" | "board";

export interface MessageEnvelope {
  key: MessageKey;
  from: NodeRef;
  to: NodeRef;
  kind: MessageKind;
  seq: number;
  generation: Generation; // system 恒 0；root 恒 1（常量 ROOT_GENERATION）
  payload: { text: string };
  /** admission 时一次裁定，落盘后永不变更（D-4：不新增 FabricRecord 状态） */
  discipline: Discipline;
  /** 规范化 topic：trim + 小写 + ≤64 chars；board 寻址与 board_fallback 使用 */
  topic?: string;
  /** answer/nack 必填：指向被应答 query 的 key */
  replyTo?: MessageKey;
  /** answer 必填 ≥1 条；其余 kind 不填 */
  evidence?: { file: string; lines?: string }[];
  /** sha256(kind + "\0" + (topic ?? "") + "\0" + normalize(text))；admit 时写入，供去重 */
  digest?: string;
  via?: { mode: "tree" | "mention"; lca: NodeRef; hops: NodeRef[] }; // 仅溯源/审计
  ttlMs: number; // progress=progressTtlMs；其余（含 query/answer/nack）=reconcileTtlMs
  createdAt: Millis;
}
```

- `FabricRecord` 壳不变，仅 `rejected.reason` 联合类型扩为 `"quota_exhausted" | "target_backpressure" | "duplicate"`（前两者成为 legacy 死值，仅历史记录出现）；新增 `terminalReason` 取值 `"board"` / `"board_fallback"` / `"board_write_failed"` / `"duplicate"` / `"revive_failed"`。
- `makeMessageKey` / `parseMessageKey` / `validNode` 增加 `"board"`（仅接受作 `to`）。board 链路 `(from, "board")` 照常逐链路单调 seq。
- **kind 语义**：
  - `query`：提问。无义务、无阻塞、可被忽略；是唯一可触发复活的 kind。
  - `answer`：回答。`replyTo` 指回 query；**强制 evidence ≥1**（答案是"另一个 LLM 的记忆"，强制证据让接收方 O(1) 抽查）。
  - `nack`：否认（"我不知道/不在范围"）。`replyTo` 必填；让发送方立刻转自查。
  - 协议类（result/directive/dead_letter）：点对点专用，恒 push、不计 inbox、不落板（§4.3/§4.6）。
- **不新增 `announce` kind（G-A 决策，§5.2）**：主动公告 = `to:"board"` + kind ∈ {progress, finding, query} + topic。M5 若实验证明需要更强公告语义，以字段约束形式（对 board 寻址强制 topic、`scope.files` glob）追加，不引入新 kind。

### 4.2 发送权限与路由规则

- **`can_message` 全链路删除**（清理清单见 §6.1-c）。agent type frontmatter 仍出现 `can_message:` 时打一次性 WARN（"v2 已移除，发送不再受限，该声明被忽略"），不报错。
- `authorize()` 重写为**纯方向性协议自洽**（不再是权限）：

```ts
export function authorize({
  kind,
  relation,
  from,
}: {
  kind: MessageKind;
  relation: MessageRelation;
  from: NodeRef;
}): boolean {
  if (kind === "dead_letter") return from === "system";
  if (kind === "result") return relation === "child"; // 结果只上行
  if (kind === "directive") return relation === "parent"; // 指令只下行
  // progress/finding/query/answer/nack：任意关系放行（含 unrelated/self/跨树/任意深度/同级）
  return true;
}
```

- **删除项**：`CanMessage` / `effectiveCanMessage` / `MentionRoute` 类型，`authorize` 的 canMessage/mention 分支，`router.admit` 的 `canMessage`/`route` 入参。
- **mention 退化为 @label 寻址语法糖**：`createMentionChannel` 收缩为"label → runId 解析 + 与 runId 寻址完全同路径的 admit"；其 v1 的 resume-spawn 复活分支删除（由 §4.4 的 W2 统一承接）。**用户侧 `/mention`（`src/mention/mention.ts` 的 installMentionInput 路径）不动**——那是用户→agent 的通道，与 fabric 无关。
- **协议完整性校验（admit 内，失败 throw）**：`kind==="answer"|"nack"` ⇒ `replyTo` 必填且 `engine.get(replyTo)` 存在、原 kind 为 `query`、`to === 原query.from`（防串线）；`kind==="answer"` ⇒ `evidence?.length ≥ 1` 且 file 非空。
- **路由**：`via` 保留仅作审计（树存在时照算 lca/hops；跨树 unrelated 时 lca=undefined 记 `"root"`、hops=[]）；`via.mode:"mention"` 当寻址来自 @label 时照记。投递与显示一律读持久化 `via.mode`，不用 relation 推断（v6 B1 规则保留）。
- **不可逆性已确认**：删闸后任意深度、正在处理 web 不可信内容的 agent 都能唤醒拥有全部工具的 root——判为**已接受残余风险**。缓解 = `formatMessage` 的"不可信输入： from -> to"头覆盖全部新 kind + answer 强制 evidence + 接收侧 inboxCap/限速。

### 4.3 投递方式裁定（`resolveDiscipline`，D-1′：按接收方状态）

在 `admit()` 内一次裁定并写入 `discipline` 字段，**落盘后永不变更**。三级（notify/pull）已塌缩为两级——对运行中 agent，"notify"与"pull"无区别（pi 没有"不触发 turn 注入运行中会话"的原语；root 的 display 行是唯一纯展示形态）。

| 目标状态                                          | kind                                                                                | discipline               | 通道/动作                                                                                                                                         |
| ------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `to==="board"`                                    | progress/finding/query                                                              | `board`                  | 同步写板（§4.5），**恒不唤醒**                                                                                                                    |
| 运行中 run（含 pending_start，等 running 后泵送） | 全部（协议类恒 push）                                                               | `push`                   | `ports.inject` = `runner.steer`；并入当前 turn 的下一次 LLM 调用，**无额外轮次**，成本=context token（§15.1 更正）                                |
| root                                              | progress                                                                            | `push` + channel=display | `ports.sendRootDisplay`（appendEntry 展示行，不进模型 context、不唤醒；沿用 v1 `effectiveChannel` 推导，受 `progressChannel`/`canRenderEntries`） |
| root                                              | finding/query/answer/nack                                                           | `push` + channel=context | `ports.sendRootContext`（steer + triggerTurn，空闲时起一轮；受 `wakeRoot`/rootInboxCap/前台延迟，§5.2 G-B）                                       |
| root                                              | 协议类（result/directive/dead_letter）                                              | `push` + channel=context | 同上，但不计入 rootInbox（§4.6 M7）                                                                                                               |
| `wakeRoot:false`                                  | root 一切入站                                                                       | 降级                     | context 类降 display + 落板；无唤醒                                                                                                               |
| 终态 run（gone）                                  | **direct + query**（且 `autoRevive` 开、`autoReviveMaxPerSession` 未尽、可 resume） | `push`（revive 动作）    | `ports.revive`：fire-and-forget spawn（§4.4 W2），工具返回 `{status:"reviving"}`                                                                  |
| 终态 run（gone）                                  | progress/finding（admit 时已知终态）                                                | `board`                  | 落板（发送方得到 `posted_board`，不误判送达）                                                                                                     |
| 终态 run（gone）                                  | answer/nack（admit 时已知终态）                                                     | `board`                  | 迟到答案归宿，topic 继承自原 query                                                                                                                |
| pump 途中目标变 gone（admit 时在跑）              | query                                                                               | `push`→revive 尝试       | revive 不合格（开关/上限/锁）→ 死信                                                                                                               |
| pump 途中目标变 gone                              | answer/nack                                                                         | `push`→board_fallback    | 落板（M4：**不签死信**）                                                                                                                          |
| pump 途中目标变 gone                              | finding/directive                                                                   | 死信（附 board 引用）    | M4：发送方需要失败信号，不能看到 delivered 误判送达                                                                                               |
| pump 途中目标变 gone                              | progress                                                                            | dropped(target_gone)     | v1 语义                                                                                                                                           |

- **协议类 kind 恒 push**：result/directive/dead_letter 点对点专用，`to:"board"` 寻址直接 throw（工具参数错误）。
- **系统死信显式 `discipline:"push"`**；`/reload` 后 v1 残留的 pending 记录无 discipline 字段 ⇒ **迁移规则：`effectiveDiscipline(record) = record.discipline ?? "push"`**（v1 全部记录本质是 push 语义）。这是 M-3 顺序 bug 的修正：判 pull/board 的条件是**显式字段**，绝不按"无 audience 即 pull"推导。`effectiveDiscipline` 为 `core/message.ts` 纯函数，pump / inboxOf / dedupe 统一经它读取（不改写磁盘旧记录）。
- `mailbox.pump()` 候选过滤条件从 `state === "pending"` 收紧为 `state === "pending" && effectiveDiscipline(r) === "push"`。

### 4.4 接收方唤醒规则

**I-W 总闸**：只有 direct 点对点消息可产生唤醒；广播恒不唤醒。在唯一出口处断言：

```ts
// src/stack.ts buildFabric() 的 ports 实现内
function assertWakeAllowed(record: FabricRecord): void {
  if (record.to === "board") throw new Error("I-W violation: board message must never wake");
  if (effectiveDiscipline(record) !== "push") throw new Error("I-W violation: non-push record cannot wake");
  if (record.kind !== "query" && <本次动作是 revive>) throw new Error("I-W violation: only direct query may revive");
}
```

- **W1（turn 唤醒，运行中目标）**：push = steer 注入。运行中子 agent：并入当前 turn 的下一次 LLM 调用，**不产生额外轮次**（§15.1 更正，成本只有 context token）。空闲 root：channel=context 的 push 触发一轮主会话（`triggerTurn:true`），受 `rootInboxCap`（12）约束；progress 恒 display 不触发。
- **W2（复活唤醒，终态目标）**：仅 `direct && kind==="query"` 触发 auto-revive，约束：
  - `slotless: true` 不占并发槽；`deadlineAt = min(发起方 deadlines.deadlineAt, 默认 budget.totalMs)`（CC4 只收紧，发起方无 deadline 用默认）；
  - **label "keep" 第三态**（G-E，§5.2）：revive spawn 不注册也不 repoint label（用户可见的 @label 寻址不被后台复活静默改写）；后续对旧 runId 的 query 由 `router.reviving`/`redirectTo` 映射指向新 run（steer），不形成复活链；
  - `autoReviveMaxPerSession: 10` 兜底成本（router 内存计数，/reload 重置——可接受，文档明示）；
  - **notifier 抑制 + 专属锚点**（B2 处置，G-D）：`origin:"fabric-revive"` 的 spawn 继承原 run 的树位置（parentRunId = 原 run 的 parent，`onSpawnEdge` 照常挂边），但**显式跳过 canSpawn 白名单与深度校验**（位置继承原 run，不是新嵌套）、**不入 notifier 完成通知队列**（其"结果"就是 answer 消息本身，只经 fabric 回流）——否则复活 run 的完成通知会以 `triggerTurn:true` 唤醒 root，绕过 I-W；
  - spawn reject（config error / resumeLocks "already has a resume in progress"）**必须捕获**：query 记录走死信（reason 记 `revive_failed` / `target_gone`），不得静默吞掉（M8）；
  - **reviving 映射**（M8 处置）：`router.reviving: Map<targetRunId, { newRunId?: RunId; queued: MessageKey[] }>`。revive 发起即登记；期间到达的同目标 query 挂起（pending 留在 engine），新 run `markRunning` 快照到达后由 pump 注入 steer；revive 失败清除映射，挂起 query 走死信。
- **广播升级通道**：广播重要到要唤醒某人 ⇒ 发送方必须显式再发一条点对点消息（具名、可审计、计入对方 inboxCap）。"广播破格唤醒"被明确否决。
- **M2 前台 root 延迟（G-B 决策，§5.2）**：root 阻塞在前台 Agent 调用期间（≤ `foregroundAutoBackgroundMs` 600s）steer 排队延迟送达，消息不丢（query TTL 24h ≫ 600s），只是延迟。行为文档化 + prompt 纪律（§4.7）兜底，不为此改动 agent-tool 等待循环。

### 4.5 看板（共享公告）

- **存储**：新增 `src/fabric/board.ts` 的 `BoardStore`。readBack 模式下 `pi.appendEntry(customType:"subagent:board")` append-only + 写后读回校验（复用 `pi-outbox-store` 模式）；非 readBack 内存数组。`session_start` 从 prefetched 条目重建（与 tree 重建同源、同批扫描）。
- **有效范围（D-3，已拍板）**：**仅当前主 session**。新主会话看板归零；跨会话沉淀是 memory 子系统的职责，不在此实现。
- **容量**：全局 FIFO `boardCap: 500`；每 topic `boardTopicCap: 50`。截断优先保留最新与**被引用条目**（引用集 = engine 记录的 `replyTo` ∪ 板内条目的 `replyTo` 命中的 key）。
- **写路径**：① 主动广播 `message_agent to:"board"`（admit 同步段内落板，I-B）；② 降级落板（inbox 满，§4.6）；③ `board_fallback`（answer/nack 的迟到归宿，topic 继承原 query 的 topic ?? ""）。
- **读路径**：新工具 `read_board({ topic?, since?, limit?, from? })`——推进 per-reader cursor（内存 `Map<NodeRef, number>`，/reload 重置，重读幂等无害）；`read_board` 加入 `RESERVED_TOOL_NAMES`（`src/runtime/tool-scope.ts`）deny-by-default，fabric 启用的 run 经 grantedReserved 注入。
- **启动注入（B1 处置，G-C 决策）**：`before_agent_start` 在子会话不触发（HOST_KEY 守卫先 return），故注入改为**宿主侧 spawn 时拼 prompt**——落点 `src/service/runtime-adapter.ts` 组装 sessionSpec 处，在 `spec.request.prompt` 尾部追加预算化块（`boardInjectBudgetChars: 2_000`）：

  ```
  ## Board（共享公告 · 摘要）
  topics: <topic 目录（名 + 条数 + 最近时间）>
  <replyTo 命中"本 run 发出的 query"的 answer/nack 条目（L0 最强命中，全文）>
  用 read_board 工具按 topic 读取全文。
  <三条 prompt 纪律，见 §4.7>
  ```

  渲染产物按"board 内容指纹"缓存（内容未变复用字符串）；resume 的 run（含 revive）同路径注入（revive 的 prompt 由 fabric 构造，天然包含）。

- **读侧相关性判定**（发送侧零集合裁定的对偶）：topic 精确匹配；`replyTo` 命中接收方自己发出的 query（L0，机器可证）。roster/兴趣域/mutation 预警已全部裁剪，不实现。

### 4.6 配额 / 收件箱满时的处理

总原则（已拍板）：**超限不拒收，只降级**。v1 的发送方配额拒收全部移除。

- **摄取预算（inbox）**：`rootInbox()` 泛化为 `inboxOf(node)`——统计该接收方 `pending|claimed` ∧ `effectiveDiscipline==="push"` ∧ channel=context ∧ **kind 非协议类**（progress/finding/query/answer/nack 计数；result/directive/dead_letter 不计——M7 优先级反转修正：协议类在预算检查前放行且不占预算，不再挤掉接收方自己问来的 answer）。默认 `inboxCap: 8`，root 沿用 `rootInboxCap: 12`。
- **满时降级**（ AdmissionResult 返回 `posted_board`/`degraded`，发送方不误判送达）：
  - answer/nack → board（topic 继承原 query）；
  - query（运行中目标满）→ board；
  - progress → root → display 行（本就不进 context）；
  - 协议类不降级、不受限（per-link 限速仍管其速率）。
- **限速**：per-link `minIntervalMs: 30_000` 保留，**超时只推迟不拒收**；新增 `receiverMinIntervalMs: 30_000`（per-接收方聚合速率，跨发送者）；root 保留更严独立值 `rootMinIntervalMs: 10_000`。throttle 零持久化（D19）不变。
- **去重**：`digest = sha256(kind + "\0" + topic + "\0" + normalize(text))`（normalize = 去首尾空白 + 连续空白折叠）；同 `(digest, to)` 在 `dedupeTtlMs: 600_000` 窗口内 ⇒ `dropped` + `rejected.reason:"duplicate"`（只拦逐字级重复）。
- **TTL**：progress = `progressTtlMs`（900s，继续生效）；其余（含 query/answer/nack）= `reconcileTtlMs`（24h）。TTL 过期终结表：query → 死信（asker 依赖"发出去了"的信号）；answer/nack → board（迟到答案归宿，**不签死信**，回答者无需知道提问者没收到）；finding/directive → 死信（v1）；progress → abandoned（v1）。mailbox 中所有硬编码 `kind==="finding"||"directive"` 的分支（TTL、pre-claim target_gone、verdict 失败共三处，M-6）统一改走**终结判定表**（新纯函数 `terminalObligation(kind): "dead_letter" | "board" | "none"`），新 kind 不再被静默丢弃。
- **死信收窄**：v1 原子序 + `dlRefs`/`dlPlaceholders` + "一条原消息至多一条死信"不变；`issueDeadLetters` 在按 sender 分批**之前**逐条判定 board_fallback（二者互斥）；死信 quota 拒发分支删除（`suppressed_sender_gone` 保留——发送者已终态时死信无意义）。
- **legacy 配置键**（解析保留、语义降级，/agent settings 标注 deprecated）：`maxPerRun`/`findingQuota`/`directiveQuota`/`deadLetterQuota` 不再参与 admission 拒收；`maxChars`（截断）与 `progressTtlMs`（TTL）继续承担机械职能；`progressChannel` 继续参与 display 推导。
- **量化声明**：接收方 context 总量的"有界"声明如实降级为**速率上界**（inboxCap 管瞬时在途量 + receiverMinIntervalMs 管注入速率 + dedupe 管重复；发送方总量配额已移除）。

### 4.7 工具面、prompt 纪律与配置

- **`message_agent` schema**（`src/tools/message-agent-tool.ts`）：

```ts
Type.Object({
  to: Type.String({ description: 'Target run id, "root", "board"（广播）, or @label' }),
  kind: Type.Union([
    Type.Literal("progress"),
    Type.Literal("finding"),
    Type.Literal("directive"),
    Type.Literal("query"),
    Type.Literal("answer"),
    Type.Literal("nack"),
  ]),
  text: Type.String(),
  topic: Type.Optional(Type.String({ description: "board 寻址/落板的 topic（≤64 chars）" })),
  replyTo: Type.Optional(Type.String({ description: "answer/nack 必填：被应答 query 的 key" })),
  evidence: Type.Optional(Type.Array(Type.Object({ file: Type.String(), lines: Type.Optional(Type.String()) }))),
});
```

删 `canMessage` dep；evidence/replyTo 的协议校验在 admit 内（§4.2）。**主会话也必须注册 `message_agent` + `read_board`**（`src/index.ts` post-guard、`fabric.enabled` 门控，from:"root"、generation 恒 `ROOT_GENERATION=1`）——否则 root 无法回答，"向主 agent 请教"不成立。

- **固定返回文案（R2 + prompt 纪律）**：工具成功返回附写死文案——「已投递，不阻塞。若收到回答会作为消息进入你的上下文。不要为此等待——继续当前工作，或先做粗筛。」
- **三条 prompt 纪律**（与机制同等重要，注入 board 摘要块 + message_agent 工具 description，写死）：① 开工先问（read_board + 广播"谁知道"）；② 问完继续；③ **答案到了就转向**——push 进来的 answer 覆盖正在做的事时立刻停止并采用（附 evidence 抽查指引）。缺第 3 条模型会无视答案继续傻干，是同类机制最常见失效模式。
- **问答四结局**（自检用例）：① 对方在跑且知道 → answer push 回来；② 在跑但不知道 → nack push 回来（立刻转自查）；③ 已终态 → 后台 auto-revive，answer 异步回流；④ 没人回/提问方已结束 → answer 按 topic 转存看板。
- **新增配置**（`FabricSettings`，`src/config/settings.ts` + `setting-specs.ts`）：

| 键                                         | 默认                      | 说明                                                                                           |
| ------------------------------------------ | ------------------------- | ---------------------------------------------------------------------------------------------- |
| `fabric.inboxCap`                          | 8                         | 非协议类 push 在途上限（run 接收方）                                                           |
| `fabric.receiverMinIntervalMs`             | 30_000                    | run 接收方聚合注入最小间隔                                                                     |
| `fabric.dedupeTtlMs`                       | 600_000                   | (digest,to) 去重窗口                                                                           |
| `fabric.boardCap` / `fabric.boardTopicCap` | 500 / 50                  | 看板 FIFO 容量                                                                                 |
| `fabric.boardInjectBudgetChars`            | 2_000                     | spawn 注入摘要块预算                                                                           |
| `fabric.wakeRoot`                          | true                      | false ⇒ root 一切入站降 display+board                                                          |
| `fabric.autoRevive`                        | 10 上限内的总开关（true） | v1.3 的 `reviveOnDirectQuery` 与 `autoRevive` 合并为单键（W2 只允许 direct query，无需再区分） |
| `fabric.autoReviveMaxPerSession`           | 10                        | 复活次数兜底                                                                                   |

### 5.3 已知取舍

- **回复延迟无上界**（R2 的对偶）：前台 root 最长 ~600s；query 无人应答则永远无回答（四结局之④落到看板）。这是非阻塞模型的本性，文档明示。
- **`/reload` 后 per-reader cursor 与 revive 计数重置**：重读幂等、复活上限重置可接受（session 生命周期兜底），不持久化。
- **删权限闸的残余攻击面**（§4.2）：已接受；缓解仅不可信输入头 + evidence 强制 + 接收侧限速。

### 6.3 测试要点

**单元（tests/fabric/、tests/core/）**

1. authorize 新矩阵：kind × from(system/非) × relation（child/parent/其他/unrelated/self）；answer/nack 的 replyTo 协议校验（不存在/非 query/to 不匹配/evidence 缺失）各一。
2. resolveDiscipline 矩阵（§4.3 表逐行）：to=board/运行中/root/终态 × kind × wakeRoot × inbox 满；**M-3 回归**：系统死信恒 push、无 discipline 的 v1 存量（hydrate 后经 effectiveDiscipline）恒 push、/reload 残留 pending 可被泵送。
3. **I-W 断言**：spy ports 下 board 寻址与降级落板记录零 `inject`/`sendRootContext`/`revive` 调用；`wakeRoot:false` 时 root 零 context push。
4. inboxOf/降级（M7 回归）：协议类不计数不降级；满时 answer→board（topic 继承）、query→board、progress→root→display。
5. dedupe：同 (digest,to) 窗口内 duplicate、窗口外放行、空白 normalize 算重复、不同 to 不互斥。
6. 终结判定表（M-6 回归）：query/answer/nack 的 TTL 与 target_gone 各走死信/board/对应终态；mailbox 三处旧硬编码分支删除后新 kind 不再静默丢弃。
7. revive（M6）：slotless/keep/跳 canSpawn/抑 notifier 四断言（spy spawn-service）；上限计满后拒绝；resumeLocks config error → 死信；reviving 期间第二个 query 挂起、新 run running 后 steer；失败后映射清除。
8. BoardStore：FIFO/topic cap、被 replyTo 引用条目截断保留、renderDigest 预算与指纹缓存、prefetched 重建、写失败 → dropped(board_write_failed) 无 pending。
9. throttle：receiver 维度跨发送者聚合；root 独立值；D19 重建不回归。
10. 转移表零改动回归：7 处 fixture 不动（显式快照断言 `allowed` 字面量未变）。

**集成（tests/integration/）**

11. /reload 全链路：board 重建、dedupe 窗口、discipline 迁移、reviving 清空、cursor 重置幂等。
12. 前台 root 延迟（G-B 文档化行为）：前台 Agent 调用期间发 query → 调用返回后送达（或按 pi 语义断言排队不丢）。

### 6.4 风险与提示

- **quota 并行改动重叠**（最高优先）：先落 quota 再落 fabric，逐文件 rebase；行号锚点一律弃用。
- **pi steer 语义依赖**：§15.1 的"同 turn 注入、无额外轮次"是 pi 0.84–0.86 的行为；peers 升级时复核 W1 成本模型与 M2 延迟声明。
- **删权限闸不可逆**：上线前在 CHANGELOG 与 agent-type 文档显著标注；WARN 文案引导用户移除 frontmatter 字段。
- **board 截断丢证据**：引用保留规则只保 replyTo 命中条目；若实验阶段发现高频丢条，调 boardCap 而非加复杂淘汰策略。
- **baseline-experiment 是总闸**：实验未过 → 本方案归档于 docs/dev/fabric-v2/，不做任何 M1+ 投入。
