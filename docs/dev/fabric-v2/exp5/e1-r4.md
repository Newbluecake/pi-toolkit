## 1. 背景与目标

### 1.1 需求

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播；
- **R2**：发送永不阻塞——发送方绝不等待对方回复；
- **R3**（前序拍板继承）：全链路不存在"发送失败"——投递层对发送方的工具调用永不返回失败（T4 回归锚），超限/失效一律**降级**而非拒收。

### 1.2 约束（继承自前序拍板，不可推翻）

- **§15.1 推翻性更正**：pi 的 steer 在当前 assistant turn 的工具调用执行完之后、下一次 LLM 调用之前送达，**并入同一外层 turn**——"push = 打断对方一轮"的成本模型是错的。对运行中 agent，push 的真实成本只有 context token。因此三级 discipline（push/notify/pull）**塌缩为两级（push / board）**，`urgent` 字段取消，闸门 G1 关闭。
- **§15.5 最小集**：3 个新 kind（query/answer/nack）+ `to:"board"` + `replyTo/topic/evidence` 三字段 + 两级 discipline + 看板 + `read_board`。roster selector、hop/maxHops、mutation、scope.symbols、L2 兴趣域三来源、`boardSenderSharePct`、`answered` supersede、`audience`、`freshness`、`announce` **全部不做**（announce 列为 M5 可选，收益存疑）。
- **§15.6 收益再评估**：看板增量有限（"开工先广播"在 I-W 下基本无效）；真正绕过压缩瓶颈的只有"向终态专家定向提问 + revive"。施工顺序与验收以此为预期基线。
- **§15.7 环境冻结**：quota 特性曾有 22 文件未提交改动与 fabric 改动面高度重叠（`stack.ts`/`settings.ts`/`spawn-service.ts`/`index.ts`/`tests/integration/fabric-wiring.test.ts`）——**不得与 quota 并行开发**，开工前确认 quota 已落地或把上述文件列为冻结面。

### 1.3 本方案覆盖

消息模型、发送权限与路由、点对点/广播投递方式、唤醒规则、看板、配额与收件箱满、文件级改动清单、测试要点。

## 3. 总体设计

### 3.0 结构总览（文字版）

```
message_agent (子 run 注入 / 主会话 post-guard)      read_board (同上)
        │ to: RunId | "root" | "board" | "@label"          │ {topic?,since?,limit?,from?}
        ▼                                                 ▼
  FabricRouter.admit() ──► BoardStore (src/fabric/board.ts, NEW)
   1 sender-running                                     ▲   │ appendEntry "subagent:board"
   2 方向性 authorize (D-2, 无 can_message)              │   │ session_start 重建; FIFO 截断
   3 digest 去重 (dedupeTtlMs)                           │   └─ 注入: runtime-adapter buildPrompt
   4 resolveDiscipline() ─── to:"board" ─────────────────┘      (topic 目录, 预算 2000 chars)
   5 inboxOf(to) 摄取预算 ──满──► 降级 board
   6 建 record (discipline 定死, D-4 不新增状态)
        │ discipline==="push"                │ discipline==="board"
        ▼                                    ▼
  FabricMailbox.pump()                 写板成功 → engine.put({state:"delivered",
   TTL/gone/退避/节流 → claim →            terminalReason:"board"})  (不进 mailbox)
   boundedSend(steerMs 赛跑) → verdict
        │ 失败 → boardFallbackDecision() 统一裁定（admit 降级/pump/verdict 三处同一函数）
        │   answer/nack → 落板; finding/directive → 落板副本 + 死信; progress/query → 落板(静默)
        ▼
  唤醒出口 (唯一出口断言 assertWakeAllowed):
   W1 运行中: runner.steer / root: sendRootContext(wakeRoot 门控)
   W2 终态+direct+query: revive spawn (slotless, deadline 夹紧, label keep,
                          notifier 抑制, 答案只经 fabric 回流)
```

### 3.1 消息模型（任务覆盖点 1）

**Kind 列表（最终）**：v1 全保留 + 新增 3 个：

| kind              | 语义                           | 方向性                      | 说明                                                                                                   |
| ----------------- | ------------------------------ | --------------------------- | ------------------------------------------------------------------------------------------------------ |
| `progress`        | 进度通报                       | 任意关系                    | v1 语义不变；supersede 逻辑保留                                                                        |
| `finding`         | 发现/结论                      | 任意关系                    | push 失败仍签死信（失败信号，D-8）                                                                     |
| `directive`       | 指令                           | **仅 parent→child（下行）** | push 失败仍签死信（D-8）                                                                               |
| `result`          | 完成交付                       | **仅 child→parent（上行）** | 系统完成投递用，不经 message_agent                                                                     |
| `dead_letter`     | 死信                           | **仅 from==="system"**      | 系统签发                                                                                               |
| `query` **(新)**  | 提问：无义务、无阻塞、可被忽略 | 任意关系                    | 唯一可触发 W2 复活的 kind                                                                              |
| `answer` **(新)** | 回答，`replyTo` 指回 query     | 任意关系                    | **强制 `evidence`**（D-12：答案是"另一个 LLM 的记忆"，强制证据让接收方 O(1) 抽查）；**强制 `replyTo`** |
| `nack` **(新)**   | "我不知道/不在范围"            | 任意关系                    | 一等公民（D-7：让发送方尽早转自查，比等超时快一个量级）；带 `replyTo`                                  |

`announce` 不进最小集（M5 可选，默认不实现）。

**字段变化**（`MessageEnvelope`/`FabricRecord`）：

- `NodeRef` 增加 `"board"`（`validNode()` 同步放行；`makeMessageKey`/`parseMessageKey` 的 generation 规则不变：system 恒 0，其余 ≥1）。
- `replyTo?: MessageKey` —— 问答关联，复用现有 key 作 correlation id。
- `topic?: string` —— 看板归档键。工具描述引导用文件路径/glob 作 topic（机器可判定，D-13 文件域优先精神）；缺省时降级路径自动派生（见 3.6）。
- `evidence?: Array<{ file: string; lines?: string; quote?: string }>` —— `kind=answer` 必填（工具层与 admit 双重校验）。
- `discipline: "push" | "board"` —— admit 时一次定死、永不变更（D-4）。
- `deliverVia?: RunId` —— 实际 steer 目标与 `to` 不同时使用（revive 重定向，见 3.4）。
- `rejected.reason` 增加 `"duplicate"`；`terminalReason` 增加 `"board"` / `"board_fallback"` / `"revive_embedded"` / `"revive_budget"`。
- **不新增** FabricRecord 状态（D-4：pending/claimed/delivered/consumed/dropped/abandoned 沿用，状态机转移矩阵与属性测试不动）。board 落板 = 直接 `engine.put({...record, state:"delivered"})`（put 不查转移表，**不做** `pending→delivered` 表增量，8 处 fixture 改动全免）。
- 明确砍掉：`urgent`、`hop/maxHops`、`mutation`、`scope.symbols`、`scope.files`、`audience`、`digest`（作为**字段**不做；去重用函数内计算，见 3.6）、`freshness`。

**TTL**：`progress` 沿用 `progressTtlMs`(15min)；`query/answer/nack/finding/directive` 沿用 `reconcileTtlMs`(默认 24h，足以覆盖 root 前台 600s 盲窗)；board 记录无 TTL（容量截断即上限）。

### 3.2 发送权限与路由规则（任务覆盖点 2）

**D-2（不可逆）：`can_message` 彻底删除。** 约束从"谁能给谁发"整体迁移到"什么进得了我的 context"（接收侧摄取预算，3.6）。

`authorize()` 重写为**纯方向性协议规则**（协议自洽，不是权限）：

```ts
// src/core/message.ts（重写）
type AuthorizationInput = { kind: MessageKind; relation: MessageRelation; from: NodeRef };
function authorize({ kind, relation, from }: AuthorizationInput): boolean {
  if (kind === "dead_letter") return from === "system";
  if (kind === "result") return relation === "child"; // 仅上行
  if (kind === "directive") return relation === "parent"; // 仅下行
  // progress / finding / query / answer / nack：任意关系全开
  //（unrelated / self 不再拒绝；跨树、任意深度、同级全通）
  return true;
}
```

- **发送方仍须 running**（v1 `admit` 的 `sender is not running` 检查不变）——终态 agent 不再发言，其遗留产出靠看板与死信。
- **mention 路由删除**：`MentionRoute`、`CanMessage`、`effectiveCanMessage()`、`AuthorizationInput.canMessage/mention` 全删；`@label` 退化为**寻址语法糖**（label→runId 后走普通路径）；`via.mode:"mention"` 保留仅作溯源展示。
- **root**：普通可寻址节点，无特殊发送权限；接收侧特殊项仅 `rootInboxCap:12`（宽于通用 8）、`rootMinIntervalMs:10s`、`wakeRoot` 开关。**主会话也注册 `message_agent` + `read_board`**（post-guard、`fabric.enabled` 门控）——否则"向主 agent 请教"不成立。
- **system**：只发死信。
- **D-11**：`tree.ts` 保留但降级为溯源标注（`via.lca/hops`、`relation` 仅作展示与信任先验）；`isRootChild` 不再 gating 任何路径。

**寻址（`to` 参数）**：`RunId | "root" | "board" | "@label"`。`@label` 经 `MentionRegistry.resolve()` 解析为 runId（解析失败返回 `unknown_label` 结果——这是寻址错误而非投递失败，不违反 R3）。

**方向性 vs 跨树**：`directive` 仅 parent→child、`result` 仅 child→parent 的判定基于 tree 关系；跨树发送 directive 会被 `authorize` 拒绝（配置错误，返回 `not_authorized`——同属寻址/协议错误，不算 R3 范围内的"发送失败"）。

### 3.3 投递方式：push / board 由什么决定（任务覆盖点 3）

**D-1′（取代 D-1）：discipline 按接收方状态划分，admit 时一次裁定（`resolveDiscipline()` 纯函数，写死不变）。**

```ts
// src/fabric/discipline.ts（新文件）
type Discipline = "push" | "board";
function resolveDiscipline(input: {
  to: NodeRef; // "board" | RunId | "root"
  kind: MessageKind;
  targetState: TreeTargetState; // pending_start | running | gone
  reviving: boolean; // 目标已有进行中的 revive（见 3.4）
  reviveAllowed: boolean; // reviveOnDirectQuery && autoRevive && 预算未耗尽
  inboxFull: boolean; // inboxOf(to) 已满（M6 分类计数，见 3.6）
  wakeRoot: boolean; // 仅 to==="root"
}): Discipline;
```

裁定顺序（**M-3 顺序修正已落实**：判"非 push"的第一条规则只能是显式广播/显式降级——v1 存量记录、系统死信、/reload 后残留 pending 一律默认 push，绝不因缺字段被判 board 后被 pump 过滤、连 TTL 分支都进不去而静默饿死）：

1. `to === "board"` → `"board"`（广播恒 1 条看板记录，O(1)，**绝不 N 路 fan-out**——D-5）；
2. `to !== "board"` 且目标 **running**（含 root、pending_start 到位后按 running 处理）→ `"push"`；若 `inboxFull` → 降级 `"board"`（D-6：超限降级，绝不拒收）；
3. 目标 **gone（终态）**：
   - `kind === "query"` 且 `reviveAllowed || reviving` → `"push"`（W2 复活后投递，见 3.4）；
   - 其余 → `"board"`（含 progress/finding 发终态目标一律落板、绝不 revive——把已结束的 agent 拉起来只为听通报是纯烧钱）。

**点对点**：running 目标 = push（`runner.steer`，root = `sendRootContext`，`wakeRoot:false` 时 root 入站整体降 `sendRootDisplay` + 看板副本，不起 turn）；终态目标 = query 可 revive，其余落板。

**广播**：`to:"board"` 恒 1 条 board 记录；**不做投递面计算、不唤醒任何人**（I-W）；接收面靠 `read_board` 主动拉取 + 启动注入 topic 目录（§15.5 砍掉 roster/L2 后的最终形态："所有会读板的 agent"）。广播重要到需要唤醒某人 ⇒ 发送方**显式再发一条点对点**（具名、可审计、计入接收方 inboxCap）。

**push 的通道细节（root）**：`progress` 沿用 `effectiveChannel()`（display 通道不占 inbox、不进 context，仅 pacing 约束）——保留但标 legacy；`query/answer/nack/finding/directive` 到 root 一律 context 通道（steer + triggerTurn，受 `wakeRoot` 门控）。

**对运行中 agent，notify 与 pull 无区别**（§15.1：steer 不加轮次），故两级即是全集，不存在第三级。

### 3.4 接收方唤醒规则（任务覆盖点 4）

**I-W（硬规则，无配置项）：只有点对点（`to !== "board"`）可产生唤醒；任何广播恒不唤醒。**

- **W1 turn 唤醒**（目标运行中）：子 agent → `ports.inject`（`runner.steer`）；root → `ports.sendRootContext`（`deliverAs:"steer", triggerTurn:true`）。pi 的 steer 并入当前外层 turn 的下一次 LLM 调用，成本只有 context token。
- **W2 复活唤醒**（目标终态）：**触发面收紧为 `direct + kind === "query"`**，由 `reviveOnDirectQuery`（默认 true）门控。`progress/finding/answer/nack` 发终态目标一律落板，绝不 revive。

**auto-revive（D-9）机制**——B2/M8 处置后的完整口径：

1. **发起**：`admit()` 发现 direct query → 终态目标 X 且无进行中 revive → fire-and-forget 发起 `spawn({ resumeFrom: X, fabricRevive: { queryKey } })`，**不 await**（R2；reject 必须捕获，§15.4）。query 记录保持 pending、`to:X`、`deliverVia` 留空。工具立即返回 `{ ok:true, status:"accepted", revive:"initiated" }`。
2. **revive 专属 spawn 路径**（`SpawnRequest.fabricRevive?: { queryKey: MessageKey }`）：
   - `slotless: true`（不进 concurrencyLimit 槽池）；
   - **跳过 canSpawn/嵌套深度校验**（revive 是系统发起，不是父 agent 工具调用）；
   - `deadlineAt` 由**提问方剩余 deadline 夹紧**（CC4 只收紧；提问方是 root 或无 deadline 时 unset，watchdog 子相位预算兜底）；
   - **label 不 repoint**：`spawn-service.ts` 的 `labelAction` 增加第三态 `"keep"`（现仅 `"register" | "repoint"`）——`@expert` 不被问答 run 抢走；
   - **notifier 抑制**：runtime-adapter 将 revive run 加入 `fabricOwnedRunIds`（与 `childRunIds` 同位的 enqueue_delivery 过滤）——复活 run 的 settle 通知**绝不**以 `triggerTurn:true` 唤醒第三方（B2 攻破点）；**答案只经 fabric 回流**：复活 prompt 内嵌 query 文本 + 指示"用 message_agent 以 `replyTo` 回答"；
   - 复活 run 完成时**未产生任何 `replyTo` 命中该 query 的 answer** ⇒ 签发一条 system `dead_letter` 给提问方（计入 `deadLetterQuota`；本方案新增决策，理由：query 虽"可被忽略"，但 revive 是系统应提问方请求发起的显式动作，静默失败违背 R3 的诚实性；与"一条原始消息至多一条死信"不冲突）。
3. **M8 并发收敛**：router 维护 `reviving: Map<RunId, { newRunId: RunId; queryKeys: MessageKey[] }>`。revive 期间到达的同目标 query：admit 正常接受（pending），pump 在新 run `markRunning` 后经 `deliverVia: newRunId` steer 进去（**绝不**因 `resumeLocks` 的"already has a resume in progress"拒绝而静默丢失——该拒绝被捕获后转为等待重试，退避后重试 revive 或 TTL 到期落板）。`spawn` 失败（config error）⇒ `reviving.delete(X)`，pending query 走 board 降级。
4. **预算**：`autoReviveMaxPerSession: 10`（会话级兜成本；revive 是一次带完整 context 的 run，缓存过期后可能比提问方自查更贵——§15.6 成本警告，工具描述如实写明）。超预算 ⇒ query 落板（`terminalReason:"revive_budget"`）。

**唤醒唯一出口断言**（§15.4 四洞的统一收口）：新增 `assertWakeAllowed(record)`（`discipline.ts`），在**全部三个唤醒出口**调用——`ports.sendRootContext` 包装、`ports.inject`（steer）包装、revive `spawn({resumeFrom})` 发起点——断言来源 `to !== "board"` 且 kind 满足对应出口规则（steer：任意 direct kind；revive：仅 query）。任何"广播 push / 广播触发 revive / revive settle 通知唤醒第三方 / 非合规 kind 复活"在出口处直接拒绝并 WARN，不依赖散落各处的入口检查。

**root 唤醒**：direct→root 的 push 会在用户空闲时也起主会话一轮（"向主 agent 请教"的必要代价），由 `rootInboxCap` + 分类摄取预算约束；`fabric.wakeRoot:false` ⇒ root 一切入站降级 display + 看板，**零 turn 唤醒**（T17 硬锚）。

**已知残余（接受）**：R-W——失效预警不唤醒，接收方可能在看到预警前基于失效前提干完活；缓解只允许点对点路径，"广播破格唤醒"明确排除。回复延迟无上界（前台 root 最长 600s 盲窗，见 6.3-⑤）。

### 3.5 看板：存储与有效范围（任务覆盖点 5）

- **范围（D-3，已拍板）**：**仅当前主 session**，不跨会话；新主会话看板归零（无陈旧治理成本；跨会话复利留给 memory 子系统手动承载）。
- **存储**：`pi.appendEntry(customType: "subagent:board")` + 读回校验，完全复用 `pi-outbox-store.ts` 的 append-only 模式；`session_start` 从 prefetched 条目重建（与 `buildFabric` 重建 tree 同源写法）。`/reload` 不清 Node 模块缓存 ⇒ board/router 状态必须可从 prefetched 条目**完整重建**（T8）。
- **写入面**：① `to:"board"` 的直接广播（kind 限 `progress/finding/query/answer/nack`——协议类 kind 不可广播）；② 各降级路径的转存副本（3.6 统一裁定）。**无主动清除机制**，只有截断。
- **容量**：全局 FIFO `boardCap: 500`；每 topic `boardTopicCap: 50`。截断优先保留 ① 最新 ② 被 `replyTo`/`ref` 引用过的条目。`boardSenderSharePct` 公平份额闸**不做**（会淘汰尚未回答的 query）。
- **读取面**：`read_board({ topic?, since?, limit?, from? })` 工具（root post-guard 注册；子 run 经 `grantedReserved` 注入；`RESERVED_TOOL_NAMES += "read_board"`），推进 per-reader cursor（内存态即可，/reload 后归零可接受——重建后全量视为新）。
- **启动注入（B1 最终处置）**：`before_agent_start` 在子会话**根本不触发**（注册在 HOST_KEY 守卫之后）——注入必须改为**宿主侧 spawn 时拼进 prompt**（runtime-adapter 的 `buildPrompt` 追加，或 `SessionSpec` system prompt 追加项；resume 的 run 同理走同一路径）。注入内容 = **topic 目录（topic 名 + 条数 + 最近活动时间，仅元数据非全文）+ `read_board` 使用指引**，预算 `boardInjectBudgetChars: 2_000`，复用 memory 的预算化渲染。§15.5 砍掉 L2 兴趣域后，"命中兴趣域条目摘要"随之取消——注入只有目录，这是有意的简化。
- **注入即 prompt 注入面**（§15.4）：topic 字符串是 agent 可控文本，进注入即构成类存储型 XSS 的持久注入面。缓解：注入只含 topic 目录（短元数据），逐条包"不可信输入"围栏（同 `formatMessage` 约定）；残余风险如实记录，不宣称已消除。

### 3.6 配额与收件箱满（任务覆盖点 6）

**D-6：超限一律降级，绝不拒收。** `admit()` 不再返回 `quota_exhausted` / `target_backpressure`；全链路不存在发送失败（T4：工具永不返回失败）。发送方 per-kind 配额（`maxPerRun/findingQuota/directiveQuota`）**降级为 legacy 记账**（计数与设置键保留，语义被接收侧预算取代）；`deadLetterQuota` 保持有效（死信仍受其约束）。

**接收侧摄取预算（核心机制）**：`rootInbox()` 泛化为 `inboxOf(node)`——统计 `state ∈ {pending, claimed}` 且 `discipline === "push"` 且走 context 通道的条数（root 的 display 通道 progress 不占 inbox，v1 语义保留）。

**M6 优先级反转修正（本方案选定：分类计数）**：接收方自己问来的 answer 不能被闲聊 progress 挤成落板。`inboxOf` 分两个类别分别对 `inboxCap` 计数：

- **通报类**：`progress/finding/directive/query` —— 共享 `inboxCap`（默认 8，root 12）；
- **回执类**：`answer/nack` —— 独立对 `inboxCap` 计数（不被通报类挤占，自身也有上界）。

任一类满 ⇒ 新 push 降级 board（D-6）。§10"总量上界比 v1 更强"的说法**不成立**，如实按**速率/预算上界**表述。

**速率**：per-link `minIntervalMs: 30s` 保留；v1 的 root 独立节流泛化为 **per-receiver 节流**（`receiverMinIntervalMs`，默认 30s；root 保留独立覆盖值 `rootMinIntervalMs: 10s`——`throttle.ts` 的 `rootNotBeforeValue` 标量泛化为 `receiverNotBefore: Map<NodeRef, number>`）。**超时只推迟不拒收**。

**digest 去重**：`digest = sha256(kind + "\u0000" + (topic ?? "") + "\u0000" + normalizedText)`（normalizedText = trim + 连续空白折叠）；同 `(digest, to)` 在 `dedupeTtlMs: 600_000` 窗口内 ⇒ 建 record 直接 `dropped`（`rejected.reason:"duplicate"`），工具返回 `{ ok:true, status:"duplicate" }`（幂等成功，不违反 R3）。已知弱点：只拦逐字重复（§15.4 如实记录）。

**push 失败的统一裁定（D-8 + M4 + M-6 三处合一）**——`boardFallbackDecision(record)` 纯函数，在 **admit 降级、`pump()` 的 TTL 分支、`pump()` 的 pre-claim target_gone 分支、`verdict()` 的 attempts_exhausted/target_gone 分支**全部走同一函数（M-6 补漏：v1 这三处硬编码了 `finding||directive` 死信，新 kind 在旧路径会被静默丢弃）：

| kind                    | push 落不了地时的处置                               | 失败信号                                         |
| ----------------------- | --------------------------------------------------- | ------------------------------------------------ |
| `answer` / `nack`       | 落板（topic 自动取 `query/<replyTo>`）              | 无死信（回执类；提问方经 read_board/注入可发现） |
| `directive` / `finding` | 落板副本 + **死信**（死信 `ref` 附 board 记录 key） | 死信（否则发送方看到 delivered 会误判送达——D-8） |
| `progress` / `query`    | 落板（topic 自动取 `inbox/<to>`）                   | 无死信（v1 同类静默语义；query 显式"可被忽略"）  |

- 落板后 record 终态：`state:"delivered"` + `terminalReason:"board"`（admit 时降级）/ `"board_fallback"`（投递中途降级），直接 `engine.put`，不进 mailbox。
- **死信签发时序不变**：`board_fallback` 判定必须逐条做在 `issueDeadLetters` 按 sender 分批**之前**；"一条原始消息至多一条死信"（`dlRefs`/`dlPlaceholders` 原子序）保持。
- **direct query → 终态目标**在裁定前先走 revive 判定（3.4），revive 不可用才落板。

**广播话痨防线**：非权限手段——工具描述写明成本、`to:"board"` **强制 topic**（无 topic 的广播属参数错误，返回 `missing_topic`，同属寻址错误而非投递失败）、容量截断 + dedupe。真实防线是 prompt 纪律，不是配额（§8.1）。

### 3.7 R2：发送永不阻塞

- `message_agent` **同步返回**（T6：工具调用耗时 < 50ms）：admit 全同步；revive 发起 fire-and-forget（reject 捕获）；`boundedSend` 仍与 `steerMs`（5s）赛跑且只在后台 pump。
- 返回文案显式写"已投递，不阻塞……不要为此等待——继续当前工作，或先做粗筛"。
- 阻塞式 consult（v1 之前的方案）已整体否决：slot 死锁 / resumeLocks 互等 / A↔B 环等待在 v2 结构上不可能出现。
- **prompt 纪律三条（与机制同等重要，写入工具描述与 agent type 文档）**：① 开工先问（`read_board` + 广播"我要查 X"——§15.6 已注明此条在 I-W 下基本无效，如实保留为软引导）；② 问完继续；③ **答案到了就转向**——push 进来的 answer 覆盖正在做的事时立刻停止并采用，附 evidence 抽查指引（缺此条模型会无视答案继续傻干，是同类机制最常见失效模式）。

| 本方案新定 a | M6 修正选"分类计数"（answer/nack 独立对 inboxCap 计数）                                                | 备选"协议类 kind 不计入"会让 result/dead_letter 无界；分类计数最小且可测                                                       |
| 本方案新定 b | revive 完成未答 ⇒ system dead_letter 给提问方                                                          | R3 诚实性；备选"静默"使 revive 失败不可见                                                                                      |
| 本方案新定 c | query push 失败/TTL 无死信（v1 progress 同）                                                           | query 显式"可被忽略"（D-7 nack 才是显式回绝）；死信面不扩大                                                                    |
| 本方案新定 d | 降级 topic 自动派生（`query/<replyTo>`、`inbox/<to>`）                                                 | D-6"绝不拒收"要求降级路径永远可用；派生键可预测、可检索                                                                        |

**明确否决清单（不再提）**：阻塞式 consult_agent；can_message 任何形态；广播 fan-out；超限拒收；失效预警破格 push（mutation）；G1/urgent；`pending→delivered` 表增量；roster/hop/maxHops/L2 隐式兴趣/scope.symbols/boardSenderSharePct/answered supersede/audience/freshness/announce（M5 前不做）；只读 consult 会话；独立"知识交接包"机制；"先修文重写再实施"（先跑 baseline-experiment）。

### 6.3 风险点与未闭环项（开工前确认/如实声明）

1. **quota 冻结面**（§15.7）：M1 前确认 quota 已落地；否则 `stack.ts/settings.ts/spawn-service.ts/index.ts/tests/integration/fabric-wiring.test.ts` 冻结。
2. **不可信输入边界**（§15.4，本方案的缓解集）：出口断言 + 注入仅元数据目录 + 围栏标签 + evidence 抽查 + revive 会话级 10 次上限 + dedupe（只拦逐字，如实记录）。删 can_message 后"处理 web 内容的深层 agent 可唤醒持全部工具的 root"是**接受的暴露面**，靠摄取预算限幅。
3. **/reload 重建**（M-7）：答案-查询关联**不建独立 openQueries 存储**，一律经 engine `select(r => r.key === replyTo)` 查询——pending/claimed 记录本就持久化，重建天然可用（本方案简化，需在 M4 测试中验证 TTL 内迟到 answer 命中）。
4. **B2 验收**：revive run 的 settle 在任何配置下不得产生 `triggerTurn:true` 的 root 唤醒（T17 扩展）。
5. **root 前台盲区（未闭环，二选一，开工前找需求方确认）**：root 阻塞在前台 Agent 调用（`foregroundAutoBackgroundMs: 600s`）期间 steer 送不进去。**本方案默认 (a)**：如实文档化——"请教 root 只在 root 空闲/后台调度下即时生效"，投递延迟由 `reconcileTtlMs`(24h) 覆盖、600s 自动转后台后 steer 落地；备选：在前台 Agent 等待循环把指向 root 的 query 暴露为 tool update（仅用户可见，不进 context）。
6. **两处字段保留确认（未闭环）**：`digest`（保留，作去重闸——本方案采纳）；`freshness/scope.files/audience`（**不保留**，不在最小集）；开工前向需求方确认一次。

### 6.4 测试要点（任务覆盖点 8）

**硬锚（继承 T 系）**：

- **T4**：`message_agent` 全路径（含 inbox 满、目标 gone、board、revive 发起）永不返回失败；参数/寻址错误除外（结构化 `not_*`）。
- **T6**：admit 同步耗时 < 50ms（revive spawn 不得进入调用栈 await）。
- **T8**：board `session_start` 重建 + `/reload` 后 router/board/reviving 预算完整重建。
- **T15′**（I-W 属性测试，roster 已砍后收敛为）：任意 kind × `to:"board"` ⇒ push 出口调用数为 0、revive 发起数为 0。
- **T16**（W2 触发面）：revive 仅 `direct + query + reviveOnDirectQuery`；progress/finding/answer/nack → 终态目标 ⇒ 落板零 revive。
- **T17**（wakeRoot:false ⇒ root 入站零 turn 唤醒；扩展：revive settle 通知同样零唤醒）。

**新增/改写**：

- `authorize` 新矩阵：任意关系放行组 + 方向性仍生效组（result 上行、directive 下行、dead_letter 仅 system）。
- `resolveDiscipline` 表驱动全分支 + **M-3 回归**：无 `discipline` 字段的存量记录 / 系统死信 ⇒ push，不被 pump 过滤饿死。
- `boardFallbackDecision` 矩阵（§3.6 表）× 触发路径三处（admit 降级 / pump TTL / pump gone / verdict 耗尽）行为一致；"一条原始消息至多一条死信"在 board_fallback 混合批次下仍成立（`dlRefs` 原子序回归）。
- `inboxOf` 分类计数（M6）：通报类洪泛不挤占 answer/nack；两类各自触顶均降级 board。
- dedupe 窗口：同 `(digest,to)` 窗口内 dropped+`duplicate`，窗口外放行，near-miss（改写一字）放行（弱点如实）。
- BoardStore：FIFO 全局/每 topic 截断；`replyTo/ref` 引用条目保留；cursor 推进；注入预算截断（2000 chars）与围栏标签存在。
- revive：label `"keep"` 不 repoint（`@expert` 连续两次问答 label 稳定）；`resumeLocks` 拒绝 ⇒ 第二提问者 query 在新 run running 后 steer 达（M8）；spawn 失败 reject 捕获且 query 落板；未答 settle ⇒ 恰一条 system dead_letter；`autoReviveMaxPerSession` 触顶落板。
- 集成（`tests/integration/fabric-wiring.test.ts` 扩展）：root 收 query（context 通道、triggerTurn）、answer 携带 evidence 端到端注入、主会话 post-guard 工具注册门控、`subagent:board` 条目持久化与重建。
- **状态机 lockstep**：无状态增量 ⇒ `tests/core` 转移矩阵/属性测试不动（D-4 验收点）；若实现引入新转移即视为违反 D-4。
- 回归保留：claimed 崩溃→pending at-least-once（T17 v1）、死信 ref 修复（T18′）、`fabric.enabled=false` 零痕迹（T19）。
