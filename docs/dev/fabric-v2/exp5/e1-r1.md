## 1. 背景与目标

### 1.1 需求

- **R1**：任意两个 agent 之间可点对点通信，也可一对多广播。
- **R2**：发送永不阻塞——发送方绝不等待对方回复。
- **R3**（由 R1/R2 推导，上游已立）：投递链路**永不因权限/额度拒收**（超限只降响度）。

### 1.2 v1 的结构性问题（为什么必须 v2）

v1 fabric 的授权模型是**发送侧权限**（frontmatter `can_message` 关系门控）+ **发送侧 per-kind 配额**。R1 要求任意寻址、R2 要求推送式投递，两者叠加后发送侧闸门全部失效——context 投毒与 turn 放大的唯一相容解是**把闸移到接收侧**（摄取预算），这是 v2 的总纲。

### 1.3 上游已拍板的关键决策（本文直接继承，不再论证）

| 决策        | 内容                                                                                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-2         | `can_message` 彻底删除，发送权限模型废除                                                                                                                                |
| D-1′        | 投递纪律按**接收方状态**划分：运行中子 agent→push；root→push（受 `wakeRoot`+配额，忙时降 display）；终态→看板或 revive。三级 push/notify/pull 塌缩为**两级 push/board** |
| D-3         | 看板仅当前主 session 有效（session entry 存储，不跨会话）                                                                                                               |
| D-5         | 广播 = 1 条 `to:"board"` 记录，恒 O(1)，绝不 N 路 push                                                                                                                  |
| D-6/D-10    | 超限不拒收，只降响度；四道幅度闸全为非权限闸                                                                                                                            |
| D-12        | announce 强制 topic；answer 强制 evidence                                                                                                                               |
| D-14（I-W） | **广播不能唤醒 agent，只有点对点可以唤醒**（需求方硬约束）                                                                                                              |

| D-9         | revive 复用 resume 分支 + slotless + fire-and-forget，预算夹紧，会话级次数上限                                                                                          |

既有实现事实（v2 依赖）：

- `createDeliveryEngine().put()` **不校验 `allowed` 转移表**——board 直达 `delivered` 依赖此事实，本方案将其升格为显式契约（§10.5）。
- `pi.sendMessage({deliverAs:"steer", triggerTurn:true})` 是 root 的 context 注入通路；`appendEntry` 是 display 通路。
- pi 的 steer 语义为"当前 assistant turn 的 tool calls 结束后、下一次 LLM 调用前注入"——**对运行中子 agent，push 的真实成本只有 context token，没有额外轮次**（§15.1 实测，D-1′ 的依据）。
- 子会话 `before_agent_start` 不触发（HOST_KEY 先 return）——看板注入必须走宿主侧 `buildPrompt()`（B1）。
- `SpawnRequest` 无 `parentRunId` 时 run 为顶层（depth 0、无 canSpawn 校验），但会 enqueue 顶层完成通知（`triggerTurn:true`）——B2 的根源。

## 3. 总体设计

### 3.1 模块划分与依赖方向

```
message_agent / read_board（工具面，host + 子 run 双注册）
        │ admit / 查询
        ▼
FabricRouter（admission 线性化点：参数校验→协议自洽→digest→discipline→put→revive 决策）
   ├─► DeliveryEngine（"subagent:fabric" outbox，六态不变，put 直写 delivered 契约）
   ├─► FabricBoard（"subagent:board" entries；post/topics/digest/hydrate）★新
   ├─► ReviveCoordinator（revive 预算/映射/失败死信）★新
   │        └─spawn({resumeFrom, slotless, quiet, labelPolicy:"keep"})─► SpawnService
   └─► openQueries（Map<sender, Set<MessageKey>>，hydrate 自 engine）
        │ pump(hint)
        ▼
FabricMailbox（候选 = discipline==="push"；P1–P6 + V 段；settleUndeliverable 统一终结核）
   └─FabricPorts：inject→runner.steer（revive 映射解析后目标）｜sendRootContext｜sendRootDisplay
FabricThrottle（per-link receiver 间隔 / root 间隔 / backoff；零持久化重建）
FabricTree（降级为溯源：relation/lca/hops 仅供 formatMessage 展示）
```

依赖方向与 v1 相同：tools → router → {engine, board, revive, tree}；mailbox → {engine, router, throttle, ports}；revive → spawn-service（晚绑定 ref，同 `spawnRef` 先例）。**无 pi 导入**的新纯模块：`board.ts`（存储经注入的 store 接口）、`revive.ts` 的决策面（spawn 调用经端口注入）。

### 3.2 核心不变量（v2 版）

| #           | 不变量                                                                                                                                                                                                                        | 说明                                                                                                                      |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| I-F1..I-F15 | v1 全部继承                                                                                                                                                                                                                   | 见 subagent-push-plan §2；seq 单调、claim 单写者、义务函数磁盘可判、claimToken 实例隔离等不动                             |
| **I-W**     | 唯一出口断言：只有 `to !== "board"` 且 `kind !== "announce"` 的消息可产生 W1（steer/triggerTurn 唤醒）或 W2（revive）；W2 另要求 `kind === "query"`。广播恒不唤醒                                                             | 落点：`mailbox.dispatch` 与 revive 分支共用 `wakeAllowed()`（§10.2）；用户侧 `@` 复活是具名用户动作，不属广播，不违反 I-W |

## 4. 消息模型（覆盖项 1）

### 4.1 kind 列表（9 值）

| kind          | 方向规则（协议自洽，非权限）       | 死信/归档义务                                    | 说明                                                |
| ------------- | ---------------------------------- | ------------------------------------------------ | --------------------------------------------------- |
| `progress`    | 任意关系（含 self/unrelated/跨树） | 无（v1）                                         | 进度通报；latest-wins supersede 不变                |
| `finding`     | 任意关系                           | 死信 + board 归档引用                            | 关键发现                                            |
| `directive`   | 仅 `parent`（下行）                | 死信 + board 归档引用                            | 指令                                                |
| `result`      | 仅 `child`（上行，内部协议）       | 无（不入 message_agent 面）                      | v1 不变                                             |
| `dead_letter` | 仅 `from === "system"`             | 永不再死信                                       | v1 不变                                             |
| `query` ★     | 任意关系                           | 死信 + board 归档引用                            | 点对点提问；唯一可 W2 复活的 kind                   |
| `answer` ★    | 任意关系                           | **board_fallback**（归档优先，归档失败回落死信） | 对 query 的回答；`replyTo` + `evidence` 必填        |
| `nack` ★      | 任意关系                           | 同 answer                                        | 无法回答/拒答；`replyTo` 必填；促使发送方尽早转自查 |
| `announce` ★  | 仅 `to === "board"`                | 无（board 写失败在 admit 同步暴露，不产生记录）  | 广播公告；`topic` 必填；恒不唤醒                    |

### 4.2 envelope 扩展（`MessageEnvelope`，最小集）

```ts
export type NodeRef = RunId | "root" | "system" | "board"; // validNode() 同步加 "board"
// 新增可选字段（v1 字段零改动）：
export interface MessageEnvelope {
  // …v1 全部字段…
  discipline?: "push" | "board"; // admit 钉死；undefined = v1 残留记录（hydrate 推断，§12 M-1）
  topic?: string; // announce 必填；query/answer/nack 可选线程线索
  replyTo?: MessageKey; // answer/nack 必填；指向被应答的 query 的 key
  evidence?: string; // answer 必填：文件路径/行号或关键引文——"答案是另一个 LLM 的记忆，
  // 可能幻觉或过期；强制证据让接收方 O(1) 抽查而非 O(n) 重查"
}
```

`FabricRecord` 追加对应可选字段 + `boardRef?: string`（board_fallback/死信归档引用，取值 = board entry id）；**不新增投递状态**（D-4）。新增 `terminalReason` 取值：`"board"`、`"board_fallback"`、`"duplicate"`。

### 4.3 被裁字段（上游 §15 定论，不实现）

`urgent`（成本模型作废）、`hop/maxHops`（无转发路径，死代码）、`mutation`（与 I-W/T15 矛盾）、`audience`（roster 裁剪后 audience 退化为 `to === "board"` 的推导值，不落盘）、`scope.symbols`。

### 4.4 TTL 与截断

`progress` = `fabric.progressTtlMs`（默认 900s）；`finding/directive/query/answer/nack/dead_letter` = `reconcileTtlMs`（既有键）；`announce` 无 pending 态故无 TTL。`maxChars`（默认 2000）截断规则不变，board 文本同受此闸。

### 4.5 溯源（树降级为标注）

`via` 保留：direct 消息记 `{mode:"tree"|"mention", lca, hops}`（`mention` 表示经 `@label` 寻址——语法糖，仅展示）；`to==="board"` 的记录省略 `via`。`relation` 不再参与授权，仅供 `formatMessage` 展示与接收方判断可信度。`formatMessage` 头部保持 `不可信输入: from -> to` 纪律并覆盖全部新 kind；answer 头部附 `replyTo`/`evidence` 摘要行，announce 头部附 `topic`。

## 5. 发送权限与路由规则（覆盖项 2）

### 5.1 授权重写：协议自洽，不是权限

`src/core/message.ts` 的 `authorize()` 重写为：

```ts
export function authorize({ kind, relation, from }: AuthorizationInput): boolean {
  if (kind === "dead_letter") return from === "system"; // 系统专用
  if (kind === "result") return relation === "child"; // 协议上行
  if (kind === "directive") return relation === "parent"; // 协议下行
  if (kind === "announce") return true; // 仅 to==="board"（admit 前置校验）
  return true; // progress | finding | query | answer | nack：任意关系全开（含 self/unrelated/跨树，R3）
}
```

- 删除 `CanMessage`/`effectiveCanMessage`/`MentionRoute` 类型与 `authorize` 的 canMessage/mention 分支；`AuthorizationInput` 收敛为 `{kind, relation, from}`。
- 全链路不再存在 `message not authorized`；`router.admit()` 中 relation 计算保留（喂 `via` 溯源），授权失败只剩**协议自洽违背**（防御分支，throw）。

### 5.2 寻址

- `message_agent.to` ∈ `runId | "root" | "board" | "@label"`。`@label` 由工具层经 `MentionRegistry.resolve()` 解析为 runId 后走统一 admit（`viaMode:"mention"` 仅作审计标注）；label 未注册 → 结构化 `{ok:false, status:"unknown_label"}`。
- 终态 run 的 label 永久有效（registry 不移除，v1 现状）；对终态目标的发送按 §7 唤醒规则处理。
- `can_message` frontmatter：解析保留、**一次性 WARN**（"v2 已移除，发送不再受限，该声明被忽略"）、不进 `AgentTypeConfig`、不进 `configHashInput`、不透传工具。`CanMessage` 类型、`agent-types.ts` 赋值处、`runtime-adapter.ts` 两处透传、`message-agent-tool.ts` `canMessage` 依赖项一并删除（M-2/M-5 清单）。

### 5.3 路由

投递路径与树无关（v1 现状保持）：push 按 `to` 的 runId 直接 `runner.steer`（revive 场景经 `ReviveCoordinator.resolveTarget()` 重定向）；board 是单一逻辑目的地。树/hops 只出现在审计与展示层。

## 6. 点对点与广播的投递方式（覆盖项 3）

### 6.1 两级 discipline（D-1′ + D-4）

discipline 在 `router.admit()` 单同步段内判定并写入记录，之后**永不变更**：

| 目标状态                                                                  | discipline             | 投递动作                                                                                                                        |
| ------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `to === "board"`（announce）                                              | `board`                | admit 段内直接完成：board append + `engine.put(state:"delivered", terminalReason:"board")`；不进 mailbox、不占投递定时器（I-B） |
| `to` = run，`targetState ∈ {running, pending_start}` 或 reviving 中       | `push`                 | mailbox pump → `ports.inject` → `runner.steer`（运行中目标的 push 只花 context token，不花额外轮次）                            |
| `to === "root"`                                                           | `push`（channel 见下） | `sendRootContext`（`deliverAs:"steer", triggerTurn:true`）或 `sendRootDisplay`                                                  |
| `to` = run，`targetState === "gone"`，kind = query，revive 开启且预算未竭 | `push`                 | fire-and-forget revive，记录 pending，等新 run running 后 steer 进去（§7.3）                                                    |
| `to` = run，`targetState === "gone"`，其余情形                            | `push`（照常 put）     | pump P2 终结核处理：answer/nack→board_fallback；finding/directive/query→死信+board 归档；progress→drop（§9.3）                  |

### 6.2 接收方水位：降级规则（D-6，永不拒收）

`inboxOf(node)`（`router.rootInbox()` 的泛化）= 该接收方 `state ∈ {pending, claimed}` ∧ `discipline === "push"` ∧ 计入 channel 的记录数（root 只计 context 通道）。admit 时：

- **非 root 目标**：`inboxOf(to) ≥ fabric.inboxCap` 且 kind 可降级（§6.3）→ 该**新消息**降级 board 直达（append 到 board，topic = `record.topic ?? "inbox"`；记录 `state:"delivered", terminalReason:"board"`），返回 `{ok:true, status:"board", boardId}`。已排队记录不动（FIFO 公平）。
- **root 目标**：`rootInbox ≥ fabric.rootInboxCap` 或 `wakeRoot === false` → 记录仍 push，但 channel 降为 **display**（`sendRootDisplay`，用户立即可见）并**追加 board 副本**（topic = `record.topic ?? "root-inbox"`，T17 锚）。display 不占 context 预算，所以计数不增。
- 协议 kind（result/directive/dead_letter）与 reply-priority kind **永不降级**（M6：不计数、不降级——它们只在协议事件或"接收方自己发过 query"时出现，天然有界）。

### 6.3 计数与降级分类

| 分类                                                             | kind                                                              | 计入 inboxOf   | 可降级 |
| ---------------------------------------------------------------- | ----------------------------------------------------------------- | -------------- | ------ |
| 协议                                                             | result / directive / dead_letter                                  | 否             | 否     |
| reply-priority（`replyTo ∈ openQueries(接收方)` 的 answer/nack） | answer / nack                                                     | 否             | 否     |
| 普通                                                             | progress / finding / query /（非 reply-priority 的）answer / nack | 是             | 是     |
| 广播                                                             | announce                                                          | —（从不 push） | —      |

### 6.4 root 通道推导（`effectiveChannel` 重写为 `rootChannel`）

```
rootChannel(record, settings, caps) =
  "display"   若 wakeRoot === false，或 rootInbox ≥ rootInboxCap
  "display"   若 kind === "progress" ∧ legacy progressChannel === "display" ∧ caps.canRenderEntries（v1 语义）
  "context"   其余
```

被删调用点收敛：v1 的 `effectiveChannel` 6 处调用（router ×2、throttle ×3、mailbox ×1）改用 `rootChannel`；非 root 目标不再有 channel 推导（全部 context，即 steer）。`progressChannel` 键保留解析、标记 legacy。

### 6.5 发送永不阻塞（R2）的落点

- `message_agent` 的 `execute` 同步返回（含 revive 分支——不等 spawn 结果，返回 `{ok:true,status:"reviving",target}`；spawn 的 Promise 由 `ReviveCoordinator` 内部 catch，失败走死信）。
- `boundedSend` 与 `settings.budget.steerMs`（5s）赛跑不变；工具调用目标耗时 < 50ms（T6 锚）。
- 广播无部分失败概念（I-B）；board 写失败是同步结构化错误，不产生悬挂承诺。
- 回复延迟无上界（root 前台等待窗最长 `foregroundAutoBackgroundMs`）——诚实边界，见 §14 风险。

## 7. 接收方唤醒规则（覆盖项 4）

### 7.1 三类唤醒

| 唤醒                          | 通路                                                                                                  | 允许的来源                                                                                         |
| ----------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **W1a** 运行中子 agent 起一轮 | `runner.steer`（steer 注入发生在当前 turn 的 tool calls 之后、下一次 LLM 调用之前——本就会发生的调用） | 任意 direct kind（成本仅 context token）                                                           |
| **W1b** root 起一轮           | `sendRootContext`（`triggerTurn:true`）                                                               | 任意 direct kind；`wakeRoot:false` 时整体关闭（降 display+board）                                  |
| **W2** 复活终态 agent         | `spawn({resumeFrom, slotless:true, quiet:true, labelPolicy:"keep"})`                                  | **仅 direct `query`**，且 `reviveOnDirectQuery` 开启、会话 revive 计数 < `autoReviveMaxPerSession` |

**广播（announce / 任何 `to:"board"`）恒不唤醒**。重要到需要唤醒某人时，发送方必须显式对该接收方再发一条点对点消息——唤醒因此永远具名、可审计、计入接收方 inboxCap（I-W 升级通道）。

### 7.2 I-W 的执行：唯一出口断言 + fail-closed

- `core/message.ts` 新增纯函数 `wakeAllowed(env: Pick<MessageEnvelope,"to"|"kind">): boolean`（`to !== "board" && kind !== "announce"`）。
- 出口断言落在**全部**三个唤醒出口：`FabricMailbox.dispatch`（inject 与两个 root 端口共用此检查）、`sendRootContext` 装配处（`stack.ts` ports）、`ReviveCoordinator.tryRevive`（另断言 `kind === "query"`）。
- 违背时 **fail-closed 降级**：`console.error("[pi-subagent] fabric I-W violation …")` + 改走 board 归档（`consumed`/`terminalReason:"board"`），不 crash 投递循环。
- `mention.ts` 的 agent 侧终态 resume 分支（v1 对 progress/finding 开放复活）**收紧**：只保留 query→统一 revive 入口；其余 kind 不再 resume。用户侧 `@`（`mention/mention.ts` `routeMention`）不动——那是具名用户动作。

### 7.3 revive 设计（B2/M8 补全）

`src/fabric/revive.ts` 新增 `ReviveCoordinator`：

```ts
export interface ReviveCoordinator {
  /** 同步：是否已受理（含已在 reviving 中）。发起 fire-and-forget spawn，绝不等待。 */
  tryRevive(target: RunId, type: AgentTypeName, requester: NodeRef, queryKey: MessageKey): boolean;
  /** reviving 映射：target → 新 runId（spawn 已受理；未 running 前 mailbox 按 pending_start 对待）。 */
  resolveTarget(target: RunId): RunId | undefined;
  isReviving(target: RunId): boolean;
  onNewRunRunning(target: RunId): void; // onSnapshot 钩子：触发 pump(target)
  onNewRunSettled(target: RunId): void; // 剩余 pending query → 死信 "revived_run_settled"
  count(): number;
}
```

spawn 参数与理由（B2 逐条修复）：

1. **不带 `parentRunId`**：顶层 run（depth 0）不触发 canSpawn 嵌套校验，fire-and-forget 的 config error 不再可能；`onSpawnEdge("root", newRunId)` 使其在 fleet 树中如实显示为 root 子代。
2. **`quiet: true`**（`SpawnRequest` 新字段）：runtime-adapter 对 quiet run 的 `enqueue_delivery` 效果**不入 notifier**（直接置 consumed，不 `sendMessage`、不 `triggerTurn`）——堵死"复活 run 结束时以完成通知唤醒 root"这条绕过 I-W 的路径（B2 后半）。**答案只经 fabric 回流**：复活 prompt 明确要求"用 message_agent 发送 answer 后再结束"。
3. **`labelPolicy: "keep"`**（`SpawnRequest` 新字段，spawn-service repoint 分支第三态）：既不 register 也不 repoint，registry 中 `@label` 仍指向原终态 run（M8：防 `@expert` 被问答 run 抢走）；新 run 取派生唯一 label（`L-2`…）仅用于显示。
4. **预算夹紧（CC4 只收紧）**：`budgetOverride.totalMs = min(类型默认 total, requester 剩余 total 预算)`；requester 为 root 时不夹紧。`slotless: true` 不占并发槽。
5. **resumeLocks 冲突（M8 前半）**：spawn 返回 `already has a resume in progress` config error 时**不**视为失败——`reviving` 映射已存在即视为受理（合并语义由 router 侧完成：同目标后续 query 在新 run running 后一并 steer 进去，绝不静默消失）。
6. 会话级预算：`autoReviveMaxPerSession`（默认 10）计满后 query 走普通终结核（死信告知发送方 target gone）。
7. 失败路径：spawn 同步 admission 失败（类型不存在等）→ 该 query 及同目标 pending query 死信（reason `revive_failed`）。

### 7.4 root 前台约束（M2 处置：如实文档化，不改前台循环）

root 在前台 `Agent` 调用等待窗内收不到 steer 注入（`foregroundAutoBackgroundMs` 兜底转后台后恢复）。本方案**不修改**前台等待循环，只把语义写死进工具描述与本文档：**向 root 的 query 在 root 空闲或前台调用已 auto-background 后可被注入**；等待窗内的 query 由 root inbox 排队（push 纪律 + 重试），最迟在前台调用转后台后送达。备选（前台等待循环里把 root query 暴露为 tool update）列为扩展点，不实现。

## 8. 看板（共享公告）（覆盖项 5）

### 8.1 存储与有效范围（D-3）

- **存储**：`pi.appendEntry(customType: "subagent:board", entry)` + 内存镜像，完全复用 `createPiOutboxStore` 模式（append-only、无 ack、写后读回）；`readBack` 不可用时退化为内存 store（G5a 同款降级，v1 装配先例）。
- **范围**：**仅当前主 session**（单主 session 内全树共享：root 与所有 run 看同一块板）。`session_start` 从 prefetched 条目重建；**不跨会话**——新主会话看板归零。跨会话沉淀走既有 memory 子系统（非目标）。
- **BoardEntry**：

```ts
export interface BoardEntry {
  id: string; // = 源 fabric 记录 key（唯一、稳定、可被 boardRef/replyTo 引用）
  from: NodeRef;
  kind: "announce" | "answer" | "nack" | "finding" | "directive" | "query"; // 归档面
  topic: string;
  text: string; // 已过 maxChars 截断
  evidence?: string;
  replyTo?: MessageKey;
  createdAt: Millis;
}
```

### 8.2 容量与淘汰

全局 FIFO `boardCap`（默认 500）、每 topic `boardTopicCap`（默认 50）。淘汰优先保留：① 最新；② 被 `replyTo`/`boardRef` 引用过的条目（`FabricBoard.refSet()`）。写入路径：announce 广播、inbox 降级副本、root display 副本、answer/nack board_fallback、finding/directive/query 死信归档（topic 固定 `"dead-letter"` 或消息自带 topic）。

### 8.3 消费面

- **`read_board` 工具**（新）：参数 `{topic?: string, since?: string /*board entry id*/, limit?: number /*默认 20*/}`；按 createdAt 升序返回条目（id/from(label 解析)/kind/topic/text/evidence）。注册面与 `message_agent` 相同：子 run 经 runtime-adapter 注入 + host post-guard（`fabric.enabled` 门控）；`RESERVED_TOOL_NAMES += "read_board"`。
- **spawn 注入（B1）**：`buildPrompt()`（runtime-adapter）尾部追加 `FabricBoard.digest(boardInjectBudgetChars)`——预算化（默认 2000 chars）的 topic 目录（topic 名、条数、最后活跃时间）+ 每 topic 最新一条的一行摘要；板空时返回 undefined（零成本）。注入走宿主侧拼 prompt，**覆盖新 spawn 与 revive resume 两条路径**（同一条 `run()` 通路）。
- **诚实边界**：board 纪律是 best-effort——没有任何机制保证某条公告被任何 agent 读到（这正是 R2 承认的前提）；其收益依赖 §8.4 的 prompt 纪律。

### 8.4 prompt 纪律（机制的一部分，写死进文案）

`message_agent` 工具描述与注入文案固定三条：① 开工先问（已有知识/看板可查就先查，I-W 下作用有限但仍保留）；② 问完继续——发出 query 后不要等待，继续当前工作；③ **答案到了就转向**——push 进来的 answer 到达后立即据此调整工作（缺此条模型会无视答案继续傻干，同类机制最常见失效模式）。UI 语言纪律按 AGENTS.md：紧凑标记英文、劝诫散文可中文。

## 9. 配额 / 收件箱满时的处理（覆盖项 6）

### 9.1 四道幅度闸（D-10，全部非权限闸）

| 闸              | 参数                                                                                                              | 行为                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 摄取预算        | `inboxCap`（默认 8）/ `rootInboxCap`（默认 12）                                                                   | 超限降级（§6.2），永不拒收（I-D/T4）                                                                                                                                             |
| digest 去重     | `dedupeTtlMs`（默认 600_000，0=off）                                                                              | `sha256(kind+topic+normalizedText)` 在 `(digest, to)` 窗口内重复 ⇒ `{ok:false,status:"duplicate"}` + `rejected{reason:"duplicate"}` 记录；**只拦逐字重复**（诚实边界，§11.2-O2） |
| 速率            | `receiverMinIntervalMs`（默认 30_000；`minIntervalMs` 为 legacy fallback 键）/ `rootMinIntervalMs`（默认 10_000） | 投递期 P5 推迟（throttle per-link 机制不变），只推迟不拒收                                                                                                                       |
| 存储/扇出天花板 | `boardCap`/`boardTopicCap`/`maxChars`/`deadLetterQuota`（默认 5）                                                 | board FIFO 淘汰；死信 per 原发送者 run 限额（`suppressed_quota` 语义不变）                                                                                                       |

### 9.2 发送侧配额的处置

`maxPerRun`/`findingQuota`/`directiveQuota`：**停用为惰性键**——保留解析 + 一次性 WARN（"v2 已改为接收侧预算，此键不生效"），admission 不再检查。`deadLetterQuota` 保留生效（死信是 system→sender 的接收侧注入，属存储闸）。v1 的 `quota_exhausted`/`target_backpressure` 两个 admission 拒绝态**删除**。

### 9.3 投递失败终结核（M-6 统一 + M-4 顺序）

mailbox 中 4 处硬编码 `kind==="finding"||"directive"` 分支（pump 的 TTL 与 pre-claim target_gone、verdict 的 attempts_exhausted 与 target_gone）统一收敛为单一入口：

```ts
settleUndeliverable(record, reason /* ttl_expired | target_gone | attempts_exhausted | policy */):
  kind ∈ {answer, nack}:
      board.post(归档, topic = record.topic ?? "fallback") 成功
        → transition → consumed, terminalReason "board_fallback", boardRef        // 无死信
        失败 → v1 死信路径（发送方仍得信号）
  kind ∈ {finding, directive, query}:
      board.post(归档, topic = record.topic ?? "dead-letter")   // 尽力而为
      → v1 死信路径，dead_letter payload 附 boardRef
  kind === progress → v1（dropped/abandoned，无义务）
```

**顺序硬约束（M-4）**：pump 的 P2 批处理中，board_fallback/归档判定必须**逐条先于** `issueDeadLetters` 按 sender 分批执行——保住"一条原始消息至多一条死信"（I-F11′ 与 v1 §16-② 证明继续成立）。

### 9.4 openQueries（reply 升级判定的状态）

`router` 内 `Map<NodeRef /*发送方*/, Set<MessageKey>>`：admit query 时登记；admit answer/nack 且 `replyTo` 指向接收方自己的未闭 query 时移除；query TTL 过期惰性清理；`onRunSettled(sender)` 时整组清空（sender gone 后 answer 走 board_fallback，无需保留）。**hydrate**：从 engine 内 `kind === "query"` 且未过 TTL 的记录重建，并扣除已有匹配 answer/nack 的项（M-7：否则迟到 answer 无法命中，reply 升级静默退化）。

### 10.1 `router.admit` 输入/输出

```ts
export interface AdmissionInput {
  to: NodeRef; // runId | "root" | "board"（@label 已由工具层解析）
  kind: MessageKind; // message_agent 面不接受 result/dead_letter
  text: string;
  generation: number; // host 钉死（v1 不变）
  topic?: string; // announce 必填（校验）
  replyTo?: MessageKey; // answer/nack 必填（校验）
  evidence?: string; // answer 必填（校验）
  viaMode?: "tree" | "mention"; // 审计标注
}

export type AdmissionResult =
  | { ok: true; status: "accepted"; key: MessageKey; seq: number; superseded?: MessageKey } // push 已入队
  | { ok: true; status: "board"; key: MessageKey; seq: number; boardId: string } // board 直达（announce/降级）
  | { ok: true; status: "reviving"; key: MessageKey; seq: number; target: RunId } // query→终态，revive 已发起
  | { ok: false; status: "invalid_params"; message: string } // kind 字段约束不满足
  | { ok: false; status: "duplicate"; key: MessageKey; seq: number; retryAfterMs: number }
  | { ok: false; status: "board_write_failed" }; // 零记录、可安全重试
// throw 保留：shutting down / sender is not running / persist failed / 协议自洽违背（防御）
```

## 11. 关键决策与取舍

### 11.1 上游拍板决策的落地要点（为什么这么做——浓缩）

- **闸移接收侧**：R1（任意寻址）+ R2（推送投递）下，发送侧任何白名单/配额都可被合法流量击穿；接收侧摄取预算是唯一与 R1/R2/R3 全兼容的闸。
- **两级 discipline**：pi steer 的实测语义（注入下一个本就会发生的 LLM 调用）使"notify 级"对运行中 agent 无意义——塌缩为 push/board 是删代码不是减功能；`urgent` 随之失去存在理由。
- **广播 = 1 条看板记录**：任何"N 路扇出"都会让 R1 的广播成本随受众线性增长并重新引入唤醒放大；O(1) 结构是 I-W 与成本上界的共同来源。
- **answer/nack 走 board_fallback 而非死信**：非阻塞语义下"迟到"不是失败而是知识沉淀；但 finding/directive/query 保留死信——否则发送方失去失败信号（parent 会看到 delivered 以为送达）。
- **I-W 唯一出口断言**：分散在"三个落点"的检查必然漏（v1 mention resume 就是反例）；所有 `sendRootContext`/`runner.steer`/`spawn({resumeFrom})` 调用点共用一个断言 + fail-closed 降级。

### 11.2 上游留白、本方案补定（O 系列）

| #   | 问题                                 | 决策                                                                                                                                                                                                                          | 理由                                                                                                                                                                                |
| --- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| O1  | announce 是否保留为独立 kind         | **保留**（第 9 个 kind）                                                                                                                                                                                                      | 广播内容需要与 progress（latest-wins supersede 不适用）、finding（死信义务不适用）语义区分的第一类身份；§15.6 对看板收益的论证本身以"agent 主动 announce"为单元；成本仅为一个字面量 |
| O2  | digest 去重去留                      | **保留**（`dedupeTtlMs` 默认 600_000，0=off）                                                                                                                                                                                 | O(1) 哈希拦截逐字重复，是四道闸中最便宜的一道；诚实标注"只拦逐字重复"——语义去重交给接收方模型（不造分类器）                                                                         |
| O3  | board 写失败语义                     | board append 抛错 ⇒ `{ok:false,status:"board_write_failed"}`，**零记录**（I-F9 不成立即无承诺），可安全重试；append 成功后 `engine.put` 抛错 ⇒ board 条目已成立（投递已发生），WARN 降级、工具仍返回 `ok:true,status:"board"` | 不产生"被 `discipline==="push"` 过滤器挡在 TTL 之外的 pending 僵尸"；与 v1 "put 抛错⇒admission 失败"的承诺方向一致                                                                  |

### 11.3 明确不做（非目标，上游定论）

## 13. 测试要点（覆盖项 8）

### 13.1 单元（`tests/fabric/`、`tests/core/`）

- **authorize 新矩阵**：9 kind × {self,parent,child,ancestor,descendant,sibling,unrelated}——6 开放 kind 全通（含 self/unrelated）；result/directive/dead_letter 按协议；`makeMessageKey`/`parseMessageKey` 接受 `"board"`。
- **board**：FIFO 容量淘汰（全局+per-topic）；被 `replyTo`/`boardRef` 引用条目的保留；prefetched 重建；readBack 缺席内存降级；digest 预算截断；`refSet` 正确性。
- **router**：kind 约束（announce 无 topic / answer 无 replyTo/evidence / nack 无 replyTo → `invalid_params`）；digest 命中 → `duplicate` + `rejected` 落盘；**T4 锚：inboxCap/rootInboxCap 饱和后新 push 降级 board 且永不 `ok:false`（除 duplicate/board_write_failed/invalid_params）**；协议 kind 与 reply-priority 不计数不降级；openQueries 登记/移除/过期/settle 清理/hydrate；v1 legacy 配额键惰性（不拒收）；board 写失败 → 零记录。

- **revive**：fire-and-forget（**T6 锚：工具调用耗时 < 50ms**）；无 parentRunId（不触发 canSpawn）；quiet 抑制（无 notifier 入队/无 triggerTurn——I-W 断言测试）；`labelPolicy:"keep"`（registry 不 repoint、新 run 派生 label）；预算夹紧（CC4 只收紧）；`autoReviveMaxPerSession` 计满回落死信；resumeLocks 冲突合并（第二个 query 不消失，新 run running 后一并 steer）；spawn 失败 → 死信 `revive_failed`；新 run settle → 剩余 query 死信。

## 14. 实施风险与要点（给下游）

1. **已知暴露面（§15.4 遗留，如实接受）**：删闸后任意深度、正在处理不可信 web 内容的 agent 都能 direct 唤醒拥有全部工具的 root（W1b）。缓解 = `wakeRoot` 开关 + root inbox cap + 工具描述纪律；残余风险上游已接受。安全加固（如 root 入站内容沙箱标注）是后续独立课题。
2. **M2 现实**：前台 Agent 等待窗内 root query 延迟无上界（≤ `foregroundAutoBackgroundMs`）；方案选择文档化（O4），工具描述必须如实告知模型。
3. **board 收益的前提**：看板与 result 面对同一压缩瓶颈；只有"定向提问+revive"（V2-E）绕过它——V2-C 单独交付的收益有限，排期时不要用"M3 性价比最高"的旧判断（§15.6 已推翻）。实施顺序按依赖排（V2-A→B→C→D→E），但**价值验收锚在 V2-E**。
4. **revive 成本**：一次带完整 context 的 run，缓存过期后可能高于提问方自己重新调研——`autoReviveMaxPerSession` 默认 10 与 `reviveOnDirectQuery` 默认 false（保守灰度）是刻意的。
5. **共享文件冻结面**（§0.2）：V2-A..E 触碰 `stack.ts`/`settings.ts`/`spawn-service.ts`/`index.ts`/`runtime-adapter.ts`/`core/types.ts`——与 quota 工作互斥，排期前确认。
6. **每阶段四件套**：`format:check → typecheck → test → build` 全绿再合入（CI 纪律）；属性测试与转移矩阵 lockstep（AGENTS.md）。
7. **运行时标识不改名**：`subagent:board` 新 customType 沿用 `subagent:*` 命名族；`[pi-subagent]` 日志前缀不变。
8. **计时器纪律**：本方案新增代码无定时器（board/revive 均事件驱动；revive 的等待由 mailbox 既有单定时器与 onSnapshot hint 承载）——无需新增 unref 关注点；模块级可变状态一律收敛进 `buildFabric` 闭包（/reload 语义）。
