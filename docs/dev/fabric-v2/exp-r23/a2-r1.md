# A2-R1 实施方案：扩展内部「静默后台 run」

> 需求：扩展内部代码（host 侧 hooks / 工具 / scheduler 等非 run 上下文，或某个 run 的发起方逻辑）
> 要能派生一种 run，同时满足三点：
> ① 不触发嵌套委派校验（canSpawn 白名单 + maxNestedDepth）；
> ② 不产生顶层完成通知，更不唤醒主会话起一轮模型调用；
> ③ 不被发起方的取消级联杀掉（发起方 run 取消/超时/被用户停止时，静默 run 独立存活）。
>
> 现状基线：`src/goal/hook.ts#runVerifier`（约 217–249 行）是今天唯一的「扩展内部派生 run」
> 先例，它**不满足**本需求——无 `parentRunId` 的 spawnAndWait 会照常发顶层完成通知
> （`ackWindowMs` 默认 0，ack 迟于同步投递链，fail-open）。本方案就是把它缺的那块补齐并产品化。

## 0. 一句话结论

**用「合成 owner id 作 `parentRunId`」这一个参数同时买到全部三点**——这是 `SubagentWorkflow`
子女 run 已在生产中验证过的同一条路径（`stack.ts:1434` 的 `parentRunId: workflowId`）。再配
「不传 `signal`」切断外部信号脐带。建议新增一个无状态 helper（`src/service/silent-spawn.ts`）
把配方固化成 API，避免调用方复制 folklore。

核心配方（先给结论，逐参数理由见 §3）：

```ts
const ownerId = makeSilentOwnerId("my-feature"); // 如 "silent-myfeature-a1b2c3d4e5f6"
const started = await stack.spawn.spawn({
  type: "general", // 任意注册过的 agent type
  prompt: "...",
  label: "my-bg-task", // 可选但建议
  parentRunId: ownerId, // ★ 核心：合成 id，绝不传真实发起方 run 的 id
  budgetOverride: { totalMs: 5 * 60_000, queueWaitMs: 60_000 },
  // signal / detachSignalOnStart：刻意不传 —— 与任何外部 turn signal 零链接
  // slotless：默认不传（false），走并发池（理由见 §3.4）
});
// started: { runId, label } | { error }；自己保存 runId，用 waitOutcome / pi.events 收结果
```

## 1. 机制依据（为什么这个配方成立）

以下每条都已对源码核实（行号为当前 master 实测位置，写代码时以函数名为准）。

### 1.1 点①：嵌套校验只对「本 SpawnService 当前跟踪中的活父」生效

校验在 `src/service/spawn-service.ts` 的 `spawn()` 内（X3 段，搜 `let depth = 0`）：

```ts
let depth = 0;
if (req.parentRunId) {
  const parent = nesting.get(req.parentRunId);
  if (parent) {                       // ← 只有命中进程内 nesting 表才校验
    if (!parent.canSpawn?.includes(req.type)) return { error: ... };  // 白名单
    depth = parent.depth + 1;
    if (depth > maxNestedDepth) return { error: ... };                // 深度（默认 3）
  }
}
```

- `nesting` 表只登记**本服务 spawn 出来的 run**（`spawn()` 里 `nesting.set(runId, ...)`），
  且父 run `finish()` 后条目即被删除。因此：
  - **不传 `parentRunId`** → depth 0 直接过；
  - **传合成 id**（从未被 spawn 跟踪）→ `nesting.get()` 为 undefined → 同样 depth 0 直接过、零白名单检查。
- 这是注释明确认可的设计（spawn-service.ts ~327–332 行："untracked/foreign parentRunId …
  is left unrestricted (depth 0, no canSpawn cap)"），不是钻空子——`parentRunId` 本就不是
  顶层 Agent 工具的模型可见参数，能传它的只有 host 侧代码和 RPC（`src/rpc/protocol.ts`
  的 `SpawnParams.parentRunId` 本就接受任意字符串）。
- **反例（不要做）**：把 `parentRunId` 设为真实发起方 run 的 id。若发起方 type 的
  `canSpawn` 不含目标 type、或深度超限，spawn 直接 config error；即使过了校验，
  也会被点③的级联杀掉（见 1.3）。注意：若发起方 run **已经结束**（nesting 条目已删），
  以其 id 为父倒是能过校验——但语义是错的（display label），且毫无必要。

### 1.2 点②：通知链路的唯一闸门是 CC2（`parentRunId !== undefined`）

完整链路：`src/core/state-machine.ts#finish()` 对每次终态无条件产出 `enqueue_delivery`
效果 → `src/service/runtime-adapter.ts` 的效果解释器 → `deps.notifier.enqueue()`
（`src/delivery/notifier.ts`，`enqueue → attempt` 同步执行，无 hold 时不等 ack）→
`src/stack.ts#sendFormatted`（~911 行）→ `pi.sendMessage({customType:"subagent:notification",...}, {triggerTurn:true})`。
**`triggerTurn:true` 就是"唤醒主会话起一轮模型调用"的机制**（对比：compact-hint/quota hint
刻意用 `triggerTurn:false`）。

唯一的过滤点是 `src/service/runtime-adapter.ts` 的 **CC2**：

- `createRuntimeRunnerAdapter()` 内维护 `childRunIds = new Set<string>()`；
- `run()` 入口（同步段，任何 await 之前）：`if (spec.request.parentRunId !== undefined) childRunIds.add(spec.runId)`；
- 三处消费，全部静默丢弃（不进 outbox、不 sendMessage、不唤醒）：
  1. `enqueue_delivery` 解释器（"child runs are consumed exclusively by their owner"）；
  2. `settleConfigFailure()`（H2/config 失败路径的快照+通知）；
  3. `deadlineNoticeHandler()`（timeout-notify 宽限/延长通知，D-8）。

**判据只是 `parentRunId !== undefined`，不检查这个 id 是不是真实 run**——所以合成 id 同样
触发 CC2。这正是 workflow 子女 run 的做法（`src/workflow/host.ts` ~599–606 行，
`parentRunId = workflowId` 合成串）。

**已排除的替代路径：`expectAck`/ack 抑制不可靠。** `spawnAndWait`/`waitOutcome` 会经
`onOutcomeAcked → notifier.ack`（stack.ts ~1119–1126 接线）消费通知，但
`ackWindowMs` 与 `coalesceWindowMs` 默认均为 0（`src/config/settings.ts:384–386`），
`notifier.enqueue → attempt → send` 是同步链，先于 ack 的微任务执行——fail-open 发通知
（delivery v2 设计文档明确承认）。要靠它静默必须把 `ackWindowMs` 调 >0 且仅覆盖
completed 类，全局副作用，不可取。

**已知缺口（潜伏缺陷，见 §4 硬化项）**：`src/service/spawn-service.ts#start()` 的
catch 安全网（`deps.notifyTerminalFailure?.(failed)`，~243 行）→ `src/stack.ts#notifyTerminalFailure`
（~1134–1167 行）**不查 childRunIds**。即：若 `runner.run()` 本身抛异常（基础设施故障，
正常路径不可达），即使是子 run 也会发一条顶层通知。要让"绝不通知"成为硬保证，需顺手修掉。

### 1.3 点③：取消级联只沿 `childrenOf` 走；外部 `signal` 是第二条脐带

级联的数据基础：`src/service/spawn-service.ts#spawn()` 仅当请求带 `parentRunId` 时登记
`parentOf.set(runId, parent)` / `childrenOf.get(parent).add(runId)`（~431–441 行）。

两条触发链：

1. **显式中止**：`spawnService.abort(runId)`（`abort_subagent` 工具 / 内部调用）先
   `cascadeChildren(runId, "parent_abort")` 再杀自身（~528–533 行）——但只级联
   `childrenOf.get(runId)` 里的直接/递归子孙。合成 owner id 下，静默 run 不在任何真实
   run 的 `childrenOf` 里，**免疫**。
2. **父 run 自身因任何原因取消**（user_stop / timeout / external）：`src/runtime/runner.ts`
   的 cancel handle 回调无条件调 `this.d.onChildAbort?.(req.runId, "parent_abort")`
   （~399–412 行），经 `src/stack.ts:1079` 接线 `onChildAbort: (id, cause) => spawnRef.current?.abort(id, cause)`
   → 走链 1。同上，静默 run 不在链上，**免疫**。

外部信号层：`SpawnRequest.signal`（经 `src/service/request-threading.ts:26` 的
`THREADED` 列表 verbatim 穿透所有 hop）进 `createCancelHandle(req.runId, gen, req.signal, ...)`。
**不传 `signal` 即无此链接**。若调用点处于主会话 turn 上下文、又想借 signal 做"启动前
准入"（admission 前已 aborted 仍会立即取消——这是特性），可传 signal +
`detachSignalOnStart: true`（runner.ts ~414 行 `if (req.detachSignalOnStart) cancel.detach()`
在 cancel handle 创建后立即摘除外部 listener）；`Agent` 工具的 `run_in_background` 分支
（`src/tools/agent-tool.ts` ~283–296 行）是现成先例。detach 只解除外部 listener，
`abort_subagent`/watchdog 走 `activeCancels` 的路径不受影响。

**owner 自己的收尸锚点**：`stopChildrenOf(ownerId, cause)`（CC1，spawn-service.ts）是唯一
对"本身不是 run 的父 id"有效的 owner-stop 入口（不查 `running.has(parentId)`），workflow
正是用它收尸。静默 run 自己 `finish()` 时会从 `parentOf`/`childrenOf` 删除自身，无泄漏。

### 1.4 与 workflow 先例的对齐

| 维度      | workflow 子女 run                                                                                                   | 本方案静默 run                      |
| --------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 合成父 id | `wf_<uuid20>`（`src/tools/workflow-tool.ts:398`）                                                                   | `silent-<ownerKey>-<rand>`          |
| 注入点    | `stack.ts:1417–1441` `createOrchestrator({..., parentRunId: workflowId})` → `host.ts:599` → `spawner-adapter.ts:46` | 直接 `stack.spawn.spawn()` / helper |
| slotless  | **false**（D-W3：故意保留并发池与 queue-timeout 保护）                                                              | 同（见 §3.4）                       |
| 收尸      | `stopChildrenOf(workflowId)`                                                                                        | `stopChildrenOf(ownerId)`（按需）   |

fabric 侧：`onSpawnEdge(parent, child)`（stack.ts，fabric enabled 时）会把合成父作为
幽灵节点写进 `FabricTree`（`src/fabric/tree.ts#append`）——workflow 已在生产这么用，
对路由无影响（该节点无 mailbox、无人可寻址），已验证无害。

## 2. 落地设计：新增 `src/service/silent-spawn.ts`

### 2.1 设计原则

- **无状态纯函数**：不持任何模块级可变状态（/reload 不变量——扩展会在同一进程重激活，
  模块缓存不失效；`src/index.ts` 的 HOST_KEY 守卫模式同理）。ownerId 由调用方持有，
  helper 每次调用都是纯翻译：`SilentSpawnRequest → SpawnRequest`。
- **service 层**：紧挨 `spawn-service.ts`（它是对 SpawnService 的薄封装，不是新子系统）。
  不改 `Stack` 接口、不改 `src/index.ts`（I7：index 只做组装）——调用方本来就持有
  `stack.spawn`（hooks 经 `holder.current?.spawn`，先例：`src/goal/hook.ts:219`）。
- helper 只在 **host 侧**可用。子会话内的扩展实例因 HOST_KEY 守卫是 inert 的，拿不到
  `stack.spawn`——这是设计而非缺陷：静默派生是宿主权限（与 X3 注释的信任模型一致）。

### 2.2 代码草图（可直接落地的骨架）

```ts
// src/service/silent-spawn.ts
import { randomUUID } from "node:crypto";
import type { SpawnService } from "./spawn-service.js";
import type { JsonSchema, RunOutcome, RunId } from "../core/types.js";

/** 合成 owner id：永远不与真实 runId 冲突（newRunId 生成器避开 records/running/tombstones，
 *  且二者格式不同；workflow 的 wf_ 前缀同理）。 */
export function makeSilentOwnerId(ownerKey: string): string {
  const safe = ownerKey.replace(/[^a-zA-Z0-9_-]/g, "").slice(0, 24) || "internal";
  return `silent-${safe}-${randomUUID().replace(/-/g, "").slice(0, 12)}`;
}

export interface SilentSpawnRequest {
  /** 出现在合成 ownerId 里的调用方标识（排查用），如 "cache-probe"、"goal-eval"。 */
  ownerKey: string;
  type: string;
  prompt: string;
  label?: string;
  cwd?: string;
  /** 建议显式给：explicit totalMs ⇒ 硬顶（D-10，无宽限无延长）。 */
  budgetOverride?: { totalMs: number; queueWaitMs?: number };
  /** 默认 false（走并发池）。仅"必须立即启动、绝不排队"的场景才 true。 */
  slotless?: boolean;
  schema?: JsonSchema; // 可选结构化输出（见 §3.8）
  modelHintOverride?: string;
  thinkingOverride?: "low" | "medium" | "high";
}

export type SilentSpawnResult =
  { ok: true; runId: RunId; ownerId: string; label?: string } | { ok: false; error: { message: string } };

export async function spawnSilent(
  spawn: Pick<SpawnService, "spawn">,
  req: SilentSpawnRequest,
): Promise<SilentSpawnResult> {
  const ownerId = makeSilentOwnerId(req.ownerKey);
  const started = await spawn.spawn({
    type: req.type,
    prompt: req.prompt,
    ...(req.label !== undefined ? { label: req.label } : {}),
    ...(req.cwd !== undefined ? { cwd: req.cwd } : {}),
    ...(req.budgetOverride !== undefined ? { budgetOverride: req.budgetOverride } : {}),
    ...(req.slotless === true ? { slotless: true } : {}),
    ...(req.schema !== undefined ? { schema: req.schema } : {}),
    ...(req.modelHintOverride !== undefined ? { modelHintOverride: req.modelHintOverride } : {}),
    ...(req.thinkingOverride !== undefined ? { thinkingOverride: req.thinkingOverride } : {}),
    parentRunId: ownerId, // ★ 三点合一的核心参数（理由见 §3.2）
    // 刻意不传：signal / detachSignalOnStart —— 静默 run 与任何外部 turn signal 零链接。
    // 若调用点确需"启动前准入"，由调用方自行加 signal + detachSignalOnStart: true
    // （agent-tool run_in_background 先例），helper 不默认提供以免误用。
  });
  return "error" in started
    ? { ok: false, error: started.error }
    : { ok: true, runId: started.runId, ownerId, ...(started.label !== undefined ? { label: started.label } : {}) };
}
```

### 2.3 接线与使用姿势

**不改任何现有文件即可用**（helper 是纯函数）。典型调用方：

```ts
// 例如某个 hook（goal 式）内部：
const stack = holder.current; // index.ts 的 session holder
if (!stack) throw new Error("no active session");
const started = await spawnSilent(stack.spawn, {
  ownerKey: "my-feature",
  type: "general",
  prompt,
  label: "my-bg",
  budgetOverride: { totalMs: 5 * 60_000 },
});
if (!started.ok) {
  /* config error（unknown type / model hint / quota gate） */
}
// 收结果（三种姿势，按需选）：
// a) 有界等待：   const r = await stack.spawn.waitOutcome(started.runId, 10_000); // settled | pending
// b) 事件回调：   pi.events.on("subagent:completed", handler) 里按 runId 过滤（stack.ts:1076 接线）
// c) 快照轮询：   stack.query.get(runId)  // status / diag / outcome
// 收尸（可选）：  await stack.spawn.stopChildrenOf(started.ownerId, "user_stop");
```

注意 a) 的 `waitOutcome(runId)`（不带 waitMs）会挂一个无定时器的 waiter，run 终态时
resolve——适合"发完就忘、稍后收"。**不要用 `spawnAndWait`**：它语义是同步等待 + expectAck，
对静默 run 既无必要（通知已被 CC2 丢弃，ack 无对象）又会把调用方挂住。

## 3. 调用配方逐参数说明

### 3.1 `type` / `prompt` / `label` / `cwd`

与普通 spawn 完全一致。`label` 建议显式给：label 会进 mention registry
（`onLabel` 接线），但 @ 自动补全只列 root 直属 run（`src/index.ts#mentionAutocompleteEntries`
过滤 `target.parent !== "root"`）——合成父的 run **不进补全**，但可被
resolve-target（exact → prefix → label）解析：即用户知道 label 就能 `@label` 对它发消息
（steer）。这是特性不是漏洞（静默 ≠ 不可交互），要在文档里写明。
`label` 不传时从 prompt 首行派生并去重（999 上限），批量后台任务建议显式命名。

### 3.2 `parentRunId: <合成 ownerId>` ——核心参数，一参三效

- **点①**：untracked parent ⇒ X3 校验整体跳过（depth 0、无 canSpawn 检查）；
- **点②**：`!== undefined` ⇒ CC2 把该 run 标记为 child，全部三类通知
  （完成/config 失败/超时宽限）被丢弃，不进 outbox、不 `sendMessage`、不 `triggerTurn`；
- **点③**：不在任何真实 run 的 `childrenOf` 里 ⇒ 对两条级联链免疫；
- 附带收益：`stopChildrenOf(ownerId)` 给调用方一个显式收尸锚点（与 workflow 同构）。
  **绝对禁止**传真实发起方 run 的 id（会同时破坏三点，见 §1.1/§1.3）。

### 3.3 `budgetOverride` ——建议显式

后台任务应自缚预算：`{ totalMs, queueWaitMs? }`。注意 **显式 `totalMs` ⇒ 硬顶**
（`applyBudgetPolicy`，D-10：`maxTotalFactor=1`，无宽限无延长——超时即 timed_out，
不会有 timeout-notify 的宽限回合；反正宽限通知对 child run 也被 CC2 丢了，行为一致）。
不传则用全局默认预算，watchdog 照常武装（每个 run 独立预算，与父无关——这正是"独立存活"
的另一面：**静默 run 也会被自己的 watchdog 正常超时杀掉**，这是防挂死底线，必须保留）。

### 3.4 `slotless` ——默认 false

- `false`（推荐，同 workflow D-W3 决策）：占 `concurrencyLimit`（默认 6）槽位、享受
  queue-timeout 保护；代价是 6 槽满时静默 run 会排队（`queueWaitMs` 超时则 config 失败）。
- `true`：`SingleSlotPool` 直接发票，必启不排队；代价是无排队保护、绕过全局并发上限
  （嵌套 Agent 工具强制 slotless 是因为父 run 已占槽）。仅"探测/ping 类必须立即启动"
  的场景用。
  默认走池：后台任务不该有能力饿死用户的前台并发。

### 3.5 `signal` / `detachSignalOnStart` ——刻意不传

不传 `signal` = 与调用时的 turn 上下文（Esc、强制压缩等外部中止源）零链接，是最简单
且最强的隔离。`detachSignalOnStart: true` 只在"要传 signal 做启动前准入、启动后解绑"
时才有意义（`agent-tool.ts` run_in_background 先例）；helper 不默认提供，调用方自行加。

### 3.6 `expectAck` ——不传（false）

expectsAck 只影响 deadline-notice 的抑制判定与 spawnAndWait 的 ack 链；CC2 已把 child run
的通知全丢，ack 无对象。传了无效果但混淆语义。

### 3.7 `resumeFrom` ——不用于本场景

resume 走同一 spawn 准入（resumeLocks 双锁互斥、目标仍在跑则拒绝并提示 steer）。
如需"重启上次的后台任务"，用普通（非静默）方式先完成旧 run，再静默 spawn 新 run。

### 3.8 `schema`（可选）

静默 run 支持 `schema` 结构化输出：`runtime-adapter.ts` 的 X10 双重校验会把
`structuredResult` 附在 `RunOutcome` 上（`applyStructuredOutputPolicy`，~523 行），
`waitOutcome` 拿到的 outcome 直接带 `structuredResult`，无需自行解析 `text`。
（CC2 丢弃 enqueue_delivery 在 `hold` 判定之前，schema 的 hold 机制对 child run 不起作用
也无害。）传 schema 时注意用真对象（`normalizeSchemaInput` 的既有教训——字符串 schema
会 throw）。

### 3.9 后续委派

静默 run 自己会进 `nesting` 表（depth 0 + 其 type 的 canSpawn）。若其 type 无 `canSpawn`
frontmatter，嵌套 Agent 工具不注入（或注入后子派生被拒——type 无 canSpawn 即禁止再派生），
正好符合"后台任务不再扩散"的默认预期；若 type 声明了 canSpawn，其孙 run 走正常校验，
行为与任何顶层 run 一致。

## 4. 坑、约束与残余风险（如实清单）

### 4.1 做不到 / 不打算做的

1. **活不过主会话**：`session_shutdown`（`src/index.ts` ~541–548 行）对**所有**非终态 run
   `query.stop(runId, "shutdown")`——`/reload`、`/new`、`/resume`、fork、quit 都会杀掉静默
   run。bash job 有跨会话收养（`handoffInProcess`/`adoptOrphans`），subagent run **没有**
   等价机制。"静默"只保证不被**发起方**级联，不保证跨会话存活。若未来需要跨会话，
   得另做收养子系统（bash 模式），本方案不含。
2. **不可见 ≠ 静默**：CC2 只断"通知"，不断"可见性"。静默 run 仍会：
   - 出现在 fleet widget——`fleet-widget.ts` 的树按 `row.parentRunId` 分组，合成父不是
     run、不在 rows 里 ⇒ 该 run 按**根行**渲染（不是被藏起来，反而是顶层一行）；
   - 出现在 `/agent status` 与 `subagent:started`/`subagent:completed` 事件流；
   - 被 `background-status` 的 `runningSubagents` 计数——影响 feishu 完成卡的
     background-idle 门控（主会话停了但静默 run 在跑 ⇒ 不发"任务结束"卡）和
     cache-keepalive 的 busy 判定。这些影响**大多是正确的**（确实有活在跑），
     但调用方要知情。若要 widget 级隐藏，需在 `FleetRow` 构建处按 ownerId 前缀约定过滤
     （产品决策，本方案列为可选后续，未包含）。
3. **发起方在子会话内时做不到**：子会话的扩展实例是 inert 的（HOST_KEY），拿不到
   `stack.spawn`。"由某个 subagent 的会话内逻辑派生静默 run"必须经 fabric 消息请求
   host 代发（如果将来需要），本方案不含。
4. **静默 run 的 message_agent 默认死信**：它作为子会话持有 `message_agent`，默认
   `can_message: parent only`，而其"父"是合成节点（无 mailbox）⇒ 发给 parent 的消息进
   dead letters。规避：给所用 agent type 配 `can_message: []`（或明确不依赖回信）。
5. **孤儿语义**：发起方（host 侧逻辑）崩溃后无人 `waitOutcome`，run 会自然跑完/超时，
   结果留在 records/tombstones 与 session 日志里，无人消费——可接受（有 watchdog 兜底），
   但要在调用方文档里写明"发起方应尽量持有 handle"。

### 4.2 已知缺陷与硬化项（建议随本方案顺手修）

1. **`notifyTerminalFailure` 的 CC2 缺口**（§1.2）：`spawn-service.ts#start()` catch →
   `stack.ts#notifyTerminalFailure` 不查 childRunId。修复建议（二选一，推荐前者）：
   - `spawn-service.ts#start()` 的 catch 里改为 `if (req.parentRunId === undefined) deps.notifyTerminalFailure?.(failed);`
     ——与 CC2 同判据（该处拿得到 `req`），一处改动同时修好 workflow 子女与静默 run；
   - 或给 `SpawnServiceDeps.notifyTerminalFailure` 增加 `isChild` 参数由 stack.ts 过滤。
     注意这是**行为变更**（今天的 workflow 子女在该异常路径上会发顶层通知），按 bug 修，
     CHANGELOG 记 fix，并补回归测试（§5.4）。
2. **`parentRunId` 是字符串信任边界**：RPC `SpawnParams.parentRunId` 本就允许任意串，
   本方案不扩大攻击面（host 侧代码本就是可信层）；但若未来把 ownerId 约定（`silent-`
   前缀）用于 widget 过滤等行为开关，过滤逻辑必须只认前缀、不赋予特权（它不改变
   spawn 语义，只是显示分组）。

### 4.3 残余风险

- **预算语义**：显式 `totalMs` 是硬顶无宽限——调用方若想要"宽限续命"语义，别传
  `budgetOverride.totalMs`（用全局预算）或明确接受硬顶。
- **label 命名空间共享**：静默 run 的 label 与普通 run 共用去重空间（999 变体上限），
  高频派发场景给确定性 label（如 `probe-<ts>`）避免撞 999。
- **fabric tree 幽灵节点**：每次静默 spawn 追加一条 `ownerId → runId` 边；run 终态后
  `tombstone()` 清理，与 workflow 节点同生命周期，无累积泄漏（已核实 tree.ts）。
- **文档漂移**：X3/CC2 的"untracked/foreign parent 不受限"是**注释载明的契约**，
  但若有人未来把 X3 改成"未知 parent 一律拒绝"（更严格的 fail-closed），本配方即碎。
  建议把 §5.1 的测试写成**契约测试**钉死该语义，改动者会先红测试再动代码。

## 5. 验证点（测试怎么写、断言什么）

测试放 `tests/service/silent-spawn.test.ts`（helper 单测）+ 在
`tests/service/spawn-service.test.ts` / `tests/service/runtime-adapter.test.ts`
补契约测试（沿用现有 stub Runner/Notifier 的测试基建）。

### 5.1 点①：绕开嵌套校验（契约测试，钉死 X3 语义）

- 构造 `createSpawnService`，先 spawn 一个 type=A、无 `canSpawn` 的"发起方 run"
  （stub runner 让它保持 running）；
- 再以 `parentRunId: <其 runId>` spawn type=B：断言返回 `error`（白名单拒绝）——
  证明校验对真实活父生效（对照组）；
- 以 `parentRunId: makeSilentOwnerId("t")` spawn type=B：断言成功且后续 snapshot 的
  `parentRunId === ownerId`；再连 spawn 5 层（每层父都用新合成 id）：断言全部成功
  （证明 maxNestedDepth 对 untracked 父不计数）。
- 深度上限对照：用真实嵌套链（活父）打到 `maxNestedDepth+1`，断言第 4 层被拒。

### 5.2 点②：零通知、零唤醒

- 用真 `createRuntimeRunnerAdapter`（stub driver/watchdog），`notifier.enqueue` 用 spy；
- 静默 spawn（带 `parentRunId`）→ 让 runner 完成：断言 spy **从未被调**
  （`enqueue_delivery` 被 CC2 丢弃）；对照：不带 `parentRunId` 的 run 完成时 spy 被调一次
  （payload.runId 正确）——证明过滤是 CC2 而非 notifier 坏掉；
- `settleConfigFailure` 路径：构造 H2/resolveSessionSpec 失败（或传已过期的
  `deadlineAt`）：断言 spy 为零（对照：顶层 run 同路径发一条）；
- `deadlineNoticeHandler`：直接喂 `notify_deadline` 效果（runId 在 childRunIds 中）：
  断言 sink 未被调（已有 RK-10 模式可抄）；
- 端到端（若要）：integration 测试断言 `pi.sendMessage` 全程未被以
  `customType:"subagent:notification"` 调用。

### 5.3 点③：取消级联免疫

- spawn 发起方 run R（真实 runId，stub 保持 running）+ 静默 run S（合成父）；
- `spawnService.abort(R.runId)`：断言 R 进入 aborted 而 **S 状态不变**（对照实验：
  若 S 的 parentRunId=R.runId，则 S 一并被 abort——证明级联机制本身在工作）；
- 模拟父 run 自身超时：让 stub runner 对 R 触发 cancel handle 的外部 signal abort
  （走 `onChildAbort` 接线）：断言 S 存活；
- `stopChildrenOf(ownerId)`：断言 S 被 abort（收尸锚点可用）；
- signal 隔离：给静默 spawn 传一个 AbortController 的 signal（错误用法对照组）+ 不传
  （配方组）：abort controller 后断言配方组 run 不受影响；
  `detachSignalOnStart: true` + signal：启动前 abort ⇒ 立即取消，启动后 abort ⇒ 存活
  （复用 agent-tool run_in_background 的既有测试模式）。

### 5.4 硬化项回归（notifyTerminalFailure 缺口）

- stub `runner.run` 直接 throw；带 `parentRunId` spawn：断言修复后
  `notifyTerminalFailure` spy **未被调**（修复前被调——先写红测试）；
  同时断言 run 仍 settle 为 failed（`finish()` 正常落 snapshot，`/agent status` 可见）。

### 5.5 helper 单测

- `makeSilentOwnerId`：前缀 `silent-`、ownerKey 消毒（非法字符剔除、超长截断、空串回退
  `internal`）、两次调用不同（随机后缀）；
- `spawnSilent`：成功路径把 `parentRunId`/可选字段正确翻译进 SpawnRequest（spy
  `spawn.spawn` 入参逐字段断言）、**不含** `signal`/`detachSignalOnStart`/`expectAck`；
  失败路径透传 `{ok:false, error}`；
- 状态机/交付矩阵：本方案不改 `src/core/state-machine.ts` 与交付生命周期，按仓库约定
  **无需**动矩阵/属性测试；若实施 §4.2-1 的修复，`tests/service/spawn-service.test.ts`
  补上述 5.4 用例即可。

### 5.6 端到端手验（一次性，不入 CI）

在 TUI 里用临时 hook 静默 spawn 一个长任务，验证：fleet widget 出现根行、主会话空闲、
`/agent stop <发起方run>`（如有真实发起方）不影响它、`/agent status` 可查、`/reload` 后
它被 shutdown 杀掉（预期内，§4.1-1）。
