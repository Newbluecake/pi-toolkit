# 实施方案：扩展内部代码发起的「静默后台 run」

需求：扩展内部代码（非模型工具调用）要能派生一种 run，同时满足——

1. 不触发嵌套委派校验（canSpawn 白名单 + maxNestedDepth）；
2. 不产生顶层完成通知，更不能唤醒主会话起一轮模型调用；
3. 不被发起方 run 的取消/超时级联杀掉。

结论先行：**现有机制已完整支持，零生产代码改动即可落地**。核心配方是一行——
`stack.spawn.spawn({ type, prompt, parentRunId: <合成id> })`。合成 `parentRunId`（一个永不指向
SpawnService 所跟踪活 run 的字符串）一次性买断全部三点，这正是 SubagentWorkflow 子女 run 的既有做法
（`src/workflow/host.ts` ≈599 行、`src/stack.ts:1434`）。本文所有行号基于当前 master。

---

## 1. 机制分析（三点各对应哪条链路）

### 1.1 点 1：嵌套委派校验为何挡不住合成父 id

校验唯一入口在 `src/service/spawn-service.ts` `createSpawnService(...).spawn()` 的 **X3 段（334–352 行）**：

```ts
let depth = 0;
if (req.parentRunId) {
  const parent = nesting.get(req.parentRunId);   // ← 关键：只认“本服务当前跟踪的活 run”
  if (parent) {
    if (!parent.canSpawn?.includes(req.type)) return { error: { kind: "config", ... } };  // 白名单
    depth = parent.depth + 1;
    if (depth > maxNestedDepth) return { error: { kind: "config", ... } };               // 深度上限（默认 3，settings.ts:389）
  }
}
```

- `nesting` 表只在 spawn 成功时写入（430 行 `nesting.set(runId, {depth, canSpawn})`），并在 `finish()`
  里删除（138 行）。**合成 id 永远 `nesting.get()` 不到 ⇒ depth 0 直通、零白名单检查**。这不是漏洞利用，
  而是 322–333 行注释明确认可的设计（"`untracked/foreign parentRunId` … left unrestricted … rather
  than rejected"）。
- 两条错误做法，务必避开：
  - 用**真实发起方 run 的 id** 作 `parentRunId`：发起方类型若 `canSpawn` 不含目标类型 → 直接被拒；
  - 想借**嵌套 Agent 工具**（`src/runtime/tool-scope.ts` 注入路径）派生：它强制
    `parentRunId = 本 run id` + `slotless: true`（`tests/service/runtime-adapter-x3-x10.test.ts:194` 的
    既有断言），天然绑死真实父，无法做静默派生。**静默派生必须直接拿宿主侧 SpawnService。**
- 附带效应（无害且合理）：静默 run 自己会以 `depth 0` 进 `nesting` 表；它若经注入的嵌套工具再派生子
  run，那些子 run 会被正常校验（depth 1）——静默 run 不是「免检通行证」的传递起点。

### 1.2 点 2：通知静默的过滤点是 CC2（`childRunIds`）

完成通知链路：核心状态机 `finish()` 对每次终态无条件产出 `enqueue_delivery` 效果 →
`src/service/runtime-adapter.ts` 的效果解释器 → notifier（outbox）→ `src/stack.ts` `sendFormatted`
（≈935–955 行）→ `pi.sendMessage({customType: "subagent:notification", ...}, {triggerTurn: true})`。
**`triggerTurn: true` 就是「唤醒主会话起一轮模型调用」的机制**（对照：compact-hint / quota hint 刻意用
`triggerTurn: false`，见 stack.ts 530/607/637/690/722 行）。

唯一的「谁的终态通知进主会话」过滤点是 runtime-adapter 的 **CC2**：

- `src/service/runtime-adapter.ts:215`：`const childRunIds = new Set<string>()`；
- `:338`：`run()` 入口（任何 `await` 之前）`if (spec.request.parentRunId !== undefined) childRunIds.add(spec.runId)`；
- `:232`：`enqueue_delivery` 解释器 `if (childRunIds.has(e.payload.runId)) return;` —— **不进 outbox、
  不 sendMessage、不唤醒**；
- `:307`：`settleConfigFailure`（config 失败通知）同样丢弃；
- `:107`：`deadlineNoticeHandler`（超时宽限/延长通知，D-8）同样丢弃；
- `:537`：`finally` 中 `childRunIds.delete(spec.runId)`。

判定条件只有一个：**`parentRunId !== undefined`**，不校验该 id 是否真实。所以合成 id 即彻底静默。
备选路径 `expectAck`（spawnAndWait → `onOutcomeAcked` → `notifier.ack` 消费通知）**不可靠**：
`ackWindowMs` / `coalesceWindowMs` 默认均为 0（`src/config/settings.ts:384-386`），enqueue→attempt→send
是同一同步链、先于 ack 微任务执行，属 fail-open。但本方案不需要它——CC2 在更上游就把 enqueue 丢了，
`notifier.ack` 只会 ack 一个从未入队的 key（no-op / 被 catch）。

### 1.3 点 3：取消级联为什么追不上合成父 id

级联的数据基础是 `src/service/spawn-service.ts:432-437`：仅当请求带 `parentRunId` 时登记
`parentOf.set(runId, req.parentRunId)` 与 `childrenOf.get(parent).add(runId)`。两条触发链：

- **链 a（显式中止）**：`spawnService.abort(runId)`（516–527 行）先 `cascadeChildren(runId)` 再杀自身
  ——`abort_subagent` 工具与 `stopChildrenOf` 都走这里；
- **链 b（任何原因的取消）**：`src/runtime/runner.ts` `createCancelHandle` 的 onCancel（≈401–412 行）
  无条件调 `this.d.onChildAbort?.(req.runId, "parent_abort")`，经 `src/stack.ts:1079`
  `onChildAbort: (parentRunId, cause) => void spawnRef.current?.abort(parentRunId, cause)` 接回链 a。
  即**父 run 超时、被用户停、被外部信号取消，都会带走它在 `childrenOf` 里的子女**。

因此：`parentRunId` 用合成 id ⇒ 静默 run 不在任何真实 run 的 `childrenOf` 里 ⇒ 两条链都追不上。它只能被
① 显式 `spawn.abort(silentRunId)`，或 ② owner 主动 `spawn.stopChildrenOf(合成id)`（workflow 正是用后者
收尸，见 `src/workflow/spawner-adapter.ts` 的 `stopChildrenOf` 转发）杀死。

外部 `AbortSignal` 层面：**不传 `signal` 即无链接**。若发起发生在主会话 turn 上下文内（hook / 工具执行期）
且要免疫 Esc / compact 强制压缩带来的 turn 中止，加 `detachSignalOnStart: true`（`src/runtime/runner.ts:414`
在 cancel handle 创建后立即 `cancel.detach()`；`src/tools/agent-tool.ts:283-292` 的 `run_in_background`
是现成先例）。注意两点边界（runner.ts 41–49 行注释即契约）：admission 前已 aborted 的 signal 仍立即取消；
detach 只解除外部 listener，`abort_subagent` / watchdog 走 `activeCancels` 的路径不受影响。

## 2. 可直接落地的调用配方

### 2.1 前置：如何拿到 SpawnService

只能在**主会话扩展实例**里发起：子会话（subagent 进程内）的扩展实例因 `HOST_KEY` 宿主守卫是 inert 的
（`src/index.ts:114-164`），其 stack 为空（实测报 "no active session yet"）。宿主侧获取方式与既有内部
消费者一致（`src/schedule/scheduler.ts:74` 的 cron 派发、`src/goal/hook.ts:56` 的 verifier 都是先例）：
闭包传入 `stack.spawn`（`src/stack.ts:1358` `createScheduler({ spawn })` 的接线模式），或经 `index.ts`
的 holder 面（`index.ts:627` `spawnAndWait: (req) => requireStack(holder).spawn.spawnAndWait(req)`）。

### 2.2 配方本体（TypeScript，可直接抄）

```ts
import { randomUUID } from "node:crypto";

// owner 标识本扩展特性，用于合成父 id 与事后收尸；id 格式任意，唯一要求是
// 永不与 newRunId() 产出的真实 run id / workflowId 相撞（加前缀即保证）。
const ownerId = `bg:${featureName}:${randomUUID()}`;

const spawned = await stack.spawn.spawn({
  type: "general", // 任意已注册 agent 类型（src/config/ 的 registry）
  prompt, // 任务全文
  label: "bg-<feature>-<seq>", // 可选但建议：/agent status、fleet widget、mention 注册表可读，
  //   否则静默 run 在 UI 里只剩裸 runId，事后无法人工排查
  parentRunId: ownerId, // ★ 核心：合成 id，三点全靠它（详见 §3 逐参数论证）
  // --- 以下按需 ---
  // slotless: true,          // 见 §3：绕并发池 vs 失去排队超时保护的权衡
  // detachSignalOnStart: true, // 发起于 turn 上下文且要免疫 Esc/强制压缩时加
  // budgetOverride: { totalMs: 30 * 60_000 }, // 可选；注意显式 totalMs ⇒ 硬顶（D-10，无宽限无延长）
  // cwd, modelOverride, modelHintOverride, thinkingOverride, schema, deadlineAt, // 按需，语义同普通 spawn
  // signal: 绝不传 —— 传了就把 run 的生死挂到调用方 signal 上
});
if ("error" in spawned) throw new Error(spawned.error.message);
const { runId } = spawned;
```

结果收集二选一：

```ts
// A. fire-and-forget + 有界轮询（推荐：发起方通常自己也是异步任务）
const r = await stack.spawn.waitOutcome(runId, 5_000); // {kind:"settled", outcome} | {kind:"pending"}
// 也可用 stack.query.get(runId) 查快照、stack.query.wait(runId, opts) 等价等待

// B. 阻塞到终态（goal verifier 的用法，src/goal/hook.ts:234）
const outcome = await stack.spawn.spawnAndWait({/* 同上参数；expectAck 由 spawnAndWait 自设 */});
```

owner 侧收尸（主会话收尾 / 特性自身取消时）：

```ts
const { stopped, pending } = await stack.spawn.stopChildrenOf(ownerId, "user_stop");
```

### 2.3 逐参数论证

| 参数                     | 传法                                                        | 为什么                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------ | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parentRunId`            | 合成 id `bg:<feature>:<uuid>`                               | ① X3 只对 `nesting.get()` 命中的活 run 校验（§1.1）→ 绕开白名单与深度；② CC2 只判 `!== undefined`（§1.2）→ 全部通知路径静默；③ 不进任何真实 run 的 `childrenOf`（§1.3）→ 级联免疫。带可读前缀是为了事故排查时一眼认出归属。**绝不能**填真实发起 run id（三点全失：白名单拒绝/级联必死/通知仍会被 CC2 吞但取消隔离失效）。                                                          |
| `signal`                 | 不传                                                        | 传了就把静默 run 挂到调用方的 signal 上；turn 一中止（Esc/压缩）runner 的 external listener 就取消它。配方里取消隔离的第三层。                                                                                                                                                                                                                                                     |
| `detachSignalOnStart`    | 仅当无法避免在 turn 上下文内拿到某个 turn signal 时配对使用 | runner.ts:414 在 cancel handle 建立后摘除外部 listener；先例 agent-tool.ts `run_in_background`。本配方「不传 signal」时此参数无意义（无 listener 可摘）。                                                                                                                                                                                                                          |
| `slotless`               | 默认不传（走并发池）；确有理由才 `true`                     | 不传 = 与普通 run 一样过 `SlotPool`：占 `concurrencyLimit`（默认 6）一槽、享有 `queueWaitMs` 排队超时保护（防饿死）。`true` = 绕池（slot-pool.ts:40-41 直接发 ticket），代价是零排队保护且并发无上限——workflow 子女**故意不 slotless** 以保留 T1 保护（spawner-adapter.ts D-W3 注释）。静默后台任务通常低优先级，**建议留在池内**，只有当「被并发池饿死」本身是问题时才 slotless。 |
| `budgetOverride.totalMs` | 按需                                                        | 不传 → 全局预算（`settings.budget`），watchdog 照常武装（零挂保证不可关）。传 → 该值为**硬顶**：`applyBudgetPolicy` 钳 `maxTotalFactor=1`，无宽限、无延长（spawn-service.ts:420-424，D-10）。「静默」≠「免死」，只是「不被发起方连坐」。                                                                                                                                           |
| `label`                  | 建议传                                                      | 进 label 注册表与 `/agent status`、fleet widget；@ 自动补全只列 root 直属 run（`src/mention/autocomplete.ts:13,68`），所以不会污染模型补全面。                                                                                                                                                                                                                                     |
| `expectAck`              | 不传                                                        | 由 `spawnAndWait` 使用时它自设；CC2 已在上游丢弃 enqueue，ack 与否对本方案无影响（§1.2）。                                                                                                                                                                                                                                                                                         |
| `runId`                  | 不传                                                        | 让 `newRunId()` 分配（352 行起，带防撞检查）；自定义 id 无收益且有撞名风险。                                                                                                                                                                                                                                                                                                       |

### 2.4 与外部契约的一致性（佐证）

RPC 协议的 `SpawnParams` 本就允许任意 `parentRunId` 字符串（`src/rpc/protocol.ts:45`）——「合成父 id」
不是新语义，而是既有外部面已默认暴露的用法。

## 3. 建议顺手修复的潜伏缺口（可选但强烈建议）

**缺口**：`src/service/spawn-service.ts:243` 的异常安全网 `deps.notifyTerminalFailure?.(failed)`
（`runner.run()` 本身抛异常时的兜底）**不检查 `req.parentRunId`**，其接收方 `src/stack.ts:1133-1167`
的 `notifyTerminalFailure` 回调直接 `notifier.enqueue(payload)`——绕过 CC2。正常路径不可达（需 runner
内部 invariant 被打破），但一旦触发：一个带 parentRunId 的子女 run（含本方案的静默 run、workflow 子女）
会在顶层弹完成通知并 `triggerTurn:true` 唤醒主会话。workflow 子女同样暴露于此（先在的潜伏缺陷）。

**最小修复**（生产代码改动，若本次只交付配方则单列为后续项）：

```ts
// src/service/spawn-service.ts  catch 块内（当前 243 行）
finish(failed);
if (req.parentRunId === undefined) deps.notifyTerminalFailure?.(failed); // CC2 对齐：子女 run 的
// 终态只归 owner，异常兜底路径不得绕过 childRunIds 过滤
```

判定信息（`req.parentRunId`）恰好在调用点作用域内，一行守卫即闭合，不需要把 runtime-adapter 闭包里的
`childRunIds` 暴露出来。

## 4. 坑、约束与残余风险（做不到的如实说）

1. **活不过主会话（硬约束，做不到跨会话存活）**：`src/index.ts:522-547` `session_shutdown` 对所有非终态
   run 无差别 `query.stop(runId, "shutdown")` —— `/reload`、`/new`、`/resume`、fork、quit 全部杀死静默
   run。bash job 有跨会话收养（`handoffInProcess` / `adoptOrphans`，stack.ts ≈1390 的 recovery 接线），
   **subagent run 没有等价机制**。若需求隐含「主会话退出后仍活」，本方案不满足，需另立收养机制（超出现有
   接缝，不在本方案范围）。
2. **静默 ≠ 隐形**：CC2 只断「通知」，不断「可见性」。静默 run 仍出现在：fleet widget（M9 组头只认
   `parentRunId === workflowId` 的已知 workflow；合成父的 run 以普通/缩进行展示——具体 fallback 渲染未
   逐行核读 widget 源码，落地时目验一次）、`/agent status`、`subagent:started` / `subagent:completed` /
   `subagent:failed` 事件（stack.ts:1076-1077 `onLifecycle` → `pi.events.emit`）。若「对模型完全不可见」
   也是需求，本方案不满足。
3. **计数副作用**：静默 run 被 background-status 计入 `runningSubagents`（`src/service/background-status.ts`）
   → 影响 feishu 完成卡门控（主会话停了但后台没停不算任务结束）与 cache-keepalive 的 busy 判定。方向上
   这是**正确**语义（确实有活在跑），但要知道它会让这两处行为改变。
4. **fabric / message_agent 回信受限**：spawn 时 `onSpawnEdge(合成id, runId)`（spawn-service.ts:437 →
   stack.ts:1126）会把「合成节点 → run」的边挂进 fabric 树。agent 类型 `can_message` 默认 parent-only：
   静默 run 的 "parent" 是合成节点（无人消费）→ 回信大概率进 dead letter。若需要回信，须在该 agent 类型
   frontmatter 显式配置 `can_message` 含 root（路由关系按树边解析，落地时用一次真实 `message_agent(to:
"root")` 验证可达性），或干脆放弃回信、只用 `waitOutcome` 拉取结果。
5. **watchdog 照常武装**：静默 run 有完整的分层 deadline（watchdog 子相位预算 + 总预算），超时会被
   正常收割（经 `activeCancels`，`detachSignalOnStart` 管不到）。这是零挂保证的一部分，**不应**试图绕开。
6. **只能在宿主实例发起**：见 §2.1。子会话内的扩展代码（例如某 hook 恰好跑在 subagent 进程里）拿不到
   SpawnService，需求方需保证发起点在主会话。
7. **§3 缺口未修前的残余风险**：runner 内部异常路径可能弹一次顶层通知（低概率、有明确修复）。
8. **resume 正交**：静默 run 终态后可被 `resumeFrom` 复活，走同一 spawn 准入（resumeLocks 按
   targetId+sessionFile 双锁互斥）；与本方案无冲突，仅提示存在。
9. **label 会被 @ 显式解析**：补全不打扰（只列 root 直属），但用户手打 `@bg-...` 仍可 resolve 并 steer。

## 5. 验证点（测试怎么写、断言什么）

新套件 `tests/service/silent-spawn.test.ts`（seeded fake 计时/驱动，模式照抄
`tests/service/nesting.test.ts` 与 `tests/service/runtime-adapter-x3-x10.test.ts`）：

1. **点 1 断言**：环境里放一个 tracked 活 run R（类型 canSpawn 不含 `"general"`）。
   - `spawn({type:"general", parentRunId: "bg:t:1"})` → 返回 `{runId}` 而非 `error`；
   - 对照组 `spawn({type:"general", parentRunId: R})` → `error.kind === "config"`（既有用例
     nesting.test.ts:96 已覆盖对照侧，补合成 id 正向侧即可）；
   - 深度侧：以合成 id 连派 5 个（每个的 parentRunId 都用同一个合成 id 或各自新的合成 id）→ 全部
     通过（真实链第 4 层会被拒，nesting.test.ts:68 已有对照）。
2. **点 2 断言**（两层）：
   - 解释器层（RK-10 模式，hand-built envelope）：向 `BasicEffectInterpreter` 喂
     `{kind:"enqueue_delivery", payload:{runId: silentId, ...}}` → 断言 `notifier.enqueue` 调用次数为 0；
     对照喂 top-level runId → 恰好 1 次。同法各喂一条 `notify_deadline`（断言 `onDeadlineNotice` sink
     未收到）。注意 envelope 须在 `run()` 的 try 块存活期内投递（`finally` 会 `childRunIds.delete`）。
   - 服务层：真实走 `spawnAndWait({parentRunId: 合成id, ...})` 至终态 → 断言 mock 的
     `pi.sendMessage` 从未收到 `customType === "subagent:notification"`（即无 triggerTurn 唤醒）；
     对照：不带 parentRunId 的 run → 恰好一次且 `triggerTurn === true`。
3. **点 3 断言**：
   - 显式中止：spawn 真实发起方 run R + 静默 run S（合成父）；`spawnService.abort(R.id)` → R settled，
     而 `query.get(S.runId).status` 仍为 `"running"`；
   - 级联链 b：让 R 走 timeout/user_stop（经 runner 取消而非 service.abort）→ S 仍 running（这才证明
     `onChildAbort` 接线追不上合成父）；
   - 收尸：`stopChildrenOf(合成id)` → S settled，且返回的 pending 快照为空。
4. **signal 免疫**：`spawn({..., signal: turnSignal, detachSignalOnStart: true, parentRunId: 合成id})` 后
   `turnSignal.abort()` → run 仍 running（已有先例测试 `tests/runtime/runner-x3-x11.test.ts` /
   `tests/tools/agent-tool.test.ts` 的 detachSignalOnStart 用例可参照）；对照：admission 前 aborted 的
   signal → spawn 结果即取消。
