# 静默后台 run（silent background run）实施方案

需求：**扩展内部代码**（extension 内部逻辑，非模型工具调用）派生一种 run，同时满足：

1. **不触发嵌套委派校验**（canSpawn 白名单 + maxNestedDepth）；
2. **不产生顶层完成通知**，不唤醒主会话起一轮模型调用；
3. **不被发起方取消级联杀掉**（发起方 run 取消/超时时静默 run 独立存活）。

结论先行：**不需要改任何生产代码**。现有 `SpawnService.spawn` 的参数面 + workflow 引擎已经踩出的先例
（`parentRunId = 合成 id`）组合即可完整落地。核心配方一句话：

> `stack.spawn.spawn({ type, prompt, parentRunId: "<合成owner id>", ... })` —— 不传 `signal`，
> 按需 `slotless` / `detachSignalOnStart` / `budgetOverride`，自己保存 `runId`，用
> `waitOutcome` / `query.get` 收结果，用 `stopChildrenOf(合成id)` 收尸。

先例：`SubagentWorkflow` 的子女 run 走的就是这条路——`src/stack.ts` 的
`WorkflowSupport.createOrchestrator()`（约 1417–1440 行）把 `parentRunId: workflowId` 传给
orchestrator，`src/workflow/host.ts` 的 `agent()` 落到 `deps.spawner.spawn({ ..., parentRunId })`
（约 598–608 行），workflowId（`wf_…` 字符串）本身永远不是被跟踪的 run。本方案把这条
"workflow 专属" 的接缝泛化为任意扩展内部代码可用的配方。

## 1. 机制核实（三点各自的接缝，均已对源码核实）

### 1.1 点 1：嵌套委派校验为什么挡不住合成父

校验唯一入口在 `src/service/spawn-service.ts` 的 `spawn()`，注释标记 `X3: nesting depth +
canSpawn whitelist`（约 334–357 行）：

```ts
let depth = 0;
if (req.parentRunId) {
  const parent = nesting.get(req.parentRunId);   // 只查「本 SpawnService 当前在跑」的 run
  if (parent) {
    if (!parent.canSpawn?.includes(req.type)) return { error: ... };  // 白名单
    depth = parent.depth + 1;
    if (depth > maxNestedDepth) return { error: ... };                // 深度上限（默认 3）
  }
}
```

- `nesting` 表只在 `spawn()` 成功路径写入（`nesting.set(runId, { depth, canSpawn })`），并在
  `finish()` 里 `nesting.delete(outcome.runId)` —— 父 run 一结束，以其 id 为父的派生也不再受校验。
- **合成 id（从未被 spawn 跟踪）不在 `nesting` 里 ⇒ `parent` 为 `undefined` ⇒ depth 0 直接放行、
  零白名单检查**。这是源码注释明确认可的设计："untracked/foreign parentRunId … is left
  unrestricted (depth 0, no canSpawn cap) rather than rejected"。
- 反面：把 `parentRunId` 设为**真实发起方 run 的 id** ⇒ 发起方类型的 canSpawn 白名单 +
  深度上限全部生效，且（见 1.3）会被级联取消。**绝不要这么传**。
- 注意：嵌套 `Agent` 工具注入路径（`src/service/runtime-adapter.ts`，`canSpawn` 驱动段）强制
  `parentRunId = 本 run id` 且 `forceSlotless: true`，无法借它做静默派生。静默派生必须直接
  拿宿主侧 `SpawnService`（见 §2.1）。

### 1.2 点 2：通知抑制（CC2）挂在哪

通知链路：状态机 `finish()` 对每次终态无条件产出 `enqueue_delivery` 效果 →
`src/service/runtime-adapter.ts` 的效果解释器 → `Notifier`（outbox）→ `src/stack.ts` 的
`sendFormatted()`（约 911–954 行）→ `pi.sendMessage(customType "subagent:notification",
{ triggerTurn: true })`。**`triggerTurn: true` 就是"唤醒主会话起一轮模型调用"的机制**
（compact-hint / quota hint 刻意用 `triggerTurn: false` 以免唤醒，可对照）。

唯一的过滤点是 runtime-adapter 的 **CC2**（`src/service/runtime-adapter.ts`）：

```ts
const childRunIds = new Set<string>();
// run() 入口（任何 await 之前）：
if (spec.request.parentRunId !== undefined) childRunIds.add(spec.runId);
```

`childRunIds` 里的 run 在**四个**出口全部被丢弃，不进 outbox、不 sendMessage、不唤醒：

| 出口                    | 位置                                                                                         | 行为                                            |
| ----------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `enqueue_delivery` 效果 | 解释器 `enqueue_delivery` 分支（约 231–238 行）                                              | `if (childRunIds.has(e.payload.runId)) return;` |
| config 失败通知         | `settleConfigFailure()`（约 307 行，`if (!childRunIds.has(runId))` 包裹 `notifier.enqueue`） | 同上                                            |
| 超时宽限/延长通知       | `deadlineNoticeHandler(childRunIds, sink)`（约 100–114 行）                                  | `notify_deadline` 效果按 runId 过滤             |
| finally 清理            | `run()` 的 `finally`（`childRunIds.delete(spec.runId)`）                                     | 集合不泄漏                                      |

所以 **`parentRunId` 设任意合成 id 即彻底静默**（只要是 `!== undefined` 的字符串，值本身不重要）。
这正是 workflow 子女 run 的做法。

**不要走 `expectAck` 路径来抑制通知**：`spawnAndWait`/`waitOutcome` 会经 `onOutcomeAcked` →
`notifier.ack` 消费通知，但 `ackWindowMs` 与 `coalesceWindowMs` 默认均为 **0**
（`src/config/settings.ts` 约 384–386 行），`notifier.enqueue → attempt → send` 是同一同步链、
先于 ack 微任务执行——fail-open 发通知（delivery-v2 文档明确承认）。CC2 的**源头丢弃**才是可靠手段。

### 1.3 点 3：取消级联的数据基础与隔离

级联取消的两条触发链：

1. **显式 abort**：`src/service/spawn-service.ts` 的 `abort()` —— 先 `cascadeChildren(runId,
"parent_abort")`（递归 `service.abort` 杀全部在跑子孙）再杀自身。数据来自 `childrenOf`/
   `parentOf` 两个 Map，**仅当请求带 `parentRunId` 时登记**（约 430–441 行 `if (req.parentRunId)
{ parentOf.set(...); childrenOf.set(...) }`），`finish()` 时双向清理。
2. **隐式级联**：任何原因取消某个 run（user_stop / timeout / external）时，`src/runtime/runner.ts`
   的 `createCancelHandle` 回调（约 390–412 行）都会调 `this.d.onChildAbort?.(req.runId,
"parent_abort")`，经 `src/stack.ts` 约 1079 行接线 `onChildAbort: (parentRunId, cause) =>
void spawnRef.current?.abort(parentRunId, cause)` —— 即**父 run 超时/被用户停，都会带走
   childrenOf 里的子 run**。

推论：

- 合成父 id ⇒ 静默 run 不在任何真实 run 的 `childrenOf` 里 ⇒ 发起方（真实 run）被 abort/超时
  **完全波及不到它**。能杀它的只有：显式 `abort(它自己的 runId)`、`stopChildrenOf(合成id)`、
  它自己的 watchdog 超时、以及 session_shutdown（见 §3.1）。
- **外部 signal 层面**：不传 `signal` 即无任何链接。若发起代码运行在主会话 turn 上下文内
  （如某个 hook 里）且想免疫 Esc / 强制压缩的 turn 中止，传 turn 的 signal +
  `detachSignalOnStart: true`：`runner.ts` 约 414 行在 cancel handle 创建后立即
  `cancel.detach()`（`external?.removeEventListener`）。现成先例是 `Agent` 工具的
  `run_in_background`（`src/tools/agent-tool.ts` 约 283–292 行）。注意两个边界：
  (a) detach 只解除外部 listener，`abort_subagent` / watchdog 走 `activeCancels` 的路径不受影响；
  (b) **admission 前已 aborted 的 signal 仍会立即取消**（`createCancelHandle` 开头
  `if (external?.aborted) cancel("external")`，先于 detach）。

## 2. 落地配方

### 2.1 接入点：扩展内部代码怎么拿到 SpawnService

结构性约束：**静默派生只能在宿主（主会话）侧发起**。子会话内的扩展实例因 `HOST_KEY`
host-claim 守卫是 inert 的，拿不到 stack；嵌套 `Agent` 工具又强制真实父 id（§1.1）。
两个可用接入模式（都是仓库既有先例）：

- **模式 A（推荐，goal/workflow 同款 DI）**：新模块不 import service 具体实现，在
  `src/stack.ts` 组装时注入窄化端口。参照：
  - workflow：`createWorkflowChildSpawner(spawn, types)`（`src/stack.ts` 约 1406 行 +
    `src/workflow/spawner-adapter.ts`）；
  - goal：hook deps 只收 `{ spawnAndWait }`（`src/goal/hook.ts:56`），由 index.ts 闭包用
    `requireStack(holder).spawn` 接线。
- **模式 B**：代码就在 `src/index.ts` 注册的 hook/工具闭包里 ⇒ 直接
  `requireStack(holder).spawn`（`holder` 是 index.ts 约 149 行的 `{ current?: Stack }`）。

### 2.2 调用配方（完整参数，逐项说明为什么）

```ts
import { randomUUID } from "node:crypto";

// 合成 owner id：同一拥有者的多个静默 run 共享一个，便于批量收尸（workflow 同款用法）。
// 命名要点：避开真实 RunId 空间（`r_` + 8 位 Crockford，src/core/ids.ts 的 newRunId），
// 用自己的前缀（如 "silent-"），防止撞上一个正在跑的 run id —— 一旦撞上，
// X3 校验与级联取消都会"意外生效"（§3.9）。
const silentOwner = `silent-${randomUUID().slice(0, 8)}`;

const spawned = await spawn.spawn({
  type: "general", // ① 必填：AgentTypeRegistry 已注册的类型名
  prompt: "...", // ② 必填：任务提示词
  label: "silent-foo", // ③ 可选但建议：/agent status、fleet 行、resolveRun 定位都靠它
  parentRunId: silentOwner, // ④ 核心：合成 id，一点同时达成三点需求（见下）
  budgetOverride: { totalMs: 10 * 60_000 }, // ⑤ 可选：显式预算（见下，注意硬顶语义）
  // slotless: true,                  // ⑥ 可选：绕并发池（默认不传，见权衡）
  // signal + detachSignalOnStart:true,    // ⑦ 仅当在 turn 上下文发起且要免疫 Esc（见 §1.3）
});
if ("error" in spawned) {
  // 同步准入失败：unknown type / 额度闸门（quota gate）/ deadlineAt 已过期 /
  // label 999 个变体耗尽等 —— 全部零副作用返回，重试安全
} else {
  const { runId, label } = spawned; // 自己保存 runId；label 可能被去重改写，以返回值为准
}
```

逐项理由：

| 参数                                                                       | 为什么这么传                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ④ `parentRunId: <合成id>`                                                  | **一点三用**：(a) 不在 `nesting` 表 ⇒ 点 1 免校验；(b) `!== undefined` ⇒ CC2 进 `childRunIds` ⇒ 点 2 全部四个通知出口被丢弃；(c) 不在任何真实 run 的 `childrenOf` ⇒ 点 3 免级联。同时它把你登记进 `parentOf/childrenOf[合成id]`，`stopChildrenOf(合成id)` 才能批量收尸。**值必须是合成 id，绝不能是发起方 run 的真实 id**（那三点全丢）。                                                 |
| ③ `label`                                                                  | 会经 `onLabel` 注册进 mention registry（**不是** root 直属 ⇒ 不进 @ 自动补全，但 `resolveRun`/`get_subagent_result` 仍可按 label 解析——见 §3.4）。不传则从 prompt 首行派生，同样会注册。                                                                                                                                                                                                  |
| ⑤ `budgetOverride.totalMs`                                                 | **建议显式传**。不传 ⇒ 用全局预算，watchdog 对每个 run 照常武装（idle/total 等 timer）；且默认预算带宽限窗口——静默 run 进宽限时它的 `notify_deadline` 被 CC2 丢弃，**主会话模型永远收不到"请延长"通知**，宽限窗口变成纯浪费等待（除非发起方代码自己调 `query.extendTimeout(runId, ms)` 救它）。显式 `totalMs` ⇒ `applyBudgetPolicy` 钳 `maxTotalFactor=1`，硬顶、无宽限无延长，语义干净。 |
| ⑥ `slotless`                                                               | 默认**不传**（false）：走 `SingleSlotPool`，占 `concurrencyLimit`（默认 6）的槽、享有 queue-timeout 保护，与 workflow 子女的 deliberate 选择一致（spawner-adapter.ts 的 D-W3 注释）。传 true 绕池但无排队保护，仅当静默 run 绝不能被排队卡住时用。副作用提醒：不 slotless 会挤占正常派单配额（§3.6）。                                                                                    |
| ⑦ `signal` + `detachSignalOnStart`                                         | 发起方是 hook/工具闭包且在 turn 上下文内时：传 turn 的 signal 做 admission 期取消 + `detachSignalOnStart: true` 在启动后脱离（agent-tool `run_in_background` 同款）。发起方不在 turn 上下文（scheduler、定时器、事件回调）则**两个都不传**——无链接即无风险。                                                                                                                              |
| 不传 `expectAck`                                                           | 保持 false。CC2 已从源头丢弃通知，ack 与否不影响静默性；`expectAck:true` 只在有同步 ack 调用方时才有意义，且 fail-open（§1.2）。                                                                                                                                                                                                                                                          |
| 可选 `deadlineAt`                                                          | 绝对时刻上限（epoch ms），仅收紧不放宽；只对"必须在天花板前完成"的场景有意义。                                                                                                                                                                                                                                                                                                            |
| 可选 `schema` / `modelOverride` / `thinkingOverride` / `cwd` / `isolation` | 按需。`schema` 会注入 StructuredOutput 工具 + 双重校验，结构化结果走 `outcome.structuredResult`（注意 memory 里记录过的 schema 入口裸断言缺陷：只传真正的 JSON Schema object）。                                                                                                                                                                                                          |
| 不传 `resumeFrom`                                                          | resume 走同一准入：`resumeLocks` 按 targetId+sessionFile 双锁互斥；目标仍在跑会被拒并提示改 steer；`resolveResumeTarget` 只接受本服务已知 run 的 sessionFile，不接受任意路径。静默 resume 没有额外豁免。                                                                                                                                                                                  |

### 2.3 结果收集与生命周期

```ts
// 等待（有界轮询；不依赖 ack）：
const r = await spawn.waitOutcome(runId, 5_000);
if (r.kind === "settled") useOutcome(r.outcome); // .text / .structuredResult / .status / .diag
// 或查快照（终态快照含 outcome；非终态给 live diag）：
const snap = query.get(runId);

// 延长（发起方代码主动救活，替代被 CC2 吞掉的宽限通知）：
await query.extendTimeout(runId, 60_000); // QueryService.extendTimeout（约 168 行起）

// 收尸：
await spawn.stopChildrenOf(silentOwner, "user_stop"); // 杀该 owner 下所有仍在跑的静默 run（workflow 同款，host.ts 约 868 行）
// 或单杀：await spawn.abort(runId);
```

- 终态结果同时留在 spawn-service 的 `outcomes` Map 与 store 快照（tombstone TTL 30 分钟）里，
  `waitOutcome` 迟到调用也能拿到。
- 一次性别忘了收尸：静默 run 没有任何"完成通知"提醒你它结束了，**发起方必须自己持有
  runId/ownerId 并在合适时机 `stopChildrenOf` / 清理引用**，否则只能等 watchdog 预算杀它。

### 2.4 建议封装（新代码落点）

新增一个纯封装模块（不改任何现有文件即可被调用；若要系统级注册则动两处）：

- **新文件** `src/silent/spawner.ts`：`createSilentSpawner(spawn: Pick<SpawnService,"spawn"|"waitOutcome"|"stopChildrenOf"|"abort">)`，
  返回 `{ spawnSilent(task): Promise<{runId,label} | {error}>, wait(runId, ms), stopAll() }`。
  内部持有 `silentOwner` id、自动加 `silent-` label 前缀、默认 `budgetOverride`。
- **接线**（二选一，遵循 I7"index.ts 只做组装"）：
  - `src/stack.ts`：在 workflow 段旁构造并挂到 `Stack` 返回值（如 `stack.silent`）；或
  - `src/index.ts`：注册你的 hook 时闭包注入 `requireStack(holder).spawn`（goal 模式）。

### 2.5 备选路径：进程外/RPC

`src/rpc/protocol.ts` 的 `SpawnParams` 本就允许任意 `parentRunId` 字符串（45 行，
`Type.Optional(Type.String())`），`src/rpc/server.ts` 的 spawn 方法原样透传给
`deps.spawn.spawn(request)`。经 RPC spawn 且带合成 `parentRunId` ⇒ 点 1+2 同样成立；RPC 请求
**不携带 signal**（schema 里没有该字段），点 3 天然满足。差别：RPC 面没有
`slotless`/`detachSignalOnStart`/`schema`/`isolation`/`resumeFrom` 字段，预算可传完整
`budgetOverride`。适合跨进程调用方；扩展内部代码用 §2.1 直接调用即可。

## 3. 坑、约束与残余风险（做不到 / 有代价的，如实列出）

1. **活不过主会话（硬边界）**：`src/index.ts` 的 `session_shutdown`（约 522–551 行）对所有
   非终态 run `query.stop(runId, "shutdown")` 并有界等待。`/reload`、`/new`、`/resume`、fork、
   quit **全部会杀掉静默 run**。bash job 有跨会话收养（`handoffInProcess`/`adoptOrphans`），
   subagent run **没有等价机制**——做不到"跨会话存活"。若主会话频繁 reload，静默 run 需要
   发起方自行持久化意图并在新会话重派。
2. **`notifyTerminalFailure` 潜伏缺口（已知缺陷，如实报告）**：`src/stack.ts` 约 1134–1167 行，
   spawn-service `start()` 的 catch 安全网在 `runner.run` **抛异常**时直接 `notifier.enqueue`
   顶层通知，**不查 childRunIds**——该异常路径上静默 run 会发顶层通知并 `triggerTurn:true`
   唤醒主会话。正常路径不可达（runner.run 内部把错误折进状态机），属潜伏缺陷。若要封死，
   需一处小改：`createSpawnService` 的 `notifyTerminalFailure` 调用前按
   `req.parentRunId !== undefined` 短路（或把 childRunIds 语义传给 spawn-service）。
   本方案按"不改生产代码"交付，此项列为残余风险 + 建议修复项。
3. **可见性不是零**：CC2 只断"通知"，不断"可见"。静默 run 仍出现在：fleet widget
   （`src/ui/fleet-widget.ts` `treeOrder`：合成父不在 present 集合 ⇒ 作为独立行渲染，
   带 `↳` nested 缩进）、`/agent status`、`subagent:completed|failed` 事件
   （`onLifecycle` 无差别转发）、以及**主会话文件里的 `subagent:run` 终态 custom entry**
   （`src/adapters/pi-run-log.ts` 的 `wrapWithRunLog` 包在共享 store 上，每个终态
   `persist_snapshot` 都会 `pi.appendEntry`——不可通过参数关闭；session-nav 会扫到它）。
   这是刻意保留的可观测性，不是漏洞，但意味着"静默"≠"隐身"。
4. **@mention 不可达（有意为之的边界）**：label 仍注册进 mention registry，但
   (a) @ 自动补全只列 root 直属 run（`src/index.ts` `mentionAutocompleteEntries`，
   `target.parent !== "root"` 过滤）；(b) 其它 subagent 通过 mention channel @ 它会被拒
   （`src/fabric/mention.ts` `not_root_child`）。`resolveRun`/`get_subagent_result`/`steer`/
   `abort_subagent` 仍可按 runId/label 操作它（这些走 resolve-target，不查 parent）。
5. **fabric 树上的孤儿边**：`onSpawnEdge(合成父, run)` 会 `fabric.tree.appendEdge`——合成节点
   无上游，root 与该 run 的 relation 是 `unrelated`。后果：静默 run 内注入的
   `message_agent` 默认只能发给 parent（合成 id，无人读，TTL 后进 dead letter）；
   主会话/兄弟 run 也无法按树关系给它发消息。**静默 run 的回报通道是结构化结果/文本
   （`waitOutcome` 收 `outcome.text` / `structuredResult`），不是 message_agent**。若确需
   消息回传，让静默 run 在 prompt 里把结果写文件/写 store，或发起方给它配
   `canMessage` 允许的其它目标。
6. **挤占并发配额**：不 slotless ⇒ 占 `concurrencyLimit`（默认 6）槽位，静默 run 会与正常
   派单竞争，用户可见排队变长；slotless 则无 queue-timeout 保护。同时它计入
   `background-status` 的 `runningSubagents`（`src/index.ts` 约 150–160 行）与
   cache-keepalive 的 `backgroundBusy`（`src/stack.ts` 约 1222 行）——**静默 run 在跑会抑制
   keepalive ping 和 feishu 完成卡**（feishu 完成类卡片被 background-idle 门控压住）。
   这是真实行为变化，评估"静默后台任务"时长时要算进去。
7. **watchdog 照常武装**：静默不是免死金牌。不传 `budgetOverride` 就吃全局预算；idle/total
   超时一样被杀（abort with cause timeout → finish → enqueue_delivery → CC2 丢弃，安静地死）。
   需要长活就显式给足 `totalMs`。
8. **免校验不遗传**：静默 run 自己 depth 0 免白名单；但它若通过注入的 `Agent` 工具再派孙 run
   （其类型 canSpawn 允许时），孙 run 以静默 run 为真实父，depth 1、白名单照查——正常行为。
9. **合成 id 撞车风险**：X3 的"untracked parent 不校验"是把双刃剑——若合成 id 恰好等于某个
   **正在跑**的 run id，校验与级联取消都会意外生效（可能直接被拒绝，或被那个 run 的取消带走）。
   用 `silent-` 前缀 + uuid 规避（真实 RunId 是 `r_` + 8 位 Crockford）。
10. **发起方自身在 turn 上下文时的细节**：`detachSignalOnStart` 只在**启动后**脱离 signal；
    admission 前已 abort 的 signal 仍立即取消（`createCancelHandle` 先检查再注册 listener，
    detach 在其后）。所以"turn 已经被 Esc 再 spawn"会当场失败（返回 aborted 结算），不是静默存活。

## 4. 验证点（测试怎么写、断言什么）

测试分层，全部可基于现有 harness（`tests/service/nesting.test.ts` 的 `controllableRunner` /
`typesRegistry`、`tests/service/runtime-adapter-x3-x10.test.ts` 的 adapter 组装、
`tests/runtime/cancel-handle.test.ts`）。建议新文件 `tests/service/silent-spawn.test.ts`
（+ 集成 `tests/integration/silent-spawn.test.ts`），断言点：

**A. 点 1 —— 免嵌套校验（spawn-service 层）**

1. 注册类型 `parent`（canSpawn: `["child"]`）与 `sibling`；先 spawn 一个真实 `parent` run
   （挂起不结算），再以它为 `parentRunId` spawn `sibling` ⇒ 断言被拒（白名单错误）——对照组。
2. 同一 `sibling` 以合成 `parentRunId: "silent-x"` spawn ⇒ 断言成功且返回 runId。
3. 造 4 层真实嵌套超深被拒的对照组 + 合成父 depth-0 放行：以合成父 spawn 的 run 再作为
   `nesting` 里的父去派孙 run 时深度从 0 重新计（断言孙 run depth 1 的行为不受影响——
   即静默 run 的 nesting 表项 depth 为 0，可查 `snapshots()` 或让孙 spawn 成功）。

**B. 点 3 —— 取消隔离（spawn-service 层）** 4. 真实父 run A（挂起）+ 合成父静默 run S 同时在跑；`abort(A)` ⇒ 断言 `abortCalls` 含 A
的子（若有真实子）但**不含 S**；S 的 runner promise 未被触碰（controllableRunner 的
settle 仍可控）。5. `stopChildrenOf("silent-x", "user_stop")` ⇒ 断言 S 被 abort（owner 收尸可用）且
`stopChildrenOf` 从不对合成 id 本身调 `runner.abort`（OS2 语义）。6. （runner 层，`tests/runtime/`）`detachSignalOnStart: true`：启动后 abort 外部 signal ⇒
run 不取消；signal 在 run 开始前已 aborted ⇒ 立即取消（admission 语义保持）。

**C. 点 2 —— 通知抑制（runtime-adapter 层 + 集成）** 7. 组装 adapter（fake notifier / fake store）：以 `parentRunId: "silent-x"` spawn 并驱动到
completed ⇒ 断言 `notifier.enqueue` **零调用**（对照：无 parentRunId 的 run 恰好一次）。8. 同 setup 但让 `deadlineAt` 已过期 ⇒ 走 `settleConfigFailure` 路径 ⇒ 断言同样零 enqueue。9. 驱动 `notify_deadline` 效果（或直接单元测 `deadlineNoticeHandler`，喂含静默 runId 的
notice）⇒ 断言 sink 未收到。10. 集成（或 stack 级）：spy `pi.sendMessage` ⇒ 断言静默 run 全生命周期没有任何
`customType === "subagent:notification"` 且没有任何 `{ triggerTurn: true }` 调用；
同时断言 `subagent:completed` 事件**有**发出（可见性语义，见 §3.3——把它钉进测试防止
未来有人"顺手修复"通知过滤）。11. 已知缺口钉板（可选，标注 known-gap）：runner.run 抛异常 + parentRunId 定义 ⇒ 当前行为
通知**仍发出**——写一个 `test.fails`/注释清晰的用例固定现状，修复 §3.2 后翻转断言。

**D. 生命周期** 12. `waitOutcome(runId)` 在 finish 后返回 settled outcome；`stopChildrenOf` 后
`waitOutcome` 返回 aborted 结算。13. session_shutdown 语义（集成）：触发 shutdown ⇒ 断言静默 run 终态为 aborted
（cause=shutdown）——把 §3.1 的硬边界钉进测试。
