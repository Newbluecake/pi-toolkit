# 静默后台 run（Silent Background Run）实施方案

> 状态：实施方案（a1-r3）。基于前序 agent 的完整探索交接（`/tmp/exp_hold/handoff-full.json`），
> 本轮已对全部关键接缝做了二次代码核实（下文行号均为本轮实测）。

## 0. 需求与结论速览

扩展内部代码（主会话宿主侧的 feature 模块）要能派生一种 run，同时满足：

| #   | 需求                                                   | 承接机制（一句话）                                                                                                                                             |
| --- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 不触发嵌套委派校验（canSpawn 白名单 + maxNestedDepth） | `parentRunId` 传**合成 id**（不是任何 tracked run 的 id）：X3 校验只在 parent 命中 `nesting` 表时触发，合成 id ⇒ depth 0、零白名单检查                         |
| 2   | 不产生顶层完成通知、不唤醒主会话                       | `parentRunId !== undefined` ⇒ CC2 把该 run 的 `enqueue_delivery` / config-failure / deadline 通知全部在效果解释器层丢弃，通知根本不产生（比 ack 抑制早一整层） |
| 3   | 不被发起方取消级联杀掉                                 | 级联建立在 `childrenOf`/`parentOf`（按 parentRunId 登记）上；合成父 id 不在任何真实 run 的 children 集合里，且不传 `signal` ⇒ 三条取消链全部够不着             |

三点共享同一个开关：**`parentRunId` = 永不指向 tracked run 的合成 owner id**。这是被
`SubagentWorkflow` 子女 run（`src/workflow/host.ts` L599-606，parentRunId=workflowId）完整验证过的
既有模式——本方案只是把它产品化为内部可复用的调用配方，不发明新机制。

**最小配方（今天就能用，零代码改动）**：

```ts
const ownerId = `silent-owner:${randomUUID()}`; // 非 r_ 前缀，格式上不可能是真 run id（见 §5.1）
const started = await spawn.spawn({
  type: "general-purpose", // 任意已注册 agent type
  prompt: "...",
  parentRunId: ownerId, // 三点的共同开关；defined 但 untracked
  // 以下全部可选，逐个理由见 §4
  label: "silent-<purpose>",
  budgetOverride: { totalMs: 10 * 60_000 },
});
// 自己收结果（通知链路已被 CC2 掐断，无人替你送）：
const result = await spawn.waitOutcome(started.runId /*, waitMs*/);
// owner 侧确定性收尸（幂等，可随时调）：
await spawn.stopChildrenOf(ownerId, "user_stop");
```

其中 `spawn` 是宿主侧 `SpawnService`（`stack.spawn`，经 `src/index.ts` 的
`holder.current.spawn` / `forwardSpawn(holder)` 可达，L624-634）。

## 1. 点 1 机制：绕开嵌套委派校验

### 1.1 校验在哪、何时触发

`src/service/spawn-service.ts` `createSpawnService().spawn()` 的 X3 段（L322-357）：

```ts
// L334-337
let depth = 0;
if (req.parentRunId) {
  const parent = nesting.get(req.parentRunId);
  if (parent) {
    if (!parent.canSpawn?.includes(req.type)) return { error: ... };  // 白名单
    depth = parent.depth + 1;
    if (depth > maxNestedDepth) return { error: ... };                // 深度上限（默认 3）
```

`nesting` 表只在 run 存活期间持有它（spawn 时 `nesting.set(runId, ...)` L430；
`finish()` 里 `nesting.delete` L138）。因此：

- **`parentRunId` 为合成 id**（从未有 run 以它为 id 被本服务 spawn）⇒ `nesting.get()` 返回
  `undefined` ⇒ 两个检查整体跳过，depth 恒 0。这不是漏洞利用，是**注释明确认可的设计**
  （L322-333：「untracked/foreign parentRunId … left unrestricted (depth 0, no canSpawn cap)
  rather than rejected」）——RPC 协议 `src/rpc/protocol.ts` L45 本就允许任意 `parentRunId`
  字符串，这条通道对外部已默认存在。
- **`parentRunId` 缺省**同样跳过校验，但缺省会失去点 2/点 3 的机制（见下），所以配方必须传合成 id。

### 1.2 反例（不要这么传）

- **传真实发起方 run 的 id**：发起方 run 正在跑 ⇒ 在 `nesting` 表里 ⇒ 它的 agent type 的
  `canSpawn` 白名单 + `maxNestedDepth` 全部适用。发起方类型没配 `canSpawn`（或没包含静默 run
  的 type）时直接 `failed(config, "nested delegation is not permitted")`。
- 发起方 run **已终态**后再以其 id 为父：`finish()` 已删 `nesting` 项，校验会跳过——但这条
  路径依赖时序（发起方先死），且终态父的语义不稳定，不要用；统一用合成 id。
- **借嵌套 Agent 工具注入路径**：`src/service/runtime-adapter.ts` L422-433 注入的嵌套 Agent
  工具强制 `parentRunId = 本 run id` + `forceSlotless: true`，无法产出静默派生。静默派生必须
  直接拿宿主侧 `SpawnService`。

### 1.3 拿 SpawnService 的唯一合法通道

子会话内的扩展实例被 `HOST_KEY` 宿主守卫置为 inert（`src/index.ts`），拿不到 stack——所以
「扩展内部代码」指**主会话宿主侧**被 `index.ts`/`stack.ts` 装配的 feature 模块，通过闭包拿
`holder.current.spawn`（访问器形式，`/reload` 换栈后不持旧引用）。

## 2. 点 2 机制：不产生顶层完成通知、不唤醒主会话

### 2.1 通知链路与唯一过滤点

```
core/state-machine.ts finish()                    每个终态无条件产出 enqueue_delivery 效果（无 per-run 开关）
  → service/runtime-adapter.ts 效果解释器          ★ CC2：childRunIds.has(runId) ⇒ return（L229-236）
  → delivery/notifier.ts enqueue→attempt          （进 outbox 前就被掐断）
  → stack.ts sendFormatted (L911-958)             pi.sendMessage("subagent:notification", {triggerTurn:true})
```

**CC2 的判定条件是 `spec.request.parentRunId !== undefined`**（runtime-adapter.ts L338，run()
入口、任何 await 之前），与父是否为真实 run 无关。同一 `childRunIds` 集合还拦下：

- **config-failure 通知**：`settleConfigFailure` 内 `if (!childRunIds.has(runId))` 才 enqueue
  （runtime-adapter.ts L311）——静默 run 的准入后失败（unknown model hint、H2 hook 抛错、
  deadlineAt 已过期等）不会发顶层通知；
- **deadline 宽限/延长通知**：`deadlineNoticeHandler(childRunIds, ...)`（runtime-adapter.ts
  L104-110）。

`triggerTurn: true` 是「唤醒主会话起一轮模型调用」的机制（stack.ts L953/L962；compact-hint /
quota hint 刻意用 `triggerTurn: false` 以免唤醒，即反向佐证）。**CC2 在通知产生之前就丢弃，
所以根本轮不到 `triggerTurn` 生效**——我们对 pi 端唤醒语义零依赖（前序 openQuestion 之一就此关闭）。

### 2.2 为什么不能走 expectAck/ack 抑制

`spawnAndWait` 强制 `expectAck: true`（spawn-service.ts L446-447），ack 经
`onOutcomeAcked → notifier.ack`（stack.ts L1127-1133）。但 `ackWindowMs`/`coalesceWindowMs`
默认均为 **0**（settings.ts L384/L386）⇒ `notifier.enqueue → attempt → send` 是同一同步链，
先于任何 ack 微任务执行——**fail-open**（docs/dev/delivery-v2/architecture.md L192-193 官方
承认）。`src/goal/hook.ts` 的 verifier（spawnAndWait 派生）就是活反例：默认配置下其完成通知
照样发。结论：**通知静默只能靠 parentRunId（CC2），expectAck 只是结果认领语义，不是静默机制。**

### 2.3 已知缺口（潜伏缺陷，建议随本方案一并修复）

`stack.ts` L1134-1167 的 `notifyTerminalFailure` 安全网——spawn-service `start()` 的 catch
（spawn-service.ts L243）在 `runner.run()` **抛异常**时直接向 notifier enqueue 顶层通知，
**不查 childRunIds**。正常路径构造不出该异常（效果解释器/reducer 的 catch 都吞错），但静默
run 的契约是「绝不发顶层通知」，且该路径的 payload 会进 outbox、跨 `/reload` 被 reconcile
重投。修法见 §3.2（3 行改动）。

## 3. 点 3 机制：不被发起方取消级联杀掉

### 3.1 级联的数据基础与三条触发链

级联登记只发生在 spawn 时 `req.parentRunId` 有值的地方（spawn-service.ts L432-441）：
`parentOf.set(child, parent)`、`childrenOf.get(parent).add(child)`。**用合成 id ⇒ 静默 run
挂在 `childrenOf.get(合成id)` 下，不在任何真实 run 的孩子集合里。**

三条会带走「真孩子」的链，对合成父的静默 run 全部失效：

1. **`abort_subagent` / 显式 abort**：`spawnService.abort(runId)`（spawn-service.ts L528-533）
   先 `cascadeChildren(runId)` 再杀自身——只遍历 `childrenOf.get(runId)`。
2. **发起方超时**：watchdog `fireDeadline`（runner.ts L380-402）→ cancel handle 的回调 →
   `onChildAbort(runId, "parent_abort")`（runner.ts L399-411）→ stack.ts L1079 接线回
   `spawnService.abort(runId)` → 同样只级联真孩子。
3. **发起方被用户停 / 任何取消原因**：与 (2) 同一漏斗（runner.ts 注释明说「cascade
   regardless of _why_ this run stopped」），仍然只走 `childrenOf`。

**发起方 run 整个死掉后，静默 run 唯一的死法**是：它自己的预算/watchdog 到期、被显式
`abort(它的runId)`、或 owner 主动 `stopChildrenOf(合成id)`（这正是 workflow 的收尸方式，
host.ts L868-875）。

### 3.2 外部信号（Esc / turn 中止）

`signal` 是 opt-in：**不传就零链接**。若调用点身处主会话 turn 上下文（比如某个工具执行期间）
且手上有 turn 的 AbortSignal，两种选择：

- 默认：**不传 signal**（配方如此）——turn 被 Esc 打断也无关；
- 若想让「spawn 准入本身」可被 turn 中止但 run 启动后独立：传 `signal` +
  `detachSignalOnStart: true`（runner.ts L414 在 cancel handle 创建后立即
  `cancel.detach()`；`Agent` 工具 `run_in_background` 是现成先例，agent-tool.ts ~L283-292）。
  注意两点：detach 只解外部 listener，`abort_subagent`/watchdog 走 `activeCancels` 的路径
  不受影响（这是想要的）；**admission 前已 aborted 的 signal 仍会立即取消**（detach 晚于
  handle 创建），所以「turn 已在取消中」时派生会同步死掉——这是特性不是 bug。

### 3.3 不可免疫的：session_shutdown

`src/index.ts` `session_shutdown` 处理器对**所有非终态 run** 调 `query.stop(runId,
"shutdown")`（~L540-546）——`/reload`、`/new`、`/resume`、fork、quit 全部会杀掉静默 run。
bash job 有跨栈收养（`handoffInProcess`/`adoptOrphans`），**subagent run 没有等价机制**。
做不到的部分如实声明：**静默 run 的存活上限 = 宿主会话/栈的存活期**；跨 `/reload` 存活需要
新增收养工程（见 §6.3）。

## 4. 完整调用配方与逐参数说明

推荐落成一个薄封装（§5），其内部发出的请求逐字段如下：

```ts
{
  type,                              // 必填。任意已注册 agent type；不经过任何 canSpawn 检查（点 1）
  prompt,                            // 必填。同普通 run
  label: "silent-<purpose>",         // 强烈建议显式传：默认 label 从 prompt 首行派生，会和
                                     //   普通派生共享「唯一化」命名空间；显式前缀便于 fleet widget、
                                     //   /agent status 里肉眼区分，也方便 label resolve 定位
  parentRunId: ownerId,              // ★ 三点共同开关。ownerId = `silent-owner:${uuid}`：
                                     //   defined（点 2 的 CC2 判定是 !== undefined）
                                     //   且 untracked（点 1 跳过 X3、点 3 不进真实 childrenOf）
  cwd,                               // 可选。语义同普通 run
  budgetOverride: { totalMs },       // 建议显式传。显式 totalMs ⇒ applyBudgetPolicy 钳 maxTotalFactor=1
                                     //   （硬顶、无宽限无延长，spawn-service.ts L420-424 / types.ts L160-162）
                                     //   ——后台静默 run 要有界；不传则用全局预算（watchdog 照常武装，
                                     //   只是宽限/延长通知也被 CC2 吞了，owner 感知不到超时过程）
  deadlineAt,                        // 可选。绝对时刻硬顶（CC4）；与 budgetOverride 二选一即可
  schema,                            // 可选。结构化输出（X10），静默 run 照常支持
  slotless,                          // 默认【不传】（false）。走并发池（默认 6 槽），与 workflow 子女
                                     //   同一决策（spawner-adapter.ts D-W3 注释）：静默 run 花的是真
                                     //   模型调用，占槽是诚实记账，且占槽 run 才有 queue-timeout 保护。
                                     //   仅当「6 槽全忙也必须立即启动」时才 true（SingleSlotPool 直接
                                     //   发 ticket，无排队超时保护，slot-pool.ts L40-43）
  // signal / detachSignalOnStart：默认都不传（§3.2）。封装层不接受调用方 signal，防误链接。
  // expectAck：不传。它只影响 claimedRunIds/ack 语义，不构成静默（§2.2）；结果统一用 waitOutcome 收。
  // resumeFrom：不传。resume 走同一 spawn 准入且要求目标非 running，与静默场景无关。
  // isolation: "worktree"：按需。语义同普通 run（reap 时提交 pi-agent-<runId> 分支）。
}
```

返回后 owner 侧的收尾 API（封装层提供）：

```ts
waitOutcome(runId, waitMs?)   // 有界等待终态；异常安全网路径也会经 finish() settle waits，
                              // waitOutcome 能拿到 failed outcome（不会悬挂）
query.get(runId)              // 快照（进度、diag）
stopChildrenOf(ownerId, cause?)  // 幂等收尸：只杀这个 owner 名下的静默 run（含尚未启动完成的，
                              // OS4 快照扫尾兜底）；不影响任何真实 run
```

## 5. 落地改动清单

### 5.1 新增 `src/service/silent-spawn.ts`（推荐，本次实施）

纯域模块（无 pi import，符合分层约定）。职责：把 §4 配方固化成 API，让调用方**无法传错**。

```ts
// src/service/silent-spawn.ts
export interface SilentSpawnOptions {
  type: string;
  prompt: string;
  label?: string;
  cwd?: string;
  budgetOverride?: { totalMs?: number; queueWaitMs?: number };
  deadlineAt?: number;
  schema?: Record<string, unknown>;
  slotless?: boolean;
  /** 不暴露 signal / detachSignalOnStart / parentRunId / expectAck —— 有意为之（§3.2/§2.2） */
}
export interface SilentRunHandle {
  ownerId: string; // `silent-owner:<uuid>`
  runId: RunId;
  label?: string;
  waitOutcome(waitMs?: number): Promise<BoundedWaitResult>;
  snapshot(): RunSnapshot | undefined;
  stop(cause?: StopCause): Promise<boolean>; // spawn.abort(runId)
  stopAll(cause?: StopCause): Promise<{ stopped: RunId[]; pending: RunId[] }>; // stopChildrenOf(ownerId)
}
export function createSilentSpawner(deps: {
  spawn: () => SpawnService; // 访问器：/reload 换栈后取新服务，不持旧引用
  query: () => QueryService;
}): {
  spawnSilent(opts: SilentSpawnOptions): Promise<{ ok: true; run: SilentRunHandle } | { ok: false; error: ErrorInfo }>;
};
```

实现要点：

- `ownerId` 前缀用 `silent-owner:`。真 run id 的格式是 `r_[0-9A-HJKMNP-TV-Z]{8}`
  （`src/core/ids.ts` L10 `RUN_ID_RE`），该前缀**格式上不可能**与任何现在/未来的真 run id
  碰撞（`newRunId` 只生成 `r_` 前缀）⇒ 永不可能意外命中 `nesting` 表。workflow 的
  `wf_*` 合成 id 是同一手法的先例。
- `label` 未传时自动补 `silent-${type}` 前缀（可读性 + 可检索）。
- spawn 返回 `{error}`（unknown type / quota gate / 不可解析 model hint 等准入失败是同步
  config error，**没有任何通知**）时原样上抛给调用方——静默 run 的失败从定义上就是调用方
  自己的责任。

### 5.2 缺口修复：notifyTerminalFailure 感知子 run（3 行）

- `src/service/spawn-service.ts` L69（`SpawnServiceDeps.notifyTerminalFailure` 签名）改为
  `(outcome: RunOutcome, opts?: { childRun?: boolean })`；
- `src/service/spawn-service.ts` L243（start() 的 catch）改为
  `deps.notifyTerminalFailure?.(failed, { childRun: req.parentRunId !== undefined })`
  ——`req` 就在作用域里，比查 map/快照都稳（`finish()` 此时已清理 `parentOf`，
  run 快照的异常路径重建也不带 parentRunId 字段，都不能用）；
- `src/stack.ts` L1134 的 `notifyTerminalFailure` 闭包开头加
  `if (opts?.childRun) return;`。

该修复同时惠及 workflow 子女 run 和嵌套 run（它们在同一路径上也会漏发）。

### 5.3 装配（遵守 I7：index.ts 只装配）

- `src/stack.ts` `buildSessionStack`：在 `spawnRef`/query 就绪后构造
  `const silentSpawner = createSilentSpawner({ spawn: () => spawnRef.current!, query: () => query })`，
  加入返回对象（L1443-1460 的 stack 字面量，加 `silent: silentSpawner` 一行）。
  （注意 `spawn` 变量在 L1446 直接可用；若闭包捕获顺序有环则用已有的 `spawnRef` 模式。）
- `src/index.ts`：需要静默派生的 feature 模块在装配处拿到
  `silent: () => holder.current?.silent`。不改任何工具面/命令面——本能力**只给扩展内部代码**，
  不对模型暴露（模型已有 `run_in_background`；RPC 面本来就允许任意 parentRunId，无需新增）。

### 5.4 不改的东西（明确）

- `core/state-machine.ts`：不加 per-run 通知开关（finish() 无条件 enqueue 保持不变；CC2 在
  解释器层过滤是既定架构，workflow 设计已定型该模式）⇒ **状态机转移矩阵/性质测试无需动**。
- watchdog / reaper / slot-pool / notifier：零改动。
- feishu-notify / HUD / fleet widget 等消费侧：零改动（副作用见 §6.2）。

## 6. 坑、约束与残余风险

### 6.1 设计性约束（配方依赖，需在 review 中守住）

1. **`parentRunId` 永远用合成 id，绝不用真实发起方 run id**——一旦传真 id，三点同时崩：
   白名单/深度校验（点 1）、级联中止（点 3）都会回来，唯一保住的是 CC2 静默。封装层不暴露
   parentRunId 参数就是为了从类型上杜绝。
2. **静默 = 完全静默，不可分期**。CC2 吞掉的是该 run 的**全部**顶层通知：完成、失败、
   config-failure、deadline 宽限/延长。owner 想要进度/超时感知必须自己做（`waitOutcome`
   轮询、`query.get` 快照）。特别是：静默 run 卡住时，watchdog 的宽限/延长过程你**看不到**，
   直到它终态（waitOutcome 才醒）。预算建议用显式 `totalMs` 硬顶，把「最多等多久」变成
   调用时就知道的数。
3. **失败也是静默的**。准入失败是同步 `{error}` 返回（好办）；准入后失败（config/timeout/
   模型错）只体现在 outcome 里。封装层必须把 `waitOutcome` 作为一等公民返回给调用方，
   并在文档里写明「不 await 结果 = 结果丢失」。
4. **`slotless:true` 有代价**：不占并发槽（好）但**没有 queue-timeout 保护**，且绕过
   `concurrencyLimit` 的全局并发意图；默认不传（false），走池子排队（代价：6 槽全忙时会
   排队，极端下死在 queue_timeout——对后台任务是可接受的诚实行为）。

### 6.2 可见性副作用（不是通知，但「看得见」）

静默只断**通知投递**，不断**可观测性**。以下地方静默 run 仍然出现，需要接受：

- fleet widget / `/agent status`：合成父不是 `wf_` 前缀，不会被折叠成 workflow 组——大概率
  浮为顶层/孤儿行（视觉未实测，属前序 openQuestion；建议 label 加 `silent-` 前缀缓解）。
- `subagent:started` 等生命周期事件照发（pi 事件总线，面向扩展，不是 turn 触发）。
- **background-status 计数**（`src/index.ts` L150-160）：`runningSubagents` 把静默 run 算
  进去 ⇒ feishu 完成卡的 background-idle 门控（`isBackgroundIdle`，feishu-notify/core.ts
  L236）会被静默 run 按住、cache-keepalive 的 busy 判定同理。通常这正是想要的语义
  （「主会话停了但后台还忙」就不该发完成卡/保活），但如果某特性想要「对 background 计数
  隐身」，本方案做不到——那需要改 `runningSubagents` 的过滤口径（不建议，如实列为做不到）。
- label/mention：label 照常注册（`onLabel`，target.parent=合成 id），`@` 自动补全只列 root
  直属 run 所以**不会出现在补全里**，但 label resolve 仍能命中（可被 steer/abort）。
  这是可接受的泄漏面。
- fabric tree：`onSpawnEdge(合成id, runId)` 会加一条以合成 id 为父的边（stack.ts L1126）。
  静默 run 的 `message_agent` 默认路由是「仅父」，父是合成节点 ⇒ 它发出的消息会进
  dead-letter/找不到收件人（具体行为属 fabric 内部，未深查）。若静默 run 需要 fabric 通信，
  在其 agent type frontmatter 里配 `can_message` 指向真实可达对象；不需要 fabric 的内部
  维护型 run 无此问题。

### 6.3 做不到的（如实声明）

1. **活不过宿主会话**：`session_shutdown`（reload/new/resume/fork/quit）一律杀掉（§3.3）。
   跨栈存活需要 bash-job 式的收养机制（把活 run 的 runner 句柄/会话文件移交新栈并重建
   watch）——现有 `SpawnService` 没有这个接缝，属新增工程，不在本方案范围。若 feature
   只要求「跨 reload 存活」，替代思路是把任务状态落盘后在新栈重派（scheduler 的 cron 语义），
   而不是保活进程内 run。
2. **notifyTerminalFailure 缺口在修复前是真实残余风险**：`runner.run()` 抛异常（正常代码
   路径构造不出，但未来 bug 可能造出）时静默 run 会漏发一条顶层通知且会跨 reload reconcile
   重投。§5.2 修掉；修复落地前这是唯一的「可能违背点 2」路径。
3. **owner 崩溃则无人收尸**（直到 run 自身预算耗尽/watchdog 超时）。`stopChildrenOf` 只是
   手段，不是保证。预算硬顶（§4）是最终兜底——这也是配方强制建议显式 `totalMs` 的原因。
4. **不改变已有外部面**：RPC `SpawnParams.parentRunId` 本就允许任意字符串（protocol.ts
   L45），即外部调用者今天就能派生「静默」run。本方案没有引入也没有收窄这个面；若将来
   要收紧 RPC，属独立工作。

### 6.4 次要坑

- **不要传 `expectAck`**：无静默收益（§2.2），反而让 run 进 `claimedRunIds`，`spawnAndWait`
  语义混入。统一 `waitOutcome`。
- **同 owner 多次 spawn** 是合法且预期的（`childrenOf` 是 Set）；`stopChildrenOf` 一次收走。
- **steer 仍可用**（label resolve 命中），无碍。
- `detachSignalOnStart` **不是免死金牌**：admission 前已 abort 的 signal 立即取消
  （runner.ts L45-47 注释）；只有「启动后」才解绑。
- 内存 `before_agent_start` 注入照常发生在静默 run 的子会话里（它是普通 run）——若不想要，
  在其 agent type 上配置（memory 侧已有 per-type 机制），不是本方案的事。

## 7. 验证点（测试设计）

新增 `tests/service/silent-spawn.test.ts`，沿用 `tests/service/nesting.test.ts` 的
`controllableRunner()` + `typesRegistry()` 模式（可抽公共 fixture）：

**T1 嵌套校验绕过（点 1）**

- 环境：type `parent` 配 `canSpawn: ["x"]`；先 spawn 一个 `parent` 类型的活 run A
  （controllableRunner 让它不 settle）；`maxNestedDepth` 用默认 3。
- 断言：
  - `spawn.spawn({ type: "y", parentRunId: A_runId })` 返回 error
    `"nested delegation is not permitted"`（对照组，证明校验在场）；
  - `spawnSilent({ type: "y", ... })`（内部 parentRunId=silent-owner:*）**成功**返回 runId，
    且 `query.get(runId)` 可见；
  - 再造一条已达 `maxNestedDepth` 的活链，`spawnSilent` 依然成功（depth 0）。
  - 封装不变式：spy SpawnService.spawn，断言发出的请求 `parentRunId` defined 且匹配
    `/^silent-owner:/`，且 `expectAck === undefined`、`signal === undefined`。

**T2 通知静默（点 2）**

- 复用 `tests/service/h2-failure-visibility.test.ts` 的 adapter harness（它已锁定
  「带 parentRunId 的 config-failure 不发通知」，L188-202）：
  - settle 一个带合成 parentRunId 的 run 到 `completed`：断言 notifier 的
    enqueue/send（或 harness 的 sendMessage spy）对该 runId **零调用**——包括完成、
    deadline notice；
  - 对照组：同 harness 下不带 parentRunId 的 run 完成时 send 恰好一次且
    `triggerTurn === true`（锁定唤醒机制在对照组存在）。

**T3 取消免疫（点 3）**

- controllableRunner：活 run A（真实派生）、`spawnSilent` 得 S、再加一个对照组
  `spawn.spawn({ ..., parentRunId: A })` 得 C。
- 依次断言：
  - `service.abort(A, "user_stop")` 后：C 的 abort 被调用（runner.abortCalls 含 C），
    **S 不在 abortCalls**，`query.get(S.runId)` 仍非终态；
  - settle A 为 `timed_out`（触发 cancel-handle → onChildAbort → 级联链）：S 仍存活
    （证明超时路径同样免疫）；
  - `handle.stopAll()` 后：S 进入 abort；`stopChildrenOf(ownerId)` 不触碰其它任何 run。

**T4 异常安全网修复（§5.2 回归）**

- 让 `runner.run` 直接 reject：断言 deps spy `notifyTerminalFailure` 被调时携带
  `{ childRun: true }`（parentRunId 请求）；`childRun: true` 时 stack 层闭包提前 return
  （可对 stack 层做纯函数化断言或用现有 stack harness）；对照组（无 parentRunId）仍会
  enqueue。
- `waitOutcome(S.runId)` 在该路径 resolve 出 failed outcome（owner 不悬挂）。

**T5 集成（`tests/integration/`）**

- 现有 harness 起主会话：宿主代码 `spawnSilent` 一个真实 run（预算小、prompt 快速完成）；
  断言：
  - 主会话收不到任何 `customType: "subagent:notification"` 的 sendMessage（全量断言，
    非仅该 runId）；
  - `waitOutcome` 拿到 completed 且文本符合 prompt 约定；
  - 期间对另一个普通 top-level run 调 abort_subagent，静默 run 不受影响；
  - 触发 `session_shutdown`（或直接调 handler）后静默 run 变 `aborted`（锁定存活上限
    的契约，防止将来有人误以为它跨 reload）。

**回归面**：不触 `core/state-machine.ts` 与 delivery 生命周期 ⇒ 转移矩阵/性质测试不动
（AGENTS.md 约定）。`tests/service/nesting.test.ts` 与 `h2-failure-visibility.test.ts`
必须保持绿（它们分别锁定 X3 与 CC2 的既有语义，本方案依赖它们不漂移）。

## 8. 备选方案与否决记录（含前序 ruledOut 摘要）

| 备选                                                              | 否决原因                                                                                                        |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `expectAck` + ack 窗口抑制通知                                    | fail-open：默认 `ackWindowMs=0`，enqueue→send 同步链先于 ack；goal verifier 即反例（§2.2）                      |
| state-machine 加 per-run「不发通知」开关                          | 改动核心状态机 ⇒ 转移矩阵/性质测试连带；CC2 在解释器层过滤是既定架构（workflow 已定型），无需新开关             |
| 不传 parentRunId（裸 spawn，scheduler 模式）                      | 点 2 直接失败：`src/schedule/scheduler.ts` 的内部派生就是反例——完成照发顶层通知并 `triggerTurn:true` 唤醒主会话 |
| 传真实发起方 run id                                               | 点 1/点 3 双崩（§1.2/§3.1）                                                                                     |
| 借嵌套 Agent 工具注入路径                                         | 强制 parentRunId=本 run id + slotless（runtime-adapter L422-433），产不出静默派生                               |
| bash job 式跨会话收养                                             | 独立子系统的进程语义（`src/bash/`），与 SpawnService 的通知/取消通道不共用；跨栈存活是新增工程（§6.3）          |
| fabric / delivery-engine / context-receipt / mention 作为抑制机制 | 前序已排查：engine 只服务 fabric 记录；receipt/mention 只影响展示不影响投递                                     |
| watchdog/reaper 关闭以「不杀」                                    | reaper 只做终态后回收；watchdog 无 per-run 开关，且关闭预算监督违背项目零挂保证基调                             |
