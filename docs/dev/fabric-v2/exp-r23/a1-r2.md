# 静默后台 run 实施方案（pi-toolkit）

需求：**扩展内部代码**（host 侧，非模型工具调用）要能派生一种 run，同时满足：

1. 不触发嵌套委派校验（canSpawn 白名单 + `maxNestedDepth` 深度上限）；
2. 不产生顶层完成通知，更不能唤醒主会话起一轮模型调用；
3. 不被发起方的取消级联杀掉（发起方 run 被取消/超时/用户停止时，静默 run 独立存活）。

结论先行：**三个点全部可以只用现有接缝满足，零生产代码改动即可用**；建议再补一个小封装 + 一个加固补丁（§3）。核心钥匙只有一个参数：**`parentRunId` 传合成 id（绝不传真实发起方 run 的 id）**。

---

## 1. 三点需求 → 机制映射

### 1.1 绕开嵌套校验（需求 1）

校验位置：`src/service/spawn-service.ts` → `spawn()` 的 **X3 段**（约 334–357 行）：

```ts
let depth = 0;
if (req.parentRunId) {
  const parent = nesting.get(req.parentRunId);
  if (parent) {                       // ← 只有父命中 nesting 表才校验
    if (!parent.canSpawn?.includes(req.type)) return { error: {...} };
    depth = parent.depth + 1;
    if (depth > maxNestedDepth) return { error: {...} };
  }
}
```

`nesting` 表只登记**本 SpawnService 跟踪的、仍在跑的 run**（spawn 时 `nesting.set(runId, ...)`，finish 时删除）。因此：

- **不传 `parentRunId`** → depth 0 直通，零白名单检查；
- **传合成 id**（从未被 spawn 跟踪的字符串，如 workflow 的 `workflowId`）→ `nesting.get()` 返回 `undefined` → 同样 depth 0 直通。

这是注释里明确认可的设计（spawn-service.ts X3 段注释原文："untracked/foreign parentRunId … left unrestricted (depth 0, no canSpawn cap)"），不是钻空子。

**反面**：若传真实发起方 run 的 id，且该 run 仍在跑（在 nesting 表里），就必须满足发起方 agent type 的 `canSpawn` 白名单 + `maxNestedDepth`（默认 3，`src/config/settings.ts`）。另外父 run 结束时其 nesting 表项即被删除（`finish()` 里 `nesting.delete`），用真实父 id 的校验行为是竞态相关的（父先死→不校验；父还活着→校验），不可依赖。

### 1.2 不产生顶层完成通知、不唤醒主会话（需求 2）

通知链路：`src/core/state-machine.ts` → `finish()` 对每次终态**无条件**产出 `enqueue_delivery` 效果 → `src/service/runtime-adapter.ts` 的效果解释器 → notifier（outbox）→ `src/stack.ts` → `sendFormatted()`（约 911–958 行）→ `pi.sendMessage({customType: "subagent:notification", ...}, {triggerTurn: true})`。

**`triggerTurn: true` 就是"唤醒主会话起一轮模型调用"的机制**（对照：compact-hint / quota hint 刻意用 `triggerTurn: false` 以免唤醒）。

唯一的"谁的完成通知进主会话"过滤点是 runtime-adapter 的 **CC2**：

```ts
// src/service/runtime-adapter.ts run() 入口（约 338 行）：
if (spec.request.parentRunId !== undefined) childRunIds.add(spec.runId); // CC2

// enqueue_delivery 解释器（约 230–236 行）：
if (childRunIds.has(e.payload.runId)) return; // 直接丢弃：不进 outbox、不 sendMessage
```

CC2 的判定条件就是 **`parentRunId !== undefined`**——与父是否为真实 run 无关，合成 id 同样生效。CC2 同样拦截：

- config-failure 通知：`settleConfigFailure()`（约 306–345 行）`if (!childRunIds.has(runId))` 才 enqueue；
- deadline 宽限/延长通知：`deadlineNoticeHandler(childRunIds, ...)`（约 104–108 行）。

这正是 workflow 子女 run 的现成做法（`src/workflow/host.ts` 约 599–606 行，`parentRunId = workflowId` 合成 id；先例接线见 `src/workflow/spawner-adapter.ts` 与 `src/stack.ts` 1434 行 `parentRunId: workflowId`）。

**不能走的死路**：`expectAck` + ack 抑制。`ackWindowMs` / `coalesceWindowMs` 默认均为 0（`src/config/settings.ts` 384–386 行附近），notifier 的 `enqueue → attempt → send` 是同一同步链、先于任何 ack 微任务执行——抑制 fail-open（`docs/dev/delivery-v2/architecture.md` 192–193 行明确承认）。goal verifier 的 `spawnAndWait` 先例正是这样：默认配置下其完成通知照样发。

**已知缺口（要在方案里修，见 §3.3）**：`spawn-service.ts` `start()` 的 catch 安全网（`deps.notifyTerminalFailure?.(failed)`，243 行）不查 parentRunId——`runner.run` 抛异常时静默 run 仍会经 `stack.ts` 的 `notifyTerminalFailure`（约 1134–1167 行）发顶层通知。正常代码路径构造不出该异常（需要效果解释器/reducer 在 catch 路径再抛错），属潜伏缺陷。

### 1.3 不被发起方取消级联杀掉（需求 3）

级联的数据基础：`spawn-service.ts` `start()` 登记 `parentOf`/`childrenOf`（约 430–441 行）——**仅当请求带 `parentRunId` 时**，登记在 `childrenOf[req.parentRunId]` 名下。两条触发链：

- (a) `spawnService.abort(runId)`（abort_subagent 工具、stopChildrenOf）→ 先 `cascadeChildren(runId)` 再杀自身（约 528–543 行）；
- (b) 任何原因取消某个 run（user_stop / timeout / external）时，`src/runtime/runner.ts` `run()` 里 cancel handle 的 onCancel 闭包都调 `onChildAbort(runId, "parent_abort")`（约 390–412 行），经 `src/stack.ts` 1079 行接线 `onChildAbort: (parentRunId, cause) => spawnRef.current?.abort(parentRunId, cause)` 再级联——即**父 run 超时/被用户停/Esc 都会带走其在 childrenOf 里的子 run**。

因此：**parentRunId 用合成 id ⇒ 静默 run 不在任何真实 run 的 childrenOf 里 ⇒ 两条链都摸不到它**。它只能被以下方式杀掉：

- 显式 `abort(静默runId)` / `query.stop(静默runId)`（对着它自己）；
- owner 主动 `stopChildrenOf(合成id)`（workflow 正是用这个收尸，CC1/OS1–OS4 语义）；
- `session_shutdown`（见 §5 硬约束）。

**外部信号层面**：不传 `signal` 即无任何链接。若调用点处在主会话 turn 上下文内、手上有 turn 的 AbortSignal，又想免疫 Esc / 强制压缩的 turn 中止，传 `detachSignalOnStart: true`（`runner.ts` 414 行：cancel handle 创建后立即 `cancel.detach()` 解绑外部 listener）——现成先例是 Agent 工具的 `run_in_background`（`src/tools/agent-tool.ts` 283–292 行）。注意：detach 只解外部 listener，走 `activeCancels` 的路径（abort_subagent、watchdog 超时）不受影响；且**在 admission 前就已 aborted 的 signal 仍会立即取消**（createCancelHandle 的 `external?.aborted` 即时检查）。

## 2. 可直接落地的调用配方

### 2.1 主配方（今天就能用，零代码改动）

调用入口：host 侧拿到当前会话的 `SpawnService`——

- stack 装配期创建的特性：`buildSessionStack` 内直接闭包引用 `spawn`（先例：`createScheduler({ spawn })`，`src/stack.ts` 1358 行）；
- `src/index.ts` 装配的特性：经 `holder.current?.spawn`（holder 模式见 index.ts 149 行起；转发先例 index.ts 280 行 `spawn: forwardSpawn(holder)`）。
- 子会话内的扩展实例因 HOST_KEY 守卫是 inert 的，**拿不到**——静默派生天然只能在 host 侧做，这与需求（"扩展内部代码"）一致。

```ts
import { randomUUID } from "node:crypto";

// ① 合成 owner id：真实 run id 形如 `r_[0-9A-HJKMNP-TV-Z]{8}`（src/core/ids.ts RUN_ID_RE），
//    `silent:` 前缀保证永不与真实 run id 碰撞，也永不命中 nesting 表。
const ownerId = `silent:${featureName}:${randomUUID()}`;

// ② 派生（stack.spawn = SpawnService）
const started = await stack.spawn.spawn({
  type: agentTypeName, // 必须是已注册的 agent type（registry 里真实存在）
  prompt: taskPrompt,
  label: `silent-${featureName}`, // 可选但强烈建议（见理由表）
  parentRunId: ownerId, // ★ 核心参数，三点全靠它，见理由表
  // slotless / budgetOverride / signal+detachSignalOnStart：按 §2.3 权衡表决定，默认都不传
});
if ("error" in started) {
  /* admission 失败：unknown type / model hint / quota gate 等，同步 config error */
}
const { runId } = started;
```

### 2.2 逐参数理由

| 参数                                                                                                | 传法                                                                                                            | 为什么                                                                                                                                                                                                                                                                                                                                                                                    |
| --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `type`                                                                                              | 已注册的 agent type 名                                                                                          | admission 有 unknown-type 快速失败；类型决定 system prompt / tools / model。静默 run 就是普通 run，全套 admission（含 quota gate、model hint 解析）照常走——这是特性不是缺陷                                                                                                                                                                                                               |
| `prompt`                                                                                            | 任务全文                                                                                                        | 无特殊语义                                                                                                                                                                                                                                                                                                                                                                                |
| `label`                                                                                             | `silent-<feature>`（可选，建议）                                                                                | 静默 ≠ 隐形：该 run 仍出现在 fleet widget / `/agent status` / label 注册表里，带前缀的 label 是唯一的人肉排障锚点。label 冲突由 `deriveUniqueLabel` 自动加序号                                                                                                                                                                                                                            |
| `parentRunId`                                                                                       | **合成 id** `silent:<feature>:<uuid>`                                                                           | 一个参数同时达成三点：① 不命中 nesting 表 → X3 零校验（§1.1）；② `!== undefined` → 进 `childRunIds` → CC2 拦掉完成/config-failure/deadline 全部通知（§1.2）；③ 只登记进 `childrenOf[合成id]` → 真实 run 的两条级联链都摸不到（§1.3）。**绝不传真实发起方 run 的 id**——那会三点全破：白名单+深度校验、childrenOf 级联、且 CC2 语义变成"由父消费"而父根本不知道要消费                       |
| `slotless`                                                                                          | 默认**不传**（false）                                                                                           | 不传 ⇒ 走并发池：占 1 个 `concurrencyLimit`（默认 6）槽，换来 **queue-timeout 保护**（`queueWaitMs` 预算）+ 与模型发起的 Agent 调用公平排队。传 true ⇒ `SingleSlotPool` 直发 ticket（`src/runtime/slot-pool.ts` 40–43 行）：不占槽也无排队超时保护。workflow 子女**故意不 slotless** 以保留排队保护（spawner-adapter.ts D-W3 注释）——除非"6 槽全忙时必须立刻启动"，否则跟随 workflow 先例 |
| `signal` + `detachSignalOnStart`                                                                    | 默认都不传；仅当调用点持有 turn AbortSignal 且在意 turn 中止时：`signal: turnSignal, detachSignalOnStart: true` | 不传 signal = 无外部链接，最简单。传了 signal 又不解绑 = turn 中止（Esc / compact-hint 强制压缩）会顺着 signal 杀掉静默 run；`detachSignalOnStart: true` 在 run 启动后立即解绑外部 listener（agent-tool `run_in_background` 先例）。注意 admission 前已 aborted 的 signal 仍会立即取消（防御检查不受 detach 影响）                                                                        |
| `expectAck`                                                                                         | **不传**                                                                                                        | 它只把 runId 加进 `claimedRunIds`（影响 `expectsAck()` 查询），对通知抑制毫无作用（CC2 才是抑制点；ack 窗口默认 0，fail-open）。省掉无谓状态                                                                                                                                                                                                                                              |
| `budgetOverride`                                                                                    | 默认不传                                                                                                        | 不传 ⇒ 用全局预算合并（类型 frontmatter `budget:` → 全局默认），watchdog 照常武装每个 run——**anti-hang 不变量保持**。传 `totalMs` ⇒ `applyBudgetPolicy` 钳 `maxTotalFactor=1`（硬顶、无宽限无延长，D-10）；要给静默 run 单独设上限时才用，并接受"到点即死无宽限"                                                                                                                          |
| `resumeFrom` / `schema` / `isolation` / `deadlineAt` / `modelOverride` / `thinkingOverride` / `cwd` | 按需                                                                                                            | 与静默性正交：`schema` 走 X10 结构化输出（注意 memory 里记录过 `Agent({schema})` 的健壮性缺口——schema 必须是 plain JSON 对象，别传字符串）；`isolation: "worktree"` 可选隔离；`deadlineAt` 是绝对墙钟硬帽（CC4）                                                                                                                                                                          |

### 2.3 收结果与收尸（配方后半段）

```ts
// 收结果（二选一）：
// (a) 有界轮询/等待：waitOutcome(runId, waitMs) → {kind:"settled",outcome} | {kind:"pending"}
const r = await stack.spawn.waitOutcome(runId, 30_000);
// (b) 一次性等到终态：spawnAndWait 会强制 expectAck:true（spawn-service.ts 445–447 行）——
//     对静默 run 无害（CC2 下 outbox 里根本没有它的记录，onOutcomeAcked→notifier.ack 是无害 no-op），
//     但语义上更推荐 spawn + waitOutcome 组合，避免无谓的 claimedRunIds 登记。

// 查状态：stack.query.get(runId)（fleet 同款快照）
// 提前停（feature 自身收尾）：owner 主动收尸，workflow 先例（CC1，不需要 ownerId 是 tracked run）：
const { stopped, pending } = await stack.spawn.stopChildrenOf(ownerId, "user_stop");
// OS4：pending 是 cascade 后仍未终态的快照，调用方需自行 sweep（或依赖下述 drain）
```

**会话级兜底**：`src/index.ts` `session_shutdown`（约 543–546 行）会对所有非终态 run 调 `query.stop(runId, "shutdown")` 再 bounded drain——静默 run 活不过 `/reload`、`/new`、`/resume`、fork、`quit`。owner 级收尾（feature 提前结束）仍应主动 `stopChildrenOf`。

## 3. 落地封装与加固（建议的代码改动）

配方能用但不该让每个调用方手搓——parentRunId 传错一个字符（传成真实 id）三点全破。建议做两件小事 + 一个加固：

### 3.1 新文件 `src/service/silent-run.ts`（纯 service 层，零 pi import，符合分层）

```ts
export interface SilentRunHandle {
  ownerId: string; // 合成父 id，owner 收尸用
  runId: string;
  label?: string;
  outcome(waitMs?: number): Promise<{ kind: "settled"; outcome: RunOutcome } | { kind: "pending" }>;
  stop(): Promise<{ stopped: string[]; pending: string[] }>; // → spawn.stopChildrenOf(ownerId, "user_stop")
}

export interface SilentRunSpawner {
  spawn(req: {
    type: string;
    prompt: string;
    label?: string;
    slotless?: boolean;
    budgetOverride?: Partial<DeadlineBudget>;
    modelOverride?: { provider: string; id: string };
    signal?: AbortSignal; // 内部自动配 detachSignalOnStart: true
    schema?: JsonSchema;
  }): Promise<SilentRunHandle | { error: ErrorInfo }>;
}

export function createSilentRunSpawner(spawn: SpawnService, featureName: string): SilentRunSpawner;
```

内部逻辑就是把 §2 的配方固化：

- `ownerId = \`silent:${featureName}:${randomUUID()}\``（`silent:` 前缀 + UUID，`RUN_ID_RE = /^r_[0-9A-HJKMNP-TV-Z]{8}$/` 保证永不碰撞真实 run id、永不命中 nesting 表）；
- 透传调用方参数，**强制** `parentRunId: ownerId`；传了 `signal` 就强制 `detachSignalOnStart: true`；**永不**透传 `expectAck`；
- `outcome()` 包 `spawn.waitOutcome(runId, waitMs)`；`stop()` 包 `spawn.stopChildrenOf(ownerId, "user_stop")` 并返回 OS4 pending 快照。

单测直接用 `SpawnService` 类型注入（与 `createWorkflowChildSpawner` 同款依赖注入风格）。

### 3.2 `src/stack.ts` 接线（两处）

- `buildSessionStack` 内、`createScheduler({ spawn })`（1358 行）旁：`const silentRuns = createSilentRunSpawner(spawn, ...)`——按 feature 分别创建或暴露工厂；
- `export interface Stack`（475 行，`spawn`/`query` 字段旁）加 `silentRuns`（或工厂方法）。`src/index.ts` 侧特性经 `holder.current?.silentRuns` 取用（现有 holder 转发模式，index.ts 280 行起）。

### 3.3 加固补丁（修 §1.2 的缺口，建议一并做）

**文件**：`src/service/spawn-service.ts` → `start()` 的 catch 块（243 行附近）。

**改法**：对齐 CC2 判据（`parentRunId !== undefined`）——

```ts
finish(failed);
if (req.parentRunId === undefined) deps.notifyTerminalFailure?.(failed); // CC2 对齐：子 run 的异常路径通知也归 owner 消费
```

**理由**：`notifyTerminalFailure` 是 `runner.run` 抛异常时的安全网，实现方（`stack.ts` 1134–1167 行）无法访问 runtime-adapter 私有的 `childRunIds`，但 spawn-service 手里有 `req.parentRunId`——与 runtime-adapter 填充 `childRunIds` 用的是同一判据。对真实嵌套子 run，异常路径的顶层通知本就是重复（父的 Agent 工具会经 `finish()`→outcomes 拿到 failed outcome），与 CC2 "子 run 由 owner 消费"语义一致。不修的话：静默 run 一旦踩中该路径，会发顶层通知 + `triggerTurn:true` 唤醒主会话，且该 payload 落进持久 outbox 后，`/reload` 重建栈时 reconcile 还会重投。

## 4. 坑、约束与残余风险（如实清单）

1. **活不过主会话**：`session_shutdown`（index.ts 543–546 行）无差别停掉所有非终态 run。bash job 有跨栈收养（`handoffInProcess`/`adoptOrphans`），subagent run **没有**等价机制——"静默 run 在 /reload 后存活"是新增工程（跨栈收养 + run 状态持久化重建），本方案不做，如实声明做不到。
2. **静默 ≠ 隐形**（CC2 只断通知不断可见性）：静默 run 仍出现在 fleet widget、`/agent status`、`subagent:started` 事件里；label 照常注册进 mention 表（@ 自动补全只列 root 直属 run，静默 run 不进补全但可被 `resolveRun` 按 label/前缀解析）。这些是**特性**（可观测性），不是 bug。
3. **background-status 计数副作用**：`publishBackgroundStatus`（index.ts 约 150 行）按 `query.list()` 非终态数 `runningSubagents`——静默 run 在跑会： 阻塞 feishu 完成卡（后台空闲门控）， 影响 cache-keepalive 的 busy 判定。派生前想清楚这两个门控是否接受被顶住。
4. **CC2 语义依赖**：整套静默性押在 "`parentRunId !== undefined` ⇒ child ⇒ 静默" 这一条判据上。若未来 CC2 被细化成"父必须是 tracked run"，合成父的静默性即破——所以封装（§3.1）+ 锁定测试（§6 T1）是必须的，不是可选的。
5. **该能力早已外部暴露**：RPC `SpawnParams` 本就允许任意 `parentRunId` 字符串（`src/rpc/protocol.ts` 45 行），外部调用方今天就能派生"静默" run。本方案没有引入新暴露面。
6. **queue_wait / 并发权衡**：非 slotless 静默 run 占并发槽（默认 6 之一），可能让模型发起的 Agent 调用排队；slotless 则无 queue-timeout 保护（但 watchdog 的 startup/total 预算照常武装，anti-hang 不降级）。二选一，别既要又要。
7. **budget 硬顶语义**：显式 `budgetOverride.totalMs` ⇒ `maxTotalFactor` 钳 1，无宽限无延长（D-10）。长任务静默 run 要么靠全局预算（有宽限/延长），要么接受到点即死。
8. **fabric tree 边**：带 parentRunId 的 spawn 会 `onSpawnEdge(合成id, runId)` → `fabric.tree.appendEdge`（stack.ts 接线）。fabric 树里多出一个悬空合成节点；fleet widget 对未知父的渲染（浮为顶层/孤儿行）**未实际启动 UI 验证**，属已知不确定点。向合成节点发 fabric 消息会走 dead-letter，无危害。
9. **admission 仍会失败**：unknown type / 不可解析 model hint / quota gate 都是同步 config error（`{error}` 返回），调用方必须处理；这不是静默性的一部分。
10. **`Agent({schema})` 已知坑**（memory 记录）：schema 参数若传成字符串会在下游炸出无定位错误——必须传 plain JSON 对象。
11. **waitOutcome/spawnAndWait 的 ack 是无害 no-op**：CC2 下 outbox 无记录，`onOutcomeAcked → notifier.ack` 返回 false 不抛错。
12. **pi 端 `triggerTurn:true` 的确切唤醒行为未验证**：本仓库只能从用法推断（compact-hint/quota 刻意用 `false` 避免唤醒）。本方案通过 CC2 从源头掐掉通知，不依赖对该行为的精确理解——这是配方选 CC2 而非 ack 窗口的又一理由。

## 5. 验证点（测试设计）

新增 `tests/service/silent-run.test.ts`（沿用 `tests/service/nesting.test.ts` / `tests/service/h2-failure-visibility.test.ts` 的 fake runner / notifier spy 模式）：

**T1 · X3 绕过（需求 1）**

- 前置：注册一个 `canSpawn: []`（或不含目标 type）的父类型；起一个真实父 run 并保持 running（使其进入 nesting 表）。
- 断言：以该父类型身份派生目标 type 的普通嵌套 spawn → 收到 config error（对照组，复现 nesting.test.ts:96 行为）；`silentRunSpawner.spawn()` 同 type 同目标 → 成功返回 runId，无 config error。
- 补充：合成 ownerId 不匹配 `RUN_ID_RE`（防未来 isRunId 误判）。

**T2 · 通知静默（需求 2）**

- notifier spy（h2-failure-visibility.test.ts:188–202 同款）注入。
- 断言：静默 run 正常走完（非 config-failure 路径，覆盖 `enqueue_delivery` 的 CC2 分支——现有测试只锁了 config-failure 路径）→ `notifier.enqueue` **零调用**（runId 维度）；触发 deadline 宽限路径 → `onDeadlineNotice` 不被调（CC2 的 deadlineNoticeHandler 分支）。
- 栈级（tests/integration）：静默 run 完成后，`pi.sendMessage` 无 `customType: "subagent:notification"` 调用 ⇒ 无 `triggerTurn:true` 唤醒。**同时断言** `subagent:started`/`subagent:completed` 事件照发（可见性是特性，防止测试把"全静默"写过头）。

**T3 · 级联免疫（需求 3）**

- 起真实父 run A（类型无 canSpawn 也能起，普通 root run）+ 经配方起静默 run S。
- 对 A 走两条链分别断言 S 仍 running：
  - (a) `spawn.abort(A, "timeout")`（abort_subagent 链）；
  - (b) `query.stop(A, "user_stop")`（runner cancel handle → `onChildAbort` → `spawnService.abort(A)` 链）。
- 然后 `silentHandle.stop()`（即 `stopChildrenOf(ownerId)`）→ S 进入终态（owner 收尸可用）；断言 `stopped`/`pending` 形状符合 OS4。

**T4 · signal 语义**

- 传 `signal` + 封装强制的 `detachSignalOnStart: true`：run 启动后 abort 该 signal → S 不受影响；signal 在 spawn 前已 aborted → S 立即取消（admission 即时检查不豁免）。

**T5 · 加固补丁回归（§3.3）**

- 注入 `run()` 必抛的 fake runner + `notifyTerminalFailure` spy。
- 断言：带 parentRunId（静默/嵌套）→ spy 零调用；不带 parentRunId → spy 恰一次。与 `h2-failure-visibility.test.ts` 的 CC2 锁定测试同向，防止未来重构把两个安全网接歪。

**T6 · 封装不变量（若做 §3.1）**

- property 风格：`createSilentRunSpawner` 产出的每个请求都带 `parentRunId`（合成前缀）、不带 `expectAck`、传 signal 时必带 `detachSignalOnStart: true`——防调用方绕过配方。

## 6. 明确做不到 / 未验证的部分

- **跨会话存活**（/reload、/new、quit 后继续跑）：需要 bash-job 式的跨栈收养机制，现有 SpawnService 完全没有，属新增工程。本方案明确不做。
- **fleet widget 对合成父节点的视觉渲染**：代码推断为浮为顶层/孤儿行，未启动 UI 实测。
- **pi 端 `triggerTurn` 的实现行为**：未读 pi 核心源码，仅凭本仓库用法推断；方案不依赖它（从源头不发通知）。
- **`stopChildrenOf` 与子 run 尚处 `start()` 异步启动段的竞态**：OS4 注释称由 pending 快照扫尾兜底，未深查测试覆盖；owner 收尸时应处理 `pending` 返回值而非假定全停。
