# 静默后台 run 实施方案（a0-r2）

> 目标：pi-toolkit 扩展**内部代码**（宿主侧 hook / 服务 / 调度器，而非模型工具调用）能派生一种 run，同时满足：
>
> 1. 不触发嵌套委派校验（canSpawn 白名单 + maxNestedDepth）；
> 2. 不产生顶层完成通知，更不唤醒主会话起一轮模型调用；
> 3. 不被发起方的取消级联杀掉（发起方 run 取消/超时时静默 run 独立存活）。
>
> 本文所有行号以当前 master 工作区为准；每条机制均已对照源码核实。

---

## 0. 一句话结论

**一个参数达成三点**：用 `SpawnService.spawn({ ..., parentRunId: <合成 owner id> })` 直接派生——`parentRunId` 指向一个**从未被 SpawnService 跟踪的合成字符串**（如 `silent-owner-<uuid>`）。

- 合成 id 不在 `nesting` 表里 ⇒ X3 校验整段跳过（depth 0、零白名单检查）——这是 `spawn-service.ts` 注释里明确认可的设计（"untracked/foreign parentRunId … left unrestricted"）；
- `parentRunId !== undefined` ⇒ runtime-adapter 的 CC2 把该 run 的所有通知（完成/config 失败/宽限延长）在进 outbox 之前丢弃——这正是 SubagentWorkflow 子女 run 的做法（`workflow/host.ts` 用 `parentRunId=workflowId`）；
- 合成 id 不是任何真实 run ⇒ 它不出现在任何真实 run 的 `childrenOf` 里 ⇒ 发起方被 abort/超时级联时扫不到它。收尸只能由发起方显式 `stopChildrenOf(合成id)`。

唯一需要动生产代码的点是一个**潜伏缺陷的修复**（§3.3.1：`notifyTerminalFailure` 安全网不查 CC2），以及一个可选的封装模块。

## 1. 机制分析：三点需求各自的接缝

### 1.1 绕开嵌套委派校验（X3）

**文件**：`src/service/spawn-service.ts`，`createSpawnService()` 内 `spawn()` 的 X3 段（约 L322-357）。

```ts
let depth = 0;
if (req.parentRunId) {
  const parent = nesting.get(req.parentRunId);
  if (parent) {                                   // ← 只有命中才校验
    if (!parent.canSpawn?.includes(req.type)) return { error: {...} };
    depth = parent.depth + 1;
    if (depth > maxNestedDepth) return { error: {...} };
  }
}
```

- `nesting` 表（L121-127）只登记**当前仍在跑、由本 SpawnService 跟踪**的 run（`nesting.set(runId, { depth, canSpawn })` 在 L430，`finish()` 里 `nesting.delete` 在 L143）。
- 因此：**不传 `parentRunId`，或传一个未被跟踪的合成 id，都按 depth 0 直接通过、零白名单检查**。源码注释（L325-333）明确认可这是受支持用法（stale/finished 引用或纯展示用途的 parentRunId），并说明模型面永远造不出这种请求（顶层 Agent 工具没有 `parentRunId` 参数）。
- 反面：若把 `parentRunId` 设为**真实发起 run 的 id**，则必须过发起方 agent type 的 `canSpawn` 白名单 + `maxNestedDepth`（settings，默认 3）——这正是要绕开的校验，且父 run 结束后其 nesting 表项即被删，之后以其 id 为父的派生不再受校验（时序脆弱，不可依赖）。

**另一个不可借用的路径**：嵌套 Agent 工具注入（`src/service/runtime-adapter.ts` L422-433，`createAgentTool({ parentRunId: spec.runId, allowedTypes: spec.type.canSpawn, forceSlotless: true })`）强制 `parentRunId=本 run id` 且受 `allowedTypes` 约束——静默派生**必须绕开工具注入路径，直接拿宿主侧 `SpawnService`**（`Stack.spawn`，经 `src/index.ts` 的 `holder` 可达，L149 `const holder: { current?: Stack } = {}`）。

**子会话限制**：子 subagent 会话内的扩展实例因 HOST_KEY 守卫（`src/index.ts` L114-144）是 inert 的，`holder.current` 恒空 ⇒ **静默派生只能发生在主进程宿主侧**（goal hook、workflow、scheduler 都是宿主侧先例）。若需求是"子 run 内部派生静默孙 run"，做不到——只能改走本方案并由发起方把任务转交宿主侧。

### 1.2 不产生顶层完成通知（CC2）

通知链路：状态机 `finish()` 对每次终态产出 `enqueue_delivery` 效果 → `src/service/runtime-adapter.ts` 的效果解释器 → notifier（outbox）→ `src/stack.ts` `sendFormatted()`（L911）→ `pi.sendMessage(customType 'subagent:notification', { triggerTurn: true })`。`triggerTurn:true` 就是"唤醒主会话起一轮模型调用"的机制（对比：compact-hint/quota hint 刻意用 `triggerTurn:false`，stack.ts L530/L607/…）。

**唯一的过滤点是 CC2**，`runtime-adapter.ts`：

- `createRuntimeRunnerAdapter()` 里维护 `childRunIds = new Set<string>()`（L208-215）；
- `run()` 入口（第一个 await 之前）：`if (spec.request.parentRunId !== undefined) childRunIds.add(spec.runId)`（L338）；
- 三处消费点全部跳过 child run：
  - `enqueue_delivery` 解释器（L230-239）：`if (childRunIds.has(e.payload.runId)) return;` —— 不进 outbox、不 sendMessage、不唤醒；
  - `settleConfigFailure()`（H2 失败路径，L295-333）：`if (!childRunIds.has(runId)) { deps.notifier.enqueue(...) }`；
  - `deadlineNoticeHandler()`（宽限/延长通知，L101-113）：`if (childRunIds.has(e.notice.runId)) return;`

所以：**给静默 run 设任意 `parentRunId`（合成 id 即可）即彻底静默**——这正是 workflow 子女 run 的先例（`src/workflow/host.ts` L599-606，`parentRunId` = orchestrator 的 `workflowId` 合成字符串）。

**不可靠的替代路径（勿用）**：`expectAck` + ack 消费。`spawnAndWait`/`waitOutcome` 会经 `onOutcomeAcked → notifier.ack` 消费通知，但 `ackWindowMs` 与 `coalesceWindowMs` 默认均为 0（`src/config/settings.ts` L384-386），`notifier.enqueue → attempt → send` 是同一同步链、先于 ack 微任务执行——fail-open 发通知。只有 `ackWindowMs > 0` 且 caller 在窗口内 ack 才能抑制，且仅限 completed 类。CC2 是结构性保证，ack 是尽力而为——**必须用 CC2**。

### 1.3 不被发起方取消级联杀掉

级联中止的数据基础：`spawn-service.ts` 的 `childrenOf`/`parentOf`（**仅当请求带 `parentRunId` 时登记**，L432-441）。两条触发链：

- **(a) 显式 abort**：`spawnService.abort(runId)`（abort_subagent、stopChildrenOf 调用）先 `cascadeChildren(runId, "parent_abort")` 再杀自身（L527-536）；
- **(b) 任何原因取消**：`src/runtime/runner.ts` `run()`（L394-418）的 cancel handle 回调，无论取消原因（user_stop/timeout/external）都会调 `this.d.onChildAbort?.(req.runId, "parent_abort")` → `src/stack.ts` L1079 接线 `onChildAbort: (parentRunId, cause) => void spawnRef.current?.abort(parentRunId, cause)` → 级联。即**父 run 超时/被用户停/被 watchdog 杀都会带走以其为父的子 run**。

因此：若 `parentRunId` 用真实发起 run 的 id，静默 run 必死；**用合成 id 则不在任何真实 run 的 `childrenOf` 里**，只能被：

1. 显式 `abort(静默run自身id)`；
2. owner 主动 `stopChildrenOf(合成id, cause)`（workflow 正是用 `stopChildrenOf(workflowId)` 收尸，`host.ts` L868-875）——`stopChildrenOf` 是唯一对"非 run 的 owner id"有效的停止入口（`abort()` 的第一行 `!running.has` 守卫会直接 return false，见 CC1 注释 L537-548）。

**外部 signal 层面**：不传 `signal` 即无链接。若在主会话 turn 上下文内发起（hook 里拿到过 turn signal）又想免疫 Esc/强制压缩的 turn 中止，传 `detachSignalOnStart: true`（`runner.ts` L414 在 cancel handle 创建后立即 `cancel.detach()`；先例：Agent 工具 `run_in_background`，`src/tools/agent-tool.ts` L283-297）。它只解除外部 listener，`abort_subagent`/watchdog 走 `activeCancels` 的路径不受影响；已在 admission 前就 aborted 的 signal 仍会立即取消（`createCancelHandle` 的已中止检查）。

## 2. 落地方案

### 2.1 调用配方（核心，可直接落地）

```ts
import { randomUUID } from "node:crypto";
import type { Stack } from "../../stack.js"; // 视封装位置调整相对路径

// —— 每个逻辑所有者一个合成 owner id（进程内一次创建，多个静默 run 可共用同一个）——
// 格式约束：不能匹配 runId 格式 /^r_[0-9A-HJKMNP-TV-Z]{8}$/（src/core/ids.ts），
// 也不要长得像 run id（spawn() 会拒收 runId 形状的 label，L366-370）。
const SILENT_OWNER = `silent-owner-${randomUUID()}`;

// stack 来自宿主侧：index.ts 的 holder.current，或 stack.ts 构建处的闭包
// （scheduler 先例：createScheduler({ spawn })，stack.ts L1358）。
const stack: Stack = /* ... */;

const spawned = await stack.spawn.spawn({
  type: "general",                 // ① 必须是 AgentTypeRegistry 已注册的类型
  prompt: "<任务指令>",             // ② 任务本体；首行别太长（会被拿去派生 label）
  label: "silent-<用途>",          // ③ 可选但建议显式传，见 ③ 说明
  parentRunId: SILENT_OWNER,       // ④ 核心：一参达成三点（绕 X3 / CC2 静默 / 脱离级联）
  // —— 以下按需 ——
  // slotless: true,               // ⑤ 绕过并发池（默认不传，见 ⑤ 权衡）
  // budgetOverride: { totalMs: 30 * 60_000 },  // ⑥ 显式总预算（硬顶），见 ⑥
  // detachSignalOnStart: true,    // ⑦ 仅当发起点持有 turn signal 时需要
  // cwd: "...", isolation: "worktree", modelOverride: {...}, schema: {...}, // 透传可选
});
if ("error" in spawned) throw new Error(spawned.error.message);
const runId = spawned.runId;

// —— 结果收集（fire-and-forget；绝不要用 spawnAndWait，见 §2.4）——
const settled = await stack.spawn.waitOutcome(runId /*, waitMs */);
if (settled.kind === "settled") { /* settled.outcome: RunOutcome */ }

// —— 显式收尸（owner 关闭/取消时）——
await stack.spawn.stopChildrenOf(SILENT_OWNER, "user_stop");
```

### 2.3 要新增/修改的文件与函数

**（唯一必须的生产代码改动）修复 `notifyTerminalFailure` 安全网的 CC2 缺口**

- 文件：`src/service/spawn-service.ts`，`start()` 的 catch 块（L216-243）。
- 现状：`deps.runner.run` 抛异常的安全网 `deps.notifyTerminalFailure?.(failed)`（L243）**不查该 run 是否 child**——栈侧回调（`stack.ts` L1134-1166）会直接 `notifier.enqueue(payload)` → `sendFormatted` → `pi.sendMessage(triggerTurn:true)`。正常路径不可达（runtime-adapter 内部吞错），但一旦触发，静默 run 会发顶层通知**唤醒主会话**，违背点 2。
- 修法（一行）：catch 里改为
  ```ts
  if (req.parentRunId === undefined) deps.notifyTerminalFailure?.(failed);
  ```
  child run 的结果只能由 owner 消费（CC2 同一语义）；workflow 子女同样受益。改后同步更新 §4 的回归测试。

**（建议）新增封装模块 `src/service/silent-spawn.ts`**

- 内容：`createSilentSpawner(deps: { spawn: SpawnService; query: QueryService })`，导出：
  - `newOwnerId(): string` —— `silent-owner-${randomUUID()}`，格式永不与 runId 冲突；
  - `spawnSilent(ownerId, req: { type; prompt; label?; budgetOverride?; slotless? })` —— 固定注入 `parentRunId: ownerId`，拒绝调用方覆写 `parentRunId`/`signal`/`expectAck`（防误用回归）；
  - `collect(runId, waitMs?)` —— 包 `spawn.waitOutcome`；
  - `reap(ownerId, cause?)` —— 包 `spawn.stopChildrenOf(ownerId, cause ?? "user_stop")`。
- 纯 DI、无 pi 依赖（与 `src/service/` 其它模块同纪律），可直接单测。
- 接线：由宿主侧调用方经 `holder.current`（index.ts）或 stack.ts 闭包取得 `spawn`/`query` 后构造——参照 `createScheduler({ spawn })`（stack.ts L1358）。若某功能（如 goal/scheduler）需要，就在其 wiring 处传入。

**不需要改的**：`runtime-adapter.ts`（CC2 现成）、`runner.ts`（detachSignalOnStart 现成）、`stack.ts`（除上述安全网修复在 spawn-service 侧外无改动）、`index.ts`（若不新增宿主入口则零改动）。

### 2.4 结果收集与生命周期

- **用 `spawn.waitOutcome(runId[, waitMs])`**（bounded wait，unref'd timer，`{ kind: "settled" | "pending" }`），或 `query.get(runId)` 轮询快照。`waitOutcome` 对刚 spawn 的 id 无 unknown-run 竞态（spawn service 自己的 waiter 表）。
- **不要用 `spawnAndWait`**：它内部 `{ ...req, expectAck: true }` 且阻塞至终态——语义上是"前台等待"，与静默后台诉求相反（且 expectAck 无谓污染 `claimedRunIds`）。
- 也可挂 `pi.events` 的 `subagent:completed`/`subagent:failed`（stack.ts L1075-1076 **照发不误**，CC2 只断通知不断 lifecycle 事件）——宿主侧监听事件是比轮询更干净的收结果方式。
- 收尸：owner 生命周期结束时 `reap(ownerId)`；单个 run 提前杀用 `spawn.abort(runId, "user_stop")`。

## 3. 坑、约束与残余风险

### 3.1 做不到的部分（如实）

1. **静默 run 活不过主会话**：`session_shutdown`（`src/index.ts` L519-547）对所有非终态 run 调 `stack.query.stop(s.runId, "shutdown")` 再 bounded drain（`abortGraceMs×3`，cap 15s）。`/reload`、`/new`、`/resume`、fork、quit 全部触发 ⇒ 静默 run 必死。bash job 有跨会话收养（`handoffInProcess/adoptOrphans`），**subagent run 没有等价机制**。要跨会话存活只能另做持久化队列（如 scheduler 的 cron 兜底重派），不在本方案范围。
2. **子会话内发起做不到**（§1.1 末）：HOST_KEY 守卫使子会话扩展实例 inert。需求若来自子 run 内部，只能由宿主侧中介。
3. **`detachSignalOnStart` 不是完全免疫**：admission 前已 aborted 的 signal 仍立即取消；它也不影响 watchdog 超时与显式 abort（那是设计——静默 run 仍受预算保护）。
4. **预算天花板照常适用**：全局 watchdog 会按时杀掉跑太久的静默 run（除非 agent-type/`budgetOverride` 放宽；显式 `totalMs` 是无宽限硬顶）。"无限期后台 run"做不到，也不应该做。

### 3.2 可见性副作用（静默 ≠ 隐身）

CC2 只断**通知**，不断**可见性**。静默 run 仍然：

- 出现在 **fleet widget**（合成 parent id 不在 present 集合也不是 workflowId ⇒ 渲染为**顶层行**，`src/ui/fleet-widget.ts` L286/L404-413）；
- 出现在 **`/agent status`** 与 `subagent:started`/`subagent:completed`/`subagent:usage` 事件（`announcedStarts` 逻辑，stack.ts L1168-1186）——HUD 的 live subagent 成本统计会计入它；
- 被 **background-status** 计入 `runningSubagents`（`src/index.ts` L150-160 `query.list()` 非终态计数）⇒ 连带两个门控：
  - **feishu 完成卡被抑制**：`backgroundIdle()` 要求 `runningSubagents === 0`（`src/feishu-notify/core.ts` L230-236、index.ts L225 等）——静默 run 在跑时主会话的完成类飞书卡不发（窗口期合并语义，不是丢失，但延迟到静默 run 结束）；
  - **cache-keepalive busy 判定**：`backgroundBusy()` 用 `query.list()`（`src/service/cache-keepalive.ts` L143/L254）——静默 run 在跑时保活 ping 继续（这通常是**期望**行为：仍有 subagent 工作在进行）。
- **label 注册进 mention registry**：不进 @ 补全（parent ≠ root，见 §2.2③），但 `resolve` 可达、`/agent status` 可见。

如果这些可见性不可接受，需要额外的过滤层（如 `RunSnapshot` 加 `silent` 标记 + widget/status 过滤）——属于后续迭代，本方案不做（改动面大且无现成接缝）。

### 3.3 陷阱

1. **`notifyTerminalFailure` 安全网缺口**（§2.3 已给修法）：修复前，静默 run 在 `runner.run` 抛异常的路径上会发顶层通知唤醒主会话。这是已知潜伏缺陷（正常路径不可达），但方案落地必须连修复一起做，否则点 2 无结构性保证。
2. **合成 id 的格式纪律**：不能用真实 run id（会被当 live nesting 关系校验）；不能长得像 `r_XXXXXXXX`（label 派生会被拒）；建议 `silent-owner-<uuid>` 前缀族，进程内永不与 `newRunId` 冲突。同一 owner 多个静默 run 共用一个 id 即可（`childrenOf` 是 Set，`stopChildrenOf` 一次全收）。
3. **不要传 `signal`，不要用 `spawnAndWait`**（§2.2 表末两条）。若封装模块不强制拦，未来调用方很容易"顺手"传个 signal 或换 spawnAndWait，静默三保证逐一破防。
4. **fabric 树边**：`onSpawnEdge(合成id, runId)`（stack.ts L1126）把合成 owner 写成树节点。后果： 静默 run 的 `message_agent` 默认路由是 parent-only（agent type `can_message` frontmatter，缺省只许发父）——发给"父"= 发给合成 id ⇒ fabric 路由 dead-letter（合成 id 无 mailbox）。若静默 run 需要回消息，给其 agent type 配 `can_message: [root]` 或显式目标； 主会话向静默 run 发 `message_agent` 是允许的（方向相反，child 收件箱正常）。树渲染上合成 id 是一个孤立挂载点，无 UI 破坏（fleet widget 不经 fabric 树）。
5. **resume 语义**：静默 run 终态后可被 `resumeFrom`（它是本服务已知 run）——resume 出的新 run 若不带 `parentRunId` 会**重新变成通知全开**的顶层 run。封装模块若支持 resume，必须同样注入合成 owner id。
6. **`/reload` 后 runId/ownerId 全灭**：所有 SpawnService 内存表（nesting/childrenOf/labels/outcomes）随 stack 重建清零。session 文件还在磁盘上，但没有任何"收养静默 run"的机制（对比 bash job 的 adoptOrphans）。发起方若要跨 reload 追踪，需自行持久化（写 session entry / 状态文件）并在 reload 后重新 resolve——本方案只提供进程内语义。

### 3.4 残余风险清单（接受即签字）

| 风险                                  | 概率                 | 影响                 | 缓解                                              |
| ------------------------------------- | -------------------- | -------------------- | ------------------------------------------------- |
| `runner.run` 异常路径发通知（修复前） | 低（正常路径不可达） | 违背点 2，唤醒主会话 | §2.3 一行修复 + §4 回归测试                       |
| session_shutdown 杀静默 run           | 确定                 | 任务中断             | 文档化；长任务配 scheduler cron 兜底重派          |
| feishu 完成卡延迟                     | 确定（run 在跑期间） | 通知延迟             | 文档化；或后续给 background-status 加 silent 豁免 |

| 合成 id 与未来某真实 id 撞车          | ≈0（uuid 前缀）      | 误级联               | 格式纪律（§3.3.2）                                |

## 4. 验证点（测试方案）

新增 `tests/service/silent-spawn.test.ts`（封装模块单测）+ 扩展 `tests/service/spawn-service.test.ts`（安全网修复回归）。断言全部针对**行为**而非实现细节：

**V1 — 绕开嵌套校验（点 1）**

- 构造：注册 agent type A（`canSpawn: ["limited"]`），先 spawn 一个 A 的 run（真实、在跑），再以它为 `parentRunId` spawn `type: "other"` ⇒ 断言 config 错误（canSpawn 白名单生效，对照组）。
- 同场景改 `parentRunId: "silent-owner-<uuid>"` ⇒ 断言 spawn 成功且无错误（X3 跳过）。
- 深度对照：`maxNestedDepth=1` 下，真实父链 depth 2 被拒；合成父 depth 0 通过。

**V2 — 无顶层通知（点 2）**

- 用 fake notifier（记录 `enqueue` 调用）+ fake driver 让 run 走到 completed。
- 断言：`parentRunId=合成id` 的 run 终态后 `notifier.enqueue` **从未被调用**（enqueue_delivery 被 CC2 丢弃）；对照组（不带 parentRunId 的 run）enqueue 恰好一次。
- config 失败路径：注入抛错的 `resolveSessionSpec` 扩展点 ⇒ 断言 child run 的 `settleConfigFailure` 不 enqueue（CC2 第二处）。
- **安全网回归（§2.3 修复后）**：注入 `runner.run` 直接 throw 的 fake Runner ⇒ 断言带 `parentRunId` 的 run 不触发 `notifyTerminalFailure`（deps spy 零调用），不带 `parentRunId` 的照常触发。

**V3 — 不被取消级联（点 3）**

- 构造：真实 run R（fake driver 挂起）+ 静默 run S（`parentRunId=合成id`，fake driver 挂起）。
- `spawn.abort(R, "user_stop")` 并等 R 终态 ⇒ 断言 **S 仍 running**（`snapshots()` 或 query.get）。
- 对照组：S 的 `parentRunId=R` ⇒ abort(R) 后 S 变 `aborted`（cause=parent_abort）。
- 超时链对照：给 R 极小 budget 让 watchdog 杀它 ⇒ 同样断言 S 存活（覆盖 runner onCancel→onChildAbort 路径）。
- 收尸口：`stopChildrenOf(合成id, "user_stop")` ⇒ 断言 S aborted；再次调用幂等（返回空 stopped）。
- detachSignalOnStart（若发起点带 signal）：传入已 start 的 turn signal，abort signal ⇒ 断言 run 存活；对照：不传 detachSignalOnStart 的 foreground run 被同一 signal 取消。

**V4 — 封装模块契约（§2.3）**

- `spawnSilent` 拒绝调用方注入 `parentRunId`/`signal`/`expectAck`（断言抛错或被剥离后请求仍带合成 owner id）。
- `newOwnerId()` 不匹配 `isRunId`；两次调用不相等。
- `collect`/`reap` 委托语义（bounded wait 返回形状、stopChildrenOf 透传 cause）。

**V5 — 集成（`tests/integration/`）**

- 走真 stack（`buildSessionStack` + fake pi）：静默 run 全周期后，断言 `pi.sendMessage` 从未收到 `subagent:notification`（triggerTurn 唤醒为零），但 `subagent:started`/`subagent:completed` 事件照发（可见性契约）。
- `session_shutdown` 触发 ⇒ 断言静默 run 被 stop（**如实断言点 3 的边界**：跨会话存活不在承诺内）。

**V6 — 现有套件回归**

- `npm run typecheck`、`npm test`（1800+ 用例）、`npm run format:check` 全绿。
- 特别关注：workflow 套件（`tests/workflow/`，CC2/stopChildrenOf 同一机制的主人）与 state-machine 转移矩阵（本方案不改状态机，理论上零影响，但要跑）。
