# fabric v2 基线实验 — 先量化重复调研，再决定工程投入

> **目的**：用**零工程量**（不写任何生产代码）的手工流程，量化「下一个 agent 重复调研」的规模、
> 以及两种干预各能削减多少。数据出来后再决定 `fabric v2`（见 [`plan.md`](./plan.md)，现已打回搁置）
> 该投多少工程、投在哪一段。
>
> 由来：两轮评审判定原方案对痛点的收益**被明显高估**（`plan.md` §15.6）——看板只收录 agent 主动
> `announce` 的内容，面对与 `result` **同一个压缩瓶颈**；真正能绕过瓶颈的只有「向终态专家定向提问
>
> - revive」，而那恰恰是原方案排在最后、且目前有 Blocker 的一段。

## 0. 两个待检验假设

| ID     | 假设                                                                                                                 | 若成立                                     | 若不成立                              |
| ------ | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------- |
| **H1** | 重复调研主要源于**交接包的压缩损失**（缺文件索引、缺负面知识、缺证据行号，导致下游不敢信而重查）                     | 只需做「结构化交接包」，通信织网价值有限   | 压缩损失不是主因，需重新诊断          |
| **H2** | 存在一类**交接包原理上覆盖不了**的信息（"你当时为什么否决 X"、"那条路你试到哪一步"），只能向带完整原始会话的专家追问 | 工程集中在「定向提问 + revive + 答案回流」 | 看板/请教机制整体价值不足，方案应废弃 |

H1 与 H2 可以同时成立，也可以同时不成立。实验要能分辨这四种情况。

## 1. 三个实验臂（全部用现有能力，零代码）

### A0 — 基线（现状）

主 agent 派 A 完成探索/分析 → 拿到 A 的 `result` 文本 → 原样（或人工摘要）拼进 B 的 prompt → B 执行。

### A1 — 结构化交接包

用 **现有** `Agent` 工具的 `schema` 参数（`SpawnRequest.schema`，X10 双重校验）强制 A 的产出结构化：

```json
{
  "conclusion": "string",
  "fileIndex": [{ "path": "string", "role": "string", "readFully": true }],
  "evidence": [{ "claim": "string", "file": "string", "lines": "string" }],
  "ruledOut": [{ "target": "string", "why": "string" }],
  "openQuestions": ["string"]
}
```

把该 JSON 原样拼进 B 的 prompt，并在 B 的 prompt 里写死一句：
**「`fileIndex` 中标 `readFully:true` 的文件已被完整读过，`ruledOut` 中的路径已被排除；除非你有具体理由怀疑，否则不要重读、不要重试。」**

> `ruledOut`（负面知识）是这一臂的核心变量——它是 `result` 自由文本里最常丢失、而下游代价最高的部分。

### A2 — A1 + 定向请教（手工版 consult）

在 A1 基础上追加流程：B 遇到交接包未覆盖的问题时，**停下并上报主会话**（prompt 里写死这条纪律，
并禁止它自行展开调研）。主会话随后：

1. `Agent({ resume: "@A", prompt: "<B 的问题>", schema: {answer, evidence[]} })` —— 复活 A，
   它带着**完整原始会话**回答；
2. 把答案用 `steer_subagent(B, answer)` 送回 B。

这就是 `plan.md` 里 M6 的**手工等价物**。它今天就能跑，不需要任何新代码。

## 2. 可比性控制（方法论坑，必须遵守）

- **同一任务不能在同一工作区跑两遍**（第一次跑完工作区就变了）。每个臂用
  `Agent({ isolation: "worktree" })` 从同一 HEAD 起跑，或全部选**只读型任务**（探索、审查、
  定位、方案评估）。推荐后者：只读任务的重复调研信号最干净。
- **A 只跑一次**，其产出同时喂给三个臂的 B（A0 用 result 文本，A1/A2 用结构化 JSON）。这样
  A 的随机性不污染臂间比较。
- **B 的模型、thinking 级别、prompt 骨架在三臂间必须完全一致**，只改交接段与纪律段。
- 每个臂**重复 2 次**取中位数（LLM 方差很大，单次不可信）。
- 样本：**3–5 个真实任务**，覆盖至少两类（一个探索型、一个需要设计取舍的）。

## 3. 测量指标（全部可从现有数据取，无需埋点）

| ID     | 指标                                                                | 取数方式                                                                                                                                                                                                        |
| ------ | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **M1** | **重复读取率** = \|B 读过的文件 ∩ A 读过的文件\| / \|B 读过的文件\| | 从 run 快照的 `diag.sessionFile` 取子会话 JSONL，提取 `read`/`grep`/`edit` 类工具调用的 `path`/`file_path` 参数。**不要用 `diag.toolHistory[].argsPreview`**——它截断到 80 字符且是容量 30 的 ring，会系统性低估 |
| **M2** | B 的总成本（USD）与 token                                           | `diag.usage.costUsd`；HUD 页脚亦有实时值                                                                                                                                                                        |
| **M3** | B 的轮次与墙钟时长                                                  | run 快照 / Agent 工具结果                                                                                                                                                                                       |
| **M4** | B 的工具调用总数、其中读取类占比                                    | 同 M1 的 JSONL 提取；`diag.toolCounts` 可交叉校验（它是不受 ring 淘汰的全生命周期计数）                                                                                                                         |
| **M5** | _(仅 A2)_ 追问次数、每次 revive 的成本、答案被采纳率                | revive run 的 `diag.usage.costUsd`；采纳率人工判读                                                                                                                                                              |
| **M6** | B 的产出质量                                                        | 人工二分判读（达标 / 不达标）。**必须记**——否则「省了成本」可能只是 B 干得更少                                                                                                                                  |

## 4. 预注册判据（先定，防止事后找理由）

| 观察                                                       | 结论                          | 行动                                                                                                              |
| ---------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| A1 相对 A0：**M1 下降 > 40%** 且 M6 不劣化                 | H1 成立                       | **只做结构化交接包**（`schema` + prompt 纪律，约 1 天工作量），fabric v2 的看板部分不做                           |
| A1 改善有限（M1 下降 < 20%），但 **A2 相对 A1 再降 > 25%** | H1 弱、H2 强 ⇒ 压缩瓶颈论成立 | 工程**集中在「定向提问 + revive + 答案回流」**，即修好的 M6（须先解 `plan.md` §15.2 的 B2、§15.3 的 M8）          |
| A1 与 A2 都显著（各 > 25%）                                | H1 + H2 均成立                | 两段都做；看板仍降级为「spawn prompt 里的预算化 headline 列表」，不做 `before_agent_start` 注入（B1）             |
| 两者都不显著（< 15%）                                      | 两个假设都不成立              | **放弃 fabric v2**，重新诊断重复调研的成因（候选：B 不信任 A 的结论；任务拆分本身就重叠；B 的 prompt 没给够约束） |
| A2 的 M5 成本 > 它省下的 M2                                | revive 不划算                 | 即便 H2 成立也不做 revive；改为要求 A 在结束前把 `openQuestions` 写得更充分                                       |

> 最后一行是本实验最容易被忽略、却最可能出现的结果：**revive 一次要重读专家的完整 context**，
> 缓存过期后这笔钱可能比 B 自己重查更贵。`plan.md` 原稿没算这笔账，本实验必须算。
