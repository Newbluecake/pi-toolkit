## 4. 7-2：7a 零行为合并

新增 `src/stack-teardown.ts`，改 `src/stack.ts`、`src/index.ts`、`src/fabric/xs/activate.ts`。

- **步骤表**：`REBUILD_STEPS` / `DEFENSIVE_STEPS` / `SHUTDOWN_STEPS` 三个有序数组，数组下标即执行顺序，逐行对应 §4.2 的 A / B / C4 三列，缺口用 `GAP-Gn` 注释标在缺席处。**偏离方案的一点**：方案写的是「一个 `TEARDOWN_STEPS` 数组」，但 A/B/C4 三条路径的顺序和成员集合本来就不同（C4 先关 schedule epoch 再 drain，A 根本不碰 schedule），一个线性数组表达不了，所以是三个数组，共用同一套组件说明。
- **`Stack.dispose(entry, env)`**：三个重载——`shutdown`（async）、`defensive`（同步）、`rebuild-handoff`（同步）。sync 步骤保持同步、异常照旧向外抛；shutdown 只在某一步真的返回 Promise 时才 `await`（不新增微任务跳数）。`rebuild-handoff` 在生产里只由「下一次 build」经 `runRebuildHandoff(previousParts)` 走到；`tests/integration/stack-dispose-api.test.ts` 钉住「在 Stack 上显式调用会消耗这次交接，下一次 build 不会再拆」。
- **`disposeXsSync()`**：C1 的同步子集（fence `session_shutdown` 事件、`xs.dispose`、`rootWakeRecovery.dispose`）。`fabric/xs/activate.ts` 的 handler 仍然是早注册、同步的独立 handler，只把三行换成这一个调用；账本 `teardown` 留在原处。
- **`previousParts`**：18 个 `let previous*` 换成唯一的模块级 `let previousParts: TeardownParts`。每次 build 创建自己的 `parts` 并立即发布为 `previousParts`，**按原位置增量写入**（18 处 `previousX = x` 一一对应成 `parts.X = x`），所以 build 中途抛错时「已创建的部分由下一次 build 拆掉」的行为不变；只有交接成功之后才替换。`isCurrent` 原来读 `previousKeepalive === self`，现在读 `parts.keepalive === self`（旧 build 的 slot 被清空即视为被取代，语义不变）。
- **`ActivationTeardown`**（接口在 `stack-teardown.ts`，对象字面量在 `index.ts`）只收**穿插在 B / C4 里**的三项：B 的 `xs.defensiveTeardown`、C4-2 的 `scheduleSurface.shutdown`、C4-23 的子会话 bash `sealAll`。**偏离方案的一点**：方案还想把 C1 账本、C2、C3 收进来，但它们是各自独立的 `session_shutdown` handler（C1 在 xs 模块、C3 在 compact-hint 模块），合并会改变 handler 数量和相对其它插件 handler 的顺序，而这正是 trace golden 和矩阵里 handler 计数钉住的东西，所以保持独立。goalHook 看门狗和 capability 监听是 G9/G11（7b），不在 7a。
- index.ts：B 块和 C4 块各缩成一次 `holder.current.dispose(...)` 调用（−137 行逻辑）；`bashKill` 步骤留在步骤表里（它只依赖 stack 和 settings）。

### G8 为什么停下

1. **冻结的 trace golden 会变**（`activate-trace.json` 是 B 档，你要求不要刷新）。该 golden 的 phase 2 在**同一个激活**上连续跑 `session_start → session_shutdown → session_start → session_shutdown`，G8 之后第二次 `session_start` 时 `holder.current` 已空，cache-ttl 的状态栏从 `set,set`（读到已拆栈的 keepalive）变成一次 `clear`；三个画像（default/minimal/max）各少 1 次调用（31→30、27→26、33→32）。这是 G8 的**必然**后果（修的就是「已拆的栈还在对外应答」），不是意外。pi 1.3 里每个会话都新 `activate()`，真实流程不会走到这个序列。侧分支里 golden 已刷新，仅供评审。
2. **两个 pinned 测试依赖旧行为**：`tests/integration/ask-user-interrupt.test.ts` 的两个用例在 shutdown **之后**用旧激活的 `Agent` 工具派发 run（「holder 仍指向旧栈」）。G8 之后 `forwardSpawn` 抛 `no active session yet`，用例需要重写（改成 shutdown 之前派发、或直接驱动 hub）。
3. 迟到路径排查（写进侧分支提交）：holder 路由的 `requireStack` 调用方只有 `forwardSpawn/Query/Workflow/Orphans/Notifier`、`forwardWorkflowQuery` 的 wait/stop/extend、`createTidyPort`、`tools/register.ts` 的 3 处和 `/task`。其余都是 `holder.current?.`（返回 undefined/空数组）。shutdown 之后 pi 不会再调度用户/模型发起的工具调用；`get_run_result` 跨 shutdown 等待时 `tryAck` 自带 try/catch（结果照常返回，ack 丢失 ⇒ 下个会话可能多收一条冗余通知）；`/task`、`bash` 覆盖在无 stack 时本来就有降级（`/task` 通知错误、`bash` 透传 pi 原生）；唯一可能把异常抛进命令的是 `/mem tidy` 的 `abort/waitOutcome`，侧分支里已加降级。没有定时器回调走 `requireStack`（本批已把相关定时器都在 shutdown 清掉）。

### tmux 真机冒烟清单（按 memory 里 live-acceptance-tmux 的流程；本包只在 worktree 里自动化验证过）

准备：`webHub`/`bashJobs` 默认开，`/agent` 能看到 fleet；用 `pi` 起一个会话，开一个 `sleep 120` 的后台 bash（`bash_job list` 能看到）和一个会跑几十秒的后台 subagent。

1. `/reload` ×3：每次之后 `/agent` 与 `bash_job list` 里 job 仍在；后台 bash 在第 2 次 reload 期间**结束**——重点看 G4：**只收到一条** `Bash job … finished`（不是两条）。HUD 的 usage 数字不再被旧栈刷新（G1）；`/goal` 进行中 reload 后不会再冒出「续跑投递失败」报告（G9）。
2. 同 cwd `/new`：后台 bash 仍存活并被新会话接管（`bash_job list` 在新会话里可见，进程没被杀）；完成时只通知一次、落在新会话。
3. `/resume`（同 cwd）与 `/fork`：同上；旧会话里还没发出的合并通知（刚好在 1–2 s hold 窗口里完成的 subagent）**不会**漏进新会话；回到那个旧会话（resume）后能收到（G2/G3 + outbox）。
4. 跨 cwd `/resume`：新模块路径；后台 bash 由新栈 `adoptOrphans` 接管；仍只通知一次；旧栈 `external`/usage 计时器已停（G1/G7）。
5. 带运行中 subagent 与后台 bash 退出 pi（`quit`）：退出不被拖慢（`bashKill` 有界）；重启后 resume 该会话，subagent 的终态通知与后台 bash 的完成通知各一次（outbox/recover），`shutdownPolicy=kill` 时 bash 被杀。
6. 观察点：全程 `grep -c "Bash job .* finished"` 与 `subagent:notification` 条数；任何「旧 pi 上收到消息」都是回归。
