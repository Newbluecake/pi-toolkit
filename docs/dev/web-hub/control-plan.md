### 3.3 时限（请求级绝对 deadline，D16）

每个写请求在 `http.ts` 入口创建 `ReqDeadline{ at = arrival + WRITE_TOTAL_MS(13_000), remaining() }`，之后每一步的预算都取 `min(本步上限, remaining() − 为后续步骤保留的余量)`：

| 层 / 步骤                                 | 预算                                                                                                                                                                        | 超时结果                                                               |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 浏览器 fetch                              | 16s（`AbortController`；> 服务器 13s + 余量，< 两 listener `requestTimeout` 15s + 网络）                                                                                    | 本地 `unknown` ⇒ 自动发一次 `queryOnly`（§3.4），不自动重执行          |
| ① Host / CSRF / cookie 存在性（仅请求头） | 同步                                                                                                                                                                        | 421 / 403 / 401                                                        |

### 3.4 幂等（D7）

| 层    | 键                            | 容量 / TTL                         | 行为                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----- | ----------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| hub   | `principal \| agentKey \| id` | 2048 / 10 min LRU（仅 hub 进程内） | 条目状态：`inflight`（同键共享 Promise）/ `done`（**只**存 agent 给出的成功与不可重试失败，重试回缓存 + `dup`）/ `unknown`（已发帧但结果未知；重试 ⇒ 带 `retry:true` 重投给 agent，由 agent 台账裁决）。可重试且 effect=none 的失败 ⇒ **删除条目**。hub 前置拒绝（CSRF/401/429/409 caps/503 无 agent）**不建条目**。同键不同载荷（`sha256(canonicalJSON(cmd))` 仅存内存、不入日志）⇒ 409 `E_BAD_REQUEST` "id reused" |
| agent | `id`                          | 512 / 30 min（进程级，§4.5）       | 收到 `cmd` **第一件事**（任何副作用之前）同步写入 `running` ⇒ 台账有无即「是否收到过」；`running` 期间同 id ⇒ 挂到同一结果（剩余预算内）否则 `E_DEADLINE{effect:"unknown"}`；终态按 hub 同规则缓存；effect=none 的可重试失败立即删除                                                                                                                                                                                 |

`queryOnly:true`：hub 查自己 LRU（done ⇒ 直接回；unknown / 无条目 ⇒ 带 queryOnly 转发）；agent 查台账 ⇒ `data{op:"query", state, result?}` 或 `E_UNKNOWN_ID`。**断言**：agent 台账 TTL（30 min）> 浏览器保留待决项的时长（10 min），所以 `E_UNKNOWN_ID` = 「该 agent 进程从未收到此 id」= 确定未执行，前端可放心提供「重新发送」。

`principal`：loopback = `"token"`，LAN = `"lan:" + userId`。浏览器 `id` = 16 字节 `crypto.getRandomValues` → base64url（K18），**每次用户动作生成一次**，重试 / 查询沿用；「修改后再提交」是新动作、新 id。

1. 断线 ≤ 30s 后重连，同 epoch 同 dialogId 表单恢复且草稿保留（`ui/ask-user-form`、`integration`）。

5. `agent_down` 后同 id ⇒ `retryable:false`（`hub/commands`）。
6. 迟到 `cmd_result` / `cmd_late` 把 `unknown` 升为 `done`，后续同 id 重试零转发（spy，`hub/commands`）。
7. hub 重启后同 id ⇒ agent 台账回 `dup`，副作用计数 = 1（`integration`）。

### 4.3 prompt 生命周期（A1 / D5）

状态：`dispatched → observed → (started | queued → consumed | dropped)`；任何一步超时 ⇒ `unconfirmed(reason)`。HTTP 回执在 `observed` 或 3s 时返回（`delivery: "observed" | "unobserved"`），之后的变化经 `ctl` 槽推送。

1. **分派**：台账登记 `{cmdId, text, state:"dispatched", at}`（text 只存在 agent 内存，用于匹配，**不**上行到 `ctl`）→ `pi.sendUserMessage(...)` 同步调用。
2. **观测**（web-hub 的 `input` handler，恒返回 `{action:"continue"}`，web-hub 自身从不 transform/handled）：
   - 只考虑 `event.source === "extension"`；候选 = 台账中 `state === "dispatched"` 且 `text === event.text`（逐字相等）的 web 项；取**最早**一项（FIFO）⇒ `observed`，记 `behavior = event.streamingBehavior ?? "idle"`（pi 在 input handler **之前**就算好了 `isStreaming`，`agent-session.js:1230`，所以这是 pi 当时的真实分派决定）。
   - **前序 handler transform**（其它扩展改写了文本）⇒ 文本不等 ⇒ 不归因 ⇒ 3s 后 HTTP 回 `unobserved`；台账 30s 后 `unconfirmed(unobserved)`。
   - **前序 handler handled**（如本仓库 `@label` 提及路由到子 agent，`mention.ts:108-122`，或第三方拦截）⇒ web-hub handler 根本不会被调用 ⇒ 同上。
   - **后序 handler**（加载顺序在 pi-toolkit 之后的第三方扩展）transform/handled ⇒ 已 `observed`，但第 3 步匹配不到 ⇒ `unconfirmed(not-delivered)`。
   - **同文本并发网页请求**：视为等价类，FIFO 归因；同文本 ⇒ 同效果，谁得到哪次观测只影响 cmdId 对应关系，不影响计数与展示正确性。
   - **同文本来自其它扩展**（`source:"extension"`，如 `/goal` 续跑、compact 工具 RESUME_TEXT，`src/index.ts:310,485,515,585`）并发：可能错归因；后果仅限展示（本项多一次 observed、对方少一次），文档注明，K10 统计频率。
   - **TUI 同文**：`source:"interactive"` 永不参与第 2 步；第 3 步的 `message_start` 匹配走队列镜像的全体 FIFO（含 TUI 项），同样是等价类语义。
   - **settle 推迟**（`_isEmittingAgentSettled`）：观测可能晚于 3s ⇒ HTTP 已回 `unobserved`，台账随后仍可转 `observed` 并推 `ctl`（HTTP 不追溯；前端以 `ctl` 为准升级展示）。
3. **投递确认**：
   - `behavior === "idle"`：此后 10s 内第一条 `message_start{role:"user"}` 的首个文本块 `=== observed 文本`（网页无图片 ⇒ 无 image hints 后缀）⇒ `started`；否则 `unconfirmed(not-started)`（无模型 / auth 失败只进 `emitError`，`agent-session.js:1260-1273`；或后序 handler 拦截）。
   - `behavior ∈ {steer, followUp}`：进入队列镜像（`source:"web"`, `cmdId`）⇒ `queued`；匹配的 `message_start{user}` ⇒ `consumed`；`hasPendingMessages()=false` 清空 ⇒ `dropped`；会话切换 ⇒ `dropped(session)`；10 min ⇒ `unconfirmed(timeout)`。
4. **前端展示**（§7.3）：`observed/started/queued/consumed` 正常；`unobserved/unconfirmed` 显示「已发送，未能确认是否进入对话——请看对话流」，**不自动重试**、不当失败处理；`dropped` 显示「已退回终端编辑器或被丢弃」。
5. 不再有 `E_NOT_ACCEPTED`（v1 D5 作废）。R4 改写见 §11。

### 4.4 队列镜像（D6）

### 4.5 进程级命令台账（A4 / A5 / D7 / D15）

- 位置：`Symbol.for("pi-subagent:web-hub:cmd-ledger")` 上的**纯数据**对象 `{ v: 1, entries: Map<id, Entry> }`（与 `connection.ts` 的 agent-id 全局同一模式；不存闭包、不存 ctx；`/reload` 后新 module 实例直接复用）。旧 module 实例遗留的底层 Promise settle 时只写这张表（纯数据），新实例通过它看到迟到结果。
- `Entry = { id, op, payloadDigest, state: "running" | "ok" | "failed", late?: true, result?: CmdResultBody, text?: string /* 仅 prompt 匹配用，终态即删 */, runId?, at, updatedAt }`。
- 容量 512 / TTL 30 min；只淘汰终态项；`running` 项受 op 级并发上限约束（每 agent 在途 ≤ 16，超出 `E_RATE`；late 悬挂 ≤ 8）⇒ 有界。
- 规则：
  1. 收到 `cmd`（非 queryOnly）**先**查表：无 ⇒ 写 `running` 再执行；`running` ⇒ 在本帧剩余预算内等待同一结果，否则回 `E_DEADLINE{effect:"unknown"}`；终态 ⇒ 回缓存（`dup:true`）；载荷摘要不同 ⇒ `E_BAD_REQUEST`（id reused）。
  2. 执行得到 effect=none 的可重试失败 ⇒ **删除条目**再回错（重试可安全重新执行）。
  3. 成功 / 不可重试失败 ⇒ 终态缓存。
  4. `E_DEADLINE{effect:"unknown"}` ⇒ 条目保持 `running`，底层 settle 后转 `ok/failed + late`，发 `cmd_late`。
  5. queryOnly ⇒ 只读：`data{op:"query", state, late?, result?}`；无条目 ⇒ `E_UNKNOWN_ID`。
- `ctl` 槽 = 台账中「本 session、最近更新」的 ≤ 32 项投影（无正文）。

### 4.6 网页斜杠命令（B-Q2 / D11 / D20）

**证据结论**（§1.1）：① `pi.sendUserMessage(text, {expandPromptTemplates:true})` 会对 `/` 开头的文本执行**扩展注册的命令**（带完整 `ExtensionCommandContext`，streaming 中也立即执行，不产生 `input` 事件），否则回落为「技能/模板展开 → 普通用户消息」；② 内置命令只在 TUI 编辑器提交处理里，扩展 API **没有** `executeCommand/runCommand`，也拿不到命令 handler；③ `pi.getCommands()` 只列扩展命令 / 模板 / 技能；④ 部分内置命令在扩展面有等价 API（`compact` / `setSessionName` / `setModel` / `setThinkingLevel` / `shutdown`；`newSession` / `reload` 仅命令 ctx）。

**覆盖范围**：扩展命令（pi-toolkit 自有 + 第三方）全覆盖；技能 `/skill:x` 与提示模板全覆盖（作为用户消息）；内置命令只覆盖下表「内置桥」列出的子集，其余拒绝并说明「仅终端可用」。**绝不**把未识别的 `/xxx` 当普通文本发给模型（`E_UNKNOWN_COMMAND`）；想发字面斜杠文本用普通 prompt（composer 的「作为文本发送」开关，§7.4）。

**执行路径**（`slash.ts`，同步入口）：

1. 解析 `name`（`^[A-Za-z0-9:_.-]{1,64}$`）与 `args`（≤ 16 KiB）。
2. 分类（同步，同一 tick 内完成 ⇒ 不存在「检查时是命令、分派时已注销」的竞态）：`pi.getCommands()` 命中 ⇒ `extension` / `template`（prompt）/ `template`（skill）；否则查内置桥表 ⇒ `builtin`；否则 `E_UNKNOWN_COMMAND`。
3. 策略：`policy = webCommandPolicy[name] ?? defaultPolicy(name, sub, busy)`；`deny ⇒ E_COMMAND_DENIED`；`confirm` 且无 `confirm:true` ⇒ `E_CONFIRM_REQUIRED{message: 摘要}`（UI 二次确认后以**新 id** + `confirm:true` 重发；确认是 UX 防误触，不是安全边界——同一 principal 本就能发任意 prompt 让模型执行任意 bash，命令不引入新权限级）。
4. 执行：
   - **extension**：`capture.arm({cmdId, reqId, origin, name, args, deadlineAt})`（§4.9；进程级 `Symbol.for` 同步槽）→ `pi.sendUserMessage("/" + name + (args ? " " + args : ""), { expandPromptTemplates: true, deliverAs: "followUp" })` → `capture.settleArm()`（同步：槽未被认领时，若 `capture.owns(name)` 转入回退队列等 settle 推迟路径，否则丢弃）。pi-toolkit 自有命令由包装层认领 ⇒ `captured:true`，按 §4.9 等完成并回显输出；第三方命令 `completion:"unknown"`、`captured:false`（输出只在终端）。`/webhub __exec` 同样经包装层认领取来源（取代 v2 的 `webInvocation` 单槽）。`deliverAs` 只在极小的回落窗口（settle 推迟期间命令被注销）才生效，followUp 最安全。
   - **template / skill**：按 prompt 路径（§4.3 生命周期，观测用原始 `/skill:x …` 文本——input 事件在展开之前，`agent-session.js:1230-1240`），但 `expandPromptTemplates: true`、`deliverAs = cmd.deliver ?? "steer"`。
   - **builtin**：内置桥（下表），同步完成 ⇒ `completion:"sync", output?`；异步（compact / model）⇒ `completion:"async"`，完成 / 失败经 `cmd_late` 回写。
5. 审计由 hub 做（`op:"command", name, kind, policy, confirmed, argsLen`，**不记 args**，U7）；TUI notify（§4.7）。

### 4.9 pi-toolkit 命令输出回显（v2.1：Q6 / U9 / D22，包 C12）

**为什么只能在注册时包装**（§1.1 证据）：`pi.sendUserMessage("/x …", {expandPromptTemplates:true})` → `prompt()` → `_tryExecuteExtensionCommand()` 内部 `createCommandContext()` 新建 ctx 并直接 `command.handler(args, ctx)`，调用方传不进任何 ctx；pi 也没有 notify 事件。但 `registerCommand` 原样保存 `options.handler`，而 pi-toolkit 的 11 个命令都通过 activate 收到的同一个 `pi` 注册——所以在 activate 入口给 `pi` 套一层只拦 `registerCommand` 的代理，就能在不改 pi、不逐个改命令的前提下，决定每次调用时把什么 ctx 交给原 handler。

**机制**

1. **接线**（C0，`src/index.ts`）：`export default function activate(rawPi) { const pi = wrapCommandApi(rawPi, () => commandCaptureRef.current); … }`。`commandCaptureRef` 是 activate 闭包里的 late-bound ref，web-hub 装配后（`:846` 块）指向 `webHubRef.current?.capture`。web-hub 未启用 / child session / C12 未合入 ⇒ ref 恒 undefined ⇒ 包装后的 handler 直接 `return handler(args, ctx)`（同一个 Promise，零行为变化）。
2. **`wrapCommandApi`** 返回 `new Proxy(rawPi, …)`：只拦 `registerCommand(name, options)`——记入 `owned: Set<string>`，把 `options.handler` 换成 `wrapped`；其余属性 `Reflect.get(target, k, target)`，函数值 `bind(target)`（K25①验证工具 / 事件 / `pi.events` 不受影响）。
3. **认领**：`capture.arm(inv)` 写同步槽 → `sendUserMessage` → pi 在同步前缀里调 `wrapped(args, ctx)` ⇒ `take(name, args)` 先比同步槽（`name`、`args` 逐字相等），命中即清槽；`settleArm()` 若发现槽没被取走且 `owns(name)`，转入回退队列（FIFO，键 `name + "\0" + args`，TTL = min(5s, 帧剩余预算)），settle 推迟路径下 handler 稍后执行时从队列认领；过期仍未认领 ⇒ `completion:"unknown", captured:false`。错认只可能发生在推迟窗口内终端手打同名同参命令，后果仅限展示（终端输出多回显一份到网页），文档注明。
4. **ctx 代理**：认领成功 ⇒ `ctxProxy = new Proxy(ctx, { get: (t, k) => k === "ui" ? uiProxy : Reflect.get(t, k, t) })`，加入 `webCtxSet`（WeakSet，供 `isWebInvocation(ctx)`）；`try { return await handler(args, ctxProxy) } catch (e) { collect({kind:"error", text}); throw e } finally { capture.finish(cmdId) }`——异常照旧抛给 pi 的 `emitError`。ctx 的 getter 都用闭包里的 `runner`（`runner.js:548-625`），委托后 `assertActive` 陈旧检查照常生效（K25③）。
5. **ui 代理**（每次访问现取 `ctx.ui`）：

| 调用                                                            | 终端                               | 网页捕获 / 返回值                                                                                                                                      |
| --------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `notify(msg, type)`                                             | **照常转发**（终端也看得到）       | `{kind:"notify", level: type ?? "info", text}`                                                                                                         |
| `setWidget(key, string[] \| undefined, opts?)`                  | 转发                               | `string[]` ⇒ `{kind:"widget", key, text: lines.join("\n")}`；工厂函数 ⇒ `{kind:"widget", key, text:"(rendered in terminal)"}`；`undefined`（清除）不记 |
| `setStatus(key, text)`                                          | 转发                               | `{kind:"status", key, text}`（清除不记）                                                                                                               |
| `editor(title, prefill)`                                        | **不打开**                         | `{kind:"text", title, text: prefill}`（`/mem doctor` 这类只读展示即输出）+ `{kind:"interactive", text:"editor"}`；返回 `undefined`                     |
| `select` / `input`                                              | 不打开                             | `{kind:"interactive", title, text:"select" \| "input"}`；返回 `undefined`（= 用户取消）                                                                |
| `confirm`                                                       | 不打开                             | 同上；返回 `false`。网页层的二次确认（`E_CONFIRM_REQUIRED`）**不**代替命令内部确认——两者确认的对象不同                                                 |
| `custom(factory)`                                               | 不打开                             | `{kind:"interactive", text:"custom"}`；返回 `undefined`                                                                                                |
| `setEditorText` / `pasteToEditor`                               | **不转发**（不覆盖终端编辑器草稿） | `{kind:"interactive", text:"editor-text"}`                                                                                                             |
| 其余（`theme`、`setTitle`、`setWorkingMessage`、`setFooter` …） | 原样委托                           | 不记                                                                                                                                                   |

出现任一 `interactive` 条目 ⇒ `needsTerminal:true`，网页显示「此命令的交互步骤需要在终端完成，网页已跳过：select / confirm …」。第三方命令不经过包装层，交互照旧弹在终端（v2 横幅不变）。

6. **文本回落（C12 的全部命令侧改动）**：`canOpenSettingsEditor(ctx)` 加 `&& !isWebInvocation(ctx)`（`src/ui/settings-editor.ts:496` ⇒ `/agent settings` 无参走既有文本列表）；`/tasklist` 的 `if (ctx.mode !== "tui")` 改为 `if (ctx.mode !== "tui" || isWebInvocation(ctx))`（`src/todo/index.ts:437` ⇒ `formatTaskList` notify），且 `:422` 的 `currentUI = ctx.ui` 在网页调用时不执行（否则 widget 宿主会被换成捕获代理）。C12 用 grep（`= ctx.ui`、`= ctx;`、`ctx.ui` 被传入长生命周期对象）逐一核对 11 个命令，同类「保存 ctx/ui」点照此处理并记入 §14；预计 0–2 处。其余命令零改动。
7. **收集窗口与回执**：窗口 = 认领 → handler Promise settle，硬上限 30s（`CAPTURE_MAX_MS`，`unref` 定时器）。`command` op 在 `min(3000, opTotal)` 内等 settle：已 settle ⇒ `cmd_result{completion:"sync", captured:true, output}`；未 settle ⇒ `completion:"async"`，settle 或 30s 到点（`completion:"timeout"`，带已收部分）后发 `cmd_late` 终结。窗口关闭后的 ui 调用只转发终端、不再收集。
8. **大小与截断**（agent 侧，发帧前）：去 ANSI（CSI / OSC）与 `\n` `\t` 以外的控制字符；单条 ≤ 8 KiB（按 UTF-8 边界截断，`clipped:true`，末尾 `…`）；合计 ≤ 32 KiB、≤ 64 条，超出保留前面、丢后面并记 `truncated{droppedEntries, droppedBytes}`；`title` ≤ 200 字符、`key` ≤ 64 字符。hub LRU 里的 output 受总字节预算 8 MiB 约束（超预算时只丢该条的 `entries`，保留状态与 `truncated`）。
9. **隐私与分发**：输出从不进审计（只记 `outputLen` / `outputEntries`，§6.4）；`cmd_late` SSE 事件**不带** output（它是广播），发起页看到自己待决项的 `cmd_late` 后以 `queryOnly` 从按 principal 分桶的 hub LRU 取回——其它用户拿不到。
10. **网页展示**（C5 `control/CommandResult.vue`）：notify 行带 level 徽标；widget / status 以 key 为小标题成块；text 用 `<pre>`（文本节点，无 `v-html`）；`needsTerminal` 提示；截断脚注「输出过长，已截断 N 条 / N KiB——完整内容见终端」；`captured:false` 显示「此命令的输出只在终端显示」。补全列表按 `output` 徽标提前告知。
11. **交互型命令的降级汇总**：有文本回落（`/agent settings`、`/tasklist`）⇒ allow，走回落；用 editor 做只读展示（`/mem doctor`）⇒ allow，预填即输出；多步交互（`/mem tidy`、`/mem restore`、`/tasklist clear`）⇒ confirm，交互步骤降级为取消——结果通常是「未执行」+ needsTerminal 提示；纯选择器（`/resume-recent` 无参）⇒ deny。第三方命令无法降级 ⇒ 维持「命令正在终端等待交互」横幅。

### 5.1 端口（`src/ask-user/remote.ts`，新，pi-free，W1 冻结签名）

```ts

  | { kind: "answer"; answers: AskUserAnswers; origin: string } // 已按 answer-codec 编码
  | { kind: "cancel"; origin: string };

}

export default function wireAskUser(pi: ExtensionAPI, opts?: { remote?: () => AskUserRemotePort | undefined }): void; // index.ts 签名变更（默认导出，旧调用 wireAskUser(pi) 仍合法）
```

### 5.2 TUI 路径（`runTuiInteraction` 改写要点）


### 5.4 web-hub 对话框桥（`src/web-hub/agent/dialogs.ts`，新）

`createDialogBridge({ setSlot, isAttached, notify, now, enabled, epoch })` 实现 `AskUserRemotePort` + `answer/cancel/detachAll/attributePrompt`：

- `open()`：`enabled && isAttached()` 否则 undefined；登记 `{dialogId:"ask:"+toolCallId, …, state:"open"}`；**恒**调用 `setSlot("dialogs", {t:"dialogs", epoch, open, closed})`（v2，D14）——`connection.setSlot` 总是更新本地槽，只有当前链路 live 且 `hello_ack.caps` 含 `dialog.v1` 时才写 socket；进 live 时重放循环按 `SLOT_REQUIRED_CAP` 过滤。因此**断线期间**（`teardownSocket()` 已清空 `helloCaps`）打开的对话框照常入槽，重连 `hello_ack` 后随槽位重放，网页照样能答。v1 的 `hubHasDialogCap()` 依赖删除。
- `answer(dialogId, answersWire, origin, cmdId)`：`epoch` 由 commands 层先校验；未知 / 已关闭 ⇒ `E_DIALOG_CLOSED`；校验（题数相等；`selected ⊆ labels`；非多选 `selected.length ≤ 1`；`other` ≤ 4 KiB；每题至少一项或 other——与 TUI `allConfirmed` 同义）⇒ 否则 `E_BAD_ANSWER`（**对话框保持打开**）；用 `encodeAnswer`（`answer-codec.ts`）编成 `AskUserAnswers`，调 `onRemote({kind:"answer",…})`：返回 false ⇒ `E_DIALOG_CLOSED`；true ⇒ 标记 `closed{by:"web", cmdId}`、刷新槽、TUI notify（§4.7）、回 ok。
- `close()`（ask_user 调用）⇒ `closed{by}`；`detachAll()`（binding `session_shutdown`）⇒ 全部 `closed{by:"session"}`。
- 桥状态在 `wireWebHub` 闭包（每 activate 一份，`epoch = MODULE_INSTANCE`）；`/reload` 后旧桥随旧 binding 释放，旧工具调用本就被中止；新桥的槽 `epoch` 不同 ⇒ 带旧 epoch 的答案 `E_DIALOG_CLOSED{stale}`（§3.5 断言 3）。

#### 6.7.1 `/webhub token rotate`（包 C8；v2.1 按 B2 / U13 重写）

**轮换意图记录** `<stateDir>/rotate.intent`（`paths.ts` `rotateIntentFile`，取代 v2 的 `rotate.pending`；读写在新 `protocol/rotate-intent.ts`，纯 node fs，agent 与 hub 共用）：

```ts
interface RotateIntent {
  v: 1;
  id: string /* 16B hex */;
  at: number;
  by: "agent" | "hub";
  pid: number;
  phase: "intent" | "token-written";
}
type IntentRead =
  { state: "absent" } | { state: "present"; intent: RotateIntent } | { state: "unreadable"; code: string };
```

- **原子写**：`open(<file>.<pid>.<rand>, "wx", 0o600)` → write → `fsync` → `rename` 覆盖目标 → `fsync(stateDir)`；推进 `phase` 同法重写。**token 也改为原子替换**（`protocol/token-file.ts` 的 `replaceTokenAtomic`，同一套 tmp + rename；取代 `writeFresh("w")` 的就地截断），读者 `readFileSync` 只会读到完整的旧值或新值。启动时清理本目录下 `token.*.tmp` / `rotate.intent.*.tmp` 残留。
- **读取三态**：`absent`（`ENOENT`）/ `present` / `unreadable`（其它异常、解析失败、非普通文件、属主不符）；`unreadable` 按 `phase:"intent"` 处理（fail-closed）。

**顺序（在线与离线同一条）**：① 写意图 `phase:"intent"` → ② 原子替换 token → ③ 意图推进 `phase:"token-written"` → ④ 作废：清内存会话 + `authGen++`、`revokeAllSessions()`（单事务 `UPDATE users SET epoch = epoch + 1; DELETE FROM sessions`）+ `lanRevokeGen++`、两个 listener 的 SSE 全部 revoke → ⑤ 删意图。任何崩溃都落到「意图存在」或「未开始」两种状态之一：

| 崩溃点     | 磁盘状态                                    | 恢复（hub 启动或运行期扫描）                                                                                           |
| ---------- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| ① 之前     | 无意图、旧 token                            | 未轮换；命令报错，用户重试                                                                                             |
| ①–② 之间   | `phase:intent`、旧 token（可能有 tmp 残留） | hub **自己完成轮换**：再原子换一次 token（`phase:intent` 下分不清 token 换没换，统一再换，幂等）→ 推进 → 作废 → 删意图 |
| ②–③ 之间   | `phase:intent`、新 token                    | 同上（token 被再换一次；用户用 `/webhub open` 取最新链接——`open` 每次现读 token 文件，`agent/index.ts:682`）           |
| ③–⑤ 之间   | `phase:token-written`                       | 保留 token，只做 ④ → ⑤                                                                                                 |
| 意图不可读 | `unreadable`                                | 按 `phase:intent`；删不掉 ⇒ 视为作废未完成（下）                                                                       |

| 端         | 行为                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| hub 启动   | **意图恢复是 hub 启动的第一步**：在 `auth` 首次 `token()`（现 `fe.listen()` 内 `http.ts:1568` 会读取并缓存 token）、`fe.listen()` 与写 hub.json **之前**同步读意图（C8 须把恢复挪到这些调用之前，并以测试断言调用顺序；另外恢复后无条件 `auth.reload()`，双保险）：`present/unreadable` ⇒ 按上表补完 token（内存会话本就为空）；LAN：在 `fe.lan.start()`（`hub.ts:249`）**之前** `await store.revokeAllSessions()`（占用 LAN 启动 deadline 预算）⇒ 成功才删意图并开放 LAN listener；失败 / 超时 ⇒ **LAN listener 不开放**，`LanStatus{state:"off", reason:"rotate-pending"}`（`protocol/lan.ts` `LanOffReason` 追加，冻结面），意图保留，loopback 照常可用（token 已是新的）；`/webhub status` 显示 `lan off · rotate-pending · /webhub restart to retry`。未配置 LAN ⇒ 补完 token 后直接删意图 |

#### 6.7.2 `/webhub stop` / `/webhub start`（包 C8；v2.1 按 B3 / U12 修订读取语义）

- **stop 标记** `<stateDir>/stopped`（0600 JSON `{v:1, at, pid, by}`，原子写同 §6.7.1），**机器级**（U12）。读取在 `protocol/stop-marker.ts`：`readStopMarker(stateDir) ⇒ {state:"absent"} | {state:"stopped", at?} | {state:"unknown", code}`：
  - `absent`：`lstat` 报 `ENOENT` 且 stateDir 可访问——**唯一**允许自动拉起的状态；
  - `stopped`：普通文件且属主 = 当前 uid（内容损坏也算 stopped：存在即意图，内容只是元数据）；
  - `unknown`：其它任何情况——`EACCES` / `EIO` / `ELOOP` / `ENOTDIR` / stateDir 不可读、非普通文件（symlink、目录）、属主不符。
- `shouldSpawnHub` 加 `stop: "absent" | "stopped" | "unknown"` 输入，**仅 `absent` 放行**（fail-closed）；每次 spawn 判定前现读（同步 `lstatSync`，整体 try/catch，不缓存）。连接仍按 backoff 尝试（有人手动起 hub 仍能连上），只是不自动拉起。hub 侧 supersede 判定读同一函数（§6.7.3）。
- **提示**（hub 此时通常不在，网页无从显示，提示只在终端）：`/webhub status` 三态——`hub stopped since <time> · /webhub start to resume`；`autostart blocked · stop marker unreadable (<code>) · check <path>, then /webhub start`；web-hub 状态键（HUD 同行显示）紧凑标记 `web stopped` / `web stop?`（`WebHubStatusView.stopMarker?` 字段与 `statusLineText` 渲染由 C0 一次写好，C8 只经 launcher → connection 端口填值）；`unknown` 首次出现时 TUI notify 一次（每进程去重）。
- `/webhub stop` 流程：**先**原子写标记（写失败 ⇒ 报错且**不**停 hub——否则停了会被其它 TUI 立即拉回）→ live + `ctl.v2` ⇒ `hub_ctl{op:"shutdown", reason:"stop"}` → ack ≤ 2s → 等 pid 退出 ≤ 5s（复用 `restart.ts` 的 `raceAck` / `waitExit`）→ 否则按 `restart.ts` fallback（身份校验后 SIGTERM / 提示手动）。旧 hub 无 `ctl.v2` ⇒ 发 `reason:"restart"`（旧 hub 只认它；效果相同：退出，标记阻止重拉）。
- hub 收到 `reason:"stop"`：SSE `hub{state:"stopping", by:"terminal"}` → 现有优雅关闭 → 退出；审计 `op:"stop"`。
- `/webhub start`：删标记（`unlink`，`ENOENT` 视为成功）→ 立即 spawn（同 restart 的 spawn 路径）。删除失败 ⇒ 仍按显式意图 spawn 一次，但 notify「stop 标记无法删除（<code>），其它终端仍不会自动拉起」。`/webhub restart` 与 `/webhub open` 同样删标记（显式意图），失败同处理。空闲自动退出（`idle.ts`）与 superseded **不**写标记。
- 前端：收到 `hub{stopping}` 后记在内存，SSE 断开时显示「hub 已由终端停止（/webhub start 恢复）」而非通用「重连中」。

#### 6.7.3 hub 版本替换 `superseded`（包 C10，arch §4.3；v2.1 按 B1 / U11 加 30 分钟上限）

- **触发**：`register` 时 `compareVersions(hello.pluginVersion, hubVersion) > 0` ⇒ `supersedePending = {nextVersion: max(已见版本), since, deadlineAt: since + SUPERSEDE_MAX_WAIT_MS}`（常量 30 min，不设设置项；测试 / 真机验收可用 hub 进程环境变量 `PI_WEBHUB_SUPERSEDE_MAX_WAIT_MS` 覆盖，**钳制到 `[10s, 30min]`**，非数字 / 非有限值 / 越界 ⇒ 回落默认 30 min 并在 hub.log 记一行 warn——该变量只能缩短、不能延长上限）。`since` 在 hub 进程内只设一次，更高版本到来只更新 `nextVersion`、**不重置** deadline。SSE `hub{supersedePending, supersedeDeadlineAt}` ⇒ 顶栏「hub 将在空闲时升级到 vX（最晚 HH:MM）」。
- **静默路径**（v2 不变）：每 `registry.tick` 与相关事件判定——所有 Rec 的 `dialogs.open` 为空、router 在途命令 = 0、KDF 在途 = 0、stop 标记为 `absent`、距上次替换 ≥ 60s ⇒ 执行（`forced:false`）。
- **强制路径**（`now ≥ deadlineAt` 且静默条件仍不满足）。**优先级（v2.1 主会话裁定）**：① stop 标记非 `absent` ⇒ 不替换——这是用户的显式停止意图（或 fail-closed 的未知状态），高于 30 min 上限；此时旧 hub 保持运行，顶栏改为「升级已暂停：hub 停止标记存在 / 不可读」，审计记一次 `supersede_blocked{reason:"stop"}`；标记恢复为 `absent` 后立即按强制路径执行（deadline 已过）。② **60s 防乒乓限流不适用于强制路径**（`deadlineAt ≥ since + 10s`，且限流只为阻止静默路径的连环替换；强制路径每个 hub 进程至多发生一次）。除 ① 外没有任何条件能让等待超过 `deadlineAt + DRAIN_MAX_MS`：
  1. **排空**（≤ `DRAIN_MAX_MS = 15s`）：SSE `hub{state:"restarting", nextVersion, forced:true, draining:true}`；`router.drain()` ⇒ 新写请求在 §6.3 步 6 前置拒绝 503 `E_HUB_RESTARTING{effect:"none", retryable:true}`（**不建 LRU 条目**，审计记拒绝行）；已转发的请求等其自身请求级 deadline 自然结束（≤ 13s，§3.3）；LAN 登录不拦截，在途 KDF 随排空一起最多等 15s。
  2. **排空到点仍在途的请求**：HTTP 以 503 `E_HUB_RESTARTING{effect:"unknown", retryable:true}` 终结。（实施注记：当前参数下请求级 13s 绝对 deadline 恒早于 15s 排空闲，仍在途的请求会先被自身 deadline 判 `E_DEADLINE`——本条 503-unknown 分支保留为协议语义，预算调长时生效；C10 验收裁定）浏览器进入 `unknown → querying`（§7.7），新 hub 起来后 `queryOnly` 由 agent 进程级台账裁决（§3.4——hub 重启不丢结果、不重复执行）。
  3. **open ask_user**：对有 open 对话框的 live agent 发 `superseded{nextVersion, yieldMs, forced:true, openDialogs:n}`（其余 agent 同帧、无 `openDialogs`）。agent 侧：对话框**不关闭**（TUI 通道本就不依赖 hub），TUI notify 一次 `web-hub upgrading · web answers paused · answer ask_user in the terminal (n open)`；槽照常本地维护（D14），新 hub 起来后重放 ⇒ 仍未作答则网页表单恢复。
  4. 之后与静默路径相同：优雅关闭 → 退出。
- **网页语义**：`hub{restarting, forced}` ⇒ HubStateBanner「hub 正在升级（等待超过 30 分钟，已强制）」；ask_user 表单进入 **suspended**（只读，Submit 禁用，草稿按 `(agentKey, epoch, dialogId)` 保留，§3.5），文案「hub 升级中——请在终端作答；hub 恢复后若仍未作答，此表单会自动恢复」。排空期已提交的答案经 2. 进入查询，终态只可能是：`ok(dup)`（web 已 claim）/ `E_DIALOG_CLOSED`（终端先答，表单折叠「已在终端作答」）/ `E_UNKNOWN_ID`（从未到达 agent ⇒ 若对话框仍 open 允许用新 id 重新提交）。其它在途写请求的终态规则相同（§3.5 表）。
- **执行**（两条路径共用）：SSE `hub{state:"restarting", nextVersion, forced}` → 发 `superseded` → 优雅关闭 → 退出；审计 `{"audit":"admin","op":"supersede","from","to","forced","waitedMs","openDialogs","inflightAtDrain","drainTimedOut"}`。
- **阻塞数据通路**（v2.1 主会话修订，C10 验收）：stop 标记阻塞期间 `SupersedeState.blocked`（250ms tick 采样、变迁时 emit）→ `HubInfo.supersedeBlocked`（冻结面新增字段）→ SSE → reducer → `HubStateBanner` 第四态「升级已暂停」；解除后立即按强制路径执行。`PI_WEBHUB_SUPERSEDE_MAX_WAIT_MS` 钳制 `[10s, 30min]`（非法值回默认），只能缩短不能延长。
- **agent 让行**（`connection.ts` `onSuperseded`）：`pluginVersion >= nextVersion` ⇒ 立即按常规重连并允许拉起；否则 `yieldUntil = now + yieldMs`，期间 `spawnBlocked()` 为真（只连不拉）⇒ 高版本 agent 先拉起新 hub；高版本 agent 若已退出，低版本在让行期满后照常拉起（新 hub 仍为低版本、不会再触发，直到高版本回来；60s 限流防乒乓，K24）。`forced` 不改变让行规则。
- **与 stop 的关系**：stop 标记 `stopped` / `unknown` 时静默与强制都不触发；superseded 不写标记。
- **前端**：`hub{restarting}` ⇒ 横幅「hub 正在升级」；SSE 重连后 `hub.version` 变化 ⇒ 现有 versionMismatch 提示刷新（UI 静态资源随 hub 版本）。

```
SSE status.queue / dialogs / ev ────────────────▶ @logic/state.js reduce ──▶ state（隐藏页不 commit，U3）
```

- 控制相关的**所有**可见状态（乐观项、在途、错误）都经 `hub.dispatch()` 进 reducer，因此受 renderGate 唯一规则约束（隐藏页零 DOM 写入）；组件内部只有输入草稿这种「用户正在前台操作」的局部状态。
- 草稿按 agentKey 存在 `useControl` 的内存 Map（切 agent 不丢；刷新丢——不用 localStorage，`source-scan` 规则不变）。

### 7.2 传输层（冻结面 `transport/types.ts` 追加）
