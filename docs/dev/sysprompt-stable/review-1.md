# 评审报告 #1：`docs/dev/sysprompt-stable/plan.md`

> 评审日期：2026-09-26 · 评审对象：system prompt 稳定化实施方案（v1，待评审）
> 评审环境：全局 `pi --version` = **0.87.1**（`/home/bluecake/.nvm/versions/node/v22.22.1/lib/node_modules/@earendil-works/pi-coding-agent`）；
> 仓库 `node_modules/@earendil-works/pi-coding-agent` = **0.84.4**；`package.json` peer = `>=0.84.0 <0.86.0`。
> 所有 pi 行为论断均对照 0.87.1 的 `dist/**/*.d.ts` 与未压缩 `dist/core/*.js`、以及 0.84.4 的同名文件逐条核验。

## 评审结论：打回

方案的**工程质量很高**——状态机、不变量、被否决备选、风险表都写得比仓库里多数 plan 扎实，对 pi 0.87 的五条核心论断我逐条核对，**行号级别全部命中**（见「已核查项」）。打回的原因只有两条，但都在开工前必须解决：

1. 方案赖以成立的 `systemPromptOptions.sections` 机制是 **pi 0.86.0 引入的**，而本仓库 peer 锁死在 `<0.86.0`、本地装的是 0.84.4。方案全文称"已从 pi 0.85 的 .d.ts 核实"——0.85 没有这个 API。照此施工 `npm run typecheck` 直接红，且在声明支持的版本上会**静默丢失全部三段内容**。
2. `triggerTurn: true` 的通知唤醒轮**不经过 `before_agent_start`**，方案落地后每次子 agent 完成通知都会往 transcript 写一条"删除三个 section"的补丁 —— 在方案自己点名的那条路径上**新增**一次整前缀重写，并与用户轮形成震荡。这是方案当前形态引入的新问题（今天不存在）。

修掉这两条 + 下面两条「严重」后可直接进入「有条件通过」，方案主体结构不需要推倒。
