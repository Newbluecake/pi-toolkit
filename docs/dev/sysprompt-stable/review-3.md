## 评审结论：有条件通过

v3 的选型转向是对的，而且不是换说法——我把简路线的五个承重点逐个放到源码上验证，**全部成立**，其中两点比方案自己写的更强：

1. **I8 不只是「同构」，是幂等**。强制 run 里我们的回放结果再经 pi 的强制投影（`pc87:dist/core/agent-session.js:1044-1060`），`getCurrentSystemMessage` 在我们的输出上重算得到 `{content: captured, toolsAdded: <全量当前工具>, timestamp: <首条 system 的 timestamp>}`，`forced === captured` ⇒ `head2` 与 `head` 逐字段相同。所以「用户轮无副作用」是**构造保证**，不是约定。
2. **review-2 #2(b)（capable 路由下 `initialTools = []`）在简路线里结构性消失**。`ai87:dist/api/anthropic-messages.js:793-800` 取 `getInitialSystemMessage(context.messages)?.toolsAdded ?? []`；我们的回放头从 `getCurrentSystemMessage` 复制 `toolsAdded`（`ai87:dist/utils/transcript.js:58-86` 返回的是**全量解析后**的工具集，不是 delta），所以 `initialTools` 完整。合成头分支不存在。
3. **`getSystemMessageText` 的渲染等价性成立**：`ai87:dist/utils/text.js:11-18` 把 `content` 与各 `sections` 以 `\n\n` 连接后 filter 空串——把整串放进 `content`、不带 sections，与 pi 自己按 sections 渲染出的字节完全一致。
4. **压缩请求不会踩到回放**：`_runDefaultCompaction` 用 `this.agent.streamFunction`（`pc87:agent-session.js:1844`）直接发请求，而 `transformContext`（= `emitContext`，`pc87:dist/core/sdk.js:248-252`）只在 `core87:dist/agent-loop.js:262-264` 的 `streamAssistantResponse` 里调用。摘要请求不会被注入错误的开头。
5. **F13 的时序成立且比方案写的更硬**：`turn_end` 由 `finishTurn` 分发（`pc87:agent-session.js:366-376` → `_dispatchTurnEndBoundary`），而 `core87:agent-loop.js:176-178` 把 `finishTurn` 放在 `emit turn_end` **之前**、`prepareNextTurn`（② 号压缩点）**之后的下一轮**。所以「`session_compact` 之后出现的 `turn_end` 必然晚于一次压缩后的请求」成立，`prefixFresh` 的免费性判据自洽。

但方案在**运维面**留了两个硬口子：回放层没有开关，快照不跨 `/reload`。两者都不动架构、改动量都是十几行，但都必须在 S1 合并前定下来——S1 是第一个 PR，而 S1 恰好就是「没有开关、触及每一次请求」的那一层。
