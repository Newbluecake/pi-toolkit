### 0.1 hub 端订阅语义（不改 hub 订阅逻辑）

- `SseClient.subscribed` 是 `Set<string>`（`hub/sse.ts:28`），`publish(…, agentKey)` 推给所有订阅了该 agent 的客户端（`sse.ts:236-245`），**不是「选中才推」**。没有每客户端主订阅上限；2 runs/client 只属于 run-transcript。
- `/api/subscribe`（`hub/http.ts:867-881`）同一 (clientId, agentKey) 的新尝试会替换 pending 对象；`runSnapshot`（`http.ts:822-847`）在 `getPending(...) !== p` 时直接返回 ⇒ **被替代或被退订的尝试，只要快照还没发出，就永远不会投递**。已发出的快照、该尝试缓冲的帧、`client.subscribed.add` 按此顺序写入**同一条有序 SSE 流**。
- `/api/unsubscribe`（`http.ts:883-889`）只删本 key 的订阅和 pending。
- `agent_down` 保留订阅，重连后发 `gap`（`hub/registry.ts:412-413`）；`agent_removed` 清掉所有客户端的订阅（`http.ts:749-752`）；新的 SSE 连接 `subscribed` 为空。
- 单槽的动机：探索中未找到任何文档或提交记录，判定为继承旧 UI 的交互假设。
- 成本面：保活会话的 `ev` 帧占用同一条 SSE 带宽，`maxBufferedBytes=2MiB` 的慢消费者断连（`sse.ts:126-129`）概率随 K 上升。断连可自动恢复，K 有界。
- 其它消费者核查：`agent.history` / `agent.sub` / `agent.items` 只被 Transcript 和 AgentDetail（`:64, :472`）读取；`priorityFor` 只看事件类型；`control.getSessionId` 读 `session`。

## 1. 设计决策

### 1.1 总体

- D2 只改变**何时**退订主订阅；数据始终在 reducer 的 `agents` Map 里（与今天一样，非选中会话的 items 本来就常驻）。
- E1 只改变**挂载时**的滚动初始位置与 following 初值；不缓存组件实例。

### 1.2 D2 —— 订阅 LRU 保活

| 决策                  | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | 理由                                                                                                                                                                                   |

| D2-1 LRU 放哪         | useHub 闭包 `sessionLru: string[]`（MRU 在尾）；纯算法 `planKeepAlive()` 放新文件 `logic/sessionKeepAlive.ts（v3 主会话裁定：放 logic/ 保持 vue-free 分层，派发文件域以此为准）`                                                                                                                                                                                                                                                                                                                              | 订阅属于副作用，与 `runSubs` / `lastSubAt` 同层                                                                                                                                        |
| D2-2 配额语义         | K = 最多保留的会话数（含当前选中）⇒ 后台保活最多 K-1 个；选中为 null（移动端回列表）时同样只留 K-1 个                                                                                                                                                                                                                                                                                                                                                                                                         | K=1 时与旧版主路径的 transport 调用序列一致（§1.3）                                                                                                                                    |

**D2-7 正确性论证（评审要求的三点）**

1. **有序性**：快照 H、该尝试缓冲的帧、`subscribed.add` 在 hub 端按序写入同一条 SSE 流（`http.ts:840-846`）；EventSource 按序分发；reducer 同步处理 ⇒ 客户端看到的顺序与 hub 写入顺序一致。
2. **最终不回退**：同一 session 下，旧尝试的快照 H1 只可能在 hub 处理新订阅 S2 **之前**已写入流（否则已被替代、不会发出）；S2 的快照 H2 必然在其后 ⇒ 客户端先应用 H1、再整体替换为 H2，最终就是 H2。H1 是 hub 在某个时刻的完整一致快照，短暂显示可以接受（产品标准：最终一致、不串 session）。
3. **新订阅失败时最终为 error**：S2 POST `!ok` ⇒ hub 不会产生 H2；`subscribe_failed` 置 `history=error` + `abandoned` ⇒ 之后到达的 H1 被丢弃；H1 若先于失败到达，随后的 `subscribe_failed` 仍把状态改为 error。S2 若 202 但快照失败 ⇒ hub 发 `history{error}`（未置 abandoned）⇒ error。
4. **不串 session**：session 替换时 `applySession` 清空 transcript 并进入 waiting（现有逻辑）。在途的旧 session 快照由 `sessionId` 比对丢弃。`sessionId` 每次 /new、/resume 到其他会话、/fork 都会变；/resume 到同一会话时内容一致，不需要丢弃。旧 agent 或旧 hub 不带该字段时**放行**（退回今天的行为：随后的 gap 会再触发一次 resync）。
5. 不要求 `attemptId`：只有在「连同一 session 的旧尝试快照也绝不允许短暂应用」时才需要，当前需求不要求（已与评审确认判据）。

### 1.3 K=1 兼容性声明（替代 v1 的「逐字节一致」）

- **一致（golden 钉住）**：主路径的 transport 调用顺序（A→B、A→null、A→B→A 限速窗口内外、hello 后切换、带 run 的切换、选中会话的 session 替换），以及 reducer 的可见投影（`sub`、`history`、`needsResync`、`items` 的长度与 id、`hasMore`）和渲染分支（骨架 / Transcript / error 提示）。
- **有意差异（逐条测试）**：
  1. `subscribe` 返回 `!ok` 后切走：旧版仍发一次无用的 `unsubscribe`（因为 `sub.failed` 非 null），新版不发（账本已删）。
  2. `retry` 后、在限速窗口内切走：旧版因 `sub===null` 不发 `unsubscribe`；新版看账本，若上一轮尝试仍登记则发一次（幂等）。
  3. 被驱逐尝试的迟到 history：旧版应用为 loaded（sub=null），新版因 `abandoned` 丢弃；切回时旧版无骨架、显示旧内容，新版走 waiting 骨架。
  4. 旧 POST 结果乱序到达：旧版会污染新尝试（例如把新尝试标成 failed），新版丢弃。
  5. 同 key 的 unsubscribe 在途时发起 subscribe：旧版并发发出，新版等退订 settle 后再发（call 顺序不变，只是时机推后）。
  6. session 替换期间在途的旧 session 快照：旧版先应用、靠后续 gap 纠正；新版直接丢弃（需要新 agent，旧 agent 放行）。
- `abandoned` 是内部字段，不出现在 `types.ts` 的 `HubState` 视图（与 `routed`/`wanted` 同类）。

## 5. 后续增量（明确不在 v1 范围）

1. **快照替换保锚**：非 following 状态下 `agent.items` 被整体替换（tail 前移）时，按锚点重定位（v1 中 scrollTop 数值不变，内容可能偏移）。

## 6. 派发建议（dev-flow）

- 两包文件域零交叉。E1：`useScrollMemory.ts`、`useTranscriptWindow.ts`、`entries.ts`、`Transcript.vue`、`contracts.ts`、`DetailBody.vue`、`AgentDetail.vue`、`DashboardView.vue`。D2：`sessionKeepAlive.ts`、`useHub.ts`、`state.js`、`App.vue`、`SettingsView.vue`、i18n、`protocol/{messages,http-contract}.ts`、`agent/snapshot.ts`、`hub/history.ts`、`AGENTS.md`。测试文件同样不交叉。**同消息并行派发**，各自独立验收（验收模型 ≠ 开发模型）。
- D2 内部顺序：D2-0（golden）先单独提交 → 再改实现。
- 合并后冒烟（`dev:hub` 或真机）：K=3 下 A→B→A 的 Network 面板没有 `/api/subscribe`；滚动位置恢复；移动端 列表↔会话 往返；设置改为「关闭」后行为与旧版一致。
