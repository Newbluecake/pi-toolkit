# 子会话 switch_context + 缓存保活 ping — L2 实施方案（v3.1，待复审）

> 需求原话：「我觉得子会话可以支持switch context」「然后支持cache ttl ping即可」。
> 范围：subagent 子会话 ① 模型自写交接的上下文切换（含 compact-hint 的 tick / 提醒 / demand）；② 子会话等待期间的前缀缓存保活 ping。
> 不在范围：子会话的 TTL 改写（on/off/adaptive）、`compact_context` / `set_compact_threshold` 进子会话、主会话行为的任何变化。
> v2：v1 被评审（gpt-sol）打回，8 条意见的处置见文末「v1→v2 评审处置」。v2 相对 v1 的主要变化：并发槽改为持有者释放 + 兜底 lease；写清 pi 自动压缩失败时子 run 的终态与交付；边界草稿按 turn_end 事件字段做结构校验和 canContinue 复算；新增每 run / 进程级美元预算；切换次数上限做成设置并进结果诊断；pi 版本门 + 真实 AgentSession conformance 测试；「关闭即回到今天」收窄为可测的零新增行为。
> v3：用户不接受「精确 0.87.x 版本门」这一 I14 例外，要求「最新版本也能使用、不依赖版本号」，最低适配目标为 npm latest。v3 把 §3.1 的版本门替换为**运行时能力检测 + 首次使用自证 + 安全降级**（§3.1），并把切换从 `continue` 契约上解耦（§0 事实 2、§2.1）。处置见文末「v2→v3 处置」。
> v3.1：v3 复审「有条件通过」，只补 4 个条件（L3(c) 按条目边界自证、runner 自证失败锁存与优先级、结算处未完成切换的兜底失败检查、L2 探针验证投影可读与文件重开后仍在），已定决策与其余设计不变。处置见文末「v3→v3.1 评审处置」。

## 0. 结论先行（四个决定方案形状的事实）

1. **主会话的 switch_context 在子会话里原样搬过去会直接把 run 结束掉。** 它靠 `ctx.compact()`，而 pi 的 `compact()` 第一步就是 `await this.abort()`（pi `agent-session.js:1865-1868`）。子会话 run 的生命就是 runner 里 `await handle.prompt(req.prompt)`（`src/runtime/runner.ts:673`）：abort 让 prompt() resolve，runner 立即 `prompt_settled` → 以切换前那句话作为最终结果完成，随后 dispose 会话，压缩打在已销毁的会话上，`onComplete` 里的 resume `sendUserMessage` 启动一个没人等的孤儿 prompt。
2. **pi 0.87 有不 abort 的原生通道：`turn_end` 边界草稿，但它有三条必须遵守的契约。** `turn_end` handler 可以返回 `{ entries: SessionBoundaryDraft[], continue?: true }`，草稿类型包含 `compaction`（`firstKeptEntryId: string | null`，null ⇒ `appendCompaction` 用自身 id，即什么都不保留，`session-manager.js:880-898`）（`types.d.ts:600-618`）。pi 在 `finishTurn` 里提交（`agent-session.js:332-364, 366-377`）：`_commitBoundaryDrafts` → `appendCompaction(..., fromHook=true)` → `_refreshFinalizedContext()` → 逐条发 `entry_appended`（`:426-450, 483-488`），下一轮请求直接用压缩后的上下文，**同一个 prompt() 不中断**，不发 `compaction_start/end`，不走 `session_before_compact`。三条契约：
   - **(a) entries 是整体替换**：`emitBoundary` 依次调用各扩展的 handler，`handlerResult.entries` 直接覆盖累积数组（`extensions/runner.js:662-681`）。handler 必须在 `event.entries`（前序 handler 的草稿）基础上组合，否则会吞掉别人的草稿。
   - **(b) 每个 handler 之后 pi 都会用 `_buildBoundaryContext(entries)` 在内存副本上重放草稿**（`agent-session.js:463-482`），抛错 ⇒ `valid=false` ⇒ 本 turn **所有**草稿作废（`runner.js:691-708`，`BoundaryDispatchResult.valid`，`runner.d.ts:35-40`）。
   - **(c) `continue:true` 只在提交后 `_buildBoundaryContext([]).canContinue` 为真时生效**，否则 pi 报 `<boundary> turn_end requested continuation without runnable model context` 并按不续轮处理（`agent-session.js:359-363, 489-494`）。`canContinue` = LLM 消息里有非 system 内容且最后一条不是 assistant，或有待投递消息（`:463-482`）。
   - **(d) 切换根本不需要 `continue`（v3 的关键事实）**：agent loop 的续轮由 `hasMoreToolCalls = !executedToolBatch.terminate` 决定，只要本 turn 执行过非 terminate 的工具就继续；扩展的 continue 只在「本来要停」时补一轮 context-only turn，有工具调用时甚至被显式清掉（pi-agent-core 0.87.1 `dist/agent-loop.js:88-90, 158-167, 184-189, 200-202`）。切换 turn 必然带着 switch_context 的工具结果，所以**v3 从不返回 `continue`**，「continue 被忽略导致 run 结束」这一失败模式在设计上就不存在。
     子会话切换就用这条路：零 abort、零摘要 LLM、零新 phase，不碰看门狗；只依赖两件事：返回的草稿被提交；提交后下一次请求用的是新上下文。两件都在运行时自证（§3.1）。handler 仍按 §2.1 用事件字段做结构校验，不满足就降级。
3. **子会话里 `session_start` 从不触发，`ctx.mode === "print"`。** `session_start` 只在 `bindExtensions()` 里发（`agent-session.js:2293-2314`），我们的 session driver 从不调它（`src/runtime/session-driver.ts:381-415` 只 `createAgentSession` + `subscribe`）；ExtensionRunner 默认 `mode = "print"`、UI 为 noop（pi `extensions/runner.js:168`）。所以子会话的新装配**不能依赖 session_start**，只能在 activate 内注册、在首个用得上的事件里惰性初始化。现有 keepalive 的 G2 闸门只放行 `tui`/`rpc`（`src/cache-ttl/keepalive-state.ts:46, 378`），子会话会被永久拦下。（bash-timeout-grace P5 已按同一结论改为 activate 内注册、首次 execute 惰性构建，见 §7。）
4. **pi 自动压缩不是 run 成功的保证。** 它是子会话唯一的兜底（用户确认 3 选 A），但以下情况会失败并最终让 run 以 `failed` 收场：overflow 恢复只做一次 compact-and-retry，第二次仍溢出即放弃（`agent-session.js:2079-2098`）；摘要 LLM 失败 / 认证失败（`_getSummarizationRequestAuth` 抛错，`:2173`）走 catch 发 `compaction_end{errorMessage}` + `session_compact_failed`（`:2249-2273`）；`!model` 或 `prepareCompaction` 返回空时静默 return false（`:2160-2166`），接着请求照常发出并可能溢出。方案不改兜底选择，但 §2.3.1 写清这些失败下的终态、诊断与交付，§6 有对应验收用例。本文不把自动压缩表述为「保证不失败」。

### 1.5 子会话空闲的真实场景

子会话没有人类空档，只在**有工具在执行、模型不发请求**时空闲：

| 场景                                                              | 典型时长                | 当前约束          | 需不需要 ping                      |
| ----------------------------------------------------------------- | ----------------------- | ----------------- | ---------------------------------- |
| 阻塞 bash（pi 内置）                                              | ≤ `toolMs`（默认 600s） | `tool_exec` phase | >≈4min 时 1-2 次                   |
| 嵌套 `Agent`（X3 注入，spawnAndWait 阻塞）                        | 可达数十分钟            | `tool_exec`       | 主要收益场景                       |
| `consult`                                                         | ≤150s 硬顶              | 同上              | 永不触发（< 240s 间隔）            |
| `web_search` / `bash_job wait`                                    | 秒级-分钟级             | 同上              | 偶尔                               |
| bash P5 的 settle-hold（`agent_before_settle` 挂起 ≤120s 后续轮） | 每段 ≤120s              | 不是工具          | 不需要：续轮请求本身就刷新 5m 缓存 |
| `retry_backoff`                                                   | 秒级                    | —                 | 不需要                             |

现有 keepalive 的「武装」= `backgroundBusy || activeTools > 0 || uiPrompts > 0`（`src/service/cache-keepalive.ts:313-318`）。子会话里只剩 `activeTools > 0`，正好对应上表。首个 ping 在最后一次真实请求后约 `keepaliveIntervalMs`（默认 240s）才发，并且要求请求不在途（`keepalive-state.ts:403`），所以短工具天然零 ping。

## 2. 总体设计

子会话的新能力放在一个 pre-guard 装配入口里，只在 `isChildSession` 时生效，**不建栈、不碰 HOST_KEY**：

```
src/index.ts (pre-guard, wireMemory 之后)
  if (isChildSession) wireChildSession(pi, preGuardSettings)   // src/child/wire.ts（新）
      ├─ wireChildContextSwitch(pi, settings)   // src/context-switch/child.ts（新）
      │     gate: compact.enabled && compact.switchTool && compact.childSessions && boundaryStaticProbe()（L0）
      └─ wireChildKeepalive(pi, settings)       // src/cache-ttl/child.ts（新）
            gate: cacheTtl.keepalive && cacheTtl.childKeepalive
```

`boundaryStaticProbe()` 是 §3.1 的 L0 结构探测（不看版本号）。注册之后，工具能不能真正暂存切换，由进程级能力状态机决定（§3.1：`unknown → observed → ready → verified`，任何一步失败 ⇒ `disabled`）。所有 `pi.on` / `registerTool` 都在 activate 内同步完成，状态在首个用得上的事件里惰性构建（§0 事实 3）。

在子会话里保持惰性（不变）：fleet widget、HUD、scheduler、fabric 路由主体、quota、adaptive、动态阈值、`/cache-ttl`、TTL 改写、`compact_context`、`set_compact_threshold`、Agent/workflow 工具面。

### 2.1 子会话 switch_context（边界草稿方案）

**工具**：复用 `createSwitchContextTool`，新增 `deps.mode: "compact" | "boundary"`，默认 `"compact"`，主会话逐字节不变。`"boundary"` 模式下：

- 跳过 print/json 拒绝分支（`switch-context-tool.ts:116`）；不调 `ctx.compact()`（`:167`）；不 `sendUserMessage`。
- **能力闸门（v3）**：执行时先读进程级能力状态（§3.1）。`disabled` ⇒ `ok:false`，文案 "switch_context is unavailable in this pi runtime (<reason>). Continue normally; your history is unchanged."；`unknown/observed`（尚未完成提交探针）⇒ `ok:false`，文案 "switch_context is not ready yet in this pi runtime; retry after your next tool call."；另有一个子会话的首次切换正在自证（`verifying`）⇒ `ok:false`，"retry shortly"（进程内同一时刻只允许一次未自证的切换，限制爆炸半径）。只有 `ready`/`verified` 才继续。 v3.1：本会话没有会话文件（`ctx.sessionManager.getSessionFile()` 为 undefined，不可持久化）时也返回 unavailable，交接必须能落盘，resume 才正确。
- 校验通过后 `store.stageForTool({ toolCallId, core, keepRecent })`，返回**非 terminate** 的结果（`terminate: true` 会让 agent loop 的 `hasMoreToolCalls` 为 false，run 可能就此结束，`agent-loop.js:167`；同时也会压过扩展决策，`agent-session.js:370-374`）。文案（英文、模型可见）写成不作保证的说法："Context switch staged; it will be applied at the end of this turn and work continues from your handoff. If the runtime cannot apply it you will be told, and your history stays unchanged."
- `resume` 参数在子会话里忽略，总是继续：不继续等于 run 以切换前那句话结束，没有意义。工具描述去掉 "Only available in interactive sessions"，改成 boundary 变体的 description / promptGuidelines（单独常量，主会话文案不动；guideline 建议 `keep_recent:false`，理由见 §2.3.2）。
- 闸门：保留 in-flight 与 60s 冷却；另加**每 run 切换上限** `compact.childMaxSwitches`（默认 5，§4）。计数 = 当前分支上带 `details.source === "pi-toolkit:switch_context"` 的 `fromHook` compaction 条数（每次调用从 `ctx.sessionManager.getBranch()` 现算，所以 resume 续写同一会话文件时计数延续，不因新 activate 清零）。达到上限时工具返回 `ok:false`，模型可见文案："switch_context limit reached for this subagent run (5/5). Continue without switching; pi's automatic compaction still runs, but it is not guaranteed to succeed, so keep outputs concise."；同时 compact-hint 停止发 hint/demand（§2.2）。

**唯一的 turn_end handler**（`src/context-switch/child.ts`），职责按顺序：

- **−1. 能力观察（每个 turn_end，先于一切）**：跑 §3.1 的 L1 结构检查。不通过 ⇒ 进程能力置 `disabled`，本 handler 返回 `undefined`（旧版 pi 上返回值本来就被丢弃），通知走版本无关通道 `pi.sendMessage`。通过且能力仍是 `observed`、本 turn 有工具结果 ⇒ 在返回的草稿末尾附上一条 L2 **提交探针**（`custom` 条目，不进 LLM 上下文），由下一次 `context` 事件核对。

0. **核对上一次切换是否真的落盘**：若闭包里有 `pendingCommit = { seq, nonce }`，在当前分支里找 `details.nonce === nonce` 的 compaction。正常情况下这一步在更早的 `context` 事件里已经由 L3 自证完成（§3.1）；这里只兜底 run 内没有经过 `context` 事件的情况。找不到 ⇒ 提交被后续 handler 的无效草稿连带作废（契约 (b)）或运行时不再提交草稿，按 §3.1 的 L3 失败处理（进程禁用 + 通知模型「上一次 switch_context 未被应用，历史未替换」），诊断记 `uncommitted`，不计入切换次数。无论结果如何都清掉 `pendingCommit`。
1. `event.outcome !== "completed"` ⇒ 清掉暂存，只回传 `event.entries`（abort/error 时绝不续轮，runner 的取消语义保持不变）。
2. 有暂存，**且** `event.toolResults` 里有该 `toolCallId`、结果 `details.ok === true && !isError` ⇒ 调用 `buildChildSwitchDrafts()`（`src/context-switch/boundary.ts`，新；它依赖 pi 运行时导出，不属于纯层），**显式传入事件字段**：

   ```ts
   buildChildSwitchDrafts({
     header: ctx.sessionManager.getHeader(),
     branch: ctx.sessionManager.getBranch(),
     cwd: ctx.cwd,
     turn: { messageEntryId, toolResultEntryIds, toolResults, priorDrafts: event.entries },
     staged: { toolCallId, core, keepRecent, seq, nonce },
     keepRecentTokens,          // pi-settings 读取，缺省 DEFAULT_COMPACTION_SETTINGS
     facts,                     // collectSessionFacts(undefined, ctx, settings) + fileListsFromBranch
     tokensBefore,              // ctx.getContextUsage()?.tokens
   }): { ok: true; entries; diag: SwitchDiag } | { ok: false; reason: SwitchRejectReason }   // v3：不再产出 continue
   ```

   结构校验（全部同步，任一失败 ⇒ `ok:false`，reason 进诊断和降级文案）：

   | #   | 校验                                                                                                                                                                                                                                                                                                                                                                                                             | reason                                |
   | --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- |
   | V1  | `toolResultEntryIds.length === toolResults.length`（pi 用 `flatMap` 丢掉未持久化的结果，`agent-session.js:346-349`，长度不等就无法按下标对齐）                                                                                                                                                                                                                                                                   | `unpersisted`                         |
   | V2  | `messageEntryId` 在 branch 里；每个 `toolResultEntryIds[i]` 在 branch 里、位于 `messageEntryId` 之后、下标严格递增（真实持久化顺序；中间允许夹 custom 条目，如保活审计）                                                                                                                                                                                                                                         | `order`                               |
   | V3  | `messageEntryId` 之后的 branch 里没有 compaction（没有并发压缩）                                                                                                                                                                                                                                                                                                                                                 | `concurrent-compaction`               |
   | V4  | `priorDrafts` 里没有 `compaction` / `context_edit`（别的扩展已经在改写本边界，叠加会互相破坏）；只接受 `custom` / `custom_message`                                                                                                                                                                                                                                                                               | `boundary-conflict`                   |
   | V5  | `keep_recent:true` 时：切点在 branch 里、位于最近一次 compaction 之后、下标 ≤ `messageEntryId` 的下标，且切点条目不是 toolResult（保留段不能以孤立 toolResult 开头）                                                                                                                                                                                                                                             | `cut-point`                           |
   | V6  | **副本预演**：`SessionManager.inMemory(cwd, undefined, [header, ...branch])` 上按最终顺序追加草稿，`buildSessionProjection()` → `convertToLlm()`，按 pi 的规则（§0 事实 2(c)）复算 `canContinue`，作为「结果上下文可运行」的健全性检查（不再用来决定 continue）；抛错或为 false 一律拒绝。副本预演用到的 `SessionManager.inMemory` / `convertToLlm` / `findCutPoint` / `estimateTokens` 在 L1 里一并做存在性探测 | `preview-invalid` / `cannot-continue` |

   草稿组装与顺序：`[compaction, ...priorDrafts(custom/custom_message), resumeMessage]`。我们的 compaction 放最前，前序扩展的 custom_message 落在它之后，不会被 `firstKeptEntryId:null` 一起丢掉。
   - `firstKeptEntryId`：`keep_recent:false` ⇒ `null`；`true` ⇒ 在本分支最近一次 compaction 之后用 pi 导出的 `findCutPoint(entries, start, end, keepRecentTokens)` 求切点。子会话整个任务通常就是一个 turn，切点几乎总落在 turn 中间，此时直接用 `firstKeptEntryIndex`（交接文本代替 pi 的 turn-prefix 摘要，与主会话 hook 取 `preparation.firstKeptEntryId` 等价）。
   - `summary` = `composeHandoff(core, appendix)`，appendix 取 facts（会话文件 + todos + 有上限的读/改文件列表），`droppedEverything` 照旧。
   - `details: { source: "pi-toolkit:switch_context", seq, nonce, keepRecent, dropped: { fromEntryId, toEntryId, entries, tokensBefore, tokensAfterEstimate } }`。`dropped` 区间取「最近一次 compaction 之后的首条」到「切点前一条」（keep_recent:false 时到 turn 末条）；`tokensAfterEstimate` 由副本投影逐条 `estimateTokens` 求和。
   - `resumeMessage` = `{ type:"custom_message", customType:"subagent:switch-context", content: SWITCH_RESUME_TEXT, display:false }`。custom message 在 LLM 侧是 user 角色（`core/messages.js:89-95`），所以只要预演通过，结构上 `canContinue` 必然为真。
   - 返回 `{ entries }`，**永不返回 `continue`**（§0 事实 2(d)）：本 turn 有 switch_context 的工具结果，agent loop 靠 `hasMoreToolCalls` 自然续轮。这样「continue 语义变化 / 被忽略」不会影响 run。
   - 成功后记 `pendingCommit = { seq, nonce, tokensBefore, droppedFirstEntryId }`，能力为 `ready` 时进程状态转 `verifying`（L3 自证由下一次 `context` 事件完成），重置 compact-hint 状态。
   - 消费即清（consume-once）。**新鲜度按结构判断，不按时钟**：只认同一 turn 的 toolCallId；到了下一个 turn_end 仍未采用就作废。不用 120s TTL，否则一起调用的长工具（600s bash）会让交接过期。

3. **降级路径**（校验失败、组装异常、能力未就绪/已禁用）：清槽。能力 ≥ `ready`（草稿通道已被 L2 证明可用）时回传 `[...event.entries, failureNotice]`；否则回传 `undefined`，同一段文案改用 `pi.sendMessage({ customType, content, display:false }, { triggerTurn: false })`：流式中进入 `_pendingCustomMessages`，本 turn 结束后 flush，**不会**像 `deliverAs:"steer"` 那样作为 steering 消息让本该结束的 run 多跑一轮（`agent-session.js:1491-1514`；0.86/0.87 同一机制，§1.6）。`failureNotice` 文案：「switch_context 未生效（原因：<reason>），历史未替换，继续当前任务；可以稍后重试」。**不带 continue**（有 tool results，循环自然继续），不计入切换次数，诊断记 `rejected:<reason>`。handler 的任何异常都在 handler 内 catch 后走这条路，绝不外抛：外抛会被 pi 记为扩展错误，本 turn 我们的草稿也就丢了。
4. 没有切换时，运行无头版 compact-hint（§2.2），产出的消息作为 `custom_message` 追加到 `event.entries` 之后返回（不 continue）。能力不是 `ready`/`verified` 时 compact-hint 不运行：不能提示模型去做运行时做不了的事。

作用域：store、`pendingCommit` 和 handler 都在本子会话 activate 的闭包里，跨会话不会串。

**为什么不给子会话注册 `session_before_compact`**：边界草稿不经过它；pi 自动压缩在子会话里仍用 pi 的通用摘要（今天就是这样）。暂存只活在「工具执行 → 同一 turn_end」之间。pi 的阈值压缩发生在下一轮请求准备阶段（`_compactBeforeNextAssistantResponse`，`agent-session.js:297-307`），那时我们的压缩已提交、store 已空。边界压缩之后**仍然可能立即再触发**一次 pi 压缩，见 §2.3.2。

### 2.2 compact-hint 在子会话（无头版）

改 `createCompactHintHook`（`src/stack.ts:668`），加两个可选 deps，默认值保持今天逐字节的行为：

- `headless?: boolean`：跳过 `:691` 的 print/json 早退；**绝不调用 `ctx.compact()`**（强制分支在 demand 用尽后直接 return）；不调用 `ctx.ui.notify`。
- `getState?: () => CompactHintState | undefined`：替代 `holder.current?.compactHint`，子会话不需要伪造 Stack。

子会话策略：

| 层               | 行为                                                                                                                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| tick             | 与主会话同一网格（`compact.usageTickStepPercent`），经草稿注入                                                                                                                                                                         |
| hint（L1）       | 与主会话同一条静态线；**动态阈值在子会话强制关闭**（不写遥测，不构造 runtime）                                                                                                                                                         |
| 强制（L2，先礼） | 越过（窗口缩放后的）强制线 ⇒ 发 demand，最多 `forceDemandTurns` 次                                                                                                                                                                     |
| 兜底（后兵）     | **交给 pi 自己的自动压缩**（阈值 = window − reserve；我们的强制线本来就被 reserve 钳在它下面，`resolveReserveTokens` 同源）。子会话不做扩展侧的强制压缩：它只能靠 abort 触发，而 abort 会结束 run。自动压缩可能失败，失败语义见 §2.3.1 |
| 窗口差异         | 百分比线天然按子会话自己的模型窗口算；`forceScaling` 按窗口缩放；绝对 tokens 线超出窗口时自动失效（`threshold.ts` 现有规则），无需新配置                                                                                               |

子会话额外的闸门：进程能力不是 `ready`/`verified`（§3.1）⇒ 整个 compact-hint 不运行；`event.toolResults.length === 0`（最后一个 turn，run 即将结束）⇒ 不发 tick/hint/demand；`pi.getActiveTools()` 里没有 `switch_context`（未授予、consult）⇒ 整个 compact-hint 不运行；**切换次数已达 `compact.childMaxSwitches`** ⇒ 只保留 tick，不再发 hint/demand（不能让模型去做做不了的事）。

状态：闭包内的 `CompactHintState`，在首个 turn_end 用 `ctx.cwd` 惰性构造（字段取值与 `stack.ts:1068-1083` 相同，`dynamic` 为 undefined）。两种情况重置它：我们自己的边界切换成功（§2.1 第 2 步）；pi 自动压缩成功，此时子会话收到 `session_compact`，为此额外注册一个只做重置的 `session_compact` handler（仍受同一闸门）。

### 2.3 与 runner / 看门狗 / deadline 的交互

- **切换期间没有新 phase**：边界提交在 pi 的 `finishTurn` 里同步完成（毫秒级，包括 V6 副本预演），夹在 turn_end 与下一个 turn_start 之间。runner 看到的是普通的 `turn_end` → `turn_start` → `model_turn`。看门狗不会误判卡死，也不需要为切换加预算。
- **总预算 / deadline**：切换不延长也不重置任何 deadline（`deadlineAt/graceUntil/hardAt` 原样）。切换后第一次请求是新前缀的冷写入，受 `firstEvent/idle/modelTurn` 正常约束。
- **取消**：runner 取消 ⇒ `session.abort()`（同时 `abortCompaction`）⇒ `outcome=aborted` ⇒ handler 清槽不续轮。
- `prompt()` 全程不 resolve，runner 的最终文本仍取最后一条 assistant 文本（切换后继续干活产生的那条）。

- **自证失败的 run 终态**（v3.1 明确锁存与优先级）：状态机的 best-effort 诊断分支**只写 diag、不改终态**，所以终态完全由 runner 在 `prompt_settled` 前决定，两条互相独立的来源：

  2. **结算处兜底检查（不依赖 agent_end、appendEntry 或事件转发）**：`prompt()` resolve 之后、组装 `promptError` 之前，runner 调 `handle.getSwitchTail?.()`（`session-driver.ts` 的 `PiSessionHandle` 新方法，同步读 `session.sessionManager.getBranch()`）：返回当前分支上最后一条带 `details.source === "pi-toolkit:switch_context"` 的 compaction 的 `{ seq, entryId }`，以及它之后是否存在 assistant 消息条目（`assistantAfter`）。**我们的 compaction 在分支上、而它之后没有任何 assistant 条目** ⇒ 切换已提交但 run 没进入下一次模型请求就结束了 ⇒ 等同锁存了 `run-ended-after-switch`。这条只读 pi 自己持久化的分支，扩展侧任何环节（`agent_end` 未发、`appendEntry` 抛错、`entry_appended` 未转发、扩展已被 invalidate）失效都不影响它。

#### 2.3.2 边界压缩后立即再次自动压缩

边界提交后，下一轮请求准备阶段 `_compactBeforeNextAssistantResponse` 用**投影估算**判断阈值（`agent-session.js:297-307`），不看 usage。所以只要「交接 + 保留段 + resume 消息」仍高于 `window − reserve`（`keep_recent:true` 保留段大、或子会话模型窗口小），pi 会**立刻**再做一次阈值压缩；请求本身溢出则走 overflow 路径。此时：

- **交接不丢**：pi 的 `prepareCompaction` 把最近一次 compaction 的 summary 当作 `previousSummary` 交给更新摘要 prompt（`compaction.js:535-546, 637`），交接内容被合并进新摘要（会被改写，不再逐字保留）。
- **不重复消费**：store 在 turn_end 已清，`pendingCommit` 只核对一次；pi 压缩不经过我们（子会话没有 `session_before_compact`），不计入 `childMaxSwitches`；`session_compact` 只重置 compact-hint 状态。
- **失败语义**：摘要失败 / 仍溢出，按 §2.3.1 结算。
- **缓解**：boundary 版 guideline 建议 `keep_recent:false`；`validateHandoff` 的长度约束保证交接本身远小于任何窗口。

**进程级 ping 账本**（`src/cache-ttl/ping-ledger.ts`，新）：挂在 `Symbol.for("pi-subagent:child-keepalive-ledger")` 上的进程级对象，同时管并发槽和美元预算。没有模块级状态，能挺过 `/reload`。

- `tryAcquire({ holderId, estimateUsd, now }) → Lease | { denied: "global-cap" | "usd-process" }`：同步、从不 await。成功时占一个槽，并把 `estimateUsd` **预留**进 24h 花费（预留防止 4 个并发 ping 同时看到同一个余额而一起超支）。
- `Lease.settle(chargeUsd?)`：释放槽，并用实际计费替换预留（`chargeUsd` 缺省 = 撤销预留）。按 lease token 幂等，第二次调用是 no-op。
- **兜底回收**：lease 有 `expiresAt = acquiredAt + CHILD_PING_LEASE_MS`，只用于防泄漏（持有者崩在 finally 之外这种不应发生的情况）。过期的 lease 在下一次 `tryAcquire` 时被回收，预留按估算计入花费（保守）；过期 token 的迟到 `settle` 是 no-op，不会误释放别的持有者的槽。
- **lease 时长的依据**（`CHILD_PING_LEASE_MS = 150_000`）：一个 ping 序列的最坏时长 = auth ≤ 30s（`authTimeoutMs`）+ 3 次尝试 × 20s 硬超时（`ping-client.ts:76, 294`）+ 退避 2s + 5s（`cache-keepalive.ts:80-81`）= **97s**；TTL 余量检查（`:575-585`）只会让它更短。150s = 97s + 53s 余量（约 1.5×）。有了 auth 超时，正常路径上 lease 永远不会先于持有者的 finally 过期；过期回收只是兜底。
- 24h 花费按小时分桶（24 个桶），滚动窗口。选滚动窗口而不是进程累计，是因为 pi 进程常驻数天，累计上限会让子保活在进程余下的时间里永久停摆。

**美元预算**：

- 每 run：`cacheTtl.childKeepaliveRunBudgetUsd`，默认 **$1.50**；进程级：`cacheTtl.childKeepaliveProcessBudgetUsd`，默认 **$10.00 / 滚动 24h**。`0` = 子会话不 ping（注意：与 `adaptiveWriteBudgetUsd` 的「0 = 闸门关」相反，这里取保守方向）。
- 每次 ping 前（在 `tryAcquire` 之前）估算 `estimateUsd = cacheReadCostUsd(model.cost, capture.prefix.tokens)`（tier 感知）：
  - 模型没有 cost 信息 ⇒ `skip("usd-unpriced", terminal)`：价格不明就无法守预算。
  - `runSpent + estimate > runBudget` ⇒ `skip("usd-run", terminal)`；ledger 拒绝 ⇒ `skip("usd-process", terminal)`。本实例停止 ping，并写一条 `budget-stop` 审计。下一个子 run 重新判定。
- 计费（`settle(charge)` 与 `runSpent`）：proven-hit 按实际 `cacheReadTokens × read 价`；proven-write 按实际 `cacheWriteTokens × write 价`；经重试最终仍是「服务端未处理」类（network / 可重试状态码）计 0；`accepted-then-lost` 等「服务端可能已计费写入」的终局 unproven 按上界 `prefixTokens × write 价` 计入预算。它只进预算账本和审计的 `budgetChargeUsd`，**不进** run 的 `usage.costUsd`，因为那不是已知的实际花费。
- `runSpent` 在惰性构造时从当前分支已有的 `subagent:cache-keepalive` 审计条目的 `budgetChargeUsd` 求和作种子，所以 resume 续写同一会话文件时不会重置。
- **默认值推算**：
  - 实测（本机会话审计，373 次 proven-hit）：前缀中位数 269k、最大 499k tokens；模型为 `claude-opus-5-5`（249 次，read $0.20/M）、`claude-opus-5`（93 次，$0.50/M）、`claude-opus-4-8`（6 次）。单次 ping 中位数约 $0.054（opus-5-5）/ $0.135（opus-5），实测最大约 $0.25。
  - 最坏单价（`models.json`）：`gpt-6-astra` 超过 272k 的档位 read $2/M、write $25/M；`claude-fable-5` read $1/M。1M 前缀 ⇒ 每次 ping $2，每 run 24 次上限 ⇒ **$48/run**；进程内没有时间维度上限，runs 累加没有尽头。这是 v1 的缺口。
  - run 预算 $1.50 ≈ 典型 opus-5 前缀一次完整缓存重写（269k × $6.25/M ≈ $1.68）。为单段等待花在 ping 上的钱超过它要避免的那次重写，就不划算。效果：opus-5-5 典型 run 可 ping 约 27 次，仍由 24 次计数上限先生效（行为同 v1）；opus-5 典型 run 约 11 次（≈ 一个完整窗口 44min）；astra/fable 1M 前缀首次估算即超 ⇒ 不 ping。这偏保守：对这类模型，ping 在经济上其实可能划算，用户可以调高预算。
  - 进程 $10/24h ≈ 185 次典型 opus-5-5 ping 或 74 次 opus-5 ping，约 6-7 个用满预算的子 run/天。它管的是单 run 上限管不到的「时间上无限多个 run」。
  - **超支上界**：预检用 read 价估算，一次 ping 若变成 write（缓存已过期），实际花费可超出估算。单 run 最多超支一个 ping 的 `(write − read)` 差价，进程最多超支 `maxConcurrent` 个。但这笔 write 只在缓存已经过期时才发生，那种情况下下一次真实请求本来也要付同一笔 write，所以期望上的边际超支约为 0；账本仍按实际计入，结果是更早停 ping。

**成本计入子 run**：`src/runtime/session-driver.ts` 的 `mapEvent` 新增一条映射：`entry_appended` 且 `entry.type === "custom" && customType === "subagent:cache-keepalive" && data.costUsd > 0` ⇒ `{ t: "message_end", usage: { input:0, output:0, cacheRead, cacheWrite, costUsd } }`。这样 X9 累加器（`state-machine.ts:491-500, 719`）→ run 成本、fleet widget、HUD 实时子 agent 成本、`/agent costs` 全都自动包含。副作用是 `lastEventAt` 被刷新，这是无害的：ping 只在「请求不在途 且 有工具在跑」时发（`tool_exec` 的截止只看 `phaseEnteredAt`，`deadline.ts:72-73`），掩盖不了静默的 model_turn。T-K7 钉住这一点。

**终态**：① `agent_settled` ⇒ 立即 dispose（子会话一个 prompt 对应一次 settle；resume 会新建会话和实例）；② 陈旧 ctx 自毁（≤1 个 tick，15s 内，期间不会发出 ping）；③ 进程级 `Symbol.for("pi-subagent:child-keepalive")` 注册表（sessionId → dispose），由 runner 的 `onReaped(runId, forkSessionFrom, sessionId)`（`runner.ts:274`，第三个参数已存在）经 runtime-adapter 转发调用，保证 reap 时同步 dispose。三条路径幂等，dispose 都会 `lease.settle()`。

**adaptive**：子会话禁用（也没有 TTL 改写通道）。理由：子会话由机器驱动，没有人类长空档，1h 入场费（plan §16.3）得不偿失；keepalive 与 adaptive 的相互依赖（§17-§20）也不带进子会话。

**与 pi 原生预热的关系**：若子会话模型声明了 `promptCache`（原生 `CacheWarmer` 有资格在 streaming 期间预热），子 keepalive 退让，新 skip 原因 `"native-warmer"`（终态），避免双 ping。本机 `cr-*` 路由没有 `promptCache`，所以实际仍由我们 ping。主会话的同类重叠不在本方案范围内，列入风险。

## 3. HOST_KEY、/reload、惰性与兼容性

- 装配入口只看 pre-guard 已有的 `isChildSession`（`src/index.ts:119`），不读也不写 HOST_KEY；主会话走 `isChildSession=false`，不执行本方案新增的子会话代码。与 memory 共用同一个布尔，已知边界相同（`:115-118` 注释）。

**要点**：

- 「错误交接」不可能出现：交接内容只会在 (a)(c) 都成立时才算生效，(c) 按被丢弃条目的边界逐条核对，而不是看总量；任一不成立，模型都会被明确告知历史未替换。反方向（上下文已被替换但模型不知道）也不可能：resume 消息与 compaction 在同一次原子提交里。
- 降级通知**不依赖边界草稿**：能力低于 `ready` 或自证失败时，一律走 `pi.sendMessage(..., { triggerTurn: false })`（排队到本 turn 结束后 flush，不触发额外一轮；0.86 与 0.87 同一机制，§1.6）。
- 最坏影响面被限制在「一次切换」：L2 在任何真实切换之前证明草稿通道；`verifying` 期间进程内只允许一次未自证的切换；失败即本进程粘滞禁用。
- 告警：能力持有者带一个监听器集合。主会话（post-guard）在 `session_start` 里注册监听器，首次进入 `disabled` 时 `ctx.ui.notify("子会话 switch_context 已在本进程停用：<reason>（pi 运行时能力检测未通过），子会话回退为仅 pi 自动压缩。", "warning")`，每进程一次；没有主会话监听器（纯 print 主进程）时退回 `console.warn("[pi-subagent] …")`。另外，子会话写一条 `subagent:switch-capability` 条目（reason），经 driver 进入 `diag.contextSwitches.capability`，get_subagent_result 可见。`/agent status` 增加一行 `child switch: verified | ready | disabled(<reason>)`。
- 粘滞：`disabled` 在本进程内不恢复。pi 本体只有重启才会变，重启后能力从 `unknown` 重新走一遍。
- L0-L3 都不看版本号。`src/adapters/pi-compat.ts` 头注释补一段「boundary 能力：结构探测 + 运行时自证（见 docs/dev/child-context-switch/plan.md §3.1）」，I14 原文不变。

- T-C1/T-C2（§6）在仓库 devDependency 版本的真实 `AgentSession` 上运行（CI 与本地 `npm test` 都跑）。devDependency 当前 = npm latest = 0.87.1。

## 5. 零 hang 与 unref

- turn_end handler 全同步，**不 await 任何 I/O**（它阻塞的是 pi 的 finishTurn）；facts 收集、`findCutPoint`、副本预演、组装都是同步调用。副本预演复制整条 branch，是 O(n) 的内存操作，毫秒级；T-S3 里放一个 5k 条目的规模用例，确认耗时有界。 新增的 `context` 观察器同样全同步、只读（返回 `undefined`，不改消息），L3 的 token 估算只在 `verifying`/复核时做一次。
- keepalive 定时器走 `systemClock.setTimer`（已 unref）；ping 有 20s 硬超时；子会话 auth await 有 30s 上限；重试退避可被 dispose 取消（`cache-keepalive.ts:385-406`）；账本 try-acquire 从不 await。整个 ping 序列上界 97s，槽由持有者在 finally 释放，lease 150s 只做兜底。
- 子会话没有新的 ref 定时器，`pi -p` 退出不受影响（T-K8 在 print 模式跑完即退出）。
- 切换不引入任何「等压缩完成」的等待；pi 兜底压缩的等待由现有 `compaction` phase 预算约束。
