# memory-jev · 项目记忆使用策略

**机制（自动打标、元数据写法、块格式与限额、工具参数）都在 `memory` 工具描述里，这里只讲策略：什么时候写、写什么、怎么对待回显。**

本 skill 针对项目记忆的 blocks / 工具 v3；不把项目用户令的直写行为套用到 `scoped_memory` 的 session/Hub 授权。`scope: global` 只表示本项目每轮常驻，**不是跨项目 Hub 记忆**。

## 何时写

1. **先查后写**：写之前先 `view`（或 `search`）确认同一事实是否已存在。已存在且仍正确 ⇒ 不写；已过时 ⇒ **原地整体重写**（`view` 拿 `rev` → `update`），绝不新增重复块；只有全新事实才 `create`。
2. **用户令当场写**：用户明确下命令、拍板、纠正行为时，立刻把这条令写进记忆（不等收尾）。用户令 = 用户说的话的忠实记录，不加自己的解读。
3. **新用户令默认 topic**：默认作为按需召回的决策记录，不默认 `scope: global`。只有用户明确要求本项目以后每次都遵守、每轮常驻等全局范围时，才标 global；模型觉得重要、复用次数多或取代了旧 global 块，都不是升级依据。没有明确授权时保留 topic，必要时询问。
4. **经验收尾写**：自己踩的坑、排障结论、调研得到的项目事实，在任务收尾阶段写，不要每个小发现都打断去写。
5. **一个块 = 一条事实**：块不是笔记本，不要往里续写第二件事；相关但独立的结论拆成同 topic 的多个块。带上下文（日期、实测来源、版本号），但不要把整个调试过程写进去。
6. **改块前先 `view` 拿最新 `rev`**：冲突意味着事实可能已被别人更新；重读、合并后再提交，不盲重试旧版本。

## 权威、期限与受众（何时标）

语法与键位见工具描述。策略上：

- **用户令标权威**：凡是转写用户原话/拍板的块都标 `authority: user`。这是来源与处置权限，不是模型自封的优先级。项目工具改写/删除用户令已无确认框，**不代表模型获准自行作废**：用户本轮明确要求时可按原意改，否则先向用户提议，获同意再改。不得把自己的推断标 user 来绕过 agent→user 的取代禁令。
- **经验标经验**：明确属于自己推断/教训（非用户指令）时保持 agent 权威。
- **临时事实带期限**：日期型失效用 `expires`，条件型失效用 `until`，不编造到期日或宣称事件已经发生。用户令到期后仍须用户决定如何处置；不要把期限提示当作删除授权。过期 agent 块可由治理归档，与用户令不同。
- **受众只按实际职责收窄**：只适用于主会话调度、交互职责的规则才考虑 `audience: main`；仅对子会话执行有意义的才考虑 child；两边都要遵守的保留共同受众。显式 audience 优先于标签推导；未显式指定时也可能被推导为 main，不能把省略理解成一定 all。`audience:` 建议只是证据，先核对语义；涉及用户令适用对象变化，向用户说明并获同意后再改。不要为了省 token 滥填 main/child，否则另一类会话会漏掉规则；这不是保密边界，显式读取仍可见。
- **私密事实标 private**：不能外发给分类器时标明；不要存密钥等秘密。

## 写完之后：按真实回显处置

- **先转述结果，再处理建议**：说明写了什么、落在哪个块及范围。`section:` / `jev:` / `similar:` / `conflict:` 是判断材料，不是授权或取代成功证明。`looks like a user order` 只有确实出自用户才补 user 权威；`looks temporary` 则核对期限。涉及用户令的合并、改写、作废都要先有用户授权。
- **`scope:` 建议必须转述并询问**：例如回显 `scope: topic ... Looks like a standing rule ...`，告诉用户「目前仍是 topic、按相关性注入；是否改为本项目每轮常驻？」在明确同意前不升级；常驻预算 `resident: ... over budget` 也只是合并/降级建议，不得因此擅自将 global 降为 topic。无论升级还是降级，都不能用模型判断代替用户决定。
- **`state snapshot:` 要收敛为有寿命的事实**：这是对未带期限的 agent 块的提示，写入已成功，不是自动修正。若记的是 run id、当前额度、进度等临时状态，补真实的 `expires` / `until`；若值得长期保存，则改写为可复用的持久结论，而不是保存易过时的数值快照。向用户转述实际采用的修正；不能确认期限时先询问，不凭空加日期。
- **`superseded:` 是已执行的取代**：按 `superseded: <旧 id> by <新 id>` 逐项告诉用户谁取代了谁、旧块不再注入；多项结果不能当作全部成功。若有 `note: <旧 id> was global; new block remains topic`，点明常驻范围变化，**新块不继承旧块的 global**，仍须询问再升级。误取代时告知单块恢复入口 `/mem restore --block <旧 id>` 并提议恢复，不用删除新块冒充撤销；删除新块不会自动恢复旧块。
- **`not superseded:` 是权限保护，不是待重试错误**：回显指出旧块是 user 时，旧用户令仍有效，agent 块永远不能取代它。向用户说明冲突双方及未发生取代，提出具体修订建议，等待用户决定；不得把 agent 块升为 user、降级旧块权威或删除旧块来绕过限制。
- **`skipped:` / `conflict:` 不等于取代**：前者按原因核对（如 rev 已变则重读），后者只是冲突建议；部分冲突应保留双方的有效信息，不能因高置信度就当作完整替代。只有 `superseded:` 才能报告本次取代已完成。
- **`voided user rule:` 必须点明**：说明改动/删除/降权/常驻降级了哪条用户令、为什么，以及依据的用户要求；不要指望仅主会话 TUI 的 warning 代替转述。若没有用户授权，承认误操作并提议纠正，不能静默带过。

## 何时显式取代

`supersedes` 用于**新事实完整覆盖或明确废弃旧块全部有效信息**、且已核对目标块的场景；一般修正同一事实仍优先原地 `update`，不要为去重滥建新块并填取代关系。它不是「相关」「部分矛盾」或给新块加优先级的标记。

- agent 新块只可指向已核实的 agent 旧块；用户原话形成的 user 新块可指向 user 或 agent 旧块，但涉及旧用户令的作废必须有用户明确决定，不能借此夹带模型推断。
- 自动路径的矩阵为 user→user、user→agent、agent→agent 可完整取代，agent→user 永禁；自动判断仍可能出错，必须逐项阅读并转述结果。**conflict 只建议，不自动取代**。
- 显式取代无需分类器也能执行，所以更要先核对，不把它当作加速按钮；它不绕过权威与版本校验，也不会让新块继承旧块 scope。不要把一次写入的意图当成已经成功的关系，以回显为准。

## 删除与恢复边界

过时优先 `update` 改写，只有整条事实彻底无效才考虑删除，用户令仍须用户决定。区分三种恢复对象：

- 已取代或归档的块：用 `/mem restore --block <id or stored name>`，单块恢复不递归恢复它曾取代的其他块。
- **已删除的块**：软删保存在 `blocks/.trash/`；blocks 布局下用 `/mem restore --trash` 列出并找回（`e0993f03` 起路由已按磁盘实际布局分派，恢复仍走块存储的锁/写入门/rev/同名冲突拒绝）。files 布局仍用项目根 `.trash/`，两种布局互不读取对方的回收站。
- files 布局的删除快照仍在项目根 `.trash/`，使用其原有 `/mem restore --trash`；不要与 blocks 的归档/取代恢复混淆。

## 降级

- 回显 `jev: not tagged (partial: …)` 或 `(off: …)`：写入已成功，只是没打上派生标签。未打标时快速通道不可依赖；确需立即参与时可补经核实的手工标签，无需等待、也不要反复重写。总开关关闭不会因补标签而重新开启注入。
- 用户令改写已无确认框（2026-11 #26），不确定该不该改时先提议、后动手；`scoped_memory` 的授权另按其工具约束，不得据此跳过确认。
- 历史块可能带着超出当前上限的字段（早期版本写的更长 `when` / `section`）：读取时按码点边界降级、**不改写文件**，`/mem doctor` 能看到具体字段与超出量。不要为了消诊断去手改用户的历史文件；要修就走 `update` 整块重写。
