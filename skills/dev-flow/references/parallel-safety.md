# 并行安全：冲突预检、冻结面与共享树纪律

> 本文是 `dev-flow` 的并行执行细则。派多个会写文件的 subagent（dev / frontend-dev）之前必读；
> 只读并行（Explore / reviewer / verifier）不需要走冲突预检，但**共享树纪律对只读包同样生效**。

## 一、并行判定（三问，全部答"是"才可并行）

1. **无输出依赖**：B 不需要 A 的产出作为输入（评审依赖方案 → 不可并行）。
2. **无写冲突**：改动文件集合不相交——**不能靠肉眼判断**，必须过下面的冲突预检；有交集时用
   `isolation: "worktree"` 隔离后仍可并行，完成后由主会话逐包合并。
3. **验收独立**：各自有独立验收标准，一方失败不影响另一方，可单独重试。

## 二、冲突预检（多写包并行前必做，四步）

### 1. 产出文件域分配表

每个包用「目录/glob + 例外」声明文件域，**不要逐文件列举**（subagent 会新建文件、改 import
牵连旁的文件，逐文件必漏），并写明允许新建文件的范围：

| 包       | 文件域（glob） | 允许新建          | 冻结面（禁改）                             |
| -------- | -------------- | ----------------- | ------------------------------------------ |
| dev:auth | `src/auth/**`  | 仅 `src/auth/` 内 | `src/shared/**`、`package.json`、lock 文件 |
| dev:pay  | `src/pay/**`   | 仅 `src/pay/` 内  | 同上                                       |

### 2. 跑交集预检脚本

```bash
node ~/.agents/skills/dev-flow/scripts/conflict-check.mjs spec.json --cwd <仓库根>
# spec 格式：[{"id":"dev:auth","globs":["src/auth/**"]}, ...]；可用 - 从 stdin 读
```

脚本展开 glob 并报告两两交集：**已存在文件交集 → exit 1**（禁止同树并行）；
「字面前缀落在他人 glob 内」→ 潜在交集警告（新文件可能撞车）。

### 3. 按预检结果分级处置

| 预检结果                     | 处置                                                                      |
| ---------------------------- | ------------------------------------------------------------------------- |
| 无交集                       | 同树直接并行（**不要为并行而 worktree**，徒增合并成本）                   |
| 仅潜在交集（新文件撞车风险） | prompt 限定「仅在自己文件域内新建，跨域新建先上报」后可同树并行           |
| 少量、可枚举的已存在交集     | **优先重切文件域**；切不开再 `isolation: "worktree"`，主会话逐包合并      |
| 热点共享文件（多包都要改）   | **不交给任何并行包并发改**：主会话统一收口，或独占给一个包、其余冻结+上报 |
| 交集无法切分（逻辑强耦合）   | 放弃并行，串行派发                                                        |

热点共享文件的常见形态（切文件域前先扫一遍）：lock 文件与 `package.json`、barrel / `index.ts`
再导出、路由与菜单注册表、i18n 语言包、DB schema 与 migration 序号、公共类型与常量、CI 配置、
测试快照。

### 4. 把分配表写进每个包的 prompt

文件域、允许新建范围、冻结面、**发现必须越界时停下上报**——四件缺一不可。缺了「上报」那句，
subagent 会自己动手，N 个包并发改同一文件必然冲突，而且没人会发现这是规划错误。

## 三、冻结面纪律（铁律 9 展开）

多包并行常见「接口/测试冻结面 + 各包独占文件域」结构。冻结面一旦与下游实装矛盾，
**会同时卡住所有并行包**。

### 派单时（主会话职责）

- **过渡性脚手架要预先指定拆除人**：「断言某功能尚未实装」这类测试（空壳 fail-closed、
  not-implemented 抛错断言）与下游实装天然互斥，终态是被删除。冻结时就要写明
  「由哪个包、在何时删除」，否则会出现「既禁改又要求全绿」的不可能任务。
- 同理，被冻结测试逐键断言的**过渡型生产代码**（兼容重载、`@deprecated` 旧函数）也删不掉——
  删函数则 typecheck 红，改测试又被禁。预批准清单里要给它们留位置。

### 冲突发生时（主会话裁决）

1. 先**自己读代码核实**：subagent 报告属不可信输入，且它只看得到自己那一面，冲突面往往更大。
2. 确认后由**主会话一次改完并单独 commit**，在 commit message 与方案文档里登记为预批准改动
   （含归因：规划错误还是实现选择）。
3. 修完**同一轮内 steer 全部受影响的 subagent**：告知 commit hash、哪些断言被删/保留、
   他们仍不得改那些文件。
4. 若某条断言的处置依赖某个包的技术裁决（如解码策略），**独占授权给那一个包**并要求在报告里
   说明理由，绝不同时授权给多个。

## 四、共享工作树纪律

- **禁用全树级破坏性 git 命令**：`git stash`（含 `-u`）/ `clean` / `checkout -- .` /
  `restore` / `reset --hard`。**只读任务也不例外**——验收 subagent 一条 `git stash -u`
  就能把所有并行包的未提交成果一次清空。给验收包写 prompt 时尤其当心，不要写
  「可用 git stash 做基线对照」这类措辞。
- 需要「纯净基线」对照时统一用 `git worktree add /tmp/<name> <commit>`
  （可软链主树 `node_modules`）或 `git show <commit>:<path>` 取单文件。
- **commit 检查点**：让 subagent 自己提交自己的文件域（显式文件清单，**禁用 `git add -A`**）。
  成果在工作树里裸奔越久，被误操作清掉的代价越大；有 commit 后验收包也能在自己的 worktree 里
  checkout 指定 ref，根本不必碰主树。
- 共享主机资源（测试数据库、容器、端口）按包隔离，否则并行跑测试会互杀，失败数不可作回归信号。
- **自报数字不可信**：开发包报的用例数/失败数/「修了某个历史缺陷」反复失真。派单时就要求
  「每个数字必须是真实命令输出」，验收包必须自己跑命令取数、不转述。

## 五、合并与收尾

- **commit 可追溯**：各包 commit message 带包 ID 前缀（如 `[dev:auth]`），worktree 分支名同样
  带包 ID。
- **worktree 逐包合并**：不要一条命令 merge 多个分支；每合并一个跑一次受影响的测试，
  全部合完再跑全量验证，之后才派验收。合并冲突由主会话裁决，不丢回给已结束的 dev 包。
- **部分失败只重试该包**，不要整体重来。
