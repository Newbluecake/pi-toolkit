# consult 细则与生产实测（consult.md）

SKILL.md「挂专家」节只保留判据与硬禁；这里放完整场景矩阵、挂载纪律展开与实测数字。
A/B 实验埋点见 [consult-ab.md](./consult-ab.md)。

## 判据与推/拉证据

下游要的知识 ① 只存在于某个已派 subagent 的会话里、② 读代码读不到、③ 交接包写不全——三条同时成立才挂。
能写进 prompt / 落盘文档的先写。实验证据：推永远比拉稳——推 7.0/7，拉 6.5/7，都不给时下游被现有代码带偏只有 2.0/7。
读不到的典型：**拍板过的决策、否决过的方案及理由、用户偏好、上一轮失败原因与已排除的假设**。

## 硬禁的实测依据

- 被评对象的作者：verifier/reviewer 挂作者问「pass 还是 fail」「最可能挑出哪些缺陷」，作者会替自己辩护，
  自述还会锚定评审（实测违规 6 + 5 次）。
- 复验让上一轮 verifier/reviewer 评新提交：31 次中 9 次撞轮次帽，还发生过原验收员收回结论把标准问松。
- consult 复述已在主会话手里的东西：复述类约占两成调用，纯浪费，还常因 2000 字截断再追问。
- 上下文 > ~250k 的专家（fable 长方案）：fork 首请求几乎不读缓存，整段上下文按写价重放，几乎必然被成本预检拒。

## 其余不挂（展开）

- 正在并行运行的兄弟写包：互相请教会把接口分歧藏进对话；共享接口进冻结面，由主会话统一推送。
- L0 / L1：微方案自足；L1 前置 Explore 的结论直接写进 dev prompt。
- 只产出文件坐标/调用链的 Explore：代码可读，推 fileIndex 就够（它 ruledOut 了大量排查路径时例外）。
- 知识在主会话或用户对话里：主会话不是 run，挂不了——写进 requirements 文档或 prompt。
- `SubagentWorkflow` 子任务可挂 `experts`，但只接受 completed 且有持久化 session 的调用，见 subagent-workflow.md。

## 成本与可靠性（生产实测）

- consult fork 首请求几乎不读缓存（cacheRead 中位 0，专家整段上下文按写价重放）。
- 成本中位 **$0.84**/次（P90 $1.64；opus 专家中位 $1.24，gpt 系 $0.6–1.0，glm 约 $0.05）；
  耗时中位 **38s**（P90 92s）；**29% 的调用拿不到完整答案**（轮次帽/成本预检/超时/专家引用写错）。
- 「不问不收费」仍成立，但挂了就要问得值。默认帽 3 轮 / $4。

## 挂载纪律（展开）

1. 先推后拉：文件坐标、关键结论、验收标准照样写进 prompt；`experts` 只补残差。
2. 只挂 1–2 个最相关的；挂多了下游也不知道该问谁。
3. prompt 里写一句「哪类问题该 consult」，代码能查的让它自己 grep；专家的 label/类型/摘要由 consult 工具自动列出。
4. 上游起好可辨识的 label（`Agent` 的 description，如 `plan:auth-refresh`）；重名歧义改传 run_id。
5. 上游还在运行也能挂（带警告，结束后才可问），但下游开工依赖其结论时仍要等 barrier。
6. 不挂就别暗示：没给 `experts` 时，prompt 里不要写「方案另有未展开的决策」之类的话。
