# 开发任务工作流（dev-flow）

**主会话做调度，重活分包给 subagent，每阶段用性价比最合适的模型，评审与制定保持独立。**

总时长 ≈ 阶段轮次 × 每轮等待。因此提速只有两条路：**砍掉不必要的阶段**（车道分级）和
**让剩下的阶段重叠**（并行 + 免等）。

## 提速五原则

1. **分级派单**：先定车道，不给小任务上全流程——这是最大的时间浪费来源。
2. **默认并行、一律后台**：能并行的一律同消息派发（主会话的 `Agent` 一律后台运行、立即返回 run_id）；
   派完就结束本轮，靠完成通知驱动，绝不 `wait: true` 干等。
3. **闸门不空转**：用户确认与方案评审同时进行；澄清（交互阻塞）期间后台预热 Explore。
4. **产物复用**：探索/方案落成文件，下游 prompt 直接给路径，禁止下游重复读同一批代码。
5. **按需算力**：thinking 按阶段降档，机械改动用 `low`；模型报错立刻按回退链换，不原地重试。

## 铁律

1. **精确 ID**：`Agent` 的 `model` 必须用速查表里的完整 `provider/modelId`；模糊别名会被
   `subagent-model-hints` 扩展 block。
2. **按序回退**：首选报错（过载/429/超时/额度耗尽）就换下一个，不在同一模型上反复重试。
   **GPT 系（gpt-sol / gpt-terra / gpt-6）在所有回退链中一律排最后，仅作兜底。**
3. **fable / gpt-6 只用于复杂任务**（L3），常规任务禁止动用。
4. **能并行必并行**：判定可并行的任务必须在**同一条消息**中发出多个 `Agent` 调用，或在
   `SubagentWorkflow` 里用 `parallel()`/`pipeline()`；顺序派发不算并行。
   **每轮派单前必须先做并行自检**（流程见「并行调度」节）；选择串行必须能指出具体硬依赖
   （谁消费谁的产物、谁和谁写同一文件），「稳妥起见一个个来」「先看看结果再说」不是合法的
   串行理由——不依赖结果的任务不许等结果。
5. **评审独立性**：评审模型 ≠ 方案制定模型；验收模型 ≠ 开发模型。
6. **先澄清后规划**：需求模糊必须先走 `dev-clarify`（HARD GATE），禁止拿模糊需求派 Plan。
7. **workflow 不越权**：`SubagentWorkflow` 只用于已确认方案后的批量执行或阶段内 fan-out，
   用户闸门必须留在主会话。
8. **进度可追踪**：L2/L3 必须用 `TaskCreate` 建 todo 并实时更新状态。
9. **冻结面只能上报不能自解**：subagent 发现「不改冻结文件就完不成任务」必须停下上报，
   主会话集中一次改完，绝不授权多个并行包各改同一文件。

### 疑难升级阶梯（fable 闸门）

难度升级一律走这条阶梯，**不得跳级**：

```
kimi-k3 → opus-5.5（疑难默认天花板；不可用时退 opus-5） → [ask_user 批准] → fable
```

- **凡用 opus 档一律优先 opus-5.5**：opus-5 更弱且更贵，只在 opus-5.5 不可用（额度/报错）时替补。
- **opus-5.5 是疑难问题的默认最高档**：架构设计、L3 方案制定、疑难 bug 定位、被打回两次的
  方案/开发任务，直接派 opus-5.5，不必请示。
- **fable 是受闸门保护的最后一档**：只有 opus-5.5 已经跑过并明确失败（方案被 reviewer 判
  Blocker、或同一问题连续 2 轮无进展）时才考虑，且**必须先 `ask_user` 拿到用户明确批准**，
  问句里要写清：为什么 opus-5.5 不够、fable 要解决的具体问题、预计成本（$10/$50，约 opus-5.5 的
  2.5 倍）。用户未点头就继续用 opus-5.5 迭代，不得自行升 fable。
- 例外：用户主动点名要用 fable 时视为已批准，无需再问。

派单前参考系统注入的 [quota] 行：订阅额度窗口内不用就作废，**优先用完订阅**——L1/L2（预警）只是提示，派单照常；只有 L3（≥90% 或即将耗尽）才跳过该 provider。[quota] 给出的替代只是**候选**（按订阅优先排序），额度层不知道任务需求：先判断候选是否胜任本阶段任务（对照本表的阶段→模型路由），胜任就优先用订阅；不胜任就按本表另选合适模型，不为用额度而硬凑。额度行不存在时按本表默认顺序。

## 第一步：定车道（先打分，再谈流程）

### 复杂度速评（10 秒打分卡）

| 维度              | 0 分           | +1                    | +2                            |
| ----------------- | -------------- | --------------------- | ----------------------------- |
| 改动文件数        | 1              | 2-5                   | >5                            |
| 模块边界          | 单模块内       | 跨 2 个模块           | 跨服务 / 跨仓库               |
| 接口契约/数据结构 | 不动           | 新增字段/端点（兼容） | breaking change / schema 迁移 |
| 设计选择          | 无（范式照抄） | 有 1 个取舍点         | 多个取舍点 / 无先例可循       |
| 风险面            | 纯读取/文案    | 写路径、可回滚        | 鉴权/迁移/删除/发版           |

| 总分 | 车道          |
| ---- | ------------- |
| 0-1  | **L0 直改**   |
| 2-4  | **L1 快车道** |
| 5-7  | **L2 标准**   |
| ≥8   | **L3 复杂**   |

**一票升级（不看分数，直接 L2 起步）**：数据迁移、鉴权/权限、发版与部署、删除或不可逆操作、跨服务协议变更。
**判定不确定时降一级起步**：L1 跑砸了再升 L2，比给所有任务上 L2 更快。
**需求模糊不是车道级别**：无论大小，需求模糊先走第 0 步 `dev-clarify`，澄清后再打分定车道。

### 车道总览与闸门矩阵

| 车道          | 流程概要                                                    | subagent 轮次 | 用户确认闸门       | 方案评审   | Todo       | 验收方式                |
| ------------- | ----------------------------------------------------------- | ------------- | ------------------ | ---------- | ---------- | ----------------------- |
| **L0 直改**   | 主会话直接改 + 最小验证                                     | 0             | 无                 | 无         | 可省略     | 主会话自验              |
| **L1 快车道** | （可选 Explore）→ dev 带 3 行微方案开工 → 抽查              | 1-2           | 无（微方案免审）   | 无         | 可省略     | 主会话抽查 diff + 复跑  |
| **L2 标准**   | Explore ∥ Plan → 评审 ∥ 用户确认 → 并行 dev → 验收 ∥ 测试   | 3-4           | **必须有**（HARD） | **必须有** | **必须建** | verifier 验收矩阵       |
| **L3 复杂**   | L2 + 前置 architect；方案升级 opus-5.5；多包并行 + 冲突预检 | 5+            | **必须有**（HARD） | **必须有** | **必须建** | verifier + 全量测试取证 |

### 车道升降级

- **升级触发（立即停手重定车道）**：dev 上报需改冻结面；微方案出现 ≥2 个取舍点；实际改动面越出
  prompt 声明的文件域；发现隐藏的跨模块/契约影响。
- **降级（只允许降流程，不允许降闸门）**：方案确认后实际改动面缩水到 L1 范围，可跳过评审环节，
  但「一票升级」命中的任务任何情况下不得降级。
- 升级时已有产物（探索结论、微方案）直接带入新车道复用，不推倒重来。

## 各阶段模型分工

| 阶段                   | 首选     | 次选                                          | 说明                                                                                                   |
| ---------------------- | -------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **核心调度**（主会话） | kimi-k3  | opus-5.5 → opus-5                             | 任务拆解、派单、汇总；启动时 `--model kimi-coding/k3-256k` 或 Ctrl+P                                   |
| **代码探索**           | glm-5.3  | sonnet → gpt-terra（兜底）                    | `subagent_type=Explore`，只读定位代码/梳理调用链                                                       |
| **架构设计**           | opus-5.5 | opus-5 → gpt-6（兜底）；简单 → kimi-k3        | `subagent_type=architect`，产出架构文档，仅 L3 或新模块从零搭建时启用                                  |
| **方案制定**           | kimi-k3  | opus-5.5 → opus-5 → gpt-sol                   | `subagent_type=Plan`                                                                                   |
| **前端开发**           | kimi-k3  | opus-5.5 → opus-5                             | `subagent_type=frontend-dev`，仅含 UI 工作时启用；含页面级 bug 排查/验证时优先派它而非 general-purpose |
| **复杂任务方案**       | opus-5.5 | opus-5 → gpt-6（兜底）                        | 仅 L3；opus-5.5 方案被判 Blocker 后才 `ask_user` 升 fable                                              |
| **疑难攻坚**           | opus-5.5 | gpt-6（兜底）                                 | 连续 2 轮无进展的 bug/重构；仍卡死 → `ask_user` 批准后升 fable                                         |
| **方案评审**           | kimi-k3  | opus-5.5 → opus-5 → glm-5.3 → gpt-sol（兜底） | `subagent_type=reviewer`，制定用 k3 系时评审改 opus-5.5；L3 用 opus-5.5                                |
| **开发实施**           | kimi-k3  | glm-5.3 → sonnet → gpt-sol（兜底）            | `subagent_type=general-purpose`                                                                        |
| **任务验收**           | kimi-k3  | glm-5.3 → sonnet → gpt-sol（兜底）            | `subagent_type=verifier`，开发用 k3 系时验收改 glm-5.3；开发用 glm-5.3 时验收改 sonnet                 |

专属 agent 定义在 `~/.pi/agent/agents/`（architect / frontend-dev / reviewer / verifier /
general / Explore），自带角色 prompt 与工具约束；调用时传 `subagent_type` 并按本表传 `model`。

其中 **frontend-dev 除 UI 编码外还内置 deveye 浏览器调试能力**：排查前端 bug 或验证页面实际表现时，
它会用 `deveye` CLI 驱动浏览器取证（`inspect` / `console` / `network` / `snapshot` 定位报错与元素，
click/type 复现交互，headless 场景走 `browser create --headless`），并在修复后重跑浏览器检查确认回归。
派单时若涉及页面 bug，prompt 里给出可访问的页面 URL / dev server 端口，让它直接开浏览器取证，
而不是只靠读代码猜。

## 各车道流程

### L0 直改（0 轮 subagent）

```
1. 主会话直接 read/edit 改完
2. 跑最小验证命令（相关单测 / typecheck / lint，取最小集合）
3. 汇报改动 + 验证输出
```

不派 subagent、不建 todo（动作 >2 个时可建 1 条防丢）。验证失败就在主会话迭代，不升级车道，
除非发现需要动第二个模块——那是升级触发。

### L1 快车道（1-2 轮 subagent）

```
1. （改动点不明时）主会话 grep/read 定位，或派一个 Explore(sonnet, thinking=low)
2. 派 dev（kimi-k3），prompt 要求：动手前先输出 3 行微方案
   （改哪几个文件 / 怎么改 / 跑什么命令验证），然后一气改完
3. 自验前移写死：dev 必须跑指定验证命令并贴真实输出
4. 主会话抽查 git diff + 复跑验证命令，通过即收尾
```

微方案**免用户确认**——这就是快车道省掉的闸门；但 dev 上报要动冻结面或越出文件域时，
必须停下上报主会话，按升级规则处理。微方案同时充当「验收清单」，verifier 不派。

### L2 标准流程

```
0. 需求模糊 → 主会话内跑 /skill:dev-clarify（同时后台预热 Explore）
1. 主会话定车道 + TaskCreate 建 todo
2‖3. 同一条消息派：Explore(sonnet) ‖ Plan(kimi-k3)
     —— 改动点未知、方案强依赖探索结论时才退化为先 Explore 后 Plan
4‖5. 方案到手：立刻贴给用户确认，同时后台派 reviewer(kimi-k3/opus-5.5)
     —— 用户读方案的时间 = 评审时间；两者都通过才开工（HARD GATE）
6. 并行开发：按文件域拆包，同消息派多个 dev / frontend-dev（先过冲突预检）
7‖8. dev 返回后：主会话 bash_job 后台跑全量测试 ‖ 派 verifier 只读 diff
9. 主会话汇总验收结论，报告用户
```

### L3 复杂（L2 前置 architect，方案升级）

```
0‖1. 同 L2（澄清 / 定车道 / 建 todo）
2. 前置 architect（opus-5.5，不可用时 opus-5）产出架构文档 docs/dev/<feature>/arch.md
   —— 可与 Explore 同消息并行
3. Plan 升级 opus-5.5（不可用时 opus-5），prompt 给出 arch.md 与 Explore 产物路径
   —— 方案被 reviewer 判 Blocker 且 opus-5.5 二次仍不过，才 ask_user 批准后升 fable
4‖5. 评审（opus-5.5 / gpt-sol，须与方案模型不同）∥ 用户确认（HARD GATE）
6. 冲突预检 → 按文件域拆 ≥2 个写包同消息派 dev；跨包共享文件进冻结面
7. 每包 dev 返回即派对应 verifier 验收（不等全部完成），主会话后台跑全量测试
8. 全部验收通过后主会话汇总；任一包被打回只重派该包，不回退整体
```

## 免等手法（照抄）

| 手法            | 做法                                                                                   | 省下     |
| --------------- | -------------------------------------------------------------------------------------- | -------- |
| 澄清期预热探索  | 进 `dev-clarify` 交互前先后台派 Explore；澄清结束时现状摘要已就绪                      | 一轮探索 |
| Explore ∥ Plan  | 目标明确时同消息派，把已知文件清单/线索直接写进 Plan 的 prompt                         | 一轮     |
| 评审 ∥ 用户确认 | 方案一到手立刻呈现给用户 + 同时后台派 reviewer                                         | 一轮评审 |
| 前端 ∥ 后端     | 文件域不交叉时 frontend-dev 与 general-purpose 同消息派                                | 一轮     |
| 验收 ∥ 测试     | 主会话 `bash_job` 后台跑全量测试，verifier 同时只读 diff + 跑定向命令                  | 一轮     |
| 自验前移        | dev prompt 写死「改完必须跑 X 命令并贴真实输出」                                       | 一次返工 |
| 产物落盘        | Explore/Plan 结果写 `docs/dev/<feature>/`，下游 prompt 给路径而非复述                  | 大量读码 |
| 下游挂专家      | 派开发/评审/验收时传 `experts: [探索/方案 agent 的 label]`，决策与否决理由按需 consult | 整段复述 |
| 长尾截断        | 给 `Agent` 传 `timeout_ms`（dev 约 15min）；超时不续等，拆小重派或换模型               | 尾部空等 |

**评审 ∥ 确认的补充规则**：用户先点头、reviewer 后报出 Blocker 时，必须停下重新确认，
不得以「用户已同意」为由带病开工。

## 提速反模式（禁止）

- **默认串行 / 顺序派发假装并行**：无硬依赖却把可并行任务拆成多轮逐个派发（最典型的总时长
  浪费）；每轮只派一个任务时必须能说出剩下任务硬依赖什么，否则就是违反铁律 4。
- `get_subagent_result(wait: true)` 干等；高频轮询同一 run_id。
- 给 L0/L1 任务套 Plan + 评审 + 验收全流程。
- 下游 subagent 重复探索（prompt 里没给文件路径/产物路径）。
- 单个模型报错后原地重试，而不是按回退链换。
- 机械性改动开 `high` thinking；只读小查询开 `high`。
- 让 verifier 重跑全量测试（应主会话后台跑，verifier 只读 diff + 定向命令取证）。
- 无文件交集却上 `isolation: "worktree"`，白白增加合并成本。
- ≤3 个子任务还去写 `SubagentWorkflow` 脚本（同消息 3 个 `Agent` 调用更快）。

## 并行调度（要点）

**派单前并行自检（每轮必做，心里过一遍即可）**：

1. 列出本轮所有待派任务（探索/方案/评审/开发/验收/测试，含主会话自己的 bash 验证命令）。
2. 逐一过三问，把任务分成「可并行组」和「硬依赖链」。
3. 可并行组同消息一次性发出（Agent 多个调用 ∥ bash_job 后台测试 ∥ 贴方案给用户确认，
   这三类动作互不阻塞，本来就是并行的）；只把硬依赖链留给下一轮。

**三问全为"是"才可并行**：无输出依赖 / 无写冲突 / 验收独立。

**可并行组合**：Explore + Plan；architect + Explore；前端 + 后端；多个独立 dev 子任务；多模块验收
（各组合的具体手法与省时估算见「免等手法」表）。

**不可并行（硬依赖）**：评审等方案产出（但可与用户确认并行）；开发等用户确认（HARD GATE）；
验收等对应开发完成；下游依赖多个上游时必须等**全部**返回（barrier），不拿部分结果开工。

**派多个写包前必须过冲突预检**，并把「文件域 / 允许新建范围 / 冻结面 / 越界先上报」四件事写进
每个包的 prompt：

```bash
node ~/.agents/skills/dev-flow/scripts/conflict-check.mjs spec.json --cwd <仓库根>
```

细则（分配表模板、交集分级处置、热点共享文件清单、冻结面纪律、共享工作树禁令、合并纪律）见
[references/parallel-safety.md](./references/parallel-safety.md)。**其中「禁用 `git stash`
等全树破坏性命令」对只读验收包同样适用**，写 prompt 时务必带上。

## Todo List 管理

主会话是 todo 的唯一维护者（subagent 不操作主会话清单）。

- **何时建**：L0/L1 可省略（超过 2 个动作时建 1-2 条）；**L2/L3 必须建**，定完车道立即
  `TaskCreate` 按阶段拆解再派单。
- **粒度**：一条 todo = 一个阶段产出或一个 subagent 任务；用户闸门单独一条；并行子任务各占一条；
  `description` 写清完成判据（如「验收矩阵全部通过」「reviewer 无 Blocker」）。
- **依赖**：用 `blockedBy`/`blocks` 表达硬依赖，与「不可并行」清单一致。
- **状态**：派发即 `in_progress` 并填 `activeForm`；**收到结果并核实后才 `completed`**
  （subagent 报完成不算数）；部分失败只把该条标回 pending 重派，不回退整体。

## Agent 调用要点

- **k3 调用顺序**：一律先 `kimi-coding/k3-256k`，失败按
  `kimi-coding/k3` → `cr-kimi/kimi-k3` 回退。
- **后台 + 通知驱动**：主会话的 `Agent` 一律后台运行（立即返回 run_id，无需也无法选前台）。派发后主会话做不冲突的准备工作
  （整理验收清单、写 todo），没活干就直接结束本轮并说明在等哪些 subagent；收到完成通知再
  `get_subagent_result` 收结果。多个并行任务**按通知到达顺序逐个收取**，先完成先处理。
  仅当通知疑似丢失时才用一次 `wait: true` 兜底，不要循环刷。
- **prompt 自包含**：subagent 没有主会话上下文，必须写清背景、文件路径、约束、验收标准和
  项目规范（发版铁律、测试命令等），不要只写「基于你的发现做 X」。
- **trust but verify**：subagent 报「完成」不代表真完成；自报的用例数/失败数经常失真，
  验收必须自己跑命令取证。
- **下游挂专家（consult）**：机制与约束见 `Agent` 工具的 `experts` 参数说明，这里只管策略。在流程里的位置：
  探索/方案 agent 结束后，派开发、评审、验收时把它们挂成 `experts`；先推后拉——代码位置、关键结论
  仍写进交接包，consult 只补交接包写不全的拍板决策/否决理由/用户偏好。成本：glm 专家单次 < $0.05；
  Claude 专家首轮要写缓存整段专家上下文（19k ≈ sonnet $0.07，长会话按比例涨）。证据与细节见
  `agent-handoff` skill「可选：让下游能向掌握知识的 agent 请教」。
- **省略 model**：不需要指定时直接省略，让 subagent 继承默认配置，不要猜。

## thinking 级别

| 阶段                | thinking                                  |
| ------------------- | ----------------------------------------- |
| 代码探索            | `low`（广撒网）/ `medium`（需梳理调用链） |
| 架构设计            | `high`                                    |
| 方案制定 / 复杂任务 | `high`                                    |
| 前端开发            | `medium`                                  |
| 开发实施            | `medium`（机械性改动 `low`）              |
| 方案评审 / 任务验收 | `medium`                                  |

模型档位限制：`claude-opus-5-5` 与 `claude-opus-5` 同为自适应思考，支持到 `xhigh` / `max`；
`gpt-6-astra` 不支持 `off`（API 拒绝 `reasoning.effort: "none"`，400），
最低 `low`；支持 `low` / `medium` / `high` / `xhigh` / `max`。

## 第 0 步：需求澄清（dev-clarify）

需求模糊（一句话想法、目标/边界/验收标准不清）时先跑 `/skill:dev-clarify <需求>`。

- **主会话内运行，不派 subagent**：靠 `ask_user` 多轮交互，模型用主会话当前模型。
  也可独立运行 `node ~/.agents/skills/dev-clarify/scripts/clarify.mjs "<需求>"`。
- **提速**：进入交互前先后台派一个 Explore 摸现状，澄清完成时探索结论已就绪。
- **产出分流**：`simple` → L0/L1 直接开发；`standard/complex` → 产出
  `docs/dev/{feature}/{feature}-requirements.md`，回本流程定车道，派 Plan 时把该路径写进 prompt。
- **两道独立闸门**：dev-clarify 的「澄清未确认禁止实施」与本流程的「方案未确认禁止开发」都不能跳。
